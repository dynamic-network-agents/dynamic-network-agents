## 问题描述

### 背景

前序讨论已确认两条平台事实：

1. **service 级入口，flow 级生效，只按发起业务校验**（ISS-0003）。`POST /services/{serviceId}/path` 内部经 `_flow_for(src,dst)` 归并为无向 flow，再 `set_path(flow)`；`GET` 同样 `get_path(flow)`。一次下发会改变同 flow 全部业务；受理校验只取 URL 里 `serviceId` 的 `requirement`。
2. **GET path 是 flow 规范表示，不是业务方向的完整路径**（ISS-0004）。无 `path_info` 时反向业务缺两端接入链路；有 `path_info` 时返回 canonical links，不按业务方向重排。

现在把这两条事实与 `docs/competition_desc/` 的官方口径逐条对照，梳理「文档与实际」的问题、矛盾点和待官方确认项。

### 实际现象

#### A. 模型级矛盾：官方文档没有 flow 层

`仿真软件接口.md` 全文没有 flow / 无向源宿对的概念：POST/GET 都以 `serviceId` 为资源，POST 语义写成「segments 自 `srcNodeId` 起经各段至 `dstNodeId` 连续贯通」（`:132`）。实现却是 flow 级共享。由此产生 4 个可观测问题：

| # | 文档口径 | 实际行为 | 性质 |
|---|---|---|---|
| A1 | 「业务路径设置」，语义上只改该业务（接口 `:115-137`） | 改一个业务 = 改同 flow 全部业务；运行时一次 POST 让 `TSV0005/BGV0009/BGV0020` 同时换到 `pathId=P01005` | 未文档化的副作用 |
| A2 | `1004` 拒绝条件写「参数不满足业务QoS需求」（接口 `:136`） | 只校验发起业务；同 flow 兄弟业务可静态违规仍 `accepted`（`BGV0009/BGV0020` 的 jitter 15.23 > 11） | 校验范围歧义/缺口 |
| A3 | GET 是「业务路径查询」（接口 `:139-141`）；POST 要求 src→dst 连续贯通 | 反向业务缺接入链路（`TSV0005` 只剩 `L00015→L00012`），或返回 flow 规范方向、首段不接业务源 | 表示层矛盾（GET 方向文档本身未明说） |
| A4 | body 的 `srcNodeId/dstNodeId` 是业务端点（接口 `:120`） | 可覆盖并指向另一个 flow，要求仍按原 `serviceId` 校验；无端点一致性校验 | 契约漏洞 |

> A3 的文档依据是 POST 的段列表语义与 GET 作为「业务路径查询」的直觉；接口文档没有显式规定 GET 的方向。因此它至少是文档缺口，严格性弱于 A1/A2。

### 预期结果

官方文档至少应做到以下之一，或明确说明现状：

1. 把 flow（无向源-宿对）写成一等资源，或在 service 入口上注明「flow 级生效、影响同 flow 全部业务」；
2. 明确 POST 受理校验覆盖哪些业务（只校验发起业务，还是聚合整个 flow）；
3. 明确 `GET /services/{id}/path` 的 `segments` 方向：业务源→宿完整路径，还是 flow 规范方向；
4. 明确 body 的 `srcNodeId/dstNodeId` 必须与 `serviceId` 端点一致，或说明可覆盖的语义；
5. `POST /simulation/start` 在评测镜像可用，或官方给出公开的替代起测方式；
6. 场景文件清单补 `service-paths.json`，并说明运行时只取 `paths[0]`；
7. 说明 `node_move` 的发布件状态与 `losMeters` 配置要求；
8. 文档化 `actual.qosMeet`、`category` 获取方式、静态 QoS 公式与容差、错误码最终语义。

### 影响范围

- 影响模块：`src/algorithms`（候选路径评估）、`src/baseline`（重路由闭环）、`src/api`（下发与启动封装）、`src/agents`（未来决策）、`docs/`、`experiments/`。
- 影响场景：所有含「同一对端点多条业务」的场景；所有通过公开 API 起测的实验；所有使用 `service-paths.json` 预置路径的场景；所有把 `node_move` 写进场景建模的方案。
- 影响业务：同 flow 的背景业务和测试业务会一起被改路；公开 API 无法按 `category` 隔离。
- 是否阻断实验：不阻断，但会直接影响重路由正确性判断、基线解释和实验可复现性。
- 对结果/评分的潜在影响：
  - 若 agent 只按单业务需求选路，可能出现「下发成功但兄弟业务变差」；
  - 若实验报告把 `accepted` 当作「业务达标」，或把静态可行当作实测达标，结果分析会被质疑；
  - 若评测环境不含 `service-paths.json`，本地基线结论不能直接外推；
  - 若方案把 `node_move` 作为主要扰动手段，实际演示可能不成立。

## 分析过程

### 初步判断

核心不是单条文档写错，而是**文档的资源模型比实现少了一层**：文档按 service 建模，实现按 flow 建模。A1-A4 都是这一层缺失的派生结果。其余 B/C/D 是发布件实现、文档维护和字段说明层面的独立差异，不应与 flow 问题混为一谈。

### 根因分析

**已核实：**

- 文档按 service 资源建模，实现按 flow 共享路径；文档没有声明 flow 级副作用和校验范围，导致 A1-A4。
- `GET path` 的表示层不按业务方向重排/补齐接入链路，导致 A3。
- 顶层使用说明的场景文件清单漏了 `service-paths.json`，且没有说明运行时只取 `paths[0]`，导致 B2。
- 错误码章节与接口章节对同一 code 的定义不一致，导致 C1。
- `actual.qosMeet`、`category`、静态 QoS 公式/容差等关键口径未在接口文档中定义，导致 D1-D4。

**待确认：**

- `POST /simulation/start` 是否仅在当前 Mac 试跑镜像缺失，评测镜像是否实现（B1）。
- `node_move` 在评测镜像是否同样失效，`linkTypes.json` 缺 `losMeters` 是否为已知发布缺陷（B3）。
- 评测场景是否随包提供 `service-paths.json`，无该文件时是否预期走 BFS（D5）。
- `source=system` 的「系统重算」触发条件（D6）。

## 解决方案

### 修复措施

平台发布件不可修改，本问题的「修复」分三层：

**1. Agent 侧适配（必须做）**

1. 以 flow 为单位决策：先聚合该 flow 全部业务的 requirement（带宽取 max，时延/抖动/丢包/误码取最严），再做候选路径评估。
2. 不依赖平台校验：本地先按聚合需求做静态 QoS 校验，`accepted` 只当作「平台受理」，不当作「业务达标」。
3. 下发后复查同 flow **所有**业务的 `actual.qosMeet`，不只发起业务。
4. 不直接用 GET path 恢复/复制：按业务 `src/dst` 定向，并从拓扑补齐两端接入链路；比较路径时用无向链路集合或 core 链路，不比较原始 segments。
5. body 的 `srcNodeId/dstNodeId` 始终传业务自身端点，避免误改其它 flow。
6. 起测封装兼容 `POST /sdn-ui/start`（ctrl token）与公开 `/simulation/start`，按环境探测选择；实验记录写明实际起测方式。
7. 场景/实验元数据记录是否包含 `service-paths.json`；无该文件时按 BFS 兜底口径解释基线。
8. 解析 `actual` 时 `qosMeet` 保持可选；解析 `time/tsUs` 时同时兼容包络顶层与 `data` 内两种位置。

**2. 文档侧同步（仓库内）**

- 根 `CLAUDE.md`「关键事实」：补「service 入口 / flow 生效 / 只按发起业务校验」「GET path 是 flow 规范表示」。
- `docs/agents/智能体设计文档.md` 路径机制小节：补校验范围、GET 方向、恢复注意事项。
- `docs/simulator/仿真器相关.md` §10：补 service 入口 vs flow 生效的副作用、GET path 表示问题、`service-paths.json` 运行时语义。
- `experiments/iss/ISS-0004.md`：补二次确认结果；本 ISS-0005 作为文档差异汇总入口。

**3. 向官方确认（建议以书面清单提交）**

1. 路径状态是否以 flow 为一等资源？service 入口是否应聚合同 flow 全部业务校验？body 覆盖 `src/dst` 是否合法？
2. `GET /services/{id}/path` 是否应返回业务源→宿方向的完整段列表？反向业务缺接入链路是否为已知缺陷？
3. 评测镜像是否实现 `POST /simulation/start`？未实现时官方推荐的公开起测方式是什么？
4. 评测场景是否包含 `service-paths.json`？无该文件时初始路径是否预期走 BFS？
5. `actual.qosMeet` 是否稳定提供？公开 API 能否获得 test/background 标识？
6. `node_move` 与 `linkTypes.json` 缺 `losMeters` 是否会在评测镜像修复？
7. 1003/1004/1001 的最终语义与拒绝报文形态是什么？

### 失败方案与注意事项

- 只给单条业务选路、假设兄弟业务不受影响 → 会被 flow 级生效推翻。
- 把 `accepted` 当作「该业务已达标」或「同 flow 其它业务不受影响」 → 错误。
- 用 GET path 返回值直接恢复/复制 → 反向业务缺接入链路，触发 1001。
- 按 `category` 做路径隔离 → 公开 API 和平台都不支持。
- 假设 `service-paths.json` 一定存在、或假设 `postEvents` 会在运行时应用 → 基线解释会错。
- 只按文档「三类场景文件」准备评测数据 → 可能丢失预置路径，基线退化为 BFS。
- 在评审材料中直接写「官方文档错误」 → 建议写成「文档未定义/实现细节差异」，附源码与实测证据，区分已验证与待确认。

## 知识沉淀

- 根因摘要：官方文档按 service 建模，实际路径状态按 flow 共享；文档没有声明 flow 级副作用、校验范围和 GET 方向，叠加场景文件清单遗漏与错误码语义漂移，形成一组「按文档实现必踩」的口径差异。
- 适用条件：所有通过公开 API 做重路由/起测/路径恢复的实验；所有依赖 `service-paths.json` 的基线；所有把 `node_move` 写进场景建模的方案。
- 可复用解决策略：agent 侧建立 flow 语义层（聚合需求、flow 级选路、flow 级复查）；路径快照/恢复按业务方向重建；起测方式做环境探测；实验元数据记录场景文件完整性。
- 失败经验：把 `accepted` 当达标、把 GET path 当业务方向完整路径、把 `service-paths.json` 当必然存在、把 `node_move` 当可用扰动。
- 是否可形成规则：`是`（「文档 service 级 ≠ 运行 flow 级；静态 accepted ≠ 实测达标；GET path ≠ 业务方向完整路径」）。
