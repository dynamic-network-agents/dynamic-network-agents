## 问题描述

### 背景

公开 API 中唯一能改变网络状态的写动作是：

```text
POST /api/open/v1/services/{serviceId}/path
```

接口名和 URL 形状是 **service 级**，容易让调用方认为“可以给某一条业务单独设路”。但仿真器的转发面实际按 **flow（无向源-宿 IP 对）** 维护路径。需要核实：这个 service 级入口到底改的是什么粒度，以及它的受理校验是否覆盖了受影响的全部业务。

### 实际现象（源码核对结果）

1. **入口是 service 级，生效是 flow 级。**
   `_set_service_path()` 从 `serviceId` 找到业务对象后，实际执行：

   ```python
   src = str(body.get('srcNodeId', it['srcNodeId']))
   dst = str(body.get('dstNodeId', it['dstNodeId']))
   (flow, _) = _flow_for(src, dst)
   ...
   (ok, err) = CTX['set_path'](flow, via)
   ```

   `_flow_for()` 用两端 `nodeId` 查 IP，再调用 `flow_of_ips(ip1, ip2)`，是无向 flow。因此给任一业务设路，等于给该业务所在 flow 的所有业务设路。

2. **GET 也是 flow 级。**
   `GET /services/{serviceId}/path` 走 `_service_path_obj()`，内部是 `get_path(flow)`。同一 flow 下不同业务查出来的 `pathId`、`segments` 相同。

3. **静态校验只按“被调用的那条业务”的 requirement。**
   `_set_service_path()` 中：

   ```python
   req = CTX.get('svc_req', {}).get(sid) or it.get('requirement') or {}
   comp = _compose_qos([...])
   violations = _qos_violations(comp, req)
   if violations:
       raise ApiError(1004, ...)
   ```

   `sid` 是 URL 里的 `serviceId`。同 flow 下其它业务的 requirement **没有参与校验**。因此存在这种可能：为业务 A 下发的路径返回 `accepted`，但该路径对同 flow 的业务 B 已经不满足 QoS，B 只能在运行时通过 `actual.qosMeet=false` 暴露。

4. **body 的 `srcNodeId/dstNodeId` 可覆盖，且不校验与 `serviceId` 端点一致。**
   源码使用 `body.get('srcNodeId', it['srcNodeId'])`，并没有比较传入值与业务自身端点。理论上可以用业务 A 的 `serviceId` 去设置另一个 flow 的路径，而 requirement 仍取 A 的。正常调用不会这样用，但接口没有拦截。

### 预期结果

接口语义应与实际副作用一致，至少有其一：

- 把 flow 作为一等资源，提供 flow 级路径设置接口，并按该 flow 全部业务的约束校验；或
- 保留 service 入口，但受理时聚合同 flow 所有业务的 requirement（带宽取 max，时延/抖动/丢包/误码取最严），任一业务不满足即拒绝。

当前实现两者都没有，正确性责任被推给了调用方。

### 影响范围

- 影响模块：`src/algorithms`（候选路径评估）、`src/baseline`（重路由闭环）、`src/agents`（未来决策）、实验分析口径。
- 影响场景：所有包含“同一对端点多条业务”的场景；sce01 中 17 个 flow 里有多个多业务 flow。
- 影响业务：同 flow 的背景业务和测试业务会一起被改路；无法按 `category` 隔离。
- 是否阻断实验：不阻断，但会直接影响重路由正确性判断和“达标率”解释。
- 对结果/评分的潜在影响：如果 agent 只按单业务需求选路，可能出现“下发成功但兄弟业务变差”，在结果分析中表现为难以解释的 QoS 回退。

0. 启动一个干净实例（不选脚本，避免事件干扰）：

1. 用公开 API 确认三条业务在同一个 flow（无向 `src/dst` 对）：

   ```bash
   TOKEN=$(python3 -c "import json;print(json.load(open('simulator/conf/gateway.json'))['openTokens'][0])")
   API=http://localhost:10100/api/open/v1
   curl -sS -H "X-Open-Token: $TOKEN" "$API/services?status=running&size=500" | python3 -m json.tool
   ```

2. 记录基线路径与实测：

   ```bash
   for sid in TSV0005 BGV0009 BGV0020; do
     echo "== $sid path"; curl -sS -H "X-Open-Token: $TOKEN" "$API/services/$sid/path"; echo
     echo "== $sid actual"; curl -sS -H "X-Open-Token: $TOKEN" "$API/services/$sid" | python3 -c "import sys,json; d=json.load(sys.stdin)['data']; print(d['actual'])"
   done
   ```

   预期：三条业务的 `segments` 相同（同一 flow 路径）。初始引流未写 `path_info` 时，`pathId` 可能都是 `P00000`、`source=system`，这是正常的；关键是 `segments` 一致。

3. 以 `TSV0005` 为入口下发候选路径：

   ```bash
   curl -sS -X POST "$API/services/TSV0005/path" \
     -H "X-Open-Token: $TOKEN" -H 'Content-Type: application/json' \
     -d '{"requestId":"verify-iss0003-001","srcNodeId":"UAV0002","dstNodeId":"UAV0001",
          "segments":[{"type":"link","id":"L00019"},{"type":"link","id":"L00011"},
                      {"type":"link","id":"L00010"},{"type":"link","id":"L00009"},
                      {"type":"link","id":"L00015"},{"type":"link","id":"L00017"}]}'
   ```

   预期返回 `result=accepted`。若返回 1004，说明平台按 `TSV0005` 的需求判定候选路径不合格，需换候选；若 1001，检查段连续性。

4. 立即复查三条业务的路径和实测：

   ```bash
   for sid in TSV0005 BGV0009 BGV0020; do
     echo "== $sid path"; curl -sS -H "X-Open-Token: $TOKEN" "$API/services/$sid/path"; echo
   done
   for i in $(seq 1 10); do
     for sid in TSV0005 BGV0009 BGV0020; do
       curl -sS -H "X-Open-Token: $TOKEN" "$API/services/$sid" | python3 -c "import sys,json; d=json.load(sys.stdin)['data']; a=d['actual']; print(d['serviceId'], a.get('jitterMs'), a.get('qosMeet'))"
     done
     sleep 3
   done
   ```

   预期：三条业务的 `GET path` 变成同一个新 `pathId`、`source=agent`、`segments` 相同；`BGV0009/BGV0020` 的 `actual.jitterMs` 升到 11 以上并出现 `qosMeet=false`；`TSV0005` 保持 `qosMeet=true`（其 jitter 上限 50）。

5. （可选，谨慎）验证 body 覆盖：用 `TSV0005` 的 `serviceId`，body 传另一个 flow 的 `srcNodeId/dstNodeId`，观察是否受理。该步骤会改非预期 flow，只在可重建的测试网中做。

判定：

- 步骤 2 三条 `segments` 相同 → 同一 flow 共用路径；
- 步骤 3 返回 `accepted` 且步骤 4 三条路径全部变化 → service 入口、flow 生效；
- 步骤 3 的 `accepted` 本身即证明平台只按 `TSV0005` 校验：候选路径静态对 `BGV0009/BGV0020` 的 jitter 已违规，却未被拒绝；
- 步骤 4 的 `BGV0009/BGV0020` 实测回退 → 兄弟业务受影响（若实测抖动未超过 11，仍以「accepted + 静态违规」作为校验缺口的证据，不把实测波动当成唯一判据）。

恢复：用原路径 `L00019 → L00012 → L00015 → L00017` 重新下发，或直接结束/重启实例。

## 分析过程

### 初步判断

平台的路径状态是 flow 级，但公开 API 资源建模和受理校验是 service 级，两者没有对齐。flow 级模型本身合理；问题在于 service 级接口没有把 flow 级副作用和校验范围表达出来。

### 排查记录

|---|---|---|---|
| 2026-11-18 | 解包 `netsim.tar`，解码 `openapi.py` | `_set_service_path()` 最终调用 `set_path(flow, via)` | 确认生效粒度是 flow |
| 2026-11-18 | 核对 `_flow_for()` | 用两端 IP 调 `flow_of_ips`，无向 | 与文档「flow 级」一致 |

| 2026-11-18 | 核对 body 覆盖 | `body.get('srcNodeId', ...)` 无端点一致性校验 | 契约漏洞，待确认是否为有意设计 |

### 根因分析

**已核实**：公开 API 以 `serviceId` 为入口，但内部把 `serviceId` 解析为无向 flow 后，按 flow 设置路径；`GET` 同样按 flow 读取。受理校验只使用被调用业务的 requirement，未覆盖同 flow 其它业务；body 的 `src/dst` 可覆盖且未校验与 `serviceId` 一致。

**待验证**：运行时是否确实出现“为 A 下发成功、B 的 `qosMeet` 回退”；以及 body 覆盖是否会被受理。

### 排除过的原因

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 只是文档没写清楚 | 核对源码与文档 | 排除：文档已说明 flow 级，源码行为也确实是 flow 级；问题在校验范围和接口契约 |
| 是 agent 侧解析错误 | 直接核对平台源码 | 排除：平台内部就是 `set_path(flow)` |
| 是初始引流竞态导致的偶发 | 源码核对 `_set_service_path()` 的受理路径 | 排除：这是运行期设路逻辑，与初始引流竞态无关（后者属 ISS-0002 相关现象） |
| 平台会校验同 flow 全部业务 | 核对 `req` 取值 | 排除：只取 URL 里的 `serviceId` |
| body 的 `src/dst` 只是必填形式 | 核对取参逻辑 | 排除：显式传入会覆盖业务端点，且无一致性校验 |

## 解决方案

### 修复措施

平台发布件不可修改，本问题的“修复”落在 agent 侧适配：

1. 以 flow 为单位组织决策，不按 service 单独规划；
2. 候选路径评估前，先聚合该 flow 下所有业务的 requirement；
3. 下发后复查该 flow 下所有业务的 `actual.qosMeet`，不只看发起业务；
4. 对外描述时明确这是平台约束，不作为 agent 侧缺陷；
5. 若后续与官方沟通，可建议其将 flow 作为一等资源，或在 service 入口上做 flow 级聚合校验。

### 涉及文件/模块

- `netsim:/opt/simulator/netsim/openapi.py`（只读核对，不修改）
- `src/algorithms/`：flow 级候选路径评估
- `src/baseline/`：flow 级下发与复查
- `src/agents/`（预留）：决策单位与冲突处理
- `docs/agents/智能体设计文档.md`、根 `CLAUDE.md`：补充“service 入口 / flow 生效 / 单业务校验”的口径

### 失败方案与注意事项

- 不要假设 `accepted` 等于“该 flow 全部业务都满足”；
- 不要为同一 flow 的不同业务分别设路，后一次会覆盖前一次；
- 不要依赖 `category` 做路径隔离，公开 API 和平台都不支持；
- body 的 `src/dst` 应始终传业务自身端点，避免误改其它 flow。

## 知识沉淀

- 根因摘要：路径状态是 flow 级；公开 API 用 service 级入口暴露，受理校验也只按单个 service，导致“入口粒度、生效粒度、校验粒度”三者不一致。
- 适用条件：所有通过 `POST /services/{serviceId}/path` 做重路由的场景，尤其是同一对端点有多条业务的 flow。
- 可复用解决策略：agent 侧建立 flow 语义层——聚合需求、flow 级选路、flow 级复查；不要依赖平台按业务隔离。
- 失败经验：把 `accepted` 当作“该业务已达标”或“同 flow 其它业务不受影响”都会出错。
- 是否可形成规则：`是`（“service 入口 ≠ service 生效；决策单位是 flow”）
- 是否可形成 Skill：`待定`
- 是否建议进入 RAG 知识库：`是`
