## 问题描述

### 背景

`POST /services/{serviceId}/path` 是按 flow 生效的。为了验证 ISS-0003，测试先读取同 flow 三条业务的 `GET /services/{serviceId}/path`，预期它们返回同一条完整路径；测试结束再按基线路径恢复。

### 实际现象

首次运行（实例刚起、没有任何 agent 下发，flow 路径为 system 初始路径 `P00000`）时：

| 业务 | 业务方向 | GET path segments |
|---|---|---|
| `TSV0005` | UAV0002 → UAV0001（反向） | `L00015 → L00012`（2 段） |
| `BGV0009` | UAV0001 → UAV0002（正向） | `L00017 → L00015 → L00012 → L00019`（4 段） |
| `BGV0020` | UAV0001 → UAV0002（正向） | `L00017 → L00015 → L00012 → L00019`（4 段） |

`TSV0005` 的返回**缺少两端接入链路** `L00019`（UAV0002–GND010）和 `L00017`（UAV0001–GND001），只剩 core 链路 `L00015`、`L00012`。

用 `TSV0005` 的 GET 返回值直接做恢复下发：

```text
POST /services/TSV0005/path
segments = L00015 -> L00012
→ 1001 段列表不连续：L00015 与当前节点 h2 不相接
```

改用完整路径 `L00019 → L00012 → L00015 → L00017` 后恢复成功。

另一次运行中，先对 `TSV0005` 下发过路径（flow 的 `path_info` 被写入），之后三条业务 `GET path` 都返回同一份完整段列表：

```text
L00019 → L00011 → L00010 → L00009 → L00015 → L00017
```

但 `BGV0009`/`BGV0020` 的业务方向是 UAV0001→UAV0002，返回段列表的首段 `L00019` 接的是 UAV0002，不接业务源节点 UAV0001。也就是说：

- **无 `path_info`（system 初始路径）**：反向业务的 GET path 缺少接入链路；
- **有 `path_info`（agent 下发后）**：GET path 直接返回 flow 规范方向的 `links`，不按请求业务的方向重排。

### 预期结果

`GET /services/{serviceId}/path` 应返回该业务 **源→宿方向**的完整段列表，包含接入链路；若平台只想暴露 flow 规范方向，至少应在文档/字段上明确“segments 是 flow 方向，调用方需自行定向”。

### 影响范围

- 影响模块：agent 侧路径恢复/复制、任何以 GET path 为输入的路径规划、`PathExecutor` 的路径校验。
- 影响业务：同一 flow 中与 flow 存储方向相反的业务（本次为 `TSV0005`、`BGV0009`、`BGV0020` 中的一个方向）。
- 是否阻断实验：不阻断，但会导致“读到的路径不能直接写回”的 1001 错误。
- 对结果/评分的潜在影响：若 agent 用 GET path 做快照/恢复/对比，可能误判路径缺失或下发失败。

## 分析过程

### 初步判断

`GET path` 的实现是 flow 级状态 + 业务级入口的组合：

- 有 `path_info` 时，直接返回 `path_info[flow]['links']`；
- 无 `path_info` 时，用 `_seg_link_ids(via, src_lab, dst_lab)` 从 flow 的 `via` 推导段列表。

问题在于 `via` 的方向是 flow 的 entry→exit，而调用方是 service；两者方向不一致时，接入链路的查找和段列表方向都会出问题。

### 排查记录

| 时间 | 排查动作 | 观察结果 | 判断/下一步 |

| 2026-11-18 16:48 | 用 TSV0005 GET 返回值恢复 | 1001 段列表不连续 | 不能直接用 GET 返回值恢复 |

### 根因分析（源码核对，具体行号待复核）

- `_service_path_obj(it)`：
  - 有 `path_info[flow]` 且含 `links` 时，直接返回该 `links`，**不按 `it['srcNodeId']/['dstNodeId']` 重排**；
  - 无 `path_info` 时，调用 `_seg_link_ids(via, src_lab, dst_lab)`。
- `_seg_link_ids()` 用 `_access_lab(src_lab, via[0])` 和 `_access_lab(dst_lab, via[-1])` 找接入链路；它假定 `via` 的方向与业务方向一致。
- `via` 是 flow 的 entry→exit 路径；对反向业务，`via[0]` 接的是业务宿节点，`via[-1]` 接的是业务源节点，`_access_lab` 找不到对应接入链路，于是两端的接入链路都被省略。
- 这不是 flow 路径本身的问题：三条业务的 core 链路 `L00015/L00012` 相同，flow 确实共用一条路；问题在 GET 的**表示层**。

### 排除过的原因

| 假设 | 验证方式 | 结果 |
|---|---|---|
| flow 路径本身对反向业务不同 | 对比 core 链路 | 排除：core 完全一致 |
| 接入链路真的不在路径上 | 对比 `service-paths.json` 与拓扑 | 排除：L00019/L00017 是两端接入链路，实际转发在用 |
| 是 agent 下发导致的 | 首次运行在 agent 下发前就复现 | 排除 |
| 只是 `pathId` 不同 | 检查 segments | 排除：segments 内容/数量不同 |

## 解决方案

### 修复措施

平台发布件不可修改。agent 侧适配：

1. 不直接使用 `GET path` 的返回值做恢复/复制；
2. 从拓扑或 `service-paths.json` 构造完整路径，并按业务的 `srcNodeId/dstNodeId` 定向；
3. 若必须使用 `GET path`，先检查首段是否接业务源节点、末段是否接业务宿节点，缺失则用接入链路补齐；
4. 下发前用 `validate_path` 做连续性校验，避免 1001。

### 涉及文件/模块

- `netsim:/opt/simulator/netsim/openapi.py`（只读核对，不修改）
- `src/algorithms/graph.py`（`validate_path`）
- `src/api/executor.py`（下发前校验）
- `src/baseline/`（路径快照/恢复逻辑）
- 测试：`tests/integration/test_iss0003_flow_path_contract.py`

### 失败方案与注意事项

- 直接用 GET path 的 segments 恢复：反向业务会缺接入链路，触发 1001。
- 只比较完整 segments 判断“是否同一条路”：会把表示差异误判为路径不同；应比较 core 链路或按无向链路集合归一化。
- 不能假设 GET path 返回顺序等于业务源→宿方向。

## 知识沉淀

- 根因摘要：GET path 是 flow 状态 + service 入口；无 `path_info` 时用 flow 的 entry→exit `via` 推导段列表，反向业务找不到两端接入链路；有 `path_info` 时直接返回 canonical links，不按业务方向重排。
- 适用条件：同一 flow 内存在与 flow 存储方向相反的业务。
- 可复用解决策略：路径快照/恢复必须按业务方向定向，并从拓扑补齐接入链路；比较路径时用 core/无向链路集合，不要直接比较原始 segments。
- 失败经验：用 GET path 的返回值直接恢复 → 1001。
- 是否可形成规则：`是`（“GET path 是 flow 规范表示，不等于业务方向完整路径”）
