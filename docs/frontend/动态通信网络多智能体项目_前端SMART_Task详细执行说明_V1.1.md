# 动态通信网络多智能体项目——前端 SMART Task 详细执行说明（V1.1）

> 状态：建议开发基线，待团队确认；版本：V1.1；日期：2026-11-07  
> 技术栈：React + TypeScript + Vite + Ant Design + AntV G6 + ECharts + Zustand + Axios + WebSocket + MSW  
> 测试栈：Vitest + React Testing Library + MSW + Playwright  
> 工期均为建议工作日，不是已承诺的日历排期。

## 1. 目标与范围

将前端工作拆成可分派、可跟踪、可验收的 SMART Task。每个功能 Task 必须同步提交单元测试和适用的集成测试，不把测试留到项目末尾。

前端负责场景配置、仿真控制、网络拓扑可视化、Agent过程展示、资源/QoS展示和实验分析；路由计算、资源优化、仿真协议逻辑由后端/算法服务完成，前端不得自行伪造算法结果。

## 2. SMART 与完成定义

- **S（具体）**：明确页面/模块、输入输出、工作边界和依赖。
- **M（可衡量）**：有代码、页面、接口、测试产物和可验证验收条件。
- **A（可实现）**：以既定技术栈和 Mock 先行方式实施，避免所有任务都阻塞于后端。
- **R（相关）**：对应动态拓扑、链路变化、业务QoS、多Agent协同或实验评估。
- **T（有时限）**：明确建议工作日、前置任务和里程碑。

**DoD（完成定义）**：功能代码、单元测试、适用的集成测试、失败/边界处理、代码审查、类型/接口文档更新全部完成，CI通过后才能标记 Done。页面能打开不等于任务完成。

## 3. 测试策略与质量门槛

| 测试层 | 工具 | 覆盖内容 |
|---|---|---|
| 静态检查 | TypeScript、ESLint、Prettier | 类型、规范、格式 |
| 单元测试 | Vitest | 工具函数、Store、Hooks、API适配器、事件reducer |
| 组件测试 | Vitest + React Testing Library | 组件渲染、表单、交互、加载/空/错误态 |
| 集成测试 | Vitest + RTL + MSW | 页面、Store、API、WebSocket之间的联动 |
| E2E | Playwright | 用户关键业务流程 |
| 契约测试 | OpenAPI/JSON Schema校验 | DTO字段、枚举、响应/事件结构 |

建议质量门槛：
- 核心业务逻辑（Store、DTO适配、事件处理、场景校验）：语句/分支覆盖率目标 ≥ 85%。
- 一般组件和页面辅助逻辑：语句覆盖率目标 ≥ 70%。
- 每个功能 Task 至少有单元测试；涉及跨模块/接口的 Task 必须有集成测试。
- 每个测试至少考虑正常路径和一个适用的失败/边界路径。
- P0关键流程必须有E2E；覆盖率不能代替业务流程测试。
- 配置类任务以构建、CI、挂载测试和配置行为验证代替不适用的业务集成测试。

## 4. 里程碑建议

| 里程碑 | 时间建议 | 结果 | 验收 |
|---|---:|---|---|
| M0 工程基础 | 第1周 | 工程、路由、类型、API、Mock、Store | CI检查与构建通过 |
| M1 场景与仿真 | 第2–3周 | 场景编辑、校验、仿真生命周期、事件注入 | Mock下完成场景到仿真启动 |
| M2 动态拓扑 | 第3–4周 | G6拓扑、详情、WebSocket实时更新 | 链路/节点变化可实时反映 |
| M3 Agent与QoS | 第4–5周 | Agent、A2A、策略、资源和QoS | 展示诊断到策略执行闭环 |
| M4 实验分析 | 第5–6周 | Dashboard、实验和指标对比 | 结果可追溯、可比较 |
| M5 联调交付 | 第6–7周 | 真实后端联调、E2E、性能和部署 | P0流程通过 |

主依赖：工程初始化 → 类型/API/Mock/Store → 场景与仿真 → 拓扑实时更新 → Agent/资源/QoS → 实验分析 → 真实后端联调与交付。可并行的任务在下表注明。

## 5. SMART Task 明细

每项估算已包含编写该任务对应测试的时间。

### A. 工程基础

#### FE-001 React工程初始化
- **目标**：建立 React + TypeScript + Vite 工程、环境配置和标准目录。
- **交付物**：可运行工程、目录结构、README。
- **单元/组件测试**：App入口可挂载；环境配置读取函数测试。
- **集成测试**：CI执行 typecheck、lint、test、build。
- **验收**：新环境按README可启动；构建成功且无TS错误。
- **依赖/工期**：无；1–2天。

**执行细化（FE-001）**
- **具体要做**：创建 React + TypeScript + Vite 单页应用；确定 Node/包管理器版本；配置开发、测试、构建环境变量；建立 api、features、components、stores、types、mocks、utils、tests 等目录；提供全局入口、错误边界和基础样式入口。
- **完成后应呈现**：执行安装命令后可启动开发服务器；首页能挂载；生产构建可生成静态资源；README 写明环境要求、启动、构建和测试命令；不在此任务中实现具体业务页面。
- **实现建议**：使用 Vite React-TS 模板；统一使用团队选定的 npm/pnpm/yarn；配置路径别名；区分 .env.development、.env.test、.env.production；环境变量通过类型声明读取，禁止业务代码散落读取 import.meta.env；入口只负责 Provider、Router、全局错误边界和样式。
- **测试范围**：单元/组件：入口挂载、环境变量解析和缺省值；集成/工程：干净环境安装、typecheck、lint、test、build 全链路；验证缺少必要配置时给出可理解提示，而不是白屏。

#### FE-002 质量工具与测试框架
- **目标**：配置 ESLint、Prettier、Vitest、RTL、覆盖率和CI。
- **交付物**：测试配置、示例测试、CI脚本。
- **单元测试**：示例工具函数和组件测试。
- **集成测试**：CI完整流水线；验证失败测试会使流水线失败。
- **验收**：统一命令可执行；覆盖率报告可生成。
- **依赖/工期**：FE-001；1–2天。

**执行细化（FE-002）**
- **具体要做**：配置 ESLint、Prettier、Vitest、React Testing Library、覆盖率工具和 CI；建立测试目录约定、测试初始化文件、公共 render 工具和测试数据工厂。
- **完成后应呈现**：开发者可用统一脚本执行 lint、typecheck、unit test、coverage、build；PR 自动执行质量检查；测试失败时 CI 失败并显示定位信息；提供一个工具函数和一个 React 组件的示例测试。
- **实现建议**：统一测试环境为 jsdom；配置 Vitest setup、测试清理、覆盖率阈值；建立 renderWithProviders，按需封装 Router/Store/Query 等 Provider；MSW server 在测试生命周期启动、重置和关闭；Playwright 可在后续任务接入，不要求本任务完成全部 E2E。
- **测试范围**：单元：示例纯函数、组件渲染与交互；集成/工程：CI 成功路径、故意引入失败测试时流水线应失败、覆盖率报告能生成；检查测试隔离，单个测试不依赖执行顺序。

#### FE-003 全局布局与路由
- **目标**：实现主框架、导航、面包屑和一级页面路由骨架。
- **交付物**：Dashboard、拓扑、场景、仿真、Agent、资源QoS、实验页面占位。
- **单元/组件测试**：菜单渲染、路由高亮、折叠、404。
- **集成测试**：导航跳转到各页面；未知路径进入404。
- **验收**：所有一级路由可访问；刷新子路由正常。
- **依赖/工期**：FE-001/002；2天。

**执行细化（FE-003）**
- **具体要做**：搭建系统主框架：侧边栏/顶部栏、页面内容区、面包屑、导航菜单、一级路由、404 页面和页面级加载容器。
- **完成后应呈现**：具备 Dashboard、场景管理、仿真控制台、网络拓扑、Agent监控、资源与QoS、实验分析等可访问的页面骨架；导航有当前选中态；页面标题和面包屑与路由一致；窄屏下布局不发生明显溢出。
- **实现建议**：使用 React Router 管理路由；布局组件与页面组件分离；菜单配置集中维护并由路由元信息生成；懒加载较大的业务页面；页面占位统一使用 PageHeader、ContentContainer 等基础壳组件；权限未确定前不自行设计复杂权限体系。
- **测试范围**：单元/组件：菜单项生成、当前路由匹配、折叠状态；集成：从菜单逐项导航、浏览器刷新子路由、未知路由进入 404、返回上一页；验证页面切换后全局布局保持。

#### FE-004 共享类型与DTO适配
- **目标**：建立统一 TypeScript 类型和后端DTO到前端ViewModel的适配层。
- **范围**：Node、Link、Flow、Scenario、ScenarioEvent、SimulationRun、TopologySnapshot、AgentTask、AgentMessage、Policy、MetricPoint、RealtimeEvent。
- **交付物**：`types/`、`adapters/`和字段说明。
- **单元测试**：字段映射、可选字段、未知枚举、单位格式、旧字段拼写兼容。
- **集成测试**：样例JSON可转换为页面模型。
- **验收**：控制链路与数据链路按独立linkId/linkPlane表达；页面不散落硬编码DTO映射。
- **依赖/工期**：数据模型V0.1；2–3天。

**执行细化（FE-004）**
- **具体要做**：定义前端领域模型和服务端 DTO 适配层，覆盖节点、链路、业务流、QoS、场景、动态事件、仿真运行、拓扑快照、Agent、A2A消息、策略、资源分配、指标和实时事件。
- **完成后应呈现**：形成可复用的 types、schemas、adapters；页面只消费稳定的 ViewModel，不直接依赖服务端原始字段；字段含义、单位、可空性、枚举和版本约定有文档。
- **实现建议**：区分 API DTO 与 UI ViewModel；用 Zod 或 JSON Schema 对外部数据做运行时校验；适配器负责字段映射、枚举兜底、单位标准化和缺失值处理；Link 必须以 linkId 为实体标识，linkPlane/type 表示 CONTROL 或 DATA，同一端点对可存在多条不同链路；不能根据节点对推导不存在的链路；仿真时间字段统一明确为 simTimeMs，墙上时钟使用 timestamp。
- **测试范围**：单元：每类 DTO 到 ViewModel 映射、可选字段、未知枚举、非法数值、单位格式和链路平面独立性；集成：代表性 JSON fixture 经 schema 校验和 adapter 后可供页面使用；验证未知字段不会导致整个页面崩溃。

#### FE-005 API客户端与错误处理
- **目标**：统一Axios实例、响应封装、错误码、请求ID、超时和取消请求。
- **交付物**：API client、错误类型和模块化API函数。
- **单元测试**：响应解包、错误码映射、参数序列化。
- **集成测试**：MSW模拟成功、400/409/422/500、超时；页面显示正确反馈。
- **验收**：页面不自行创建Axios实例；错误反馈一致且可追踪。
- **依赖/工期**：FE-004；2天。

**执行细化（FE-005）**
- **具体要做**：封装统一 HTTP 客户端、API 模块、请求/响应拦截、超时、取消、错误归一化和请求追踪信息。
- **完成后应呈现**：场景、仿真、拓扑、Agent、资源、指标、实验等模块通过各自 api 文件访问服务；页面不直接调用 Axios；错误统一包含 message、code、status、requestId 和可选 fieldErrors。
- **实现建议**：建立 apiClient 和按领域拆分的 service；baseURL 从环境配置读取；统一处理 401/403/409/422/5xx；对可取消查询使用 AbortController；写操作不做无依据的自动重试；保留服务端 requestId/traceId；接口路径和字段以双方确认的 API 契约为准。
- **测试范围**：单元：响应解包、错误归一化、查询参数序列化、取消请求；集成：MSW 模拟成功、校验错误、版本冲突、服务异常、超时；验证页面能区分字段错误、冲突和系统故障。

#### FE-006 Zustand状态管理骨架
- **目标**：拆分场景、仿真、拓扑、Agent、指标等Store。
- **交付物**：Store、selectors、状态更新约定。
- **单元测试**：初始状态、action、selector、runId切换清理、不可变更新。
- **集成测试**：多组件共享更新；切换runId后旧数据不残留。
- **验收**：无跨运行数据污染；核心状态变化有测试。
- **依赖/工期**：FE-004；2天。

**执行细化（FE-006）**
- **具体要做**：建立按领域划分的 Zustand Store、selectors 和状态更新约定，管理当前场景、当前 run、拓扑快照、实时事件、Agent任务、策略、指标和 UI选择态。
- **完成后应呈现**：各页面共享同一份当前运行状态；Store 不保存可由组件轻易推导的大量重复数据；切换场景或 run 时相关状态有明确清理策略；异步请求状态可区分 idle/loading/success/error。
- **实现建议**：按 scenario、simulation、topology、agent、resource、metric、ui 拆分；把服务端事实状态与本地临时编辑态分开；使用 selector 避免无关组件重复渲染；通过 action/reducer 风格函数集中处理关键事件；所有运行数据按 runId 隔离，必要时按 snapshotVersion/seq 防止旧数据覆盖新数据。
- **测试范围**：单元：初始状态、action、selector、run切换、事件更新、不可变性；集成：两个以上组件订阅同一状态、切换 run 后旧拓扑/指标/消息清理、晚到的旧请求不能覆盖新 run。

#### FE-007 Mock REST与WebSocket
- **目标**：建立REST与WebSocket共享同一运行态的Mock系统。
- **交付物**：MSW handlers、fixtures、Mock WS Provider、固定随机种子、Mock开关。
- **单元测试**：Mock状态转换、事件生成、固定seed可复现。
- **集成测试**：REST写入后GET和WS事件反映相同状态。
- **验收**：`VITE_USE_MOCK`可切换；UI标记Mock；同输入结果可复现。
- **依赖/工期**：FE-005/006；2–3天。

**执行细化（FE-007）**
- **具体要做**：建立可复现的 Mock 服务，覆盖 REST API 和实时事件通道；让场景保存、仿真运行、拓扑变化、Agent消息、策略和指标在同一模拟运行态中保持一致。
- **完成后应呈现**：无需真实后端即可演示核心业务流程；Mock 数据有固定 seed；页面明确显示 Mock 模式；REST 查询到的状态与 WebSocket 推送的状态一致；可切换 Mock/真实服务。
- **实现建议**：MSW 拦截 REST；实时通道建立可替换的 MockWebSocketProvider；用统一内存状态仓库维护 nodes、links、flows、runs、events、policies、metrics；事件由场景时间线或手动触发产生；Mock 与真实服务实现相同接口，不让页面感知数据来源；避免每个页面各自维护一份假数据。
- **测试范围**：单元：状态转换、固定 seed 可复现、事件生成和时间推进；集成：REST 写入后 GET 返回一致状态，WebSocket 事件与查询结果一致，切换 run 不串数据；验证关闭 Mock 后请求发往配置的真实 API。

### B. 场景配置与仿真控制（P0）

#### FE-010 场景列表与选择
- **目标**：展示场景列表，支持搜索、状态筛选、分页和场景选择。
- **交付物**：场景列表页和API接入。
- **单元测试**：筛选参数、状态映射、分页。
- **集成测试**：MSW多场景数据下筛选、分页、跳转；覆盖空态和错误态。
- **验收**：列表数据、分页和场景ID正确。
- **依赖/工期**：FE-003/005/007；1–2天。

**执行细化（FE-010）**
- **具体要做**：实现仿真场景列表页，支持加载、搜索、按状态/标签筛选、分页、选择、创建入口和进入编辑。
- **完成后应呈现**：表格或卡片展示场景名称、描述、节点/链路/业务数量、更新时间、版本和状态；有加载、空数据、错误和刷新状态；点击行进入场景详情或编辑页。
- **实现建议**：建立 ScenarioListPage、ScenarioTable、ScenarioFilters；筛选条件进入 URL query，便于刷新和分享；分页由服务端支持时走服务端分页；列表数据由 scenario API 获取；创建和复制入口只接已实现能力，不虚构服务端行为。
- **测试范围**：单元：筛选条件构造、状态标签映射、分页参数；组件：空态、错误态、加载态和行操作；集成：MSW 多条场景下筛选/分页/选择/跳转，刷新后查询条件保持。

#### FE-011 场景基础信息与节点配置
- **目标**：创建/编辑场景信息和节点集合。
- **范围**：名称、描述、seed、时长；节点类型、角色、状态、位置和资源。
- **交付物**：场景表单、节点配置表格/抽屉。
- **单元测试**：表单校验、节点序列化、必填和范围。
- **集成测试**：创建/编辑→提交API→重新读取一致；失败时保留输入。
- **验收**：非法字段不能提交；保存后版本刷新。
- **依赖/工期**：FE-004/005/010；2–3天。

**执行细化（FE-011）**
- **具体要做**：实现新建/编辑场景基础信息和节点配置，包括名称、描述、随机种子、仿真时长、节点类型、角色、在线状态、位置、移动属性和平台资源属性。

## 6. 必须通过的集成测试与E2E场景

### IT-01 场景创建和保存
创建场景→添加节点→分别配置控制/数据链路→添加业务和QoS→添加动态事件→保存并回读。  
**通过条件**：字段完整；链路平面不合并；非法引用被拦截。

### IT-02 仿真生命周期
选择场景→创建run→启动→暂停→恢复→停止→切换run。  
**通过条件**：状态以服务端确认为准；非法状态转换有反馈；旧run数据清理。

### IT-03 链路中断—诊断—重路由—业务恢复
注入链路中断→拓扑更新→运维Agent诊断→资源Agent生成策略→协调器校验/应用→路径和QoS变化。  
**通过条件**：traceId串联任务和策略；只展示后端返回的路径/指标。

### IT-04 链路退化与QoS资源调整
注入带宽/时延/丢包变化→显示QoS违规→接收资源策略→显示调整结果。  
**通过条件**：实测值、阈值、违规原因可区分；不伪造恢复结果。

### IT-05 高优先级业务加入与资源抢占
新增业务→展示资源冲突→接收分配策略→展示各业务资源变化。  
**通过条件**：分配结果来自后端；优先级解释遵从接口约定。

### IT-06 WebSocket断线恢复
接收事件→断线→服务端状态变化→重连lastSeq→补发或快照同步。  
**通过条件**：无重复应用；无法补发时可重同步；最终状态一致。

### IT-07 实验结果对比
选择至少两次实验运行→核对场景版本、seed、算法版本→比较指标。  
**通过条件**：单位一致；缺失值明确；指标可追溯到run。

## 13. 本版本的任务执行口径

### 13.1 每个 Task 的工作边界

- Task 的“具体要做”描述本任务需要完成的业务能力和范围；没有列出的能力不应默认纳入本 Task。
- “完成后应呈现”描述交付后用户能看到或开发团队能检查到的结果，不等同于视觉稿；页面布局细节可在 UI 设计阶段继续细化。
- “实现建议”是推荐的工程路径，不是要求所有组件必须按唯一方式实现；如团队调整技术方案，应保持数据契约、状态语义和验收结果不变。
- “测试范围”定义测试层级和验证对象。本版本暂不展开测试用例编号、逐步操作、输入数据和预期值，后续单独形成测试用例规格。

### 13.2 功能开发的标准交付包

每个功能 Task 的 PR 至少应包含：
1. 页面/组件/服务代码及必要的类型定义；
2. 对应的单元测试或组件测试；
3. 涉及 API、Store、WebSocket 或跨组件协作时的集成测试；
4. 加载、空数据、错误、无权限（如适用）、重复提交和数据缺失等状态处理；
5. 必要的接口字段说明、截图或录屏；
6. README/开发说明中与本 Task 有关的配置或运行方式更新。

### 13.3 建议统一的页面状态

列表、详情、图表和面板应根据实际场景实现适用状态，避免只实现成功态：
- Initial：尚未请求或尚未选择对象；
- Loading：正在加载；
- Success：正常展示；
- Empty：请求成功但没有数据；
- Error：请求失败，提供重试或返回操作；
- Stale：实时连接中断或数据版本落后，提示数据可能不是最新；
- Partial：部分接口/部分字段缺失，但其余内容仍可使用。

### 13.4 建议统一的数据语义约束

- **节点与链路**：节点以 nodeId 标识；链路以 linkId 标识。同一节点对可以有多条链路；CONTROL 和 DATA 是独立链路实体，不得合并、补造或共用一套参数。
- **业务需求与网络测量**：QoS 需求阈值与实际测量值分开保存、分开展示；缺少阈值/测量值时显示未知，不擅自按 0 或达标处理。
- **仿真时间与现实时间**：事件调度、曲线横轴和仿真进度使用 simTimeMs；创建时间、接收时间和心跳时间使用 timestamp。二者不能混用。
- **运行隔离**：拓扑、Agent消息、策略、资源和指标都必须关联 runId；不同 run 的状态不能混合。
- **版本与顺序**：实时事件按 runId、seq、snapshotVersion 等服务端定义进行校验；重复、乱序和缺口必须有处理策略。
- **算法结果归属**：路径、资源分配、策略可行性和 QoS 达标结论由后端/算法服务给出；前端负责呈现、筛选、格式化和可解释性展示，不伪造结果。

### 13.5 后续测试用例文档建议结构

后续可以按本文件的 Task ID 建立独立测试用例文档，建议字段为：
`Case ID / Task ID / 测试层级 / 测试目标 / 前置条件 / 输入数据 / 操作步骤 / 预期结果 / 清理动作 / 自动化状态`。
本版本只定义测试范围，具体 Case ID 和逐条用例留待测试设计阶段补充。
