# 动态通信网络多智能体项目------前端详细设计方案（React）

> 版本：V1.0\
> 定位：竞赛原型与复赛可部署系统的前端设计基线\
> 前端框架：React + TypeScript + Vite\
> 数据模型与接口：以《前后端数据模型与接口规范_v1.0》为**唯一事实源**；本文只做页面与交互设计，不重复定义字段、枚举与接口

------------------------------------------------------------------------

## 1. 文档目标与设计原则

### 1.1 建设目标

建设一套面向无人平台动态通信网络资源管控的可视化仿真与多智能体协同管控前端。系统应让使用者能够：

1.  配置无人平台节点、通信链路、业务流及动态事件；
2.  启动仿真并观察节点、链路、拓扑和业务状态的实时变化；
3.  观察通信网络运维智能体、通信网络资源控制智能体及协调器的任务执行过程；
4.  查看链路质量、带宽资源、路由变化、业务 QoS 保障结果；
5.  对不同场景、算法版本和策略进行可复现实验与量化对比。

前端是仿真系统的交互与可观测界面，不负责实现路由算法、带宽优化算法或大模型推理。前端负责配置、展示、交互、调用后端接口、呈现实验结果。

### 1.2 设计原则

-   **场景驱动**：场景配置是仿真的输入基础，节点、链路、业务和事件都应可编辑、可保存、可复用。
-   **动态可视**：拓扑图必须反映节点上下线、链路通断、链路质量变化和路由切换。
-   **控制面与数据面分离**：前端展示时明确区分控制链路与数据链路，不能默认任意两个节点之间同时存在两类链路。
-   **业务 QoS 可解释**：展示业务类型、优先级、QoS
    目标、实际测量值及是否达标。
-   **智能体过程可追踪**：每次任务通过 taskId / traceId
    串联感知、诊断、策略生成、仲裁、下发和执行反馈。
-   **接口先行、Mock
    可替换**：即使后端尚未完成，也使用与正式接口一致的数据结构和 API
    封装。
-   **实验可复现**：保存场景版本、随机种子、仿真参数、算法版本、策略记录和指标结果。
-   **渐进式实现**：先打通"场景配置---仿真运行---拓扑实时更新---结果记录"主链路，再增加复杂分析能力。

### 1.3 范围边界

  --------------------------------------------------------------------------
  前端负责                              后端/仿真/智能体负责
  ------------------------------------- ------------------------------------
  场景和参数配置、表单校验              场景合法性最终校验与仿真执行

  拓扑图、链路、路由和业务可视化        拓扑计算、邻居发现、路由计算

  仿真开始/暂停/单步等控制请求          仿真时钟、事件调度和状态推进

  Agent 状态、消息、工具调用展示        Agent 推理、A2A 消息、工具执行

  策略审批/确认交互（如启用人工确认）   策略生成、约束校验、冲突仲裁和下发

  指标图表、实验报告展示                指标计算、实验数据持久化
  --------------------------------------------------------------------------

前端不应在浏览器中自行计算"最终路由"或"最优带宽分配"。可提供本地表单预校验和轻量提示，但最终结果以仿真服务返回为准。

## 2. 用户角色与核心使用流程

### 2.1 主要用户

-   **实验人员**：创建场景、配置参数、运行实验、导出结果。
-   **算法/智能体开发人员**：观察 Agent
    决策链、工具调用、策略输入输出和失败原因。
-   **评审/演示人员**：快速理解网络状态、故障影响、策略执行和 QoS
    改善效果。
-   **系统管理员**：管理场景模板、数据集、算法版本和系统配置。

### 2.2 主流程

1.  进入系统，选择已有场景或创建新场景。
2.  配置节点、控制链路、数据链路、业务流和动态事件。
3.  保存场景并执行配置校验。
4.  启动仿真，前端订阅 WebSocket 实时事件。
5.  拓扑、链路指标、业务状态和 Agent 执行过程同步刷新。
6.  用户可暂停、单步推进、注入事件或调整仿真速度。
7.  仿真结束后生成实验记录，查看指标、事件时间线和策略效果。
8.  对比不同算法/策略或不同场景，导出实验报告。

## 3. 信息架构与页面规划

建议采用左侧主导航 + 顶部项目/仿真状态栏 + 中央工作区的布局。

  ---------------------------------------------------------------------------------------------------
  一级页面                主要功能                                            优先级
  ----------------------- --------------------------------------------------- -----------------------
  系统总览 Dashboard      当前仿真、网络摘要、业务 QoS、Agent 状态、最近实验  P0

  网络拓扑                节点/链路图、链路详情、路由路径、邻居/拓扑/路由表   P0

  场景配置                节点、链路、业务流、动态事件、场景模板              P0

  仿真控制台              开始/暂停/恢复/停止/单步、时间轴、事件注入          P0

  Agent 监控              Agent 状态、A2A 消息、任务链路、工具调用、策略记录  P1

  资源与 QoS              带宽分配、链路质量、业务 QoS、资源抢占              P1

  实验分析                指标统计、对比实验、事件复盘、结果导出              P1

  数据集与算法版本        测试集、算法版本、场景/实验关联                     P2

  系统设置                用户、权限、显示偏好、连接状态                      P2
  ---------------------------------------------------------------------------------------------------

### 3.1 全局布局

-   **顶部栏**：项目名称、当前场景、仿真状态、仿真时间、WebSocket
    连接状态、用户菜单。
-   **侧边栏**：上述一级页面。
-   **主工作区**：页面内容。
-   **全局通知区**：接口错误、仿真状态变化、Agent 异常、策略下发结果。
-   **全局详情抽屉**：节点、链路、业务流、Agent、策略的详情可复用抽屉。

### 3.2 全局状态

建议使用 Zustand 或 Redux Toolkit 管理跨页面状态。推荐 MVP 使用
Zustand，状态边界清晰后再考虑 Redux Toolkit。

全局状态只保存跨页面共享且需要同步的数据： 
- 当前projectId、scenarioId、runId； 
- 当前仿真状态与仿真时钟； 
- 当前拓扑快照版本； 
- 当前选中的 nodeId / linkId / flowId； 
- WebSocket连接状态； 
- 用户显示偏好。

表格筛选、抽屉开关、局部表单输入等页面状态留在组件内部，避免全局 Store
膨胀。

## 4. 页面详细设计

## 4.1 系统总览 Dashboard

### 页面目标

快速判断当前网络是否正常、关键业务是否达标、Agent 是否正在处理任务。

### 页面区域

1.  **仿真摘要卡片**：仿真状态、已运行时长、节点数量、在线节点数、链路数量、可用链路数。
2.  **网络健康卡片**：网络连通度、平均时延、平均丢包率、可用带宽。
3.  **业务 QoS 概览**：话音、视频、图片、数据的达标率和异常业务数。
4.  **Agent 状态**：运维 Agent、资源控制 Agent、Coordinator
    的在线/空闲/执行中/异常状态。
5.  **近期事件**：节点下线、链路中断、链路质量恶化、业务新增、策略下发等。
6.  **最近实验**：实验名称、场景、算法版本、运行时间、关键指标。

### 关键交互

-   点击节点/链路数量跳转拓扑页并应用过滤条件。
-   点击 QoS 异常业务跳转资源与 QoS 页。
-   点击 Agent 卡片跳转 Agent 监控页并选中对应 Agent。
-   点击最近实验进入实验详情。

### 所需数据

总览聚合接口 `GET /dashboard/summary`（见规范 §7.11），返回仿真摘要、网络指标、QoS 汇总、Agent 摘要、最近事件和最近实验。若后端暂无聚合接口，前端可组合调用拓扑/指标/Agent/事件接口（规范 §7）；不建议长期在浏览器端拼装大量全量数据。

## 4.2 网络拓扑页

### 页面目标

展示动态组网结构、节点状态、控制/数据链路、链路质量和业务路由。

### 拓扑画布

节点类型建议支持：
- UAV：无人机；
- UGV：无人车；
- USV：无人艇；
- UUV/AUV：无人潜航器（若场景使用）；
- RELAY：中继节点；
- BASE：地面站/基站；
- C2：指挥控制节点；
- EDGE：边缘计算/任务节点。

节点展示信息：
- 节点名称/ID、类型、在线状态；
- 可选位置/高度/速度；
- 当前簇/角色（普通节点、簇头、协调节点等）；
- 资源概况（剩余能量、可用带宽等，若仿真模型提供）。

链路展示信息：
- 链路平面 linkPlane：CONTROL / DATA；
- 链路介质类型 linkType：如 microwave / satellite 等（见规范 §6.2）；
- 方向：单向/双向；
- 状态：UP / DEGRADED / DOWN / UNKNOWN；
- 时延、抖动、带宽、误码率、丢包率；
- 当前承载业务流数量（若后端提供）。

**重要约束**：控制链路与数据链路必须作为独立链路实体展示。一个节点对之间可以只有控制链路、只有数据链路、两者都有，或两者都没有。不能仅根据节点相邻关系自动补齐链路。

### 视觉编码建议

-   节点形状/图标表示平台类型；
-   节点边框或角标表示在线/异常状态；
-   控制链路和数据链路采用不同线型或颜色；
-   链路状态使用颜色区分，链路类型使用线型区分；
-   被选中业务的路径高亮；
-   故障链路保留在图上并标注 DOWN，避免故障后消失导致无法复盘；
-   图例始终可见，支持显示/隐藏控制链路、数据链路、异常链路和业务路径。

颜色只是建议，最终需满足色彩对比度要求；状态不能只依赖颜色，还应有图标/文字。

### 右侧详情面板

点击节点显示：
- 基本信息、在线状态、位置；
- 邻居表；
- 节点路由表；
- 节点承载业务；
- 节点资源状态；
- 最近事件。

点击链路显示：
- linkId、linkPlane、linkType、srcNodeId、dstNodeId；
- 状态和参数；
- 参数趋势；
- 承载业务；
- 最近状态变化；
- 控制链路/数据链路属性。

点击业务路径显示：
- flowId、源/目的节点；
- 当前路由节点序列；
- 路径经过的链路及瓶颈链路；
- QoS 目标与当前测量值。

### 拓扑数据接口

本页所需接口见《前后端数据模型与接口规范_v1.0》§7.8（拓扑快照、节点/链路详情、邻居表、路由表、业务路径）与 §8.3 实时事件。要点：拓扑快照统一为 `GET /simulations/{runId}/topology`；`links[]` 必须保留 `linkPlane`，不得按节点对自动补齐控制/数据链路。

### 技术建议

拓扑图采用 AntV G6。图布局、节点拖拽、缩放、框选、路径高亮、图例和详情面板应封装成独立组件。

## 4.3 场景配置页

### 页面目标

通过可视化表单定义一套可复现的动态通信场景。

建议采用 Tab 或分步配置： 1. 场景基本信息； 2. 节点配置； 3. 链路配置；
4. 业务流配置； 5. 动态事件配置； 6. 场景校验与保存。

### 节点配置字段

-   `nodeId`、`name`、`nodeType`；
-   初始状态 `status`；
-   位置坐标（如仿真支持）；
-   角色/簇信息；
-   初始资源（电量、处理能力等，按仿真模型提供）。

### 链路配置字段

-   `linkId`；
-   `linkPlane`：CONTROL 或 DATA；
-   `linkType`：介质类型（如 microwave，见规范 §6.2）；
-   `srcNodeId`、`dstNodeId`；
-   `direction`；
-   `status`；
-   `delayMs`、`jitterMs`、`bandwidthBps`、`ber`、`packetLossRate`；
-   可选传播范围、信道、干扰等级等扩展字段（仅在仿真后端支持时启用）。

控制链路和数据链路应分 Tab
或通过类型筛选管理，表单字段可共享，但不能共用同一条记录来隐式表示两种链路。

### 业务流配置字段

-   `flowId`、业务名称；
-   `serviceType`：VOICE / VIDEO / IMAGE / DATA；
-   `srcNodeId`、`dstNodeId`；
-   `priority`；
-   `requiredBandwidthBps`；
-   QoS 目标：最大时延、最大抖动、最大丢包率、可靠性要求；
-   业务开始时间、持续时间、流量模型（恒定/突发/周期，若后端支持）。

业务 QoS
默认值应来自后端配置或赛题/实验参数，不应把示例门槛写死为不可修改的前端常量。若暂无正式门槛，显示"示例配置"，并允许用户编辑。

### 动态事件配置

支持事件类型：
- 节点上线/下线；
- 链路 UP/DOWN；
- 链路参数变化（带宽、时延、抖动、误码率、丢包率）；
- 业务新增/结束/参数变化；
- 干扰增强/减弱（仅在仿真器实现后启用）；
- 复合事件。

每个事件至少包含：
- `eventId`、`eventType`；
- `triggerMode`：按仿真时间/按条件触发；
- `triggerAtMs`；
- `targetId`；
- `payload`；
- `durationMs`（可选）；
- `repeat` / `randomConfig`（可选，需后端支持）；
- `enabled`。

### 场景校验

前端做基础校验：
- ID 唯一；
- 链路两端节点存在；
- 业务源/目的节点存在；
- 参数为合法数值且不越界；
- 事件目标存在；
- 时间和持续时间合法。

后端做最终校验：
- 拓扑连通性和可达性；
- 资源容量与业务需求冲突；
- 事件之间是否存在非法冲突；
- 仿真器是否支持指定参数和事件类型。

### 场景接口

见《前后端数据模型与接口规范_v1.0》§7.6（场景 CRUD、校验、克隆、乐观锁与归档约定）。场景模板列表接口如需要，待后端补充进规范。

## 4.4 仿真控制台

### 页面目标

控制仿真生命周期，并将仿真时间、事件注入、网络变化和 Agent
活动放在同一时间轴下观察。

### 控制区

-   开始；
-   暂停；
-   恢复；
-   停止；
-   单步推进；
-   仿真速度（例如 0.5x、1x、2x、5x，具体以仿真器支持为准）；
-   当前仿真时间；
-   运行状态；
-   事件注入快捷入口。

### 时间轴

时间轴按时间展示：
- 场景预设事件；
- 实际触发事件；
- 节点/链路状态变化；
- Agent 任务开始/结束；
- 策略生成、仲裁、下发和执行；
- QoS 告警。

点击时间轴事件，可定位到对应节点、链路、业务或 Agent 任务。

### 事件注入

支持运行时注入的事件必须由后端声明能力。前端先调用
`GET /simulations/capabilities`（见规范 §7.7）
获取支持的事件类型和字段范围，再动态生成表单。若暂未实现
capabilities，可先采用固定 Mock
配置，但要集中管理，不要散落在页面组件中。

### 仿真接口

见《前后端数据模型与接口规范_v1.0》§7.7（创建运行、生命周期控制、状态机、单步/调速、运行时事件注入）与 §8 实时事件。所有控制接口应返回最新 `SimulationRun`；前端不能仅凭按钮点击就假定操作成功，必须等待后端响应，并处理 `INVALID_SIMULATION_TRANSITION`、`FEATURE_NOT_SUPPORTED` 等错误。

## 4.5 Agent 监控页

### 页面目标

展示多智能体协同的可观测过程，而不是把 Agent 简化成几个在线状态灯。

### Agent 类型

-   运维
    Agent：态势采集、拓扑感知、链路质量评估、异常检测、故障诊断、自愈建议。
-   资源控制 Agent：资源调度、路由动态调整、带宽分配、业务 QoS 保障。
-   Coordinator：任务分派、策略校验、冲突仲裁、统一下发（若系统采用该角色）。

### 页面区域

1.  Agent 卡片：状态、当前任务、最近心跳、处理耗时。
2.  任务列表：taskId、taskType、状态、开始/结束时间。
3.  A2A 消息流：发送方、接收方、messageType、时间、关联 taskId。
4.  工具调用列表：工具名、输入摘要、输出摘要、执行耗时、成功/失败。
5.  决策链路时间线：感知→诊断→候选策略→仲裁→下发→执行反馈。
6.  策略详情：路由调整、带宽分配、优先级变化、受影响业务、策略理由。

### 可追踪性要求

每个 Agent 任务、A2A 消息、工具调用和策略记录都应携带 `taskId` 或
`traceId`。前端通过 traceId 聚合事件，才能完整复盘一次链路故障恢复过程。

### Agent 接口

见《前后端数据模型与接口规范_v1.0》§7.10（Agent 状态/任务、A2A 消息、工具调用、策略查询/校验/应用）与 §8.3 实时事件。

## 4.6 资源与 QoS 页

### 页面目标

解释"网络资源如何分配"以及"业务是否得到保障"。

### 链路资源视图

-   链路当前带宽、已分配带宽、剩余带宽；
-   时延、抖动、丢包率、误码率趋势；
-   链路利用率；
-   控制链路与数据链路分类筛选。

### 业务 QoS 视图

按业务流展示：
- 业务类型、源/目的节点、优先级；
- QoS 目标；
- 当前测量值；
- 达标状态；
- 当前路径；
- 是否发生降级、限流或抢占。

业务类型的关注重点：
- 话音：时延、抖动；
- 视频：带宽、连续性；
- 图片：带宽与可靠性；
- 数据：丢包率、可靠性。

具体 QoS
阈值由场景或后端策略提供，前端只负责展示和校验，不应擅自定义竞赛统一标准。

### 资源分配视图

-   各链路带宽分配堆叠图；
-   各业务优先级队列；
-   带宽抢占/释放记录；
-   策略执行前后对比；
-   资源不足导致的未满足需求列表。

### 接口

见《前后端数据模型与接口规范_v1.0》§7.9（链路/业务指标、资源分配与历史、QoS 汇总与单业务详情）。

## 4.7 实验分析页

### 页面目标

对仿真结果进行量化评估，支撑算法调试、方案论证和竞赛展示。

### 核心指标

优先覆盖赛题明确关注的：
- 状态感知时间；
- 策略生成时间；
- 策略下发时间；
- 网络连通度；
- 业务保障能力。

建议扩展：
- QoS 达标率；
- 故障恢复时间；
- 路由收敛时间；
- 带宽利用率；
- 关键业务中断时长；
- Agent 任务成功率；

-   基线算法与多智能体算法对比；

## 5. 前端数据模型

前端类型定义（`NodeType`、`LinkPlane`、`LinkStatus`、`NetworkNode`、`NetworkLink`、`BusinessFlow`、`Scenario`、`ScenarioEvent`、`SimulationRun`、`TopologySnapshot`、`AgentInstance`、`AgentTask`、`AgentMessage`、`Policy`、`MetricPoint` 等）**统一以《前后端数据模型与接口规范_v1.0》第 4–5 章为准**，前端通过共享 `types/` 或 OpenAPI 生成，本设计文档不重复定义。

## 6. API 与实时事件（引用规范）

统一前缀 `/api/v1`，REST 负责查询和控制，WebSocket 负责实时事件。**接口总表、请求/响应结构、错误码、分页、WebSocket 事件信封与断线恢复，统一以《前后端数据模型与接口规范_v1.0》第 7–8 章为准**，本设计文档不重复列出。

要点回顾：

- 统一成功/错误响应包裹在 `data`，错误用 `code` + HTTP 状态码表达（规范 §7.2–7.3）。
- 拓扑快照统一为 `GET /simulations/{runId}/topology`（规范 §7.8）。
- WebSocket 信封含 `seq`/`version`，按 `lastSeq` 断线补发或重同步快照（规范 §8.4）。
- 前端 API 层统一解包 `data`、统一处理超时/鉴权失效/状态冲突；业务组件不直接拼接 URL 或解析原始响应。

## 7. 后端接口尚未具备时的 Mock 方案

### 7.1 总体策略

采用"接口契约先行 + Mock Server + 可切换数据源"的方式。页面始终调用统一
API 模块，不允许组件直接读取硬编码 JSON。后端就绪后只需切换 API Base URL
或关闭 Mock，不应重写页面。

推荐：
- `MSW (Mock Service Worker)`：拦截浏览器中的 REST 请求；
- 本地 JSON/TypeScript 工厂函数：生成初始场景和拓扑；
- WebSocket Mock Provider：模拟实时事件流；
- `VITE_USE_MOCK=true/false`：环境变量控制；
- `src/mocks/fixtures`：静态样例；
- `src/mocks/scenarios`：场景生成器；
- `src/mocks/handlers`：REST Mock handlers；
- `src/mocks/ws`：实时事件模拟器。

### 7.2 Mock 分层

  --------------------------------------------------------------------------------------------
  层级                    Mock 内容                             目的
  ----------------------- ------------------------------------- ------------------------------
  静态 Fixture            节点、链路、业务、Agent、策略样例     页面布局和组件开发

  API Mock                REST 查询/控制接口                    联调前保持真实调用方式

  行为 Mock               开始/暂停/单步/停止状态机             让控制台交互可用

  事件 Mock               节点下线、链路断开、指标变化、Agent   演示动态场景
                          消息                                  

  算法结果 Mock           路由切换、带宽调整、QoS 变化          演示策略闭环，不冒充真实算法
  --------------------------------------------------------------------------------------------

### 7.3 必须模拟的动态闭环

建议实现至少三个可演示场景：

**场景 A：链路中断与路由恢复** 1. 初始拓扑中 U1---R1---B1---C
存在可用路径； 2. 仿真运行到指定时间，R1---B1 链路 DOWN； 3.
拓扑页面将链路标记为 DOWN； 4. 运维 Agent 收到拓扑变化并产生故障诊断；
5. 资源 Agent 生成替代路径； 6. Coordinator 校验并下发策略； 7.
仿真器/Mock 更新业务路径； 8. 业务 QoS 恢复，实验事件时间线记录全过程。

**场景 B：链路质量退化与 QoS 保障** 1. 数据链路带宽下降或丢包率上升； 2.
视频或图片业务出现 QoS 告警； 3. 运维 Agent 输出链路质量异常； 4. 资源
Agent 调整路径或资源分配； 5.
页面展示调整前后链路指标、带宽和业务达标率。

**场景 C：新增高优先级业务与资源抢占** 1. 新增话音业务； 2.
当前链路剩余资源不足； 3. 资源控制 Agent 生成资源重分配/抢占策略； 4.
Coordinator 仲裁后下发； 5. 页面显示各业务分配带宽变化及优先级影响。

### 7.4 Mock 数据生成规则

-   使用固定随机种子，保证同一场景重复运行可复现。
-   事件按 `simTimeMs` 排序；同一时刻事件使用稳定顺序。
-   事件字段与正式 WebSocket 协议完全一致。
-   REST Mock 与 WebSocket Mock
    共享同一份内存态，避免页面查询状态和实时事件相互矛盾。
-   不使用纯随机数直接生成每次变化，否则截图、演示和回归测试不稳定。
-   在 UI 明确标注"Mock 数据 /
    模拟策略结果"，避免将演示数据误认为真实仿真结果。

### 7.5 Mock 与真实后端切换

``` ts
// src/config/env.ts
export const useMock = import.meta.env.VITE_USE_MOCK === "true";
export const apiBaseUrl = import.meta.env.VITE_API_BASE_URL ?? "/api/v1";
```

开发环境：

``` env
VITE_USE_MOCK=true
VITE_API_BASE_URL=/api/v1
```

联调/部署环境：

``` env
VITE_USE_MOCK=false
VITE_API_BASE_URL=http://127.0.0.1:8000/api/v1
```

生产构建建议默认关闭 Mock；如需演示包，可单独构建 `demo`
环境，并在界面显著标识演示模式。

### 7.6 Mock 能力边界

Mock 可以验证：
- 页面布局、表单交互、状态管理；
- REST 请求结构与响应解析；
- WebSocket 事件处理、重连和快照恢复；
- 动态拓扑渲染；
- 事件时间线和 Agent 流程展示；
- 实验结果图表。

Mock 不能证明：
- 路由算法正确；
- 带宽优化结果最优；
- Agent 真正完成推理；
- 仿真指标符合真实网络；
- 复赛测试集可通过。

这些必须通过真实仿真器、算法和 Agent 服务验证。

## 9. 关键交互与异常处理

### 9.1 仿真控制按钮状态

  仿真状态    可用操作
  ----------- ----------------------------
  CREATED     开始、删除（若后端支持）
  RUNNING     暂停、停止、注入事件
  PAUSED      恢复、单步、停止、注入事件
  STOPPED     查看结果、重新创建运行
  COMPLETED   查看结果、复制实验
  FAILED      查看错误、重新运行

按钮可用状态必须来自后端 `SimulationStatus`，不能只由前端本地状态推断。

### 9.2 错误处理

-   网络超时：提示重试，保留用户输入。
-   WebSocket 断开：显示连接异常，自动重连；重连后重新同步快照。
-   场景校验失败：按字段定位错误，并展示后端校验消息。
-   仿真控制冲突：刷新仿真状态，不重复盲目发送控制请求。
-   Agent 执行失败：展示失败阶段、错误摘要和 traceId。
-   图表无数据：显示空状态，不渲染虚构曲线。
-   指标延迟：显示数据更新时间和延迟提示。

### 9.3 权限和危险操作

停止仿真、删除场景、覆盖场景等操作应二次确认。若系统需要多人协作，应在后端实现权限校验，前端仅负责展示权限和控制按钮，不作为安全边界。

## 10. 性能、可靠性与可访问性

-   拓扑图采用增量更新，避免每条事件都销毁重建整张图。
-   大规模节点/链路场景启用图渲染性能优化、视口裁剪或聚合显示。
-   高频指标采用采样、聚合和节流；历史数据分页查询。
-   Agent 消息和事件时间线采用虚拟列表，避免 DOM 数量持续增长。
-   图表只展示当前时间窗口，历史区间按需加载。
-   WebSocket 心跳、断线重连、退避策略和快照补偿必须实现。
-   关键操作提供键盘可达性、明确标签和状态文本。
-   状态颜色同时配合文字/图标，兼顾色觉差异。
-   长时间运行的实验需支持页面刷新后按 runId 恢复状态。

## 12. 前后端联调优先级与接口交付清单

建议后端按以下顺序提供接口，避免前端等待全部服务完成：

**第一批（前端主链路）** 1. 场景列表/详情/保存/校验； 2.

5. WebSocket 基础事件协议。

**第二批（动态展示）** 1. 节点/链路状态变化； 2. 链路质量指标； 3.
业务流状态和路径变化； 4. 事件历史查询。

**第三批（多智能体可观测）** 1. Agent 状态； 2. Agent task； 3. A2A
消息； 4. 工具调用； 5. 策略生成、校验、应用反馈。

**第四批（实验评估）** 1. QoS 指标； 2. 资源分配快照和历史； 3.
实验记录； 4. 实验指标与对比； 5. 数据集和算法版本。

每个接口交付时应同时提供：
- 请求/响应 JSON Schema 或 TypeScript 类型；
- 字段含义、单位、枚举值；
- 错误码；
- 示例数据；
- 是否支持分页、排序和筛选；
- 是否支持 WebSocket 实时推送；
- 数据更新频率和保留周期。

## 13. 风险与待确认事项

以下内容需要与仿真器和 Agent
后端团队确认，当前不能仅凭前端设计假定已经具备：

1.  节点是否提供真实坐标、移动轨迹和速度；若没有，拓扑布局由前端自动布局。
2.  控制链路与数据链路是否有独立
    ID、方向、参数和状态；建议后端明确建模。
3.  链路参数单位及丢包率/误码率取值范围。
4.  业务 QoS 阈值、业务流量模型和优先级定义。
5.  仿真器是否支持单步、变速、暂停后事件注入。
6.  是否支持运行时新增业务、修改链路参数和节点上下线。
7.  Agent 是否输出结构化 task、message、tool-call 和 policy 事件。
8.  是否有统一 traceId、taskId、policyId。
9.  策略是否需要人工审批，还是自动仲裁后直接下发。
10. 实验指标由谁计算，统计窗口和公式如何定义。
11. 测试集是否通过文件上传、数据集 ID 或后端预置方式接入。
12. 是否需要用户登录、权限和多用户并发实验。

在这些事项确认前，前端应采用可选字段和能力发现接口，不应把尚未实现的能力伪装成正式功能。

## 14. 第一版 MVP 建议

如果时间紧，第一版不要追求所有页面齐全。优先做出一条可演示、可联调、可复现的闭环：

1.  **场景配置**：节点、控制/数据链路、业务流、三类动态事件；
2.  **拓扑展示**：动态节点/链路状态、链路详情、业务路径；
3.  **仿真控制**：开始、暂停、恢复、停止、单步；
4.  **Agent 过程**：运维 Agent、资源控制 Agent、Coordinator
    的任务和策略时间线；
5.  **结果分析**：状态感知时间、策略生成时间、策略下发时间、网络连通度、业务
    QoS 达标率。

推荐先用 MSW + 固定随机种子的事件模拟器完成端到端 Mock，再逐项替换为真实
API。这样既能尽早形成竞赛演示系统，也能避免 Mock
与正式接口结构不一致造成返工。

## 附录 C：设计结论

本项目的前端技术路线建议采用 **React + TypeScript + Vite + Ant Design +
AntV G6 + ECharts + Zustand + Axios + WebSocket + MSW**。

核心不是做一个普通后台，而是构建一套动态通信网络仿真可视化与多智能体协同观测平台。开发顺序应围绕"场景配置---仿真控制---拓扑变化---Agent
决策---资源调度---QoS
结果---实验评估"展开。接口尚未实现时，使用与正式协议一致的 Mock
数据和事件流；后端就绪后逐步切换，确保前端结构无需推倒重来。
