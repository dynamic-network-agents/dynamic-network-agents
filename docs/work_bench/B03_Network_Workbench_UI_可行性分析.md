## 0. 效力边界（2026-11-24 确认）

**设计说明与设计稿只约束视觉与展示风格**——布局、栅格、配色、图表形态、交互方式、空态样式。**业务语义、数据相关性、指标建模一律以既有文档为准**，设计稿不构成新增数据模型的依据：

| 权威来源 | 约束内容 |
|---|---|
| `work_bench/CLAUDE.md` | 三条硬约束、数据口径、核心数据模型（Service → Flow → Path） |
| `B03_DebugConsole_P0-P3任务分析.md` | 范围决策（明确不做）、已核实事实、运行期基线 |
| `B03_DebugConsole_task_split.md` | Epic / 里程碑划分 |
| `docs/agents/智能体设计文档.md` §7 | 两套 QoS 公式与容差 |

由此产生三条落地规则：

1. **设计稿出现的新对象，只有能被既有口径解释才实现**（如"风险链路"按 §8.1 落，不新建链路模型）；
2. **设计稿没有、但口径要求的必须补**（Flow 标识、静态/实测分离、"估算"标记、计划/实际事件分轨、未知不显示为 0），不因图上没画就省；
3. **设计稿的导航不得扩大既有范围**（历史回放 / What-if / 3D / 计划-实际对照属"明确不做"），未实现入口置灰，不做空页面。

## 1. 材料清点与验证边界

- 目录下只有**一份图片 + 一份说明**，设计稿为单屏（全局总览），未包含抽屉、二级页、空态/异常态的设计。

## 3. 视觉稿与既有口径的冲突（按口径改，不按图改）

### 3.1 "整体状态 正常"与同屏证据矛盾

同一屏里"风险链路 3 条"+"SVC0007 不达标"，却判"整体状态 正常"。说明 §3.1（[:58](docs/work_bench/B03_Network_Workbench_UI_设计说明.md#L58)）要求"指标必须有明确统计口径"，但没给聚合规则。

按 §0，"整体状态"是设计稿自造的对象、没有既有口径可依。两种处置，须择一（见 §8.2）：

- **实现**：按 §8.2 三档规则算，那一屏应显示"告警"；
- **不实现**：这一格改显示既有事实（数据健康 live/partial/stale），不引入新指标。

### 3.2 "L001 带宽阻塞 利用率 115%"是需求侧估算，不是实测拥塞

`demandBps` 是经过该链路的各业务 `requirement.bandwidthBps` 之和（[load.py:5-8](work_bench/backend/analysis/load.py#L5-L8)），`measuredBps` 只是业务级收包速率汇总、明确"仅作估计"（[:68](work_bench/backend/analysis/load.py#L68)）。所以：

- 115% 的正确表述是"**需求超订**"（需求 ≥ 容量），不是"实测带宽阻塞"；
- 说明 §5.2（[:138-146](docs/work_bench/B03_Network_Workbench_UI_设计说明.md#L138-L146)）自己要求标"估算"，设计稿上没有任何估算标记；
- 真实基线里 Top 需求/容量已达 2.57（[P0-P3:184](docs/work_bench/B03_DebugConsole_P0-P3任务分析.md#L184)），进度条/百分比必须能表达 >200% 与"容量为 0/缺失"。

### 3.3 地理底图与"闪烁点"装饰不可用

- 坐标是**平面米制**，不是经纬度：场景 `area` 为 120000×120000（[net-topo.json](simulator/data/scenarios/sce20261012-conf01/sce10/net-topo.json)），节点坐标量级 1e4 米。设计稿上的地图底影无对应真实地理信息，属装饰。
- 场景规模差异极大：`conf02/sce01` = 20 节点 / 30 链路，`conf01/sce01` = 50 / 100，`conf01/sce10` = 300 / 500。设计稿按 34 节点 / 92 链路出图，500 链路时需要 LOD/抽稀/按风险过滤，否则线会糊成一团。
- UAV 实时坐标来源仍待核对：`node_move` 脚本当前失效（[CLAUDE.md:77](CLAUDE.md#L77)），"节点位置优先用真实坐标"在移动场景下退化为静态初值。

### 3.4 关键业务表没有 Flow 标识

`work_bench/CLAUDE.md` 硬要求"界面须明确区分「业务 Service」与「路径控制对象 Flow」"（[:30](work_bench/CLAUDE.md#L30)）。设计稿主表只有 `路径 P00031`，读者无法看出这条业务与谁共享路径、改它会影响谁。建议：主表加 `Flow` 列（`flowKey` 短码或成员数徽标），或在"路径"列 hover 显示"与本表 N 条业务共享"。

### 3.5 顶栏缺数据健康状态

说明 §2.2（[:40](docs/work_bench/B03_Network_Workbench_UI_设计说明.md#L40)）要求顶栏展示"数据健康状态（正常/延迟/部分接口失败）"，设计稿顶栏只有状态/实例/仿真时间/更新时间，健康只在左下角一行"数据正常"。二者不一致，需择一。

### 3.6 "测试业务 40/47"的分母口径不可信

`svc-meta` 对缺 `category` 的业务默认返回 `'test'`（[openapi.py:2141](sim_src/netsim/openapi.py#L2141)）。这意味着"测试业务数"可能把未分类业务算成测试业务，而"未知"永远显示为 0。说明 §3.1 要求"不确定分类单独标注未知，不可强行归类"，与仿真器默认值冲突。**处置：分母改为"取到 category 的业务数"，并对 `categorySource != simulator` 的业务单独计"未知"。**

## 6. 布局与分辨率决策（已确认）

工作台部署在服务器、由远程浏览器访问，**客户端分辨率不固定**。2026-11-24 确认按以下方案执行：

- 主设计基准取 **1920×1080**（设计稿实际 1672×941 更接近这个档位），向下兼容 **1440×900**，向上自适应铺满；
- 窗口宽度 <1600px 时，第二行（关键业务 / 链路负载 / 事件）折叠为 Tabs（一次一表，可切换）；≥1600px 时平铺三列；
- 说明 §12 验收 #1"首屏 5 秒内看清仿真状态、风险链路和受影响业务"在 1440×900 下靠 Tabs 仍可满足（风险链路在拓扑 + 热点 Top3，受影响业务在 Tabs 首屏）。

### 期 1：全局总览（对齐设计稿首屏）

### 期 2：Flow 分析页 + 诊断增强

## 8. 风险链路 / 整体状态 判定规则

这两个卡片都没有接口，只能自算。**链路风险规则 A 与整体状态规则 B 均已确认（2026-11-24），按 v0 实现，后续开发中再补。**

### 8.1 链路风险规则 A（已确认，v0）

**计入"风险链路"计数的三类**：

| 代号 | 条件 | 数据依据 | 缺失时 |
|---|---|---|---|
| R1 断 | `link.status == "down"` | `/links` | — |
| R2 超订 | `demandBps / capacityBps > 1.0`，且 `capacityBps > 0` | `load.py` 的 `demandUtilization` | 容量缺失/为 0 → 不判，标"未知" |
| R3 劣化 | 相对上一次成功观测，`delayMs` 涨幅 ≥50%，或 `packetLossRate` 绝对涨幅 ≥0.01 | 上一条成功快照的同 `linkId` 参数 | 无前值（冷启动/实例切换）→ 不判 |

口径约束：

- **R2 必须标"估算"**：`demandBps` 是各业务 `requirement.bandwidthBps` 之和（[load.py:5-8](work_bench/backend/analysis/load.py#L5-L8)），不是实测吞吐；文案写"需求超订"，不写"带宽阻塞"。
- **R3 的前值取"上一次成功快照"**，不必解析 `link_state_changed`：直接复用 `Collector._prev["links"]`（[snapshot.py:146-148](work_bench/backend/snapshot.py#L146-L148)）；实例切换时清空基线，避免跨实例误判。
- **去重**：一条链路同时命中多条只计 1 条，展示列出全部原因；展示严重度排序 `R1 > R3 > R2`。
- **不计入计数**：R4 承压（有 `qosMeet=false` 的业务经过该链路、且该链路是其静态 QoS 瓶颈项）只进热点排序，避免与"业务不达标"重复计数。
- **数据不可信时给"未知"**：链路采集失败或 `health != live` 时，KPI 显示"未知"，不显示 0。
- **阈值可调**：50% / 0.01 先写常量并注明"初值，待运行期调"。

### 8.2 整体状态规则 B（已确认，v0）

按下表计算（"未知"优先，保证数据不可信时不给结论）：

| 状态 | 条件 |
|---|---|
| 未知 | `health != live` |
| 异常 | 存在 R1 链路，或 `qosMeet = false` 的业务占比 > 30% |
| 告警 | 存在 R1/R2/R3 任一风险链路，或存在 `qosMeet = false` 的业务 |
| 正常 | 以上都不满足 |

口径约束：

- **状态必须带理由**：卡片同时给出触发原因（如"3 条风险链路""18/40 业务不达标"），不只给一个色块；
- **`health != live` 时一律"未知"**，不得用缓存数据算状态；
- 30% 阈值先写常量并注明"初值，待运行期调"；
- 按此规则，设计稿那一屏应为"告警"（3 条风险链路 + 1 条不达标业务），与图上"正常"不一致——以规则为准。
