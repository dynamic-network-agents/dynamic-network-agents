# B03 仿真环境调试控制台：评审与优化建议

> 文档类型：企划书评审 / V1.1 优化建议\
> 项目代号：B03-WorkBench\
> 整理日期：2026-11-18\
> 定位：面向 B03 资源管控智能体的独立、只读网络观测与诊断工作台

------------------------------------------------------------------------

## 1. 总体结论

原企划书的方向是正确的，而且对 B03
智能体研发有实际帮助。它解决的不是一般意义上的"把仿真器界面重新做一遍"，而是仿真器自带前端难以直接回答的几个关键问题：

-   当前网络拓扑、节点、链路和业务究竟是什么状态？
-   多条业务如何共享同一条 flow 路径？
-   哪些链路是真正的流量瓶颈，瓶颈上承载了哪些业务？
-   业务 QoS
    不达标，是路径本身不满足静态约束，还是路径可行但运行时发生拥塞？
-   仿真脚本计划发生的扰动，是否真的在运行时发生了？

**核心判断：技术栈和独立只读架构基本合理，但当前 V1.0
更像一个网络态势展示
Dashboard，还没有完全成为面向算法调试的诊断工作台。**

建议不推翻原方案，而是在 V1.1 中重点补齐：

1.  数据模型和时间一致性；
2.  flow 级路径与业务映射；
3.  热点链路和热点节点的计算口径；
4.  静态 QoS 与实测 QoS 的分层诊断；
5.  事件计划与实际事件的对照；
6.  面向"迁移一条 flow 会影响什么"的分析能力；
7.  只读安全边界和数据健康状态。

第一版不建议追求
3D、复杂动画或大而全的页面数量。优先保证数据正确、分析可信、问题可定位。

## 2. 原企划书合理的部分：建议保留

### 2.1 独立进程、前后端分离

React + Vite + TypeScript 前端，FastAPI 后端，通过 WebSocket
向前端推送聚合后的数据，这个结构适合当前任务。

建议继续坚持：

-   前端不直接访问仿真器 API；
-   后端是唯一的仿真器 API 客户端；
-   前后端独立启动、独立调试；
-   调试控制台与 Agent 主程序解耦；
-   仿真器发布件只读，不修改仿真器代码和场景文件。

这样既能避免调试界面影响 Agent 的运行，也能让控制台在 Agent
尚未完成时独立开发。

### 2.2 离线数据与实时 API 双数据源

离线场景文件适合提供基线信息，例如：

-   `net-topo.json`：初始拓扑和链路参数；
-   `bg-service.json`：业务分类、需求、优先级等场景配置；
-   `scripts/script-NN.json`：计划注入的扰动事件；
-   `service-paths.json`：生成器预置候选路径和相关快照。

实时 API 则提供仿真运行时的节点、链路、业务、路径和事件状态。

两类数据的职责应明确区分：

  ----------------------------------------------------------------------------------------
  数据类型                主要用途                                 是否代表当前运行状态
  ----------------------- ---------------------------------------- -----------------------
  离线场景数据            初始配置、业务分类、计划事件、候选路径   否

  实时 API 数据           当前节点、链路、业务、路径和实测 QoS     是

  控制台分析结果          flow 聚合、瓶颈识别、路径影响分析        由前两者计算得出
  ----------------------------------------------------------------------------------------

### 2.3 先做 2D 拓扑，3D 后置

2D
拓扑足以支撑第一阶段的大部分调试任务。尤其应优先使用场景中的真实节点坐标，而不是一开始完全依赖力导向布局。

建议：

-   默认使用场景坐标展示；
-   支持缩放、平移、节点定位和局部展开；
-   力导向布局作为可选视图，而非唯一布局；
-   3D 作为后续展示增强，不作为 MVP 的验收条件。

### 2.4 业务、路径、热点视图值得保留

业务表、路径高亮、链路参数对照、QoS
仪表盘和事件时间轴都具有实际价值。需要调整的是它们之间的数据关联和诊断逻辑，而不是简单增加更多独立页面。

## 3. 必须修正的关键问题

### 3.1 flow 是路径控制和分析的核心对象

这是整个调试控制台最重要的数据建模前提。

仿真环境中的路径不是简单的"每条业务各自一条路径"。同一对 UAV
源/目的端之间的多条业务会共享 flow 级路径。路径设置接口虽然以
`serviceId` 作为请求入口，但底层按源/目的 IP 识别 flow。

因此：

-   多条业务可能映射到同一个 flow；
-   同一 flow 内的业务共享路径；
-   修改其中一条业务的路径，可能改变同一 flow 内其他业务的路径；
-   不能把业务列表中的每一条记录都当作独立路径控制对象；
-   flow 的路径是否可行，应综合考虑该 flow 内所有相关业务的 QoS 需求。

**建议的数据关系：**

``` text
Service
  ├── serviceId
  ├── serviceType
  ├── category
  ├── priority
  ├── requirement
  ├── actual
  └── flowKey
          │
          ▼
Flow
  ├── flowKey = srcIP + dstIP（按实际实现规范化）
  ├── srcNodeId
  ├── dstNodeId
  ├── memberServiceIds[]
  ├── pathId
  └── pathSegments[]
          │
          ▼
Path
  ├── nodes[]
  ├── links[]
  ├── staticQoS
  └── measuredQoS（由成员业务汇总或关联展示）
```

建议在界面中明确区分"业务 Service"和"路径控制对象
Flow"。业务详情应能跳转到所属 Flow，Flow 详情则展示全部成员业务。

### 3.2 不要仅凭 serviceId 前缀判断 test/background

原企划书提出从离线文件读取 `category`，实时侧再用 `TSV` / `BGV`
前缀推断。这个方案可以作为辅助映射，但不应把前缀推断当作唯一事实来源。

建议采用以下优先级：

1.  以离线 `bg-service.json` 中的 serviceId 映射 `category`；
2.  实时 API 返回的 serviceId 与离线映射匹配时，继承离线分类；
3.  未匹配的实时业务标记为 `unknown`；
4.  只有在验证过命名规则稳定后，才允许用 serviceId 前缀作为 fallback；
5.  UI 中明确显示分类来源，例如 `offline_mapping` / `prefix_inferred` /
    `unknown`。

这样可以避免新场景、服务 ID 规则变化或运行时业务增删导致错误分类。

### 3.3 静态 QoS 与实测 QoS 必须分开展示

不能把"路径静态校验通过"理解为"业务运行时一定达标"。

静态路径 QoS 是路径参数的合成检查，主要口径为：

-   时延：路径各链路时延求和；
-   抖动：路径各链路抖动平方和开方；
-   带宽：路径瓶颈链路带宽，即各链路带宽最小值；
-   丢包率：按各链路丢包率组合计算；
-   误码率：按链路误码率近似累加，并考虑实现中的容差。

实测 QoS 则来自业务运行时最近一秒的统计值，包含：

-   `avgDelayMs`
-   `jitterMs`
-   `effBwBps`
-   `errPct`
-   `packetLossRate`
-   `qosMeet`

建议将两套指标明确分成两个区域：

  维度       静态路径 QoS                   实测业务 QoS
  ---------- ------------------------------ --------------------------
  数据来源   当前路径上的链路参数           业务运行时统计
  主要回答   这条路径从参数上是否满足需求   业务实际运行是否满足需求
  典型用途   路径候选过滤、路径可行性分析   运行效果诊断、拥塞识别
  结果解释   静态可行 / 静态不可行          实测达标 / 实测不达标

**重要字段口径：** `actual.errPct` 是百分数（0～100），而
`requirement.ber` 是无量纲误码率。不能把二者直接比较。界面应以 API
给出的 `actual.qosMeet`
作为实测综合达标状态，并在逐项诊断时显式处理单位和指标定义差异。

### 3.4 热点链路不能只看"经过多少条 flow"

原企划书中的"每链路占用 flow 数、需求带宽和 vs
容量、超载比例"方向正确，但需要进一步明确计算口径。

**flow 数量不等于链路负载。** 一条链路上经过 10 条低速 flow，与经过 2
条高带宽 flow，负载情况可能完全不同。

建议分别统计：

  -----------------------------------------------------------------------------------------------------
  指标                     建议定义                                             用途
  ------------------------ ---------------------------------------------------- -----------------------
  `flow_count`             经过该链路的不同 flow 数                             竞争者数量

  `service_count`          经过该链路的业务数                                   业务规模

  `demand_bps`             经过该链路的业务需求带宽之和                         需求侧负载估计

  `measured_bps`           经过该链路的业务实测有效带宽汇总（若数据口径允许）   实测负载近似

  `capacity_bps`           当前链路带宽容量                                     链路供给能力

  `demand_utilization`     `demand_bps / capacity_bps`                          需求容量比

  `measured_utilization`   `measured_bps / capacity_bps`                        实测利用率近似
  -----------------------------------------------------------------------------------------------------

其中：

``` text
demand_bps(link)
  = Σ requirement.bandwidthBps(service)
    对所有路径经过该 link 的业务求和

demand_utilization(link)
  = demand_bps(link) / capacity_bps(link)
```

需要注意：业务的 `actual.effBwBps`
是业务级实测统计，不一定等同于链路层的真实吞吐量。因此 `measured_bps`
只能在确认统计口径适合聚合后使用；否则应标注为"业务实测带宽汇总估计"，不要直接称为链路实际利用率。

热点判断建议分成三个层次：

1.  **结构热点**：节点度数、介数中心性等拓扑结构指标；
2.  **流量热点**：经过的 flow 数、业务数、需求带宽；
3.  **性能热点**：链路参数劣化、业务 QoS 不达标、拥塞相关证据。

不要把结构中心性直接等同于拥塞。一个中心性很高的节点可能当前没有明显负载；一个中心性不高的链路也可能因为承载少数高带宽业务而成为瓶颈。

第一版可以先展示各项原始指标，不急于合成为一个"热点分数"。如果后续确实需要综合风险分数，应把归一化方法、权重和阈值做成可解释配置。

### 3.5 共享 Flow 的可行性应按成员业务综合判断

如果一个 Flow
中有多条业务，不能只拿其中一条业务的需求来判断路径是否可行。

建议 Flow 详情中提供：

-   成员业务列表；
-   每条业务的五项 QoS 需求；
-   当前路径静态 QoS；
-   每条业务的实测 QoS；
-   哪些业务约束最严格；
-   哪一项指标导致候选路径不可行。

当多个业务共享路径时，路径选择必须满足该 Flow
中需要保障的业务约束。对带宽需求，至少要清楚区分"单业务需求"和"共享链路上的聚合需求"，不能把二者混成一个值。

## 4. 数据采集与后端架构优化

### 4.1 统一 Network Snapshot

建议后端不要让前端分别拼接节点、链路、业务、事件等多个接口的结果，而是生成统一快照：

``` json
{
  "instance_id": "当前仿真实例标识",
  "sim_time_us": 0,
  "received_at": "后端接收时间",
  "snapshot_version": 1,
  "data_health": "live",
  "nodes": [],
  "links": [],
  "services": [],
  "flows": [],
  "events_cursor": 0
}
```

字段仅为建议的数据结构示意，实际字段应与接口返回保持一致。

每次快照应尽可能保证来自同一仿真实例、相近的仿真时刻。若接口数据的
`tsUs` 差异过大，应标记为部分快照或数据不同步，而不是无提示地混合展示。

### 4.2 统一时间轴和实例标识

建议统一保留：

-   `instanceId`
-   `t0TsUs`
-   `tsUs`
-   `sinceTsUs`
-   `nextSinceTsUs`
-   `effectiveTsUs`（若存在路径生效回执）

仿真时间和本机接收时间应分开保存：

-   仿真时间：用于事件排序、脚本时间对齐和状态回放；
-   接收时间：用于判断 API 是否延迟、断连或数据过期。

不要仅用浏览器本地时间作为仿真事件时间。

### 4.3 轮询和接口调用控制

原企划书提出每 1～2
秒轮询节点、链路和业务，这是一个可以作为初始值测试的方案，但需要避免服务详情接口造成
N+1 请求。

建议：

-   `/nodes`、`/links`、`/services` 使用分页读取，并确认是否取全；
-   `/services` 先取列表，再按需获取详情；
-   业务详情请求采用并发上限；
-   详情缓存按 serviceId 和仿真时间更新；
-   只有用户打开某个业务/Flow 详情时，才提高该对象的刷新优先级；
-   `/events` 使用 `sinceTsUs` 游标增量读取，轮询间隔不得超过接口约定的
    10 秒；
-   遇到频控、超时或部分失败时采用退避和数据健康标记，而不是持续高频重试。

### 4.4 数据健康状态

控制台需要让开发者知道"屏幕上的数据是否可信"。

建议至少有以下状态：

  状态             含义
  ---------------- --------------------------------------
  `LIVE`           最近一次采集成功，数据处于新鲜窗口内
  `STALE`          仍有数据，但超过预期刷新周期
  `PARTIAL`        部分接口成功，当前快照不完整
  `DISCONNECTED`   与仿真器连接失败
  `OFFLINE`        当前使用离线场景数据，没有实时连接

界面同时展示：

-   最近一次成功采集时间；
-   当前仿真实例；
-   当前仿真时间；
-   最近一次事件游标；
-   WebSocket 连接状态；
-   最近一次完整快照时间。

## 5. 事件时间轴：从"脚本展示"升级为"计划与实际对照"

原企划书希望显示脚本事件时间轴，这个功能值得保留，但不能直接把脚本文件里的事件当成已经发生的事实。

建议把时间轴分成两条：

### 5.1 计划事件（Planned）

来自 `scripts/script-NN.json`，表示场景计划在某个相对 T0
时刻触发什么事件。

### 5.2 实际事件（Observed）

来自实时 `GET /events`，表示仿真器实际对外报告了什么变化。

### 5.3 对照逻辑

  计划事件   实际事件     UI 表现
  ---------- ------------ -------------------------
  有         有且匹配     已发生
  有         尚未观察到   待发生 / 未观测到
  有         有但不匹配   计划与实际不一致
  无         有           非计划事件 / 运行期事件

还应考虑脚本事件可能派生出多个实际事件，不能简单要求一对一匹配。可以使用事件类型、目标对象、`srcEventId`、时间窗口等字段辅助关联。

**已知注意事项：** 项目代码检查记录中，`node_move`
存在脚本属性结构与移动处理读取字段不一致，以及链路类型配置缺少
`losMeters` 等问题，可能导致移动事件未按预期生效。因此控制台应以实际 API
观测到的节点位置和事件为事实来源；脚本内容只表示计划，不应直接驱动"实际位置"动画。

## 6. 页面与交互结构建议

不建议把每种数据拆成彼此孤立的页面。调试工作通常从一个异常出发，需要连续追踪
Service、Flow、Path、Link 和竞争业务。

建议采用"全局总览 + 专项分析 + 统一详情面板"的结构。

### 6.1 全局网络总览

首屏回答"当前网络整体怎么样"：

-   2D 网络拓扑；
-   节点在线/离线状态；
-   链路 up/down 状态；
-   链路参数劣化标记；
-   当前运行业务数量；
-   test 业务实测达标率；
-   未达标业务数量；
-   热点链路 Top N；
-   数据健康状态和仿真时间。

### 6.2 Flow 分析页

这是建议重点投入的页面。

选择一个 Flow 后展示：

-   源 UAV、目的 UAV；
-   Flow 内所有成员业务；
-   当前路径和路径生效信息；
-   路径经过的节点、链路；
-   每条链路的五项参数；
-   每条链路上还有哪些其他 Flow；
-   成员业务各自的 QoS 需求和实测状态；
-   该 Flow 的候选路径和静态可行性。

### 6.3 链路详情页/侧边栏

点击链路后展示：

-   链路类型、两端节点、当前状态；
-   当前五项 QoS 参数；
-   离线基线参数与当前参数差异；
-   经过的 Flow 和业务；
-   需求带宽汇总、容量和需求容量比；
-   经过业务的实测 QoS 概览；
-   该链路是否是当前路径上的性能瓶颈候选。

### 6.4 业务详情页/侧边栏

展示：

-   serviceId、类型、分类、优先级、状态；
-   源/目的节点；
-   五项 QoS 需求；
-   五项实测值和 `qosMeet`；
-   所属 Flow；
-   当前共享路径；
-   未达标指标及可能相关的链路。

### 6.5 路径比较与 What-if 分析

建议增加本地分析能力，但第一版只做"模拟计算"，不向仿真器下发任何变更。

例如选择一条 Flow，尝试将其从当前路径迁移到候选路径，控制台本地计算：

-   原路径释放了哪些链路上的需求负载；
-   新路径增加了哪些链路上的需求负载；
-   哪些链路的需求容量比会升高或降低；
-   Flow 内成员业务的静态 QoS 是否满足；
-   其他共享链路 Flow 是否可能受到影响；
-   当前数据是否足以支撑该判断。

此功能能把"看见热点"进一步变成"理解迁移影响"，直接服务于 Agent
算法调试。

## 7. 技术选型与目录结构建议

### 7.1 技术栈结论

  -----------------------------------------------------------------------------------
  层                      原方案                   建议
  ----------------------- ------------------------ ----------------------------------
  前端                    React + Vite +           保留
                          TypeScript               

  后端                    Python + FastAPI +       保留

## 8. 只读与安全边界

这是调试控制台必须明确落实的工程约束，而不是只写在文档里的原则。

### 8.1 API 白名单

控制台后端只实现仿真器公开 API 的 GET 调用：

-   `GET /topology`
-   `GET /nodes`
-   `GET /nodes/{nodeId}`
-   `GET /links`
-   `GET /links/{linkId}`
-   `GET /services`
-   `GET /services/{serviceId}`
-   `GET /services/{serviceId}/path`
-   `GET /events`
-   `GET /time`

明确禁止控制台调用：

-   `POST /services/{serviceId}/path`
-   `POST /simulation/start`

### 8.2 凭据保护

-   Token 只由后端读取；
-   Token 不发送给前端；
-   Token 不进入 WebSocket 消息；
-   Token 不打印到日志；
-   默认仅绑定 localhost；
-   如需局域网访问，应增加控制台自身的访问认证。

### 8.3 离线文件只读

控制台只读取场景文件，不应修改 `simulator/`
发布件或生成数据。任何场景生成、仿真启动和 Agent
控制动作都应由各自独立流程负责。

## 9. 建议的实施优先级与验收标准

建议把原来的 P0～P5 调整为以下顺序：

  ---------------------------------------------------------------------------------------------------------------------
  阶段              目标                核心交付                           验收标准
  ----------------- ------------------- ---------------------------------- --------------------------------------------
  P0                工程与数据契约      前后端骨架、配置、统一模型、只读   可独立启动；只注册 GET；Token 不出现在前端
                                        API 客户端                         

  P1                数据采集与总览      离线加载、实时采集、统一快照、2D   节点/链路/业务数量与 API
                                        拓扑                               对得上；显示数据健康状态

  P2                Service/Flow/Path   业务映射、Flow 聚合、共享路径展示  能从业务定位 Flow，也能从 Flow
                    关系                                                   找到全部成员业务

  P3                QoS 与热点诊断      静态 QoS、实测 QoS、链路负载指标   两套 QoS

  P4                事件对照            计划事件与实际事件双时间轴         能识别已发生、未观测到、不匹配和非计划事件

### MVP 建议范围

如果需要尽快投入使用，MVP 只要求：

1.  能读取离线场景；
2.  能连接实时 API；
3.  能展示 2D 拓扑和链路参数；
4.  能展示业务与 Flow 的对应关系；
5.  能高亮 Flow 当前路径；
6.  能显示业务实测 QoS；
7.  能识别基础热点链路；
8.  能显示数据是否新鲜、是否断连。

事件回放、What-if、3D 都可以放到后续版本。

## 10. 建议补充的测试用例

为了避免控制台"看起来正常但数据实际错误"，建议为数据层和分析层建立固定测试场景。

### 10.1 Flow 分组测试

-   同一源/目的 UAV 的多条业务应归为同一个 Flow；
-   源/目的反向是否应视为同一个 Flow，必须与仿真器实际 `_flow_for`
    逻辑一致，不可仅凭"链路无向"自行假设；
-   不同源/目的组合应归为不同 Flow；
-   Flow 成员业务增删后，聚合结果应正确更新。

### 10.2 QoS 计算测试

-   单链路路径；
-   多链路路径；
-   带宽瓶颈链路变化；
-   丢包率组合；
-   抖动合成；
-   误码率单位转换与容差；
-   静态通过但实测不达标；
-   静态不通过的候选路径。

### 10.3 热点计算测试

-   多条低带宽 Flow；
-   少数高带宽 Flow；
-   多业务共享同一 Flow；
-   链路容量变化；
-   链路 down；
-   需求带宽超过容量；
-   结构中心性高但流量低；
-   结构中心性低但需求负载高。

### 10.4 数据一致性测试

-   API 分页；
-   单个业务详情请求失败；
-   事件游标续读；
-   仿真实例切换；
-   API 超时；
-   WebSocket 断连重连；
-   快照部分成功；
-   仿真时间戳不一致。

## 11. 最终建议

建议将项目定位从：

> 仿真环境调试控制台（workbench）

进一步明确为：

> **B03 Network Agent Workbench：面向网络资源管控智能体的只读观测、诊断与策略分析工作台。**

但这不意味着第一版要做成复杂的运维平台。它的首要职责仍然是帮助开发者快速回答：

1.  网络现在是什么状态？
2.  哪些业务没有达到 QoS？
3.  这些业务属于哪些 Flow，共享什么路径？
4.  哪些链路承载了过多需求或出现性能劣化？
5.  某条 Flow 如果迁移，可能缓解哪些链路、影响哪些业务？

**开发顺序上，建议始终坚持：数据正确性 \> 对象关系正确性 \> 诊断解释能力
\> 页面丰富度 \> 视觉效果。**

原 V1.0
的技术选型和总体方向可以保留，按本文调整数据模型、分析口径和实施顺序后，就可以进入工程拆分和
MVP 开发。
