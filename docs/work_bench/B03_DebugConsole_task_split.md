> 依据：`B03_调试控制台企划书评审与V1.1优化建议.md`\
> 目标：交付一个独立运行、只读、安全、数据口径可信的网络观测与诊断工作台\
> 文档版本：Task Split 1.0\
> 日期：2026-11-18

## 0. 项目目标与执行原则

### 0.1 交付目标

建设一个面向 B03 资源管控智能体研发的调试工作台，使开发者能够：

1.  查看当前仿真网络拓扑、节点、链路和业务状态；
2.  理解 Service、Flow、Path 之间的关系，识别共享路径；
3.  查看业务静态 QoS 与运行时实测 QoS，并定位不达标项；
4.  识别链路结构热点、流量热点和性能热点；
5.  对照仿真脚本中的计划事件与运行时实际事件；
6.  在本地分析候选路径迁移影响，不向仿真器写入任何状态。

### 0.2 必须遵守的原则

-   **只读：** 调试控制台只调用仿真器 GET
    API；不得调用路径变更、仿真启动等 POST 接口。
-   **独立：** 控制台可以在 Agent 主程序尚未完成时独立启动和测试。
-   **时间一致：** 节点、链路、业务和事件必须关联仿真实例与仿真时间。
-   **口径可解释：** flow
    数量、业务需求带宽、实测带宽、链路容量不能混为一个指标。
-   **事实与推断分离：** 实时 API
    是运行状态事实；离线文件是场景配置/计划信息；分析值必须标注为计算结果或估计值。
-   **先正确后好看：**
    优先完成数据正确性、对象关系、诊断逻辑，再优化动画和视觉效果。

### 0.3 建议优先级定义

  优先级   含义
  -------- ------------------------------------
  P0       阻塞项目启动或安全边界，必须先完成
  P1       MVP 核心功能，首个可用版本必须完成
  P2       增强诊断能力，MVP 后尽快完成
  P3       后续体验和高级能力，可延后

## 2. Epic A：工程初始化与安全边界（M0）

### A-01 初始化前后端工程

-   优先级：P0
-   负责人角色：全栈/工程负责人
-   任务内容：
    -   建立 `work_bench/backend` 与 `work_bench/frontend`；
    -   前端采用 React + Vite + TypeScript；
    -   后端采用 Python + FastAPI；
    -   配置开发环境、依赖管理、启动命令和基础日志；
    -   提供 `.env.example`，不提交真实 Token。
-   依赖：无
-   验收标准：
    -   前后端可以分别启动；
    -   前端可访问后端健康检查接口；
    -   README 说明环境准备和启动步骤；
    -   仿真器不可用时，前端仍能进入离线/空状态页面。

### A-02 建立只读仿真器 API Client

-   优先级：P0
-   任务内容：
    -   封装统一 HTTP Client；
    -   从后端环境变量读取 API Base URL 和 Token；
    -   统一处理超时、错误码、重试和日志脱敏；
    -   只暴露 GET 方法或 GET endpoint 函数；
    -   覆盖拓扑、节点、链路、业务、业务详情、路径读取、事件、仿真时间等公开查询接口。
-   依赖：A-01
-   验收标准：
    -   Token 只存在于后端；
    -   前端请求和 WebSocket 消息中不包含 Token；
    -   仿真器 API Client 不提供 POST/PUT/PATCH/DELETE 通用调用入口；
    -   日志不输出 Token；
    -   仿真器断连时返回可识别错误状态，不导致后端进程退出。

### A-03 安全与运行配置

-   优先级：P0
-   任务内容：
    -   默认监听 `localhost`；
    -   配置 CORS 白名单；
    -   为 WebSocket 增加连接状态和异常关闭处理；
    -   如后续开放局域网访问，再增加控制台自身认证；
    -   仿真器场景文件以只读方式加载。
-   依赖：A-01、A-02
-   验收标准：
    -   默认不对局域网开放；
    -   不修改仿真器发布件和场景文件；
    -   代码检索确认无仿真器写接口调用；
    -   离线文件加载过程不产生写操作。

### A-04 定义统一数据契约

-   优先级：P0
-   任务内容：
    -   定义 Node、Link、Service、Flow、Path、Event、NetworkSnapshot
        模型；
    -   保留 API 原始字段，避免过早丢弃信息；
    -   分开记录仿真时间和本机接收时间；
    -   为离线映射字段记录来源；
    -   为估算字段增加 `is_estimated` 或等价标记。
-   依赖：A-01
-   验收标准：
    -   后端模型有类型定义和字段说明；
    -   缺失字段可表达为 null/unknown，不伪造默认事实；
    -   API 原始数据到内部模型的转换有单元测试。

## 3. Epic B：离线场景加载与实时数据采集（M1）

### B-01 离线场景数据加载器

-   优先级：P1
-   任务内容：
    -   读取 `net-topo.json`；
    -   读取 `bg-service.json`；
    -   读取 `scripts/script-NN.json`；
    -   读取 `service-paths.json`（若当前场景提供）；
    -   建立 serviceId 到 category/需求/优先级的映射；
    -   记录文件版本或文件摘要，便于排查场景不匹配。
-   依赖：A-04
-   验收标准：
    -   文件缺失或格式异常时给出明确错误；
    -   离线数据不会覆盖实时状态；
    -   未匹配到离线分类的业务标记为 `unknown`；
    -   分类来源可追踪为 `offline_mapping`、`prefix_inferred` 或
        `unknown`。

### B-02 实时拓扑、节点和链路采集

-   优先级：P1
-   任务内容：
    -   采集拓扑、节点和链路列表；
    -   处理分页和全量读取；
    -   规范化节点 ID、链路 ID 和链路端点；
    -   保留链路五项参数：`delayMs`、`jitterMs`、`bandwidthBps`、`ber`、`packetLossRate`；
    -   识别节点/链路状态变化。
-   依赖：A-02、A-04
-   验收标准：
    -   UI 统计数量与 API 全量数据一致；
    -   分页数据不会重复或漏项；
    -   链路端点可映射到已知节点；
    -   缺失参数显示未知，不擅自补值。

### B-03 实时业务列表与详情采集

-   优先级：P1
-   任务内容：
    -   获取 `/services` 列表；
    -   按需获取 `/services/{serviceId}` 详情；
    -   支持并发上限、缓存和失败隔离；
    -   保留 requirement、path、actual、status、priority 等字段；
    -   正确处理 `actual.errPct` 的百分数单位。
-   依赖：A-02、A-04
-   验收标准：
    -   大量业务下不会无上限并发请求；
    -   单个业务详情失败不影响其他业务；
    -   列表与详情状态可识别是否过期；
    -   不将 `errPct` 与 `requirement.ber` 直接比较。

### B-04 事件增量采集

-   优先级：P2
-   任务内容：
    -   使用 `sinceTsUs` 增量读取 `/events`；
    -   持久维护 `nextSinceTsUs` 游标；
    -   处理重复事件、游标回退和实例切换；
    -   轮询间隔不超过 10 秒。
-   依赖：A-02、A-04
-   验收标准：
    -   连续轮询不重复堆积事件；
    -   重启后可按策略恢复或重置游标；
    -   仿真实例切换时不会把旧实例事件混入新实例。

### B-05 统一 Network Snapshot 聚合

-   优先级：P1
-   任务内容：
    -   聚合 nodes、links、services、flows、events cursor；
    -   记录
        `instance_id`、`sim_time_us`、`received_at`、`snapshot_version`；
    -   计算快照完整性；
    -   对不同接口时间戳差异设置容忍窗口；
    -   通过 WebSocket 推送快照或增量更新。
-   依赖：B-01、B-02、B-03、A-04
-   验收标准：
    -   前端主要视图使用统一快照；
    -   快照能区分完整、部分成功和过期；
    -   不同仿真实例的数据不会混合；
    -   前端不需要自行拼接多个仿真器 API 响应。

### B-06 数据健康与连接状态

-   优先级：P1
-   任务内容：
    -   定义 `LIVE`、`STALE`、`PARTIAL`、`DISCONNECTED`、`OFFLINE`；
    -   展示最近成功采集时间、仿真实例、仿真时间、事件游标；
    -   展示 WebSocket 连接状态；
    -   实现失败退避和恢复后重新采集。
-   依赖：B-05
-   验收标准：
    -   API 断连后界面明确显示 `DISCONNECTED`；
    -   部分接口失败显示 `PARTIAL`；
    -   旧数据不会继续伪装成实时数据；
    -   恢复连接后状态可回到 `LIVE`。

## 4. Epic C：2D 网络总览（M1）

### C-01 2D 拓扑画布

-   优先级：P1
-   任务内容：
    -   展示节点与链路；
    -   优先使用场景真实坐标；
    -   支持缩放、平移、适配画布和节点定位；
    -   区分 UAV、ground、air 节点类型。
-   依赖：B-05
-   验收标准：
    -   节点位置稳定，不因每次刷新大幅跳动；
    -   节点类型可视区分；
    -   节点数量较多时仍可操作；
    -   坐标缺失时才启用备用布局，并标明布局模式。

### C-02 节点和链路状态渲染

-   优先级：P1
-   任务内容：
    -   节点在线/离线状态；
    -   链路 up/down 状态；
    -   链路五项参数的摘要提示；
    -   参数异常或状态变化的视觉标记。
-   依赖：C-01、B-02
-   验收标准：
    -   视觉状态与 API 字段一致；
    -   点击节点/链路可打开详情面板；
    -   不以颜色作为唯一状态表达方式。

### C-03 总览指标区

-   优先级：P1
-   任务内容：
    -   展示节点数、链路数、运行业务数；
    -   展示 test 业务实测达标率和不达标数量（分类可信时）；
    -   展示热点链路 Top N（基础版）；
    -   展示数据健康状态。
-   依赖：B-03、B-06、D-02
-   验收标准：
    -   指标注明统计范围和数据时间；
    -   unknown 分类不混入 test 达标率分母；
    -   部分数据缺失时显示不完整状态。

## 5. Epic D：Service / Flow / Path 关系建模（M2）

### D-01 Flow Key 生成与聚合

-   优先级：P1
-   任务内容：
    -   根据仿真器实际 flow 识别规则生成 flowKey；
    -   将同一 flow 的 Service 聚合为成员列表；
    -   记录 src/dst 节点与 IP；
    -   明确验证源/目的反向是否属于同一
        Flow，不可仅因链路无向就自行合并。
-   依赖：B-03、A-04
-   验收标准：
    -   同源/目的组合的业务分组与仿真器实现一致；
    -   不同组合不误合并；
    -   反向组合有明确测试结论；
    -   每条业务都能定位到所属 Flow 或显示未解析原因。

### D-02 Flow 路径对象

-   优先级：P1
-   任务内容：
    -   从实时业务详情/路径接口解析当前路径；
    -   将路径抽象为 Path 对象；
    -   记录路径节点序列、链路序列和关联 Flow；
    -   支持路径版本或最近观测时间。
-   依赖：D-01、B-02、B-03
-   验收标准：
    -   Flow 详情显示唯一当前路径；
    -   路径节点与链路连续性通过校验；
    -   路径未知或数据不一致时明确提示；
    -   不把 Service 误当作独立路径控制对象。

### D-03 Service 分类与来源标记

-   优先级：P1
-   任务内容：
    -   离线 serviceId 映射 category；
    -   未匹配业务标记 unknown；
    -   经过验证后才启用 ID 前缀 fallback；
    -   UI 显示分类来源。
-   依赖：B-01、B-03
-   验收标准：
    -   分类结果可追溯；
    -   新增或未知 serviceId 不被强制归类；
    -   分类不确定性在 UI 可见。

### D-04 Flow 分析视图

-   优先级：P1
-   任务内容：
    -   Flow 列表和筛选；
    -   显示源/目的、成员业务数、当前路径；
    -   展示成员业务 QoS 状态；
    -   点击 Flow 后高亮拓扑路径；
    -   显示经过链路和共享路径关系。
-   依赖：D-01、D-02、C-01
-   验收标准：
    -   能从 Flow 定位全部成员业务；
    -   能从 Service 反向定位 Flow；
    -   路径高亮与路径详情一致；
    -   同一 Flow 的成员业务明确显示共享路径。

### D-05 Service 详情与跨对象跳转

-   优先级：P1
-   任务内容：
    -   展示 serviceType、category、priority、status；
    -   展示 QoS requirement 和 actual；
    -   展示所属 Flow 和共享路径；
    -   支持 Service → Flow → Path → Link 的跳转。
-   依赖：D-02、D-03、D-04、E-01
-   验收标准：
    -   Service 详情不重复构造独立路径；
    -   跨对象跳转保留当前选择上下文；
    -   缺失指标显示 unknown，而不是 0。

## 6. Epic E：QoS 与热点诊断（M3）

### E-01 静态路径 QoS 计算

-   优先级：P1
-   任务内容：
    -   实现路径时延求和；
    -   实现抖动平方和开方；
    -   实现路径带宽取最小值；
    -   实现多链路丢包率组合；
    -   实现误码率近似累加和对应容差；
    -   将静态路径结果与 Service/Flow 需求逐项比较。
-   依赖：D-02
-   验收标准：
    -   单链路和多链路测试通过；
    -   与仿真器静态校验口径一致；
    -   每项结果可追溯到参与计算的链路参数；
    -   静态结果与实测结果分区展示。

### E-02 实测 QoS 展示与诊断

-   优先级：P1
-   任务内容：
    -   展示
        `avgDelayMs`、`jitterMs`、`effBwBps`、`errPct`、`packetLossRate`；
    -   展示 API 的 `qosMeet`；
    -   按 requirement 标出逐项达标情况；
    -   处理百分数与无量纲比率的单位差异。
-   依赖：B-03、D-05
-   验收标准：
    -   `qosMeet` 作为综合实测状态来源；
    -   `errPct` 不与 `requirement.ber` 直接比较；
    -   展示数据统计时间窗口；
    -   静态可行但实测不达标的情况可以被清晰呈现。

### E-03 链路负载聚合

-   优先级：P1
-   任务内容：
    -   统计 `flow_count`；
    -   统计 `service_count`；
    -   汇总经过链路的业务需求带宽 `demand_bps`；
    -   读取链路 `capacity_bps`；
    -   计算 `demand_utilization`；
    -   在统计口径确认后，再考虑汇总业务 `actual.effBwBps`
        作为实测带宽估计。
-   依赖：D-02、D-04、B-02、B-03
-   验收标准：
    -   同一 Flow 的成员业务数与 Flow 数分别统计；
    -   不把 flow_count 当作链路利用率；
    -   需求带宽汇总规则有测试；
    -   估算值在 UI 明确标记为估算值。

### E-04 热点识别与解释

-   优先级：P1（基础）/ P2（综合评分）
-   任务内容：
    -   分开计算结构热点、流量热点、性能热点；
    -   结构指标可包括节点度数、介数中心性；
    -   流量指标使用 Flow 数、业务数、需求带宽；
    -   性能指标结合链路参数和业务 QoS 结果；
    -   初版展示原始指标，不急于合成黑盒分数。
-   依赖：E-01、E-02、E-03
-   验收标准：
    -   能区分"中心性高"和"实际拥塞"；
    -   热点结果能解释触发原因；
    -   缺失数据不被当作低风险；
    -   Top N 可点击定位链路/节点。

### E-05 QoS 与热点联动诊断

-   优先级：P2
-   任务内容：
    -   从不达标 Service 定位所属 Flow；
    -   从 Flow 定位路径链路；
    -   显示路径上可疑链路及其承载业务；
    -   提供证据字段和关联关系，不把相关性描述成确定因果。
-   依赖：D-04、D-05、E-01～E-04
-   验收标准：
    -   能从不达标业务追踪到路径和链路；
    -   能查看同链路其他竞争 Flow；
    -   诊断说明区分事实、估算和可能原因。

------------------------------------------------------------------------

## 7. Epic F：计划事件与实际事件时间轴（M4）

### F-01 计划事件解析

-   优先级：P2
-   任务内容：
    -   解析 `scripts/script-NN.json`；
    -   提取计划时间、事件类型、目标对象和参数；
    -   以仿真 T0 为基准映射到仿真时间轴；
    -   原样保留未知事件字段供诊断。
-   依赖：B-01
-   验收标准：
    -   计划事件展示不依赖实时事件接口；
    -   计划时间与仿真时间基准一致；
    -   未识别事件不会静默丢弃。

### F-02 实际事件展示

-   优先级：P2
-   任务内容：
    -   展示 `/events` 返回的实际事件；
    -   支持按时间、类型、目标对象过滤；
    -   维护事件游标和实例 ID；
    -   对事件进行去重。
-   依赖：B-04、B-05
-   验收标准：
    -   实际事件只来自实时 API；
    -   不将计划事件伪装成已发生事件；
    -   仿真实例切换后事件列表正确隔离。

### F-03 计划/实际事件关联

-   优先级：P2
-   任务内容：
    -   按事件类型、目标对象、时间窗口和可用关联 ID 匹配；
    -   支持一条计划事件对应多条实际事件；
    -   标记已发生、待观测、不匹配、非计划事件。
-   依赖：F-01、F-02
-   验收标准：
    -   关联规则可配置、可解释；
    -   无法确认匹配时显示"未关联"，不强行配对；
    -   对照结果可查看原始计划和实际事件。

### F-04 事件驱动的状态核对

-   优先级：P2
-   任务内容：
    -   对照节点状态、链路状态和实际坐标变化；
    -   计划事件只作为预期，不直接驱动实际拓扑状态；
    -   对 `node_move` 等事件核对实际观测结果。
-   依赖：F-03、B-02
-   验收标准：
    -   实际拓扑只由实时观测数据更新；
    -   计划与实际不一致时有明确提示；
    -   不因脚本中存在移动事件就直接移动节点图标。

## 8. Epic G：候选路径比较与 What-if（M5）

### G-01 候选路径生成/导入

-   优先级：P2
-   任务内容：
    -   优先读取场景提供的候选路径数据；
    -   若需自行生成，使用当前可用拓扑生成候选简单路径；
    -   排除 down 链路和不连通路径；
    -   对候选数量设置上限。
-   依赖：D-02、B-02
-   验收标准：
    -   候选路径均可映射到现有节点和链路；
    -   不生成重复路径；
    -   数据不足时明确显示无法生成。

### G-02 候选路径静态 QoS 比较

-   优先级：P2
-   任务内容：
    -   对候选路径计算静态 QoS；
    -   按 Flow 全部成员业务需求检查；
    -   展示每项约束的通过/失败原因；
    -   排序依据可解释。
-   依赖：E-01、D-04、G-01
-   验收标准：
    -   共享 Flow 的成员业务约束全部纳入；
    -   候选路径不可行时指出具体指标；
    -   不把排序分数当作绝对最优保证。

### G-03 Flow 迁移影响估算

-   优先级：P2
-   任务内容：
    -   用户在本地选择一个 Flow 和候选路径；
    -   估算原路径释放的链路需求；
    -   估算新路径增加的链路需求；
    -   对比迁移前后的 `demand_utilization`；
    -   展示同链路其他 Flow 和业务；
    -   明确说明这是 what-if 估算，不是真实仿真结果。
-   依赖：E-03、G-02
-   验收标准：
    -   迁移前后计算可复现；
    -   不修改实时快照；
    -   不向仿真器发送任何写请求；
    -   对共享路径影响范围有明确说明。

### G-04 What-if 结果解释

-   优先级：P2
-   任务内容：
    -   展示改善的链路、恶化的链路；
    -   展示受影响的业务和 QoS 风险；
    -   对缺失数据和估算假设进行提示。
-   依赖：G-03
-   验收标准：
    -   每个结论有对应指标；
    -   不将估算结论描述为确定效果；
    -   可清除分析并恢复当前实时视图。

## 9. Epic H：历史快照与展示增强（M6）

### H-01 快照历史缓存

-   优先级：P3
-   任务内容：
    -   保存有限时间窗口的快照或关键指标；
    -   控制内存/磁盘占用；
    -   按仿真实例隔离历史数据。
-   依赖：B-05
-   验收标准：
    -   可配置保留时间和容量；
    -   历史数据不会跨实例混用；
    -   清理策略有测试。

### H-02 时间回放

-   优先级：P3
-   任务内容：
    -   按仿真时间回放节点、链路、业务和事件状态；
    -   支持暂停、继续、拖动时间轴；
    -   标记历史数据缺口。
-   依赖：H-01、F-02
-   验收标准：
    -   回放使用仿真时间而非浏览器时间；
    -   历史缺失区间明确提示；
    -   回放不会触发仿真器控制接口。

### H-03 3D 拓扑（可选）

-   优先级：P3
-   任务内容：
    -   在 2D 核心体验稳定后评估 3D；
    -   复用统一 Node/Link/Flow 数据模型；
    -   不改变诊断逻辑。
-   依赖：C-01、C-02
-   验收标准：
    -   3D 不成为唯一拓扑入口；
    -   低性能设备可回退到 2D；
    -   3D 开发不影响 MVP 交付。

## 10. 测试任务拆分

### T-01 Flow 分组单元测试

-   同一源/目的组合多业务归组；
-   不同源/目的组合不误合并；
-   反向组合按仿真器真实规则验证；
-   成员业务变化后聚合正确。

### T-02 QoS 计算单元测试

-   单链路和多链路路径；
-   时延求和；
-   抖动平方和开方；
-   带宽最小值；
-   丢包率组合；
-   BER 容差；
-   `errPct` 单位处理；
-   静态通过但实测不达标。

### T-03 热点指标测试

-   多条低带宽 Flow；
-   少数高带宽 Flow；
-   同 Flow 多 Service；
-   容量变化；
-   链路 down；
-   需求超过容量；
-   高中心性低负载；
-   低中心性高需求负载。

### T-04 数据采集与一致性测试

-   API 分页；
-   详情接口单项失败；
-   API 超时和断连；
-   事件游标续读；
-   仿真实例切换；
-   WebSocket 断连重连；
-   快照部分成功；
-   时间戳不一致。

### T-05 只读安全回归

-   仿真器 API Client 仅允许 GET；
-   全项目搜索禁止的 POST 路径；
-   Token 不出现在前端构建产物和 WebSocket；
-   离线文件不会被修改；
-   What-if 操作只修改本地分析状态。

## 12. Definition of Done（统一完成标准）

任何任务合并前至少满足：

-   [ ] 有明确输入、输出和字段口径；
-   [ ] 有正常路径测试；
-   [ ] 有缺失数据/异常数据测试；
-   [ ] 错误状态可观测，不静默吞错；
-   [ ] 不引入仿真器写操作；
-   [ ] 日志不泄露 Token；
-   [ ] UI 能区分实时事实、离线配置和估算结果；
-   [ ] 对外字段和接口有简短文档；
-   [ ] 关键算法有可复现样例。

## 13. MVP 验收清单

首个可用版本必须全部满足：

-   [ ] 控制台可独立启动；
-   [ ] 离线场景数据可加载；
-   [ ] 实时 API 可连接，断连状态可见；
-   [ ] 2D 拓扑显示节点和链路；
-   [ ] 节点、链路状态和链路参数正确；
-   [ ] 业务列表和详情可查看；
-   [ ] Service 与 Flow 的归属关系正确；
-   [ ] Flow 当前共享路径可高亮；
-   [ ] 业务实测 QoS 和 `qosMeet` 可查看；
-   [ ] 静态 QoS 与实测 QoS 分开展示；
-   [ ] 基础热点指标可查看；
-   [ ] 数据健康状态可见；
-   [ ] 只读安全回归通过。

**MVP 不要求：**
3D、历史回放、自动路径下发、仿真启动、复杂综合热点评分。

## 14. 风险与待确认事项

以下事项在实现前必须通过代码或接口实测确认，不应由前端自行假设：

1.  Flow Key 的规范化规则，尤其源/目的反向是否共享同一 Flow；
2.  `/services`、`/nodes`、`/links` 的分页边界和全量读取方式；
3.  服务详情与路径接口中路径字段的最终结构；
4.  `actual.effBwBps` 是否可用于跨业务求和并近似链路吞吐；
5.  `actual.errPct` 与 `requirement.ber`
    的定义关系，除单位外是否存在统计口径差异；
6.  离线业务文件与实时 serviceId 的覆盖率；
7.  计划事件与实际事件的关联字段是否足够；
8.  仿真实例切换时事件游标和历史快照的重置规则；
9.  场景坐标是否始终可用，以及移动节点坐标的实时来源。

对于尚未确认的内容，先显示 `unknown` 或"待验证"，不要在数据层固化猜测。

## 16. 给开发者/代码代理的执行约束

开始编码前先检查现有项目目录和仿真器接口，不要覆盖已有实现。实施时遵循：

1.  先完成 A-01、A-02、A-04，再扩展业务功能；
2.  每个 Epic 完成后运行对应测试，不要一次性生成整个项目后再调试；
3.  未确认的 API 字段先保留原始响应并标注待确认；
4.  不允许为了让页面显示而伪造数据或默认填零；
5.  所有分析结果都应能追溯到输入字段和计算规则；
6.  不得调用仿真器写接口；
7.  不得把计划事件直接当成真实事件；
8.  不得把业务级实测带宽直接宣称为链路实际利用率；
9.  不得把每条 Service 都当作独立 Flow；
10. Agent 目录或算法模块未稳定前，work_bench 必须保持独立可运行。

**最终交付判断：** 只有当 MVP 验收清单全部通过，且数据关系、QoS
口径和只读安全测试通过后，才认为 V1.1 调试控制台具备可供 Agent
研发日常使用的基础条件。
