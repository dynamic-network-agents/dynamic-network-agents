# B03 Network Workbench 前端改版设计说明

> 目标：将当前“接口数据堆叠页”改造成面向算法调试、网络态势感知和 QoS 排障的工作台。设计遵循信息优先级清晰、异常可定位、详情可下钻、默认只读的原则。

## 1. 设计目标与原则

### 1.1 核心目标
- 在一个屏幕内快速回答：仿真是否正常、网络哪里异常、哪些业务受影响、异常可能由什么链路或路径引起。
- 从全局拓扑进入链路、Flow、Service 和 Path 详情，避免在多个孤立表格之间来回寻找。
- 为算法调试保留足够的原始观测信息，同时避免原始 JSON 挤占主界面。

### 1.2 设计原则
1. **态势优先**：先展示状态与异常，再展示明细。
2. **异常驱动**：风险链路、QoS 不达标业务、关键事件应有明显但克制的视觉提示。
3. **渐进披露**：常用字段直接展示；完整对象、原始 JSON、低频字段放入抽屉或折叠区。
4. **统一时间**：所有图表、拓扑、事件和业务详情必须标注同一仿真实例与仿真时间快照。
5. **只读安全**：调试台只调用 GET 接口；不得调用路径提交、仿真启动等写接口。
6. **数据诚实**：缺失值显示“未知/暂无数据”，不能用 0 代替；脚本预期事件与仿真器实际观测事件必须区分。

## 2. 页面信息架构

### 2.1 左侧主导航
- 全局总览
- 网络分析
- 业务分析
- QoS 诊断
- 路径对比
- 事件时间轴
- 历史回放
- 系统设置

导航采用窄侧栏，图标 + 短标签；当前页面高亮。首版可以只实现“全局总览”和各模块的详情抽屉/二级页面，其余入口按迭代逐步开放，避免空页面。

### 2.2 顶部状态栏
展示：
- 仿真状态（运行中/暂停/已结束/未知）
- instanceId
- 仿真时间（由 tsUs/t0TsUs 计算）
- 最近数据更新时间
- 数据健康状态（正常/延迟/部分接口失败）

顶部不放大段说明文字。状态栏应固定高度，避免挤占主内容区。

## 3. 全局总览布局

桌面端建议以 1440×900 为主要设计基准，采用 12 栅格布局，页面内容区宽度自适应。

### 3.1 第一行：核心 KPI
建议 5 张紧凑卡片：
- 在线节点：在线数 / 总数
- 活动链路：活动数 / 总数
- 测试业务：测试业务数 / 可识别总数
- 风险链路：风险链路数量
- 整体状态：正常/告警/异常

规则：
- 指标必须有明确统计口径和时间戳。
- 不确定分类（例如无法可靠识别 test/background 的服务）应单独标注“未知”，不可强行归类。
- 卡片点击后跳转到对应筛选后的列表。

### 3.2 主区域：网络拓扑 + 右侧诊断栏

左侧约 8 栅格，右侧约 4 栅格。

**网络拓扑卡片**
- 显示 UAV、地面节点、空中节点；图例固定在标题栏。
- 链路按状态显示正常/异常，风险链路加粗或虚线；颜色之外还应使用线型/图标区分，避免只依赖颜色。
- 节点位置优先使用仿真器提供的真实坐标；缺少坐标时使用稳定布局，并标记“布局估算”。
- 支持缩放、平移、框选/搜索节点、按节点类型过滤、按风险状态过滤。
- 点击节点打开节点详情；点击链路打开链路详情；点击链路上的风险标记显示异常原因摘要。
- 不要在拓扑中同时显示所有服务标签，避免视觉噪声。选中 Service/Flow 后再高亮其路径。

**右侧诊断栏**
- 业务 QoS 达标率趋势：测试业务与背景业务分开（仅当分类可信时）。
- 热点分析 Top N：链路利用率、时延风险、丢包/误码风险分别展示，不能把带宽利用率当成唯一拥塞指标。
- 每条热点提供“查看链路”入口，联动拓扑高亮。

### 3.3 第二行：关键业务、链路负载、事件摘要

**关键业务状态**
建议列：业务 ID、类型、源→目的、QoS 状态、实际时延/抖动、路径 ID。
- 默认优先显示 QoS 不达标和高优先级业务。
- 支持按 serviceType、QoS 状态、优先级筛选。
- 点击业务打开 Service 详情抽屉。

**链路负载排行**
建议列：排名、链路 ID、需求带宽、容量、利用率、状态。
- 将需求带宽与实测吞吐分开展示。
- 利用率的计算口径必须在 tooltip 中解释；如果实际吞吐无法可靠映射到链路层，就只展示“需求/容量估算”，不要伪装成实测利用率。
- 点击链路联动拓扑和链路详情。

**事件时间轴摘要**
- 展示最近 5–8 条实际观测事件。
- 类型包括节点状态变化、链路状态变化、业务状态变化等。
- 时间使用统一仿真时间；事件详情默认折叠。
- 脚本计划事件使用另一种视觉标识，不得与 `/events` 实际事件混为一谈。

## 4. 详情交互与下钻

建议采用右侧 Drawer 或中等宽度详情面板，不要每次点击都跳到新页面。

### 4.1 Service 详情
- 基本信息：serviceId、serviceType、category（可信时）、priority、src/dst、状态。
- QoS 要求：delay/jitter/BER/loss 上限、bandwidth 下限。
- 实测指标：avgDelayMs、jitterMs、effBwBps、errPct、packetLossRate、qosMeet。
- 当前路径：节点序列、链路序列、路径版本/更新时间（若可获得）。
- 关联 Flow：同一 src/dst 对应的 Flow，以及共享该 Flow 的其他 Service。

重要：`actual.errPct` 是百分比，而 `requirement.ber` 是无量纲 BER，不能直接比较。`actual.qosMeet` 应作为仿真器给出的整体达标判定；单项诊断需明确单位转换和口径。

### 4.2 Flow 详情
- Flow 标识、src/dst、共享 Service 数量。
- 共享路径和路径经过的链路。
- 该 Flow 内所有 Service 的 QoS 要求与实际状态。
- 由于同一 src/dst 的多个业务可能共享 Flow 路径，不能只按单个 Service 的要求判断路径是否合适。

### 4.3 Link 详情
- 链路端点、状态、delayMs、jitterMs、bandwidthBps、ber、packetLossRate。
- 经过该链路的 Flow 数量和 Service 数量。
- 需求带宽汇总、容量、利用率估算及其口径。
- 受影响 Service 列表和相关事件。
- 分别呈现带宽、时延、抖动、误码、丢包风险。

## 5. 数据与指标口径

### 5.1 统一快照
前端应将一次采集的数据组织成统一快照，建议字段：
- `instance_id`
- `sim_time_us`
- `received_at`
- `source`
- `version`
- `nodes[]`、`links[]`、`services[]`、`events[]`
- `data_health`：各接口成功/失败、数据年龄、分页完整性

避免拓扑来自一个仿真时刻、业务表来自另一个时刻、事件列表又来自第三个时刻。

### 5.2 热点指标
至少区分：
- Flow 数量：结构性经过关系，不代表流量大小。
- 需求带宽：链路上业务需求的汇总。
- 实测吞吐：仅在确认统计语义后使用。
- 链路容量：`bandwidthBps`。
- QoS 风险：时延、抖动、BER、丢包等多维风险。

推荐将“结构中心性”和“实时拥塞风险”分开展示。若做综合分数，必须展示权重和构成，不能只给一个不可解释的风险分。

### 5.3 静态路径 QoS 与实测 QoS
- 静态路径指标用于判断路径属性的组合结果。
- `actual` 是近期测量统计；`actual.qosMeet` 是实测 QoS 的综合判定。
- 静态路径满足要求，不代表实测业务一定达标。
- 前端必须明确标注“路径估算”与“业务实测”，不要放在同一列混用。

## 6. 原始数据与接口调试区

当前页面中大量原始 JSON 和完整接口表格应迁移到“数据检查”折叠面板：
- 接口名称、请求时间、耗时、成功/失败状态。
- 原始响应 JSON，支持复制、搜索、折叠。
- 分页游标、事件 sinceTsUs/nextSinceTsUs 等采集元信息。
- 默认收起，不占据总览主视图。

数据表格应支持列排序、筛选、固定表头、分页和行详情；不应将 100 多条记录一次性铺满首页。

## 7. 只读与安全边界

调试前端默认只读：
- 允许使用 GET 接口读取节点、链路、业务详情、事件等信息。
- 不得调用 `POST /services/{serviceId}/path`。
- 不得调用 `/simulation/start` 等仿真控制写接口。
- 路径对比和 What-if 首版只做本地计算/展示，不提交仿真器。
- 如果未来加入智能体动作观测，应记录“感知→决策→提交意图→结果”，并由独立权限控制动作执行；调试台本身仍不暗中执行动作。

## 8. 页面状态与异常处理

必须覆盖以下状态：
- 首次加载：骨架屏 + 当前连接状态。
- 正常运行：显示统一快照和最近更新时间。
- 数据过期：显示“数据已延迟”，保留最后一次成功快照并标注时间。
- 部分接口失败：仅将对应模块置为不可用，不要把整页清空。
- 无数据：显示明确空态和原因，不显示伪造的 0。
- 实例切换：清空旧实例缓存，避免不同 instanceId 数据混合。

## 9. 视觉规范

- 主背景：浅灰蓝，卡片白色，边框轻量；左侧导航深海军蓝。
- 主色：蓝色用于选中、链接和主要交互；绿色表示正常；橙色表示警告；红色表示异常。
- 字体：中文优先系统字体；数字使用等宽数字风格，便于比较。
- 卡片间距统一；减少粗重阴影和大面积渐变。
- 表格密度适中，表头清楚，行高约 36–40px；长 JSON 不进入普通表格。
- 图表应有坐标轴、单位、时间范围、图例和空数据状态。
- 颜色不是唯一状态编码方式，同时使用文字、图标、线型或形状。

## 11. 实施优先级

### P0：先保证可信
- 统一快照和仿真实例时间。
- 节点、链路、业务、事件数据采集和错误状态。
- 严格只读接口封装。
- 字段单位、空值和 QoS 口径校验。

### P1：完成可用总览
- KPI 卡片。
- 2D 网络拓扑及节点/链路详情。
- 关键业务表、链路排行、事件摘要。
- Service/Flow/Link 之间的联动下钻。

### P2：增强诊断能力
- QoS 趋势、热点多维排名。
- 路径对比和本地 What-if。
- 计划事件与实际事件分轨展示。

### P3：研发辅助能力
- 快照历史与回放。
- 智能体感知、决策、动作结果追踪。
- 3D 拓扑仅在确有空间分析需求时增加。

## 12. 验收标准

1. 首屏能在 5 秒内看清仿真状态、风险链路和受影响业务。
2. 从一条异常业务可在 2 次点击内定位到其 Flow、路径和相关链路。
3. 点击风险链路后，拓扑、链路详情、经过该链路的业务列表同步联动。
4. 所有指标具有单位、统计口径和数据时间；未知值不会伪装成 0。
5. 不同模块展示同一 instanceId 和同一快照时间，或明确标注数据不同步。
6. 原始 JSON 默认折叠，不影响日常排障。
7. 自动化测试确认页面不会请求任何仿真器写接口。
8. 接口失败、数据过期、无数据和实例切换均有明确 UI 状态。
