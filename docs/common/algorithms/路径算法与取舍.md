## 1. 候选路径生成：Yen K-最短

**代码**：`src/common/algorithms/path/k_shortest.py::k_shortest_paths`

```text
function candidate_paths(G, s, t, K):
    paths = []
    for p in nx.shortest_simple_paths(G, s, t, weight="delay"):
        paths.append(p)
        if len(paths) == K: break
    return paths
```

- 权重用 `delay`（时延）作为第一启发式；
- $K$ 建议 $30\sim 100$（网络规模而定，实验 E09 标定）；
- 只在 `status=up` 链路上搜；两端节点须 `online`；剔除 EXT001；
- NetworkX `shortest_simple_paths` **不支持 MultiGraph**，故先折叠成简单图
  （每对节点保留权重最小的一条边）——**并行链路的差异在这一步丢失**，
  因此并列链路场景需另行验证。

### 1.1 为什么用 K-最短而不是全枚举

| 方案 | 优点 | 缺点 | 本项目取舍 |
|---|---|---|---|
| 全枚举所有简单路径 | 一定能找到最优 | 路径数指数级，大拓扑不可行 | ✗ |
| 最短路（K=1） | 最快 | 常常 QoS 不可行或容量不划算 | ✗ |
| **Yen K-最短** | 可控代价，覆盖多条可行通道 | K 是硬截断，可能漏解 | ✓ |
| 代价最优搜索（A*） | 单 flow 更优 | 多 flow 场景仍需贪心框架 | 备选（单 flow 场景可换） |

$K$ 的作用是**给多样性留预算**：备选通道越多，越容易在容量竞争时找到"挤得下"的路。

## 2. 单 flow 选路

**代码**：`src/common/algorithms/path/single_flow.py::optimize_flow`

```text
function optimize_flow(G, f, weights):
    cand = candidate_paths(G, f.s, f.t, K)
    feasible = []
    for P in cand:
        qos = compose_qos(P, G)              # 静态五项
        ok = check_qos(qos, R_f)             # flow 需求 R_f
        if ok: feasible.append((cost(P), margin(P), P))
    if feasible is empty: return None        # 报告无可行路径
    sort feasible by (cost asc, margin desc) # 代价优先，裕度次之
    return feasible[0].P
```

> **历史位置**：这是**早期单 flow 选路**，**已不在闭环里**，仅保留做离线对比
> （任务清单 T3.2）。闭环用的是多 flow 联合规划，见 [flow 级联合选路](flow级联合选路.md)。
> 保留它的价值：作为多 flow 贪心的**单流基线**——多 flow 方案在单流退化场景下
> 不应劣于它。

## 3. 候选的过滤与排序

候选从 K-最短出来后，要过三道：

| 步骤 | 判据 | 代码 |
|---|---|---|
| 排除惩罚路径 | 实测违约过的路径（`PlanConfig.excluded_paths`） | `flow/candidates.py::_feasible_candidates` |
| **静态 QoS 硬过滤** | 五项指标全部满足 flow 需求 | `common/modeling/qos_checker.py::check_qos` |
| 按代价排序 | 链路代价升序（`delay`/`jitter`/`bandwidth`/`packet_loss`/`ber` 加权） | `common/modeling/link_quality.py::path_cost` |

**排除的兜底**：若排除后一条候选都不剩，**回退到不排除**——flow 彻底失去路径
比走一条实测违约的路更糟。（实测违约路径进惩罚集，见
[闭环状态机与收敛判据](../control/闭环状态机与收敛判据.md) §4。）

**代价只用于排序**：链路代价**不参与 QoS 判定**（见
[数学建模方案](../modeling/数学建模方案.md) §3.2 的口径声明）。

## 4. 路径表示与归一化

**代码**：`src/common/algorithms/flow/candidates.py::normalize_path`

路径在系统里有三种表示：

1. **节点序列**：`k_shortest_paths` 的输出；
2. **链路 id 序列**：实际下发的形式（`segments` 里 `type=link` 的 `id`）；
3. **方向**：仿真器存的 flow 路径方向取决于**最后一次提交**的顺序，可能与本端约定相反。

`normalize_path` 把路径归一化成 `flow_key[0] → flow_key[1]` 方向；不连续/链路缺失
返回 `None`（视为无路径）。**容量记账要求路径从 `flow_key[0]` 起步**，故必须先归一化。

## 5. 取舍小结

| 决策 | 取值 | 理由 |
|---|---|---|
| 候选算法 | Yen K-最短 | 可控代价上限，通道多样性 |
| 权重 | `delay` 优先 | 时延是业务 QoS 的第一约束 |
| K | 30（默认） | 待 E09 标定 |
| 排序键 | 代价升序 | 静态 QoS 已是硬约束，代价只在可行解间比较 |
| 不可行处理 | 报无路径，不降级 | 降级路径会被 1004 拒绝，白耗动作预算 |
