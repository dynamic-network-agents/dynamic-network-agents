# 算法扩展指引

> 定位：**`src/common/algorithms/` 的扩展规约**——新增算法放哪、接口契约是什么、
> 怎么验证、哪些坑不能踩。
> 目的：让算法能持续扩展，而**不重演"flow_xxx.py 平铺"的旧问题**。

---

## 1. 扩展地图：新增什么放哪

| 你要新增的 | 落在 | 理由 |
|---|---|---|
| 新的**候选路径算法**（如 A*、代价最优搜索、时变路径） | `path/` | 产出的是「一条 flow 的候选路径集」 |
| 新的**单 flow 选路策略** | `path/` | 只看一条 flow 的 QoS 与代价 |
| 新的**flow 级联合优化**（如 ILP、局部搜索变体、多轮贪心） | `flow/` | 产出的是「所有 flow 的路径映射」 |
| 新的**图/容量口径**（如新的链路类型容量语义、时变带宽） | `topology/` | 图模型与资源记账 |
| 新的**QoS 指标**或判定容差 | `common/modeling/` | 数学内核，不是算法 |

**判定口诀**：产出的对象是「路径」→ `path/`；是「路径映射」→ `flow/`；
是「图或负载」→ `topology/`。

## 2. 三条接口契约

### 2.1 候选算法契约

```python
def your_candidates(graph, flow_key, requirement, config) -> list[list[str]]:
    """返回该 flow 的静态可行候选路径（链路 id 序列），按代价升序。

    约束：
    - 必须是**纯函数**：同输入同输出，不看已装路径、不读仿真器；
    - 每条路径必须是**连续的**（`validate_path` 通过），方向为 flow_key[0]→[1]；
    - 必须已通过静态 QoS 硬过滤（`check_qos(compose_qos(path, graph), requirement)`）；
    - 长度 ≤ config.candidate_path_count。
    """
```

接入点：`common/algorithms/flow/candidates.py` 里替换/追加候选来源。

### 2.2 flow 级策略契约

```python
def your_planner(flows, graph, config) -> dict[FlowKey, FlowPlan]:
    """返回 flow_key -> FlowPlan。

    约束：
    - **纯函数**：输出只取决于 (flows, graph, config)，不看已装路径；
    - 每个 FlowPlan 必须填 flow_class / requirement / weight / candidates / path；
    - path 要么是连续的链路 id 序列，要么 None（无可行路径）。
    """
```

接入点：`common/algorithms/flow/planner.py`（门面）——保持 `plan(flows, graph, config)`
的签名不变，调用方（`common/control/loop.py`）零改动。

> **保持门面签名不变的意义**：`common/control/` 与 `common/perception/` 不需要知道
> 用的是哪个规划器。将来 agent 与 baseline 各自选不同规划器时，也只需换门面实现。

### 2.3 容量记账契约

新增容量口径时，必须同时明确三件事：

1. **方向语义**：是否按方向独立记账（当前口径：是）；
2. **累加语义**：求和 vs 取最大（当前口径：求和）；
3. **裕度作用点**：$\rho$ 乘在带宽上还是别处（当前口径：`bw×(1-ρ)`）。

> 这三点任意一个含糊，都会让「容量约束」变成不可验证的黑箱。

## 3. 已知的可优化点（当前刻意不做）

| 点 | 现状 | 风险 | 备注 |
|---|---|---|---|
| 局部搜索的负载重算 | 每次试算候选**全量重算**（O(n²)） | 大拓扑慢 | 优化需证明与全量重算**结果一致**；增量更新易在"减载"时算错 |
| K-最短的 MultiGraph 折叠 | 折叠成简单图，**并列链路差异丢失** | 并列链路场景候选可能不完整 | 需改用支持 MultiGraph 的 K-最短实现 |
| `weighted_score_with_paths` 改写 `plans` | 临时改 `p.path` 再 `try/finally` 恢复 | 异常路径可能留污染 | 纯函数契约下的妥协 |
| 贪心排序的稳定性 | `sorted` 按 `(hard, -weight, bandwidth)` | 相同权重的 flow 顺序依赖入参顺序 | 已保证可复现，但可加显式 tie-break |

## 4. 验证方法（每个扩展都必须过）

### 4.1 单元测试（跟随被测模块）

放在 `src/common/algorithms/<子域>/tests/`，遵循现有风格：
- 用**固定的小图**（如 4 节点 3 链路）构造可手算的期望；
- 断言**具体路径/分数**，不只断言"非空"；
- 边界场景：无可行路径、只有一条候选、全部候选被排除。

### 4.2 黄金快照比对（防回归）

```bash
PYTHONPATH=src uv run python scripts/plan_dump.py > /tmp/plan.json
```

`scripts/plan_dump.py` 输出 `{flow_key: path}` + 分类 + 权重 + 得分的 JSON。
**改动算法后必须 diff**：有意变化要在版本记录里说明理由，无意变化是回归。

### 4.3 离线场景验证

```bash
PYTHONPATH=src uv run python scripts/feasible_bound.py simulator/data/scenarios/sce20261010-conf02/sce01
```

给出该场景的可达上界与最优摆法，用于判断新算法是**真的更好**还是只是换了摆法。

### 4.4 全量回归

```bash
uv run pytest src/ tests/
```

## 5. 四个不能踩的坑

### 5.1 不要让规划器看到"当前已装路径"

规划器一旦读到 incumbent，就会为了"保持现状"而牺牲全局最优（实测 sce05 592→384）。
**现状优先**的诉求应该由**调用方的闸门**（Δmin）来满足，而不是塞进规划器。

### 5.2 不要把 LLM 塞进规划器

规划器在热路径上，必须**确定性**且**快**。LLM 只做解释、优先级增强、故障诊断建议，
输出不能直接决定链路（见 `src/CLAUDE.md` 硬约束）。

### 5.3 不要把两套 QoS 混用

- 静态 QoS（提交校验口径，`compose_qos` + `check_qos`）用于**候选过滤与受理判定**；
- 实测 QoS（逐秒 `actual.qosMeet`）用于**运行期评分**。

静态通过**不代表**实测一定达标。混用会导致"看起来达标其实没达标"。

### 5.4 不要绕过下发闸门

任何写动作都必须过 `common/control/dispatch_gate.py`：
**修复失效路径** or **加权达标数增益 ≥ Δmin**。绕过闸门会导致路径 churn
（永不停歇地改路），在评测里表现为动作数爆炸。

## 6. 扩展检查清单

新增算法时逐条确认：

- [ ] 落在正确的子域（`path/` / `flow/` / `topology/` / `modeling/`）
- [ ] 满足纯函数契约（同输入同输出，不读仿真器、不看已装路径）
- [ ] 保持了 `plan(flows, graph, config)` 门面签名（调用方零改动）
- [ ] 有单元测试（固定小图 + 具体断言）
- [ ] 黄金快照 diff 已确认（变化是有意的）
- [ ] 离线场景验证对比过可达上界
- [ ] 全量测试通过
- [ ] 版本记录 `versions/日期_task_subtask.md` 已写
- [ ] 文档已更新（对应 `docs/common/algorithms/` 下的篇章）
