# 拓扑构建与容量记账

> 定位：**`src/common/algorithms/topology/` 的算法规格**——网络图怎么建、容量怎么记。
> 关联：flow 级选路见 [flow 级联合选路](flow级联合选路.md)；链路参数权威源见
> `simulator/conf/linkTypes.json`。

---

## 1. 建图（`graph.py::build_graph`）

把仿真器的节点/链路载荷转成 NetworkX `MultiGraph`。

### 1.1 筛选规则

| 对象 | 规则 | 理由 |
|---|---|---|
| 节点 | 只收 `status=online` | 下线节点不可用 |
| 链路 | 只收 `status=up` | 断链不可用 |
| **EXT001** | **按 nodeId 显式剔除** | 合成的"外部引接点"，非业务端点（`packetsFwd` 恒 0）；留着会把 1Gbps 光纤误当业务链路 |
| 并行链路 | 用 `MultiGraph` 保留 | 两点间可能有多条不同 `linkId` 的链路（fiber + satcom 等） |

### 1.2 边属性

每条边携带**5 项链路参数** + `delay` 权重：

| 属性 | 来源 | 用途 |
|---|---|---|
| `delay_ms` / `jitter_ms` | `links[].params` | 静态 QoS 合成、K-最短权重 |
| `bandwidth_bps` | `links[].params` | 容量记账 |
| `ber` / `packet_loss_rate` | `links[].params` | 静态 QoS 合成 |
| `delay` | 同 `delay_ms` | K-最短路径的边权重 |

### 1.3 关键坑：params 只能从 `/links` 取

`GET /topology` 的 `links` **不带 params**（只有 id 与端点），`GET /links` 才带。
**用 `/topology` 建图会让所有链路参数变成 0** —— 静态 QoS 判定会全部失真。

代码里对应 `SnapshotSource._build_graph`：分别调 `get_topology()` 取节点、
`get_links()` 取链路。

### 1.4 UAV 的"接入链路"

仿真器端别模型把 ground→sN(交换机)、uav/air→hN(主机)，且**两端都是主机的链路直接报错**
「端别模型不成立」（`sim_src/netsim/sdncommon.py` 的 `adapt_spec`）。所以 UAV 的流量
**只能经「UAV—地面」这类接入链路出入**。

`access_links`（`uav_access_links`）据此查表：每个 UAV 一条最粗的相邻链路，
**只用于判 F1/F2**，不参与容量记账（容量按 `capacity_map` + `DirKey` 逐链路逐方向算）。
详见 [flow 级联合选路](flow级联合选路.md) §2 的近似口径说明。

## 2. 容量记账（`capacity.py`）

### 2.1 方向键

方向键 `(link_id, sign)`：`sign` 由该跳 `(tail, head)` 按节点 id 字典序定
（`tail < head` → +1，否则 -1）。

**为什么必须按方向**：仿真器 `apply_link` 对链路两端各挂一个 `rate=bw` 的 TBF，
A→B 与 B→A 是**两个独立令牌桶**。把两方向加总后对一个 bw 比，会严重高估容量。

### 2.2 需求累加

`directional_demand(flow_src, services, path, graph)`：把每条业务按其
`src→dst` 方向累加到路径各链路的方向上。

- `flow_src` 是 flow 的名义源（无序对里字典序较小者）；服务方向与之相反时按反向遍历路径；
- 路径与业务不连续时**抛 ValueError**（暴露数据不一致，而不是静默算错）。

口径：**求和**（同 flow 多业务叠加在同一链路上，负载相加），与静态 QoS 判定用的
漏斗带宽 `B=min b` **不同，勿混用**。

### 2.3 容量判定

`fits(demand, load, capacity, rho)`：每个方向叠加后 ≤ `bw × (1 - rho)`。

- $\rho$（`bandwidth_headroom`，默认 0.2）是**摆放裕度**；
- 与「预测达标阈值」`utilization_limit`（默认 1.0）是**两个不同阈值**，勿混用。

### 2.4 容量账本（`flow/models.py::CapacityState`）

把「图 + 单向容量表 + 当前方向负载」打包成一个账本对象，规划期各处读同一份：

| 方法 | 用途 |
|---|---|
| `from_graph(graph)` | 按图建空账本 |
| `demand(services, path, flow_src)` | 算方向需求 |
| `add(demand)` | 累加进负载 |
| `fits(demand, rho)` | 容量判定 |
| `recompute(plans)` | 按各 flow 路径**重算**整份负载（返回新 dict，不改本账本） |
| `with_load(load)` | 换一份负载（试算候选时不污染当前账本） |

> **为什么要打包**：原先 `graph + load + cap` 三个参数在六个函数间反复传递，
> 容易出现"某处用了别的 load"。打包后容量口径只有一个来源。

## 4. 与仿真器侧的关系

仿真器自身的带宽口径与本项目**不完全一致**：

- 建 Mininet 链路时带宽经 `sdncommon._bw_mbit()` **封顶 1000Mbps**（tc 把 >1Gbps
  限到 1000Mbps）；
- `ctrl.seed_baseline_link_params()` 会用 `net-topo.json` 的原始值重新 `apply_link`；
- `/links` 的返回值又受运行期覆盖影响。

**结论**：不要只凭一处代码断言带宽，以**运行期 `/links` 与启动日志**为准。
（详见 [仿真器相关](../../simulator/仿真器相关.md) §11.2 方向性口径。）
