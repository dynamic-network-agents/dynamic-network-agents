# 感知口径与事件机制

> 定位：**`src/common/perception/` 的感知契约**——冻结快照包含什么、事件怎么来、
> 哪些事件值得重规划、事件的时间窗口与节奏。
> 关联：接口语义见 [接口清单与语义](../simulator/接口清单与语义.md)；
> 仿真器侧机制见 [仿真器相关](../../simulator/仿真器相关.md)。

---

## 1. 快照：一次冻结的规划输入

`src/common/perception/snapshot.py` 的 `SnapshotSource.fetch()` 一次性拉齐**规划所需的
全部输入**，打成 `NetworkSnapshot`：

| 字段 | 内容 | 来源 |
|---|---|---|
| `graph` | NetworkX MultiGraph（只收 up 链路 + online 节点，剔除 EXT001） | `/links` + `/topology` |
| `flows` | 按 flow（无序端点对）分组的业务 | `/services` + `/services/{id}` |
| `current_paths` | 每个 flow 现状已装路径 | `/services/{id}` 的 `path.segments` |
| `test_service_flow` | test 业务 serviceId → flow_key（校验采样范围） | 同上 + `category`/`TSV*` 前缀 |

**为什么必须冻结**：规划器是纯函数，同一快照重算必然同结果——这是闭环「不再下发」
不动点的依据。epoch 内不再回头读仿真器（批内不重算），否则会拿"自己刚造出来的
中间态"求最优。

**拉取顺序为「先业务后拓扑」**：事件轮询发生在快照之前，三者共同构成 epoch 的冻结视图。

## 2. 事件机制

### 2.1 事件类型

- `node_state_changed`：节点上下线/位置变化；payload 含 `instanceId`、`nodeId`、`state`、`position`；
- `link_state_changed`：链路参数/状态变化；payload 含 `instanceId`、`linkId`、`event`、`params`；
- `service_state_changed`：业务状态/路径变化；payload 含 `instanceId`、`serviceId`、`status`、`pathChanged`。

### 2.2 事件号

- 脚本事件：`EVT001`~`EVT999`，按计划时刻升序，同刻按脚本数组序；
- 运行期人工/API 事件：从 `EVT1000` 起自增；
- `srcEventId`：仅脚本事件派生的事件携带，指向触发它的脚本事件号。

### 2.3 注入过程（实现）

脚本引擎在 `netsim` 容器 `/opt/simulator/netsim/script_engine.py`：

1. `load()` 读取 `scripts/<script>.json`，要求非空数组，每项含 `time`、`eventType`，按 `(time, idx)` 排序并编号 `EVT001...`；
2. `start()` 记录 `self._t0 = time.time()`，启动调度线程；
3. 调度线程对每个事件等待到 `T0 + time`，调用 `api.apply(eventType, attrs, eid)`；
4. `_fire()` 记录 `planned_us`、`eff_us`，计算 `deviationMs = eff_us - planned_us`；
5. 事件类型由 `apply` 落到网络：链路参数（tc）、链路状态（up/down）、节点上下线、节点移动、业务新增；
6. 遇到 `stop` 事件结束；脚本文件热修改会触发热重载（保留已发事件）。

因此 T0 是**脚本真正开始执行时**设定的；慢启动只会推迟 T0，不会让相对 T0 的事件提前丢失。

### 2.4 事件时间窗口

| 套件 | 事件窗口 | stop |
| --- | --- | --- |
| conf01 | T0+3~26 分钟 | 1800s |
| conf02 | T0+3~26 分钟 | 1800s |
| conf04 | T0+2~27 分钟 | 1800s |

前 2~3 分钟是基线窗口；最后几分钟是收尾窗口。提前结束（自动结束分钟数小于事件时间）会漏掉后续事件。

## 3. 事件游标：时间口径

`src/common/perception/events.py` 的 `EventSource` 维护 `sinceTsUs` 游标。

- `sinceTsUs` 是仿真器事件日志**自己的**时间轴（Unix 纪元微秒，服务器时钟），
  服务端按 `event.tsUs > sinceTsUs` 严格过滤，所以只需原样回传 `nextSinceTsUs`，
  **不需要把本地时钟对齐到仿真器**。
- 启动时用 `GET /time` 的 `tsUs` 初始化游标，只是为了不从 0 开始重放历史事件
  （事件日志跨重启保留，环形 5 万条）。取不到则退化为 0（重放历史，只会多触发一次规划，
  不影响正确性）。
- 轮询、合窗、防抖等计时**一律用单调时钟**（`time.monotonic`），墙钟被 NTP 调整不影响计时。

## 4. 可行动事件过滤（防自激）

只认可行动事件：

| 事件 | 是否可行动 |
|---|---|
| `link_state_changed` | ✅ 链路状态/参数变化 |
| `node_state_changed` | ✅ 节点上下线 |
| `service_state_changed` 且 `status ∈ {stopped, failed, finished, pending}` | ✅ 业务状态变化 |
| `service_state_changed` 且 `pathChanged=true` 且 `status=running` | ❌ **自己下发产生的，忽略** |

最后一条是**硬要求**：仿真器 `_set_service_path` 收尾会 `record_service`，于是每次
下发都产生一条 `pathChanged` 事件。若不过滤，POST → 事件 → 重规划 → POST 会**自激成
死循环**。

事件成簇到达时先**合窗**（等最后一个可行动事件静默 `event_coalesce_s`）再规划，
避免一条事件簇触发多次全量规划。

## 5. 决策流程与时间管理

1. 启动后先等待 T0（页面/API 返回 `t0Time`/`t0TsUs`）；
2. T0 后前 2~3 分钟是基线窗口，先建立初始业务/路径快照；
3. 持续轮询 `/events`（≤10s），同时定期拉 `/topology`、`/links`、`/services`；
4. 对受影响业务计算候选路径并下发；
5. 用 `/services/{id}` 的 `actual.qosMeet` 复查；
6. 事件持续到约 T0+26/27 分钟，脚本在 1800s 发 stop；自动结束看门狗到点也会终止；
7. 结束后仿真写日志，测评软件自动读取；智能体不需要再提交结果。

慢环境与 T0：

- T0 由脚本引擎 `start()` 设置，发生在 TX/RX 就绪门通过之后；
- 环境慢只会推迟 T0，不会让 T0 相对事件提前触发；
- 真正会漏事件的是把自动结束设得比事件窗口短，或中途手动结束。
