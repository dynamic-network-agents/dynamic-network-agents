# 研发记录系统建设企划书

> 项目：B03 资源受限环境下通信网络资源管控\
> 文档版本：V1.0（讨论稿）\
> 建设阶段：第一阶段------静态实验记录与问题关联

## 1. 建设背景

项目研发过程涉及仿真场景理解、网络与业务参数分析、算法调试、智能体联调和实验评估。每次调试通常都依赖特定的场景套件、场景实例、脚本、拓扑、业务配置及代码版本。如果这些信息仅存在于开发人员的终端、临时笔记或聊天记录中，后续容易出现以下问题：

-   无法快速确认某个问题出现时使用了哪套场景、哪个脚本及哪一版输入数据；
-   相同问题在不同实验中重复出现，缺少统一的问题编号和关联关系；
-   实验结果与问题分析分散，难以判断某次修改是否真正解决问题；
-   难以复现实验，也难以积累可供后续算法、Agent、RAG 和 Skill
    使用的工程经验。

因此，拟建设一套轻量级研发记录系统，将实验记录、问题清单和二者之间的关联统一管理。第一阶段优先实现静态场景数据自动导入和研发上下文自动关联，不追求一次性建设完整平台。

## 2. 建设目标

### 2.1 总体目标

建立"实验记录---问题记录---关联关系"三位一体的研发知识记录机制，使每次实验有据可查、每个问题有源可溯、每项修复有实验验证。

### 2.2 第一阶段目标

1.  **实验自动导入**：从仿真环境现有场景目录读取静态 JSON
    和统计文件，生成标准化实验定义记录。
2.  **输入快照与版本追溯**：记录源文件路径、文件哈希、导入时间和必要的场景元数据，避免仅凭文件名判断场景是否相同。
3.  **问题规范记录**：提供统一的问题模板，支持人工填写现象、预期、复现步骤、原因、修复和验证结果。
4.  **上下文自动填充**：创建问题时自动带入当前实验、场景套件、场景实例、脚本和
    Git 版本等已能获取的信息。
5.  **实验与问题关联**：支持一个问题关联多个实验、一个实验关联多个问题，并记录关联类型及确认状态。
6.  **相似问题提示**：第一版根据场景标识、模块、标签和关键词进行规则匹配，给出候选问题，由开发人员确认，避免未经确认的错误合并。

### 2.3 暂不纳入第一阶段的内容

-   仿真运行期间的 API 事件、网络状态、业务 QoS 和路径变化自动采集；
-   自动分析根因、自动生成修复方案；
-   LLM 语义检索、RAG、Skill 自动生成；
-   完整 Web 管理后台、复杂权限系统和多用户协同平台；
-   自动修改官方仿真器及其生成工具。

上述内容可在静态记录稳定后分阶段扩展。

## 3. 设计原则

1.  **先静态、后动态**：第一阶段只处理可从场景文件直接读取的数据。
2.  **自动采集、人工判断**：工具负责导入、填充、编号和关联建议；研发人员负责问题定性、原因分析和结论确认。
3.  **实验定义与运行实例分离**：静态场景组合属于实验定义，不虚构仿真运行
    ID。未来真正启动仿真后，再为每次运行生成独立 Run 记录。
4.  **原始证据不可覆盖**：自动导入的源文件快照和哈希应保留；源数据变化时生成新的定义版本，不静默覆盖旧记录。
5.  **关联关系独立管理**：问题与实验采用多对多关系，关联信息由独立关系文件维护。
6.  **自动关联必须可解释**：自动匹配保存匹配依据、置信等级和是否人工确认。
7.  **不修改官方仿真环境**：记录工具作为独立工具目录运行，仿真环境按交付约定使用。

## 4. 业务对象与核心概念

### 4.1 实验定义（Experiment Definition）

第一阶段的实验定义描述一组静态实验输入，主要由以下内容构成：

-   场景套件：`suiteId`
-   场景实例：`scenarioId`
-   脚本：`scriptId`
-   初始网络拓扑：`net-topo.json`
-   初始业务配置：`bg-service.json`
-   脚本事件：`scripts/script-NN.json`
-   全局链路类型能力范围：`conf/linkTypes.json`
-   场景统计：`<场景标识>-stats.md`（如存在）

同一场景文件组合再次导入时，可识别并复用已有定义；若输入文件内容发生变化，应形成新的定义版本。

### 4.2 实验运行（Experiment Run）

实验运行是未来扩展对象，代表某次真实启动的仿真过程。运行阶段再记录
`instanceId`、`t0Time`、`t0TsUs`、运行事件、状态快照、路径调整、实际 QoS
和结果等。

第一阶段不要求创建 Run，也不把静态导入时间当作仿真运行时间。

### 4.3 问题（Issue）

问题记录研发过程中发现的缺陷、异常、性能问题、算法不足、接口理解偏差或实验异常。问题可以尚未复现，也可以关联多个实验进行排查和验证。

### 4.4 关联关系（Relation）

实验与问题之间通过独立关系记录建立联系。建议支持以下关系类型：

  关系类型          含义
  ----------------- --------------------------
  `discovered_in`   问题首次在该实验中发现
  `reproduced_in`   问题在该实验中复现
  `verified_in`     在该实验中验证修复或结论
  `regression_in`   问题在该实验中回归
  `related_to`      实验与问题存在辅助关联

## 6. 自动化工作流程

### 6.1 导入实验

开发人员指定场景套件、场景实例和脚本。工具自动：

1.  定位对应场景目录；
2.  读取拓扑、业务、脚本和链路类型配置；
3.  解析节点数、链路数、业务数、事件数、事件类型分布和事件时间范围；
4.  校验必需文件及 JSON 格式；
5.  计算各源文件 SHA-256，并生成整体 manifest 哈希；
6.  根据输入内容判断是否已有相同实验定义；
7.  生成或复用实验记录；
8.  将本次实验设为当前工作上下文。

建议命令示例：

``` bash
python tools/experiment_manager/main.py experiment import \
  --suite sce20261104-conf01 \
  --scenario sce01 \
  --script script-01
```

### 6.2 激活当前实验上下文

实验导入或选择后，将当前上下文写入
`records/context/current.json`。至少保存：

-   `experiment_id`
-   `suite_id`
-   `scenario_id`
-   `script_id`
-   `manifest_hash`
-   `activated_at`

当前上下文应明确作用范围，例如当前工作区或当前开发终端。若上下文不存在或已失效，创建问题时必须提示用户选择实验，不应猜测。

### 6.3 创建问题

开发人员通过统一入口创建问题：

``` bash
python tools/experiment_manager/main.py issue create \
  --title "链路中断后业务路径未及时切换"
```

工具自动完成：

-   分配唯一问题编号；
-   读取当前实验上下文；
-   将实验 ID、场景套件、场景实例、脚本和文件哈希写入问题记录；
-   记录当前 Git 分支和 commit（若可获取）；
-   自动建立 `discovered_in` 关系；
-   根据标题、模块和标签检索相似问题并提示。

问题现象、预期结果、复现步骤、根因和解决方案由开发人员补充。

### 6.4 相似问题关联

第一版采用规则匹配，不使用大模型。建议按以下顺序匹配：

1.  相同实验定义 ID；
2.  相同场景套件、场景实例和脚本；
3.  相同模块分类与标签；
4.  标题及描述关键词重合。

匹配结果仅作为候选。对自动推荐的关系保存 `match_reason`、`confidence` 和
`confirmed`。只有当前实验与新建问题的直接关系可以按明确上下文自动建立；历史问题的合并或关联建议需人工确认。

### 6.5 实验验证问题

问题修复后，开发人员切换到新的实验定义或重新导入变更后的场景，运行验证并将实验关联到问题，关系类型设为
`verified_in`。若再次出现同类问题，可标记 `regression_in`。

## 7. 静态数据采集范围

  ------------------------------------------------------------------------------------------------
  数据来源                   采集内容                                     用途
  -------------------------- -------------------------------------------- ------------------------
  `net-topo.json`            区域、节点、链路、节点类型、链路类型及参数   描述初始网络拓扑

  `bg-service.json`          业务 ID、类型、类别、源宿、优先级、QoS       描述业务负载
                             需求、媒体引用                               

  `scripts/script-NN.json`   相对 T0 时间、事件类型、事件属性及对象       描述动态扰动计划

  `conf/linkTypes.json`      各链路类型能力范围                           记录链路参数的约束依据

  场景 `*-stats.md`          场景统计、路径及静态 QoS 分析（如文件存在）  辅助分析和人工核对
  ------------------------------------------------------------------------------------------------

第一阶段以场景静态文件为事实来源。对于文件中没有提供的字段应留空或标记未知，不通过推测补齐。

## 8. 数据管理与版本策略

### 8.1 标识

-   实验定义：`EXP-0001`、`EXP-0002`......
-   问题：`ISS-0001`、`ISS-0002`......
-   关系：可使用关系记录 ID，或由关系管理器生成稳定唯一键。

编号由工具统一分配，不由开发人员手工指定。

### 8.2 哈希

至少计算以下哈希：

-   `topology_hash`：`net-topo.json`；
-   `services_hash`：`bg-service.json`；
-   `events_hash`：对应脚本 JSON；
-   `link_types_hash`：`linkTypes.json`；
-   `manifest_hash`：上述文件路径、文件哈希和导入规则版本组成的整体摘要。

文件名相同但内容不同，必须识别为不同输入版本。哈希应基于原始文件字节计算；如另需规范化
JSON 哈希，应单独命名，不替代原始文件哈希。

### 8.3 原始快照

导入后保留解析后的结构化快照及源文件定位信息。若项目选择复制源文件，应记录复制来源和哈希。重新导入发现内容变化时，生成新的实验定义版本，不覆盖旧记录。

### 8.4 关系记录

关系单独保存在 `relations/relations.json`，至少包含：

``` json
{
  "relation_id": "REL-0001",
  "issue_id": "ISS-0001",
  "experiment_id": "EXP-0001",
  "relation_type": "discovered_in",
  "source": "current_context",
  "match_reason": "创建问题时当前实验上下文匹配",
  "confidence": 1.0,
  "confirmed": true,
  "created_at": "YYYY-MM-DDTHH:mm:ss+08:00"
}
```

以上为字段示例，具体时间和置信度由工具实际生成，不应把示例值当成真实记录。

## 10. 实施计划

### 阶段一：数据规范与模板

-   确定实验定义、问题和关系的数据字段；
-   建立三份 Markdown 文档；
-   用一个现有场景验证字段是否足够；
-   明确文件哈希、编号和状态枚举。

### 阶段二：静态实验导入

-   实现场景目录解析；
-   生成实验定义和结构化快照；
-   实现数据统计、校验和哈希；
-   建立实验索引及查询功能。

### 阶段三：问题记录与上下文

-   实现问题创建、编号和模板生成；
-   实现当前实验上下文激活；
-   创建问题时自动填充上下文；
-   自动建立问题与当前实验的关系。

### 阶段四：关联推荐与验证

-   实现规则式相似问题检索；
-   支持人工确认和维护关系；
-   输出问题---实验关联报告；
-   使用真实开发调试流程试运行并完善。

## 11. 验收场景

建议至少通过以下验收用例：

1.  导入一个已有场景，生成实验定义及统计摘要；
2.  重复导入完全相同的文件组合，系统能够识别并复用已有定义；
3.  修改某个输入文件后重新导入，系统识别出新的内容版本且保留旧记录；
4.  激活实验后创建问题，问题自动带入实验和场景信息；
5.  在没有当前上下文时创建问题，系统明确提示选择实验，不错误关联；
6.  同一问题关联多个实验，多个问题也可关联同一实验；
7.  相似问题推荐能展示匹配依据，未经确认的推荐不会被当成已确认事实；
8.  从问题记录能够反查关联实验，从实验记录能够反查关联问题。

## 12. 后续演进方向

-   **V2：运行时记录**。接入仿真启动与公开 API，记录
    `instanceId`、`t0Time`、`t0TsUs`、事件轮询结果、网络状态、业务状态、路径设置及实际
    QoS。运行时数据应与静态实验定义关联，形成独立 Run。
-   **V3：知识沉淀**。将已验证的问题根因、解决方案和实验结论整理为知识条目；再引入语义检索、RAG、Skill
    和 Agent 辅助诊断。
-   **V4：实验分析**。支持算法版本对比、场景难度分层、回归测试、批量实验和指标可视化。

## 13. 项目约束与注意事项

1.  仿真场景脚本事件的 `time` 是相对仿真开始时刻 T0
    的秒数；静态记录应保存原始时间值，不误写为绝对时间。
2.  `linkTypes.json` 是链路类型能力范围的依据，应记录其哈希或版本信息。
3.  业务 QoS 需求与运行时 `actual`
    实测值是不同数据；第一阶段只记录静态需求，不生成或伪造实测指标。
4.  当前公开控制接口的实际控制动作是业务路径设置。带宽分配、队列调度等不能作为当前已实现的控制能力写入实验记录。
5.  静态路径 QoS 判定与运行时实际 QoS
    需要区分；未来接入运行数据时应分字段保存。
6.  仿真环境及其生成工具属于交付环境，记录工具应独立实现，避免修改官方发布件。
7.  不将令牌、密钥或其他敏感配置写入记录、日志或 Git。
