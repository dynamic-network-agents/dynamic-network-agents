# 研发记录系统：现阶段方案与后续扩展计划

> 文档类型：实施方案（手工版 V0）· 日期：2026-11-18
> 上位文档：[研发记录系统建设企划书.md](研发记录系统建设企划书.md)（完整工具化方案）
> 模板：[实验记录模板.md](实验记录模板.md)、[问题清单模板.md](问题清单模板.md)

## 1. 定位与取舍

企划书描述的是一套**可运行的工具系统**（静态导入器 + 编号分配 + 关系管理 + 相似问题推荐）。现阶段（初赛截止 12/15 前）采用**手工约定版**：只保留「实验记录 + 问题清单 + 人工关联」三件事，工具全部推迟。

**取舍依据：**

| 维度 | 完整工具化 | 手工版（现阶段） |
|---|---|---|
| 建设成本 | 数天（schema + importer + CLI + 测试） | 约半小时（模板 + 约定 + 样例） |
| 对初赛评分贡献 | 间接（评分不奖励记录工具本身） | 直接（支撑实验验证 24 / 结果分析 16 的叙事） |
| 主要风险 | 工具未完成前记录仍是空白 | 记录质量依赖人工纪律 |

**核心判断：先让记录真正发生，再考虑让记录自动化。** 记录的价值来自「写了什么」，不是「用什么工具写的」。

## 2. 现阶段方案（已落地）

### 2.1 目录与文件

记录本体放在仓库根 `experiments/`（与根 `CLAUDE.md`「场景库与结果报告」的定位一致），不新增 `records/` 顶层目录。

```
experiments/
├── README.md          # 工作流与约定（唯一操作手册）
├── index.md           # 编号登记表：EXP / ISS 两张表，占号防冲突
├── exp/               # 实验记录，一实验一文件
│   └── EXP-0001.md
└── iss/               # 问题记录，一问题一文件
    └── ISS-0001.md
```

实际操作以 [experiments/README.md](../../experiments/README.md) 为准，本文只说明方案与演进。

模板仍保留在 `docs/experiments/`，记录文件是模板的**实例**。

### 2.2 工作流（四步）

1. **占号**：在 `experiments/index.md` 对应表加一行，写下个编号 + 标题 + 日期。
2. **写实验记录**：复制实验模板 → 填场景来源与真实统计 → 存 `exp/EXP-xxxx.md`。
3. **写问题记录**：复制问题模板 → 填现象/预期/根因/修复/验证 → 存 `iss/ISS-xxxx.md`。
4. **回填 index**：把状态更新回索引表。

### 2.3 与企划书的裁剪对照

| 企划书能力 | 现阶段做法 | 理由 |
|---|---|---|
| F-01 场景目录导入 | 人工按 `suiteId/scenarioId/scriptId` 找目录 | 场景目录结构稳定，人工定位成本低 |
| F-02 静态 JSON 解析 | 一次性脚本统计后手填 | 统计口径简单，不需要常驻工具 |
| F-03 数据统计 | 手填（已用真实场景验证） | 同上 |
| F-04 文件哈希与版本识别 | 手工 `shasum -a 256`，非必填；内容变则开新 EXP 号 | 版本追溯主要交给 git |
| F-05 编号与索引 | `index.md` 手工占号 | 单人开发，撞号风险可控 |
| F-06 当前实验上下文 | 在问题记录里手填实验编号 | 无 CLI，上下文靠人记 |
| F-07/F-08 问题模板与自动关联 | 模板 + 双向手写关联字段 | 关联仅 `EXP-xxxx` + 关系类型文本 |
| F-09 相似问题推荐 | **不做** | 问题量级尚小，人工回忆足够 |
| F-10 关系维护与查询 | **不做独立关系表** | 用两个模板里的「关联实验/关联问题」字段替代 |
| F-11 汇总报告 | **不做** | 最终由《结果分析报告》人工汇总 |

### 2.4 现阶段硬约束

- **不虚构运行数据**：未真正启动仿真，`instanceId` / `t0TsUs` / 实测 QoS / `qosMeet` 一律留空或标「V2 预留」。
- **事实与推断分离**：实测值、静态需求、分析结论分栏；假设标注为假设。
- **不记录敏感信息**：令牌、密钥不入记录、日志、git。
- **原始时间原样保存**：脚本事件 `time` 是相对 T0 的秒数，不转绝对时间。
- **缺失即留空**：查不到的字段写「—」或「未知」，不填 0 冒充事实。
- **不修改仿真器发布件**：记录工作不触碰 `simulator/` 下的任何文件，只读取场景数据。

### 2.5 已知不足（接受）

- 编号依赖人工纪律，多人并行时有撞号可能（当前单人不构成问题）。
- 关联散落在两份记录中，无全局反查视图。
- 统计字段需人工抄录，存在抄错风险（已用真实场景核对一次样本）。
- 无相似问题提示，重复问题可能被重复创建。

## 3. 后续扩展计划

升级不是按时间排，而是**按触发条件**启动，避免过早工具化。

### V1.5 轻量脚本辅助（触发：手工抄录连续出错，或实验数 ≥ 10）

- 一个只读统计脚本：给定 `suiteId/scenarioId`，输出节点/链路/业务/事件统计的 Markdown 片段，粘贴进实验记录。
- 仍不写记录文件、不分配编号，避免形成第二套数据源。
- 预计落位：`tools/experiment_manager/`（企划书目录），或先放 `experiments/scripts/`。

### V2 静态导入工具（触发：实验数 ≥ 30，或开始多人协作）

- 实现企划书 F-01～F-06：场景目录定位、JSON 解析、统计、哈希、编号分配、当前上下文。
- 生成 `experiments/exp/EXP-xxxx.md` 结构化初稿，人工补充实验设计部分。
- 编号分配权从 `index.md` 手工占号迁移到工具，索引改为工具生成（只读）。

### V3 关联管理（触发：需要回答「某问题在哪些实验出现过」「某实验波及哪些问题」）

- 引入 `relations/relations.json`（企划书 §8.4 结构），支持 `discovered_in` / `reproduced_in` / `verified_in` / `regression_in` / `related_to`。
- 增加关系查询命令与双向反查视图。
- 迁移策略：从现有两份记录里的关联字段**一次性抽取**生成，不重新人工录入。

### V4 运行时记录（触发：仿真稳定跑通、能连续采集）

- 接入公开 API，记录 `instanceId` / `t0Time` / `t0TsUs` / 事件轮询 / 路径调整 / 实测 QoS。
- 为每次真实启动建立独立 Run 记录，与静态实验定义关联。
- **前置条件**：`POST /simulation/start` 实际可用（当前镜像未实现，需走 UI 的 `/sdn-ui/start`），或明确由外部启动后只读接入。

### V5 知识沉淀（触发：问题记录 ≥ 50 且已有重复模式）

- 将已验证根因/解决方案整理为知识条目，再评估 RAG / Skill / Agent 辅助诊断。
- 相似问题推荐（企划书 F-09）在此阶段以规则匹配起步，不先上大模型。

### 演进路线总览

```
V0 手工版（当前）
 └─▶ V1.5 只读统计脚本
      └─▶ V2 静态导入 + 自动编号
           ├─▶ V3 关联管理（relations.json）
           └─▶ V4 运行时记录（依赖 API 可用）
                └─▶ V5 知识沉淀 / 相似问题推荐
```

## 4. 升级时的迁移原则

1. **记录只增不改**：旧 EXP/ISS 文件保持原样，工具不得静默覆盖或重新编号。
2. **单一事实源**：编号与索引只能有一个维护者（手工期是人，工具期是工具）。
3. **不制造并行系统**：新工具必须就地读写 `experiments/` 现有结构，不新建 `records/` 副本。
4. **先验证再推广**：每个版本先在一个真实场景/问题上跑通（如 EXP-0001、ISS-0001），再全面使用。
5. **与初赛节奏对齐**：V2 及以后安排在初赛提交（12/15）之后，除非记录量先到达触发条件。
