## 0. 建模对象与边界（先定死"能做什么"）

**唯一控制手段 = 重路由**：`POST /services/{serviceId}/path`。公开接口没有带宽分配、队列调度、准入控制、跳频等动作，一切决策最终只能归约为"为业务（flow）选择一条端到端路径"。

由此产生的三条硬性建模约束：

1. **flow 级路径共享**：`_flow_for(src,dst)` 按源/目的 IP 键控，且匹配**无序对**（A→B 与 B→A 是同一 flow）；同一对 UAV 之间的所有业务（含 `background` 与 `test`）**共用同一条路径**。优化单位不是 `service`，而是 `flow`（源-目 UAV 对）。
2. **双重 QoS 口径**：路径提交时用**静态路径 QoS**（拒绝不满足者，错误码 1004）；运行时评分用**实测 QoS**（`actual.qosMeet`）。静态通过 ≠ 实测达标，两者必须分别建模并建立"预测—执行—测量—反馈"闭环。
3. **只保 test，background 作杠杆**：评分只认 `test` 业务的 `qosMeet`，`background` 不计分、只作负载/让路对象。**保护对象限定为 test**；test/background 分类需内部 `/api/ctrl/v1/svc-meta`（`ctrlToken`），拿不到时用 `serviceId` 前缀 `TSV*` 或统一保护兜底。

**建模目标函数（一句话）**：在动态扰动下，为每条 flow 选择一条满足其全部业务 QoS 硬约束的路径，使"业务保障率"最高、路径切换代价与链路资源竞争代价最小。

## 2. 网络图模型 $G(t)$

**定义**：时变无向加权图 $G(t)=(V,E(t))$。$V$ 固定（节点集合由场景生成），$E(t)$ 随时间随事件变化——链路可 `up`/`down`，链路参数可劣化（`link_param_change`），节点可下线（`node_offline`，连带其邻接链路失效）。

**图的构建规则（关键，直接决定路径合法性）**：
- 只有 `status=up` 的链路进入 $E(t)$；
- 链路两端节点必须 `status=online`；
- 业务源/目的节点只可能是 `uav`；`ground`/`air` 只作转发；
- `EXT001` 是外部引接点，业务路径永不穿越它，构建图时剔除。

**数据来源**：`GET /topology`、`GET /links`、`GET /nodes`、`GET /events`（增量更新）。

**代码映射**：`src/algorithms/graph.py::build_graph()` → 返回 NetworkX `MultiGraph`（并行链路用 `MultiGraph` 而非 `Graph`，因为两点间可能存在多条不同 `linkId` 的链路）。

## 3. 链路质量模型

### 3.1 链路五项指标

| 指标 | 符号 | 单位 | 端到端合成方向 |
| --- | --- | --- | --- |
| 时延 | $d_e$ | ms | 累加 |
| 抖动 | $j_e$ | ms | 平方和开根 |
| 带宽 | $b_e$ | bps | 取最小值（瓶颈） |
| 误码率 | $\varepsilon_e$ | 无量纲 | 近似累加 |
| 丢包率 | $p_e$ | 无量纲(0~1) | 乘积合成 |

### 3.2 归一化（用于软代价，**不用于硬约束**）

五类指标量纲差异巨大（时延 vs 误码率），综合代价前必须归一化到 $[0,1]$。归一化基准取 `conf/linkTypes.json` 的**链路类型取值区间**（这是唯一权威源）：

$$
\hat{d}_e = \frac{d_e - d_{\min}(\tau)}{d_{\max}(\tau) - d_{\min}(\tau)},\quad
\hat{j}_e = \frac{j_e - j_{\min}(\tau)}{j_{\max}(\tau) - j_{\min}(\tau)}
$$

其中 $\tau=\text{linkType}(e)$，$[d_{\min},d_{\max}]$ 为该类型时延区间。带宽是**越大越好**，取反向指标：

$$
\hat{b}_e = \frac{b_{\max}(\tau) - b_e}{b_{\max}(\tau) - b_{\min}(\tau)}
$$

丢包率、误码率同类归一化（正向，越小越好）：$\hat{p}_e$、$\hat{\varepsilon}_e$ 按各自类型区间线性映射到 $[0,1]$。

> **工程要点**：归一化只用于"可行路径之间的排序"，**绝不**用于 QoS 判定。QoS 判定只用原始物理量（第 5 节），否则会造成量纲污染、误判约束。

### 3.3 链路综合代价

$$
c_e = w_d \hat{d}_e + w_j \hat{j}_e + w_b \hat{b}_e + w_p \hat{p}_e + w_\varepsilon \hat{\varepsilon}_e,\quad \sum_k w_k = 1,\ w_k\ge 0
$$

路径代价为逐跳累加：$C(P) = \sum_{e\in P} c_e$。

> 默认权重建议 $w_d=0.4,\ w_j=0.15,\ w_b=0.25,\ w_p=0.1,\ w_\varepsilon=0.1$，在实验 E08 做敏感性分析。权重放在 `config/qos_weights.yaml`，运行时可调。

**代码映射**：`src/math_modeling/link_quality.py::link_cost(link, weights)`（单链路）、`path_cost(link_ids, graph, weights)`（路径累加）；归一化在模块内 `_normalize` / `_normalize_bandwidth`，基准取 `linkTypes.json` 类型区间。

## 4. 端到端 QoS 合成模型（双口径，精确对齐仿真器）

### 4.1 静态路径 QoS（下发校验口径）

设路径 $P=(e_1,\dots,e_n)$，各链路参数为 $(d_i,j_i,b_i,p_i,\varepsilon_i)$：

$$
D(P)=\sum_{i=1}^n d_i,\qquad
J(P)=\sqrt{\sum_{i=1}^n j_i^2},\qquad
B(P)=\min_{i} b_i
$$

$$
L(P)=1-\prod_{i=1}^n (1-p_i),\qquad
E(P)\approx \sum_{i=1}^n \varepsilon_i
$$

> 误码率 $E(P)\approx\sum\varepsilon_i$ 是**小误码率近似**（$\varepsilon_i\ll 1$ 时 $1-\prod(1-\varepsilon_i)\approx\sum\varepsilon_i$），本场景 $\varepsilon_i\le 10^{-3}$ 量级，近似误差可忽略，但与仿真器逐项核对过，口径一致。

### 4.2 实测 QoS（运行时评分口径）

来自 `servicesim-rx` 逐秒统计，字段与量纲：

| 字段 | 含义 | 量纲 |
| --- | --- | --- |
| `avgDelayMs` | 收包单向时延平均 | ms |
| `jitterMs` | RFC3550 平滑估计 | ms |
| `effBwBps` | $\min(\text{发送速率},\text{接收速率})$ | bps |
| `errPct` | 无效包/收包 $\times 100$ | % |
| `packetLossRate` | $(\text{期望}-\text{结算})/\text{期望}$ | 0~1 |

**静态 vs 实测 差异点（建模必须写清楚）**：
- 抖动：静态用 RMS 合成 $\sqrt{\sum j_i^2}$，实测用 RFC3550 递推平滑；
- 带宽：静态取瓶颈链路参数，实测取实际端到端吞吐（受 tc 限速、拥塞、TCP 行为影响）；
- 丢包/误码：静态用链路参数合成，实测用真实报文统计。

结论：静态模型负责"哪些路径会被 API 接受"；实测模型负责"路径到底行不行"。两者缺一不可。

**代码映射**：`src/math_modeling/path_qos.py::compose_qos(path, graph) -> QoSMetrics`（静态）、`src/math_modeling/measured_qos.py`（实测）。

> **qosMeet 的时序口径（读之前要等稳态）**：`actual` 是「最近 1 秒」逐秒快照。默认 `settle_ms=300`（在途 ≤300ms 的包不计丢包）；首秒无序号基线，接收端把首秒丢包强置 0；加上 TBF 队列与 OVS 流表进入稳态、媒体首文件的开销，**启动/换路后应 ≥30~60s 再读**，并连续读多秒看趋势（95% 边缘的业务会抖），不要拿单秒快照下结论。

## 5. 业务 QoS 约束模型

### 5.1 静态判定（提交前自检 + 预测 API 是否 1004）

对业务 $s$，其需求 $(D_s^{\max},J_s^{\max},B_s^{\min},L_s^{\max},E_s^{\max})$，路径 $P$ 满足静态 QoS 当且仅当：

$$
D(P)\le D_s^{\max}+1.0,\quad
J(P)\le J_s^{\max}+10^{-9},\quad
B(P)\ge B_s^{\min}
$$

$$
L(P)\le L_s^{\max}+10^{-9},\quad
E(P)\le E_s^{\max}+10^{-12}
$$

> 容差 $+1.0$ms（时延）、$+10^{-9}$、$+10^{-12}$ 是仿真器硬编码的容差，建模时**必须原样保留**，否则自检与仿真器判定不一致会导致误提交或漏提交。

### 5.2 flow 级可行约束（关键：多业务共用路径）

flow $f$ 内多个业务共用路径 $P_f$，则 $P_f$ 必须同时满足 $S_f$ 中**每个**业务的约束，等价于满足"最严格需求"的交集：

$$
D(P_f)\le \min_{s\in S_f} D_s^{\max},\qquad
J(P_f)\le \min_{s\in S_f} J_s^{\max},\qquad
B(P_f)\ge \max_{s\in S_f} B_s^{\min}
$$

$$
L(P_f)\le \min_{s\in S_f} L_s^{\max},\qquad
E(P_f)\le \min_{s\in S_f} E_s^{\max}
$$

定义 flow 需求向量 $R_f = \left(\min D^{\max},\ \min J^{\max},\ \max B^{\min},\ \min L^{\max},\ \min E^{\max}\right)$，则 flow 可行判定退化为单业务判定：

$$
\boxed{\ \text{feasible}(P_f, f) = \bigwedge_{k=1}^5 \big[\text{metric}_k(P_f)\ \text{满足}\ R_f^{(k)}\big]\ }
$$

**代码映射**：`src/math_modeling/qos_checker.py::check_qos(path_qos, requirement) -> {feasible, violations[], margin{}}`；`src/math_modeling/flow.py::group_services_by_flow()`。

### 5.3 裕度（margin）与鲁棒性

对每条可行路径，计算每项指标的**剩余裕度**，用于排序与风险预测：

$$
m_D = D^{\max}-D(P),\quad
m_B = B(P)-B^{\min},\quad
m_L = L^{\max}-L(P),\quad \dots
$$

路径稳健度 = $\min_k$（归一化后的 $m_k$）。裕度越大的路径，对后续扰动越不敏感。带宽裕度 $m_B$ 尤其重要——两条路径都可行时，优先选带宽余量大的（后续多 flow 挤占时更不易违约）。

## 6. 路径优化模型

### 6.1 单 flow 最优路径（精确可解）

决策：在候选集 $\mathcal{P}_f$ 中选路径。$\mathcal{P}_f$ 由 K-最短路径生成（第 7 节）。

$$
\min_{P\in\mathcal{P}_f}\ C(P)\quad \text{s.t.}\ \text{feasible}(P,f)=\text{true}
$$

即：先 QoS 硬过滤，再按综合代价升序取第一条。无可行解则返回 `None` 并告警（不要退化成 best-effort 违规路径）。

**复杂度**：K-最短路径 $O(K\,|V|(|E|+|V|\log|V|))$ + 每条路径一次 QoS 合成 $O(|P|)$。

### 6.2 多 flow 联合优化（共享带宽竞争）

单 flow 局部最优可能把多个高带宽 flow 挤到同一瓶颈链路，导致实测带宽掉线（静态判定不查跨 flow 竞争，但实测会违约）。因此加**共享容量约束**。

**先修正一个口径**：链路带宽由 `tc tbf rate=bw` 实现，且 `apply_link` 对链路**两端各挂一个** `rate=bw` 的 TBF，所以链路是**全双工**的——A→B 与 B→A 是**两个独立令牌桶**。容量约束必须**按方向**记账，不能把两方向加总后对一个 $b_e$：

$$
\sum_{f:\ e\in P_f,\ \text{dir}} \mathrm{dem}_f(\text{dir}) \ \le\ b_e \cdot (1-\rho),\qquad \forall e\in E,\ \forall\text{dir}\in\{A\to B,\ B\to A\}
$$

其中 $\mathrm{dem}_f(\text{dir})$ 是 flow $f$ 在该方向上经过 $e$ 的**全部业务带宽之和**（含 test 与 background）：

$$
\mathrm{dem}_f(\text{dir}) = \sum_{s\in S_f:\ s\ \text{沿该方向经过}\ e} B_s^{\min}
$$

> **与 §5.2 的区别（关键，勿混用）**：$R_f$ 的带宽取 $\max$ 是**静态 QoS 判定**的需要（路径瓶颈要压住最大的单业务）；而**容量记账**要用**求和**（同 flow 多业务叠加在同一链路上，负载相加）。两者口径不同。

**硬约束 vs 软约束**：

- **接入链路（UAV–GND 最后一跳）上的容量是硬约束**：每个 UAV 基本只有一条像样接入链路，背景业务目的 UAV 固定、只能走这条链路；当 test 业务单独就超容时，**重路由无解**。这类 flow 记为 F1（见 §6.5）。
- **骨干链路（gnd–gnd）上的容量是软约束**：可通过把纯背景 flow 绕到其他骨干链路来缓解，允许轻微超载（$\rho$ 作裕度）。

联合优化目标（多商品流 + QoS 侧约束，NP-hard）：

$$
\min_{\{P_f\}} \sum_{f\in F} \alpha_f\, C(P_f)
$$

$$
\text{s.t.}\quad \text{feasible}(P_f,f)=\text{true}\ (\forall f),\quad
\sum_{f:e\in P_f,\text{dir}}\mathrm{dem}_f(\text{dir})\le b_e(1-\rho)\ (\forall e,\forall\text{dir})
$$

其中 $\alpha_f$ 为 flow 权重（由业务优先级聚合，见 6.4）。该问题精确求解用整数规划（`pulp`/`ortools`），工程上用**贪心顺序分配 + 局部搜索**近似（第 7.3 节）。

> **建模边界**：静态路径下发 API **不检查**跨 flow 容量约束（它只按单路径逐业务查 QoS），所以上式是**智能体自己加的预测约束**，不是 API 的硬约束。工程上它应作为"目标/启发式"，骨干段必要时允许轻微超载；但**接入段的硬约束不可放宽**。

### 6.3 动态重路由与切换代价

事件触发后重优化，目标加入**切换惩罚**抑制频繁抖动：

$$
\min_{\{P_f\}} \sum_f \alpha_f\, C(P_f) + \lambda\sum_f \mathbb{1}\!\left[P_f \ne P_f^{\text{old}}\right]
$$

引入**切换门槛（hysteresis）**：仅当满足以下任一条件才切换：

1. 当前路径失效（含链路 down、节点 offline）；
2. 当前路径实测 QoS 违约（`actual.qosMeet=false`）；
3. 存在替代路径使综合代价降低超过阈值 $\Delta_{\min}$（避免无意义微调）。

否则**保持原路径**。这直接对应"路径切换是否有必要"的决策点。

### 6.4 优先级与权重

服务 `priority∈[1,8]`（只读）。flow 权重由业务优先级聚合，建议：

$$
\alpha_f = \sum_{s\in S_f} 2^{\,\text{priority}(s)} \cdot \mathbb{1}[s.\text{category}=\text{test}]
$$

即：只对 `test`（计分）业务加权，指数放大高优先级业务。`background` 业务不参与权重，仅在"为 test 让路"时被动重路由。

> **优先级方向（已定按现状，等官方确认）**：官方赛题/接口文档只把 `priority` 当字段列出（如 `priority:6`），**没有定义 1 高还是 8 高**。本项目**按现状采用 8 最高、1 最低**（$2^{\text{priority}}$ 指数放大）建模，**等后续官方确认**；若官方口径相反，权重方向需整体翻转。

### 6.5 硬不可行识别（F1/F2/F3 分类）

分配前先给每个 flow 分类，避免把动作浪费在物理不可能的目标上：

| 类 | 判据 | 处理 |
| --- | --- | --- |
| **F1 硬不可行** | 端点接入链路**纯 test** 方向需求 > 容量 | 标 `sacrifice`，不投入动作；报告单列 |
| **F2 背景诱因** | test-only 放得下，但 test+background 超容 | 尽力保 test（背景让路/牺牲），不保证 |
| **F3 可行** | 全放得下 | 正常分配 |

「接入链路」指 UAV–GND 的最后一跳。每个 UAV 基本只有一条像样接入链路（本场景 UAV0001 只有 L00017），背景业务目的 UAV 固定，**绕不开**这条链路，所以 F1 是**物理容量墙**，不是路由问题。

> 本场景（sce20261010-conf02/sce01）实测：test-only 最高只占接入链路 60%，但 test+background 把 UAV0001 入向推到 143%、UAV0003 入向推到 146%，F1 集中在这几台 UAV 的 test 业务上。

## 7. 求解算法（可直接编码）

### 7.1 候选路径生成：K-最短路径（Yen 算法）

```text
function candidate_paths(G, s, t, K):
    paths = []
    # 用 NetworkX shortest_simple_paths（Yen's K-shortest，无环）
    for p in nx.shortest_simple_paths(G, s, t, weight="delay"):
        paths.append(p)
        if len(paths) == K: break
    return paths
```

- 权重用 `delay`（时延）作为第一启发式；K 建议 $30\sim 100$（网络规模而定，实验 E09 标定）。
- 只在 `status=up` 链路上搜；两端节点须 online；剔除 EXT001。

**代码映射**：`src/algorithms/k_shortest_paths.py`。

### 7.2 单 flow 优化伪代码

```text
function optimize_flow(G, f, weights):
    cand = candidate_paths(G, f.s, f.t, K)
    feasible = []
    for P in cand:
        qos = compose_qos(P, G)              # 静态五项
        ok = check_qos(qos, R_f)             # flow 需求 R_f
        if ok: feasible.append((cost(P), margin(P), P))
    if feasible is empty: return None        # 报告无可行路径
    sort feasible by (cost asc, margin desc) # 代价优先，裕度次之
    return feasible[0].P
```

### 7.3 多 flow 联合优化（贪心 + 局部搜索）

```text
function optimize_all(G, F, weights, rho):
    order = sort F by alpha_f desc          # 高权重 flow 优先占路
    residual_b[e] = b_e * (1 - rho)         # 每链路剩余容量
    assign = {}
    for f in order:
        cand = candidate_paths(G, f.s, f.t, K)
        # QoS 硬过滤 + 剩余容量软过滤
        valid = [P for P in cand if feasible(P,f)
                 and all(residual_b[e] >= B_f for e in P)]
        if valid empty: valid = [P for P in cand if feasible(P,f)]  # 允许轻微超载
        P* = argmin over valid of cost(P)
        assign[f] = P*
        for e in P*: residual_b[e] -= B_f
    # 局部搜索：随机扰动 1~2 条 flow，若总代价下降则接受（若干轮）
    return assign
```

**代码映射**：`src/algorithms/flow_planner.py`（待建；本方案的落地点，见 `docs/task_split/flow_planner_task.md`）。

### 7.4 动态重路由主循环

```text
loop:
    ev = poll_events(since)               # GET /events，≤10s 轮询
    update G, links, services from ev     # 增量更新 + 版本号
    affected = flows_with(failed_path or qos_violation)
    if affected empty and no significant gain: continue
    new_assign = optimize_all(G, affected, ...)
    for f in affected:
        if switch_worth_it(f, new_assign[f], delta_min): 
            submit_path(f, new_assign[f]) # POST /services/{id}/path
    sleep 1s
```

**代码映射**：`src/baseline/reroute_loop.py`（`Orchestrator.step/run`）+ `src/api/executor.py`（`PathExecutor.execute`）。

## 10. 落地优先级与验证闭环

按依赖顺序分三批落地，每批有可独立验收的产物：

1. **P0（数学内核）**：$G(t)$ + 链路代价 + 静态 QoS 合成 + QoS 判定。**验收**：给定人工路径，五项指标与仿真器 `_compose_qos` 一致，判定结果与 API 1004 一致。
2. **P1（优化）**：K-最短 + 单 flow 优化 + flow 分组 + 多 flow 贪心 + 切换门槛。**验收**：三类扰动（节点下线/链路中断/链路劣化）下自动算出可行替代路径并成功下发。
3. **P2（增强）**：共享容量约束 $\rho$、优先级权重 $\alpha_f$、局部搜索、参数敏感性实验。**验收**：多业务竞争场景下 test 保障率高于无协同基线。

**统一闭环（贯穿全部）**：

$$
\boxed{\ \text{网络建模}\ G(t)\ \rightarrow\ \text{链路评价}\ c_e\ \rightarrow\ \text{QoS 合成与判定}\ \rightarrow\ \text{路径优化}\ \rightarrow\ \text{动态重路由}\ \rightarrow\ \text{实测反馈}\ \rightarrow\ (\text{回到网络建模})\ }
$$

> 本文所有"可实施"结论均以 `simulator/conf/linkTypes.json`（链路参数权威源）、`docs/competition_desc/仿真软件接口.md`（接口权威）、`docs/agents/智能体设计文档.md`（两套 QoS 核实）为准，公式与容差已逐项对齐仿真器真实判定口径。
