# sce01 无脚本场景：静态可达性与最优 flow 摆法

> 分析日期：2026-11-25
> 场景：`simulator/data/scenarios/sce20261010-conf02/sce01`（40 条业务 / 17 个 flow / 10 条 test）
> 复现：`PYTHONPATH=src .venv/bin/python scripts/feasible_bound.py simulator/data/scenarios/sce20261010-conf02/sce01`
> 口径：**无脚本 = 零事件的静态场景**（`仿真软件接口.md:167` 一次测试实例只跑一个脚本；
> 不带 `scriptId` 时不加载脚本引擎，见 `仿真器相关.md` §11.5⑤）。因此本文所有数字都是**稳态**结论。

---

## 0. 结论摘要

| 问题 | 答案 |
| --- | --- |
| 最多几条 test 业务能达标？ | **5 / 10**（可证明的上界，且可达） |
| 上界由什么决定？ | 每个 UAV 只有一条可用接入链路 → **接入段方向负载与路由无关** |
| 哪 5 条物理不可达？ | TSV0002 / 0005 / 0006 / 0007 / 0008（全部端点在 UAV0001） |
| 生成器基线（`paths[0]`）达标几条？ | **3 / 10** |
| 当前规划器达标几条？ | **5 / 10**（命中上界） |
| 600 次随机搜索的最优？ | **5 / 10**（命中上界，与规划器同解集） |

**一句话**：这个场景的天花板不是选路问题，是**背景业务把 UAV0001 的接入链路压满了**；
重路由能做的（把 3 条提到 5 条）已经做完，剩下的 5 条在不改拓扑/不停业务的前提下无解。

> 跨场景对照见 §7：同一个方法在 conf02/sce05 上给出的上界是 46/50，但实际只做到 7~8——
> 说明接入段上界**只在接入段是瓶颈时才紧**，sce05 的瓶颈在骨干。

## 1. 前提（哪些是可证明的）

| 前提 | 依据 |
| --- | --- |
| 路径按 flow（无序端点对）共享，同对 UAV 的业务共用一条路径 | `sim_src/netsim/openapi.py` 的 `_flow_for`（`仿真器相关.md` §10.1 已核实） |
| 每个 UAV 只有一条可用接入链路 | 场景数据 `net-topo.json`：7 个 UAV 各只有 1 条 >1Mbps 的邻接链路（UAV0001 另有 L00018 是 42kbps 的 VHF，不可承载业务流量） |
| 接入链路上某方向的总负载 = 该方向所有业务需求之和 | 由上两条推出：路径是**简单路径**（Yen / BFS 只产不重复节点的路径），所以每条业务在任一 UAV 的接入链路上至多经过一次，该方向的总和与绕行方式无关 |
| 带宽是**按方向**独立的令牌桶（A→B 与 B→A 互不争抢） | `sim_src/netsim/ctrl.py` `apply_link` 给链路两端各挂一个 `rate=bw` 的 TBF（`仿真器相关.md` §2.4） |
| 一条业务在接入段被压住就不可救 | TBF 是共享令牌桶：方向负载 >100% 时按比例丢包，而背景业务终点固定、绕不开该接入链路 |
| `qosMeet` 需要五项全部满足 | `sim_src/servicesim/servicesim/core.py` 的 `qos_meet`（`智能体设计文档.md` §248-§253） |

**本文"达标"的定义是模型口径**：一条 test 业务达标 ⇔ 它**自身方向**上所经每条链路的利用率 ≤ 100%。
这是容量维度的可达成上界，**不含**排队时延、抖动、丢包对实测 `qosMeet` 的影响（见 §6）。

## 2. 接入段上界（与路由无关）

| UAV | 接入链路 | 容量 | 出向需求 | 出向 | 入向需求 | 入向 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| UAV0001 | L00017 微波 | 29M | 31.5M | **109%** | 41.5M | **143%** |
| UAV0002 | L00019 微波 | 20M | 13.2M | 66% | 15.9M | 79% |
| UAV0003 | L00021 微波 | 23M | 21.9M | 95% | 33.6M | **146%** |
| UAV0004 | L00023 5G | 31M | 13.4M | 43% | 24.6M | 79% |
| UAV0005 | L00025 5G | 25M | 14.4M | 58% | 4.3M | 17% |
| UAV0006 | L00027 5G | 28M | 26.6M | 95% | 2.4M | 8% |
| UAV0007 | L00029 微波 | 26M | 20.8M | 80% | 19.5M | 75% |

### 2.1 逐条 test 业务判定

| 业务 | 方向 | 优先级 | 类型 | 接入段（出/入） | 结论 |
| --- | --- | ---: | --- | --- | --- |
| TSV0001 | UAV0003→UAV0007 | 2 | data | 95% / 75% | ✓ 可达 |
| TSV0002 | UAV0004→**UAV0001** | 2 | video | 43% / **143%** | ✗ 入向超容 |
| TSV0003 | UAV0003→UAV0002 | 5 | image | 95% / 79% | ✓ 可达 |
| TSV0004 | UAV0002→UAV0007 | 7 | data | 66% / 75% | ✓ 可达 |
| TSV0005 | UAV0002→**UAV0001** | 3 | data | 66% / **143%** | ✗ 入向超容 |
| TSV0006 | **UAV0001**→UAV0004 | 4 | video | **109%** / 79% | ✗ 出向超容 |
| TSV0007 | **UAV0001**→UAV0006 | 5 | voice | **109%** / 8% | ✗ 出向超容 |
| TSV0008 | UAV0006→**UAV0001** | 8 | video | 95% / **143%** | ✗ 入向超容 |
| TSV0009 | UAV0005→UAV0006 | 4 | data | 58% / 8% | ✓ 可达 |
| TSV0010 | UAV0006→UAV0007 | 6 | image | 95% / 75% | ✓ 可达 |

**上界 = 5 条**：5 条不可达的业务全部端点在 UAV0001，且分别卡在该 UAV 的出向（109%）与入向（143%）上。
UAV0003 的入向 146% 同样危险，但没有 test 业务的目的地是 UAV0003，所以不触发。

> 这 5 条不可达的业务恰好是**决策文档 §6 里那组"F2 硬失败"**（5 条 test 落在 3 个 flow 上）。
> 注意这是 **F2**（test+bg 超容），不是 F1（纯 test 超容）——本场景 F1 为空集，纯 test 最高只到 60%。

### 2.2 flow 级视角

5 条不可达业务落在 **3 个 flow** 上（`UAV0001↔UAV0002` / `UAV0001↔UAV0004` / `UAV0001↔UAV0006`）；
5 条可达业务恰好落在 **5 个不同的 flow** 上（3 个混合 + 2 个纯 test），每个 flow 各 1 条 test。
所以"达标 5 条 test"与"达标 5 个 flow"在此场景等价，不存在"一个 flow 里部分达标"的模糊地带。

## 3. 可达集的最优 flow 摆法

对每个 flow 枚举静态可行候选（3~23 条），做随机重启贪心 + 局部改进（600 次，seed=7），
最优稳定落在 **5/10**，与 §2 的上界一致 → **5 是可达的最优值**。

| flow | 含 test | 路径 | 判定 |
| --- | --- | --- | --- |
| UAV0003↔UAV0007 | TSV0001 (p2) | L00021 > L00007 > L00002 > L00029 | 达标 |
| UAV0002↔UAV0003 | TSV0003 (p5) | L00019 > L00012 > L00015 > L00006 > L00005 > L00021 | 达标 |
| UAV0002↔UAV0007 | TSV0004 (p7) | L00019 > L00012 > L00015 > L00001 > L00029 | 达标 |
| UAV0005↔UAV0006 | TSV0009 (p4) | L00025 > L00015 > L00013 > L00027 | 达标 |
| UAV0006↔UAV0007 | TSV0010 (p6) | L00027 > L00010 > L00009 > L00015 > L00001 > L00029 | 达标 |
| UAV0001↔UAV0002 | TSV0005 (p3) | L00017 > L00015 > L00012 > L00019 | 接入段 143%，不可达 |
| UAV0001↔UAV0004 | TSV0002, TSV0006 | L00017 > L00015 > L00009 > L00010 > L00023 | 同上 |
| UAV0001↔UAV0006 | TSV0007, TSV0008 | L00017 > L00015 > L00013 > L00027 | 同上 |

**最优解不唯一**：搜索与规划器给出的 5 条达标集合相同，但 TSV0001 与 TSV0010 的具体走法不同
（搜索走 `L00021 > L00007 > L00002 > L00029`，规划器走 `L00021 > L00005 > L00006 > L00001 > L00029`）。
说明达标集合是稳定的，而**具体路径是多解的**——这对防抖有利（不必追求唯一解），
也意味着"改路"不等于"变好"，正是闭环 Δmin 闸门要拦的东西。

## 4. 三方案对比

| 方案 | 达标数 | 达标的业务 | 最忙方向 |
| --- | ---: | --- | --- |
| 生成器基线（`service-paths.json` 的 `paths[0]`） | **3 / 10** | TSV0001, TSV0003, TSV0004 | 153%（L00013 入） |
| 当前规划器（greedy + 局部搜索） | **5 / 10** | + TSV0009, TSV0010 | 146%（L00021 入） |
| 600 次重启搜索的最优 | **5 / 10** | 同上 | — |

基线缺的 TSV0009 / TSV0010 被压在 146%（L00021 入）与 153%（L00013 入）方向上；
规划器把它们挪开后达标。**这 2 条正是 `仿真器相关.md` §11.2 说的"边缘"业务**，数值吻合。

注意规划器方案下最忙方向仍有 146% / 143% / 140% —— 全是**接入段与被背景占满的骨干**，
与 5 条达标业务的自身方向无关（这 5 条自己的方向都在 100% 以内）。

## 5. "必须有几条 flow 是怎么样的" —— 直接回答

要在不改拓扑、不停业务的前提下保住 5 条 test 达标，**至少**要满足：

1. **5 条达标 test 必须落在 5 个不同的 flow 上**（本场景恰好如此），且每个 flow 的路径
   使其自身方向上每条链路利用率 ≤ 100%；
2. **UAV0001 的 3 个 flow 无法贡献达标**——它们的 test 全部依赖 L00017 的 109%/143% 方向，
   该方向由 5 条背景业务（终点都是 UAV0001）填满，绕不开；
3. 达标的 5 条里，**TSV0001 / TSV0003 / TSV0010 的接入方向是 95%**，属于边缘：
   稍有排队或抖动就会掉。真正"稳"的只有 TSV0004（出 66%）与 TSV0009（出 58%）。

所以报告里建议这样表述：**该场景理论上限 5 条，模型口径可达 5 条，但其中 3 条处于 95% 边缘，
实测预期 2~5 条；不可达的 5 条属物理容量墙，不是路由能力问题。**

---

## 6. 边缘与风险（模型 ≠ 实测）

1. **本文口径只覆盖容量维度**。实测 `qosMeet` 还要求时延/抖动/丢包/误码达标：
   - 95% 方向会有 TBF 排队（队列 `latency=400ms`，见 `仿真器相关.md` §2.4），
     时延紧的业务（如 TSV0001 的 265ms、TSV0003 的 195ms）可能被排队拖垮；
   - `qosMeet` 是逐秒快照（`仿真器相关.md` §11.5④），边缘业务会抖动。
2. **背景业务全部 running 是前提**。若脚本停掉部分背景业务，UAV0001 的入/出向会下降，
   那 5 条"不可达"业务可能变得可达——但无脚本场景没有这种事件。
3. **`priority` 方向（8 高 / 1 低）是工程约定**，官方未定义（`仿真器相关.md` §11.5①）。
   本文只用它排序与算权重，不影响上界结论。

## 7. 跨场景验证：这个上界在 sce05 上**不紧**

同一个脚本跑 conf02/sce05（180 业务 / 172 flow / 50 条 test）：

| 指标 | sce01 | sce05 |
| --- | ---: | ---: |
| 接入段上界 | **5 / 10** | **46 / 50** |
| 因接入段超容不可达 | 5 条 | 4 条（TSV0012/0044 卡 UAV0046 出 114%，TSV0037/0046 卡 UAV0019 出 124%） |
| 生成器基线 `paths[0]` | 3 / 10 | **6 / 50** |
| 当前规划器 | 5 / 10（= 上界） | **7 / 50** |
| 随机重启搜索最优 | 5 / 10（= 上界） | **8 / 50**（150 次重启，seed=7） |

**结论一：接入段上界是"上界"，但只在接入段是瓶颈时才紧。**

- sce01：接入段就是瓶颈 → 上界 5 = 实际可达 5，**紧**。
- sce05：接入段普遍只有 8%~81%，**真正的瓶颈在骨干**（微波/5G mesh 链路互相争抢），
  上界 46 形同虚设，实际只做到 7~8。

**结论二：sce05 上"8 → 46"这个缺口，随机重启贪心也填不上**（150 次重启只比规划器多 1 条）。
说明缺口不是"搜索次数不够"，而是**需要真正的全局优化器**（最小费用流 / LP / 按瓶颈链路
做整数规划），而不是继续调贪心的顺序或重启次数。这是后续优化明确的投入方向。

所以本文的推导方法要这样用：

1. **先用接入段判定"哪些业务根本不可能"**（sce01 的 5 条、sce05 的 4 条）——
   这一步永远正确，且给出了报告里"物理不可达"的硬证据；
2. **再看实际达标数离上界多远**：差得远说明瓶颈在骨干，此时要靠**全局负载均衡**
   （把挤在瓶颈链路上的 flow 分散到备选路径），而不是继续在接入段上找原因；
3. 不要把接入段上界当成"应该能拿到的分数"。

sce05 上"8/46"这个巨大缺口，正是 `仿真器相关.md` §11.2 描述的拥塞画像
（背景业务在 20~30Mbps 的微波/5G mesh 上叠满），也是后续优化的重点方向。

## 8. 局限与待核对

| 项 | 状态 |
| --- | --- |
| 上界"5 条"是**容量维度**的上界 | 已证（§1 前提 + §2 推导） |
| 该上界在**实测**下是否还能达到 | **待核对**：需跑一次无脚本测试，用 `/services/{id}` 的 `actual.qosMeet` 逐秒采样对比 |
| 随机搜索的 5/10 是"最优"还是"最好找到" | 最好找到，且与上界一致；因上界已由接入段证明，两者重合即证明 5 是最优 |
| 是否存在"停部分背景业务"的更优策略 | 本文不涉及（无脚本场景没有该动作） |
| 官方评测是否按业务加权（而非按 flow 二元） | **待核对**：`docs/competition_desc/` 只给了文本评分项，未给公式 |

## 9. 复现

```bash
# 全量输出（上界 + 三方案对比 + 最优摆法），约 9s
PYTHONPATH=src .venv/bin/python scripts/feasible_bound.py \
    simulator/data/scenarios/sce20261010-conf02/sce01

# 大场景（180 业务 / 172 flow）建议降重启次数，约 1 分钟
PYTHONPATH=src .venv/bin/python scripts/feasible_bound.py \
    simulator/data/scenarios/sce20261010-conf02/sce05 --restarts 150

# 只算上界与现状，不做搜索
PYTHONPATH=src .venv/bin/python scripts/feasible_bound.py <场景目录> --no-search
```

脚本口径与本文件一致：接入段上界、`paths[0]` 基线、当前规划器、随机搜索最优，
输出各自的达标业务集合与 flow 摆法。换场景（conf01/sce10 等）直接换目录即可。
