动态通信场景建模组网方案

结合赛题《资源受限环境下通信网络资源管控》任务说明书的背景描述，以及 MANET/战术数据链/QoS 等协议标准与成熟方案，给出面向"动态通信场景建模"的组网方案，并对比"智能体自感知自组网"与"无智能体的普通网络配置"。

1. 场景背景与建模需求（源自赛题任务说明书）

赛题背景原文要点：

随着无人平台在复杂任务场景中的广泛应用，机动通信网络经常处于高动态、窄带宽、强干扰等恶劣条件下，网络拓扑快速变化，无线链路断续多发，可用带宽动态收缩，电磁干扰随机出现，导致时域-空域-频域资源高度不确定，网络资源始终处于受限状态。未来通信网络需要从"人工配置、中心调度"转向"分布式、自感知、自决策、自协同"的智能化自治模式。

赛题「动态通信场景建模」子任务明确要求：

根据无人平台业务协同业务需求（涵盖数据、图片、话音、视频等业务类型）的 QoS 要求，依托仿真环境，使用节点下线、链路参数调整、业务需求调整等方式，模拟拓扑快速变化、链路随机通断、带宽时变、资源约束等多种组合场景。

由此，场景建模需覆盖四类扰动源 + 四类业务，构成组合场景。

2. 总体组网架构

采用分级混合式组网：接入网（分布式自组网）+ 中继层 + 骨干网，配合"数据面分布式 + 管控面多智能体分层"的控制/数据面分离架构。

4. 多智能体角色与协作机制

管控面由三类角色协同，正好对应赛题口号"看网络、判状态、调资源、保协同"：运维智能体 = 体检医生（感知 + 诊断），资源控制智能体 = 开药医生（决策 + 调度），协调器 = 调度台（编排 + 仲裁）。

4.1 协调器（Coordinator）

协调器是管控面的"总调度"，自己不做感知也不做算法，只负责把流程串起来、把冲突消解掉。

职责说明
任务分派接收用户任务/定时任务/仿真事件，统一编号（traceId、taskId）
构建快照把全网状态汇总成统一网络快照，分发给各 Agent
调度执行决定先跑运维 Agent 还是并行跑，控制执行顺序和依赖
冲突仲裁多个业务争资源、候选策略不一致时，做裁决
策略校验校验拓扑有效性、带宽容量、业务优先级、安全边界
下发与反馈把通过校验的策略下发仿真器，接收执行结果、更新指标

关键点：协调器是"逻辑上的协调中心"，不是数据必经中心；数据流不经过它，它只下发"策略"；且可降级——协调器失效时，簇头临时接管或退化为预置规则。

4.2 运维智能体（O&M Agent）

运维智能体是"眼睛 + 诊断医生"，负责感知和诊断，只输出"结论和约束"，不负责最终调度。赛题原文定义：负责全网态势采集、拓扑感知、链路质量评估、异常事件检测、故障诊断、自愈建议生成。

能力具体做什么
态势采集采集节点在线状态、链路时延/抖动/带宽/误码率/丢包率
拓扑感知感知全网拓扑、连通分量、关键节点
链路质量评估用 ETX 等指标评估每条链路好坏
异常检测识别节点离线、链路中断、质量退化、拓扑分区
故障诊断定位"断在哪、影响哪些业务、根因是什么"
自愈建议生成恢复建议（不是最终策略）

输出：诊断结果 + 影响范围 + 约束条件（如"L12 不可用"、"L18 带宽低于阈值"），交给资源控制智能体。

4.3 资源控制智能体（Resource Control Agent）

资源控制智能体是"手 + 策略制定者"，负责决策和调度，基于运维诊断结果和业务需求，用确定性算法算出具体方案。赛题原文定义：基于运维感知结果和无人平台业务协同需求，进行资源调度、路由动态调整、带宽分配、业务 QoS 保障。

能力具体做什么
业务需求分析读取各业务流的带宽/时延/丢包率/优先级要求
路由调整调用算法算候选路径、动态切换路由
带宽分配用 OR-Tools 线性/整数规划分配带宽
QoS 保障按业务类型（数据/图片/话音/视频）分优先级保障
生成候选方案输出结构化候选策略（不是直接执行）

输出：候选路由 + 带宽分配 + QoS 调整方案，交给协调器校验。

链路 L12 中断（仿真事件）
        │

4.5 为什么分三个角色

  1. 职责单一、可解释：感知和决策分离——运维 Agent 只说"事实和约束"，资源 Agent 只说"方案"，避免一个 Agent"既当运动员又当裁判"。
  2. 冲突需要一个中立仲裁者：多个业务抢同一条链路时，必须有协调器按优先级裁决，不能靠某个 Agent 自己拍板。
  3. 闭环完整：感知→诊断→决策→仲裁→执行→反馈，各环节可追溯（traceId 串联）。
  4. 对应赛题硬性要求：赛题明确"至少包含运维智能体、资源控制智能体两种"，协调器是保证闭环和冲突仲裁的加分项（评分项 2.2 协同体系架构）。

一句话总结：

角色一句话类比
运维智能体看网络、判状态（感知+诊断）体检医生
资源控制智能体调资源、保协同（决策+调度）开药医生
协调器统一编排、冲突仲裁、策略下发调度台/护士长

5. 组网方式与协议选型

层次组网方式协议/标准选型理由
接入网（末端集群）分布式自组网AODV（RFC 3561）反应式稀疏、流量少、节点机动
中继/骨干（密集区）分布式 + 分层OLSRv2（RFC 7181）主动式低时延、拓扑稳定、MPR 降开销
骨干上联集中链路微波/卫星（参考 Link 16 MIL-STD-6016、TTNT）高带宽回传、超视距
断续链路兜底容迟容断Bundle Protocol（RFC 9171）、DTN（RFC 4838）链路随机通断时存储转发
QoS 保障优先级队列/预留DiffServ（RFC 2475）、RSVP（RFC 2205）按业务类型分队列调度
管控面协同多智能体 A2A运维 Agent ↔ 资源 Agent ↔ 协调器感知→诊断→调度→仲裁闭环

6. 动态场景建模（核心）

按赛题三种建模手段 + 业务类型，构建典型场景矩阵：

场景注入方式（赛题手段）扰动源主要验证点
S1 节点下线指定节点 status→down拓扑快速变化故障感知、拓扑重算、业务恢复
S2 链路中断链路丢包率突增/status→down链路随机通断故障定位、替代路径生成
S3 带宽下降动态降低 bandwidthBps带宽时变、资源约束带宽重分配、QoS 保障
S4 链路质量波动改变 delayMs/jitterMs/ber/packetLossRate干扰/质量退化链路质量感知、策略稳定性
S5 业务需求变化新增流/提高最低带宽/降低时延上限业务需求调整资源竞争、优先级调度
S6 电磁干扰随机降 SNR/误码率、动态频谱受限强干扰换频/跳频、抗干扰策略
S7 多重/组合故障多节点+多链路同时异常多扰动叠加多 Agent 协作、复杂约束处理

场景建模要点：每种场景需定义（拓扑、业务需求、事件序列、随机种子、时长），并固定随机种子与事件序列保证可复现。业务类型与 QoS 门槛如下：

业务类型带宽要求时延敏感丢包敏感QoS 策略
话音低带宽高（时延/抖动）中高优先级、低时延队列
视频高带宽中中大带宽保障
图片中带宽低高可靠性保障
数据可变低高尽力/低丢包队列

7. 动态场景下的链路建立过程

沿用"邻居发现 → 链路质量测量 → 拓扑建立 → 路由计算 → 链路维护"生命周期（详见《无人平台组网设计方案》第 5 章），动态场景下叠加以下处理：

环节静态网络行为动态场景下的强化
邻居发现周期 HELLO节点下线 → 邻居表 lifetime 超时自动清除
链路质量测量RSSI/SNR → ETXber/packetLossRate/bandwidthBps 时变 → ETX/ETT 动态更新边权
拓扑建立主动式洪泛/按需探测链路状态变化（LSA）触发增量更新，而非全量重算
路由计算Dijkstra/K 最短路故障后 K 最短路提供备用路径，CSPF 过滤约束
链路维护周期探测断续链路用 DTN 存储转发；失效就近局部修复（AODV）

8. 对比：智能体自感知自组网 vs 无智能体的普通网络配置

核心判断：普通网络（OSPF/OLSR 等路由协议）本质只做"可达性 + 尽力转发"，是协议级、反应式、无业务语义的；智能体系统在其上叠加"感知—诊断—决策—协同"的管控面，实现业务级、主动式、跨层协同。两者不是替代关系，而是管控面增强数据面。

对比维度无智能体普通网络配置智能体自感知自组网
状态感知仅路由协议维护可达性，无链路质量/业务 QoS 感知运维 Agent 主动采集全网态势、拓扑、链路质量、业务 QoS
故障诊断只检测"链路断了"，触发路由收敛诊断"断在哪、影响哪些业务、根因、如何恢复"
资源调度固定路由 + 固定带宽 + 静态 QoS 配置资源 Agent 按业务 QoS 动态分配带宽、调整路由、优先级
业务语义无（所有业务等同转发）LLM 理解数据/图片/话音/视频差异，差异化保障
跨层协同路由/带宽/QoS 各自独立路由 + 带宽 + QoS + 优先级协同优化
应对带宽时变无感知，只能拥塞丢包动态重分配、抢占、降级保障关键业务
应对链路断续被动等待路由收敛或丢包主动 DTN 存储转发 + 预测性重路由
抗毁/降级中心失效即瘫痪（集中式）或纯协议收敛协调器可降级为簇头接管 → 本地自治
可解释性黑盒（协议自动收敛，无决策记录）决策链可追溯（traceId、快照版本、策略依据）
评价口径连通性、收敛时间状态感知时间、策略生成/下发时间、业务 QoS 达标率、故障恢复时间

论述要点：

  1. 普通网络（如 OLSR/OSPF）能自动收敛，但收敛是"尽力而为"：它只保证重新连通，不区分业务重要性，不理解带宽时变下的 QoS 需求，也无法解释"为什么这么路由"。例如链路带宽从 8Mbps 收缩到 1Mbps，OSPF 感知不到（链路仍 up），仍按原路径转发，导致视频业务拥塞丢包。
  2. 智能体系统在协议之上做"业务级管控"：运维 Agent 把 bandwidthBps 变化识别为"带宽下降"事件并归因，资源 Agent 结合视频业务的 QoS 要求，用 OR-Tools 重新分配带宽、用 K 最短路切换路径、提高话音优先级，实现协议层做不到的跨层优化。
  3. 分工边界：路由/转发由 MANET 协议确定性完成（可复现、低时延），理解、诊断、调度、仲裁由智能体完成（可解释、业务级）。这正是赛题"LLM 不替代确定性算法"的设计原则。
  4. 量化对比目标：赛题要求在相同拓扑、业务、事件序列、随机种子下，对比"静态基线 / 传统算法组 / 多智能体协作组"三组，重点看业务 QoS 达标率、故障恢复时间、带宽利用率的差异，而非仅比连通性。
