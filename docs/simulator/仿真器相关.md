## 1. 这个仿真环境是什么

这是赛题配套的**无人集群通信网络仿真环境**，用于训练和评测资源管控智能体：

- 网络中有无人平台（uav）、地面节点（ground）、空中节点（air）；
- 链路有光纤、卫通、VHF、UHF、微波、5G 等类型；
- 脚本事件会制造节点上下线/移动、链路中断/劣化、业务新增等扰动；
- 智能体通过 HTTP API 观测网络/业务状态，并下发业务路径，保障时延、抖动、带宽、丢包率、误码率等 QoS；
- 测评软件根据日志、业务统计和智能体行为打分。

## 2. 系统架构

### 2.1 容器职责

```
浏览器 :10000
   │
   ▼
netsim 容器
 ├─ nginx :9988          前端页面（index.html/app.js/style.css/ECharts）
 │    ├─ /sdn-api/  → 控制面 :8080/api/open/v1
 │    ├─ /sdn-ctrl/ → 控制面 :8080/api/ctrl/v1
 │    └─ /sdn-ui/   → 控制面 :8080/ui
 ├─ ctrl.py :8080        控制面 / 公开 API / UI 元数据
 ├─ sdnlab.py            建网、拆网
 ├─ OVS + netns + veth + tc  仿真网络本体
 └─ ui-worker.sh         页面"开始/结束"任务执行体
   │
   ├─ servicesim-tx 容器  :8090  业务发送端（总览页 :10001）
 └─ servicesim-rx 容器  :8092  业务接收端（总览页 :10002）
```

关键结论：

- **主仿真页面由 netsim 容器提供**，不是 tx/rx 容器。
- tx/rx 是业务收发容器；它们通过 `nsenter` 注入到每个业务节点的网络命名空间。
- eval 是独立模块，负责测评与大模型网关，不在本次已完整试跑范围内。

### 2.3 网络仿真是怎么做的

不是只用一个 socket 或状态字段，而是：

- 每个业务节点一个 Linux 网络命名空间；
- 节点分配真实 IP（如 UAV `10.1.1.x`、AIR `10.3.0.x`）；
- veth 接到 OVS 网桥（s0、s1…）；
- 链路用 tc 的 netem/htb 设置时延、抖动、带宽、丢包、误码；
- 业务媒体是真实 UDP 报文，从源节点 netns 经 veth、OVS、受损链路到目的节点 netns；
- 节点上下线是网络层不可达/恢复，链路中断是切断对应链路，节点移动会更新位置并连带改变距离相关链路参数。

### 2.4 链路参数如何落地：netem + tbf

2.3 只说“用 tc 施加损伤”；这一节给出实际命令与语义。源码入口是 `sim_src/netsim/ctrl.py` 的 `apply_link`（解码件第 258 行）；镜像内路径 `/opt/simulator/netsim/ctrl.py`。

建网时 Mininet 的 TCLink 先按 `bw/delay/loss` 挂一轮（默认 HTB + netem）；控制面启动后 `seed_baseline_link_params()` 会重新挂 `netem + tbf`，把 `jitter` 和 `ber` 补上。链路两端都会挂 qdisc，业务报文每跳经历一次出队损伤。

| 参数 | 内核机制 | 实际命令（简化） | 语义与注意 |
| --- | --- | --- | --- |
| 带宽 | **TBF 令牌桶** | `tc qdisc add dev X parent 1:1 handle 10: tbf rate 24mbit burst 100kbit latency 400ms` | **上限**，不是管道容量；流量低于 rate 时不起作用；超速先排队、队满再丢包 |
| 时延 | **netem delay** | `netem delay 5.2ms` | 每个包在队列里真实等待；端到端逐跳累加 |
| 抖动 | **netem delay + 分布** | `netem delay (d+j/2)ms (j/2)ms distribution sdnlab-uniform` | 每包从 `[d, d+j]` 均匀取延时；**平均是 `d+j/2`**，不是 `d` |
| 丢包 | **netem loss** | `netem ... loss 0.2%` | 按概率独立丢包 |
| 误码 | **netem corrupt** | `netem ... corrupt 0.01%` | 按 `ber×100%` 的**包损坏概率**翻位；不是物理比特误码率 |

**为什么 5Gbps 光纤不需要真的跑 5Gbps。** 带宽在仿真里是“闸门”，不是“发动机”：

- 业务发送速率 = `requirement.bandwidthBps × 1.03`；单业务从 voice 的 99kbps 到 video 的约 11Mbps；
- 全场景合计：conf02/sce01 的 40 条业务约 142Mbps，conf01/sce10 的 500 条约 1016Mbps；
- 光纤在 `net-topo.json` 里是 6.6~9.9Gbps，最忙的一条也只承载 423Mbps；
- 因此本地 socket 或 veth/OVS 能不能达到 5Gbps，不影响“这条链路不被业务打满”这个结论。

**1000Mbps 封顶要分清位置。** `sdncommon._bw_mbit()` 在**建 Mininet 链路**时把超过 1000Mbps 的值封顶（启动日志会打印 `s1-s7 7400Mbps→1000`）；但 `ctrl.seed_baseline_link_params()` 又会用 `net-topo.json` 的原始值重新 `apply_link`，`/links` 的返回还受运行期 `x009` 覆盖。**不要只凭一处代码断言 `/links` 的带宽值**，以运行期 `/links` 和启动日志为准。

**带宽与队列是耦合的。** TBF 队列容量约为 `rate × latency`（latency=400ms）。聚合流量超过 rate 时：

1. 先表现为排队时延升高（`avgDelayMs` 上升）；
2. 队列排满后开始丢包（`packetLossRate` 上升、`effBwBps` 下降）；
3. 收端 `effBwBps = min(发送速率, 接收速率)`，低于需求即带宽项不达标。

静态 QoS 的 `B = min b` 假设“链路独享、无排队”；实测是“多业务共享 + 排队”，两者必然分叉。这正是 11.2 的拥塞根因。

**TBF 按方向独立（全双工），不是两方向共享一个桶。** `apply_link` 对 `link_ends()` 返回的**两个端点各挂一份** `netem + tbf`（`ctrl.py:271-289`，`link_ends` 在 `:212-221`），所以 A→B 和 B→A 是**两个独立的令牌桶**（各自 `rate=bw`）：反方向的流量**不互相抢带宽、也不互相注丢包/时延**。由此有两个容易踩的坑：

- 「带宽」要按**方向**分别对比容量（每方向 `Σ需求 ≤ bw`），**不能把两方向需求加总后对一个 `bw`**——那是半双工口径，会高估利用率（见 11.2 的口径更正）；
- 双向业务（同节点对、方向相反）在链路上互不影响，它们的耦合只来自「flow 共路径」（见 10.1），不是带宽争抢。

**两个实现口径（容易误读）：**

- **抖动抬高平均时延**：netem 命令是 `delay (d + j/2) ± j/2`，每包延时均匀落在 `[d, d+j]`，均值 `d + j/2`；静态公式用的是 `D = Σd`，所以实测平均会带 `Σ(j/2)` 的正偏差。
- **`ber` 是包级损坏率**：代码是 `corrupt min(99, ber×100)%`，`ber=1e-4` 表示 0.01% 的**包**被翻位；真正的物理 BER 会随包长放大，仿真没有做这个换算。收端 32 字节业务头里有 CRC32，翻坏的包被计为无效包，形成 `errPct`。

### 2.5 控制面与数据面的边界

- **数据面**：OVS 流表 + netns + veth + tc，内核里真实转发 UDP 报文。
- **控制面**：`ctrl.py :8080`（对外 :10100），负责 API、状态采集、事件处理、路径下发。

控制面挂了，**已经装好的 OVS 流表通常还在转发**；但智能体看不到 `/links`、`/services`、`/topology`，也改不了路径，事件处理也会停。**API 超时 ≠ 网络停了**，排查时要先区分是哪一层出问题。

#### 4.2.1 已知限制：Rosetta 下控制面约 11 分钟超时

实测记录（`experiments/iss/ISS-0005-email.md`）：**40 条业务跑约 11 分钟后，`ctrl.py:8080` 全接口超时**。这是本机 Mac 试跑的限制，不是场景或算法本身的问题。

- **现象**：`GET /links`、`/services`、`/topology`、`POST /services/{id}/path` 全部超时；UI :10000 转圈。tx/rx 可能还在发/收，日志还在写，但智能体已经失去观测和控制通道。
- **原因（合理解释，未做完整 profiling）**：镜像是 `linux/amd64`，在 arm64 Mac 上靠 Rosetta 转译用户态。控制面每个请求要做大量重活——逐链路 `nsenter -t <pid> -n tc qdisc show`、`ip -o link show`，聚合 tx/rx 状态，处理事件；每条命令都是一次 amd64 子进程 fork/exec，Rosetta 下很贵。UI 每 2 秒轮询一次，智能体也在轮询，请求叠加后 CPU/线程顶不住，响应时间超过超时阈值。
- **“单线程”是概括**：当前镜像的 `ApiServer` 实际是 `ThreadingHTTPServer`，但处理器里大量串行子进程 + 全局锁，Rosetta 下有效吞吐会塌到接近单线程。
- **时间点**：默认 T0+3 分钟进入事件窗口，11 分钟时事件、重路由、状态刷新都已上来，负载比 T0 高。
- **影响**：Mac 上 11 分钟后的运行结论不可信；ISS-0005 只取 T0 后早期窗口，就是这个原因。闭环重路由要尽早验证，完整 30 分钟跑批放到 Linux x64。
- **缓解**：少开 UI 标签页；智能体降低轮询频率（`/events` ≤10s，`/links`、`/services` 按需拉），超时后指数退避；卡住时先 `docker stats` 看 netsim 容器 CPU。

## 5. 重选场景/脚本与 TX/RX 重启规则

核心规则：**每次网络重建后，重启一次 TX/RX。**

`ui-worker.sh` 的判定：

- 套件+场景相同、当前网在、且没有遗留 down 链路 → 复用当前网，不重建；
- 换套件或场景 → 一定拆网重建；
- 同套件/场景但上一轮脚本留下断链 → 也会重建恢复基线。

重建会销毁旧节点的网络命名空间，旧 TX/RX 注入随旧 netns 失效。TX/RX 入口 `start-tx.sh` 是一次性 bootstrap，不会可靠地自动重注入（尽管部分注释提示有 watcher）。因此：

```bash
docker compose -f mac-docker-trial/compose.local.yml restart tx rx
```

执行时机：

- 点“结束”后，空网重建完成、节点表刷新后；
- 点“开始”且套件/场景变化（或触发重建）后，节点表刷新后；
- 同一套件/场景、网络干净时，只换脚本通常不需要重启。

## 6. 页面怎么用

### 6.1 控制条

顶部从左到右：

- 套件（suite）；
- 场景（scene，sce01~）；
- 脚本（script-01~，可选“不选脚本”）；
- 自动结束（分钟，1~1440，默认 30）；
- 开始 / 结束。

点“开始”立即启动（没有“按钟点预约”功能）；T0 是脚本真正开始执行的时刻。

### 6.2 页面状态

- 运行徽标：未开始/运行中/业务受理中/已结束等；
- T0、当前套件/场景/脚本、事件进度 `fired/total`；
- 右侧业务列表：只显示测试业务（category=test），状态 running/stopped/finished/failed；达标列显示 达标/未达标/实测填充中；
- 拓扑图：节点按类型着色，可适配/显示文字；
- 事件时间轴：横轴自 T0 起。

### 6.3 自动结束与脚本 stop

- 每个脚本末尾有 `stop` 事件，时间为 1800s（30 分钟）；
- 页面“自动结束 N 分钟”是看门狗：到 N 分钟执行“结束”（13号 stop + 拆网重建空网）；
- 可随时手动点“结束”提前终止；
- 若 N 小于脚本最后事件时间，会提前结束并漏掉后续事件。

### 6.4 事件时间窗口

| 套件 | 事件窗口 | 脚本 stop |
| --- | --- | --- |
| conf01 | T0+3~26 分钟（180~1560s） | 1800s |
| conf02 | T0+3~26 分钟（180~1560s） | 1800s |
| conf04 | T0+2~27 分钟（120~1620s） | 1800s |

单个脚本不一定用满窗口（有的最后事件在 14~25 分钟）；前 2~3 分钟是纯净基线窗口，最后几分钟是收尾窗口。

### 6.5 T0 与慢环境

T0 由脚本引擎在**脚本真正开始执行时**设置（`script_engine.py` 的 `start()` 里 `self._t0 = time.time()`），不是建网时设置。

因此本地 Docker 慢、TX/RX 晚就绪，只会把 T0 整体往后推，不会让 T0+3 分钟的事件"提前跑掉"；就绪门通过后才下发开始请求。

## 8. 常见错误与排查

### 8.1 “场景不存在：data/scenarios/.../net-topo.json”

原因：容器挂载到了空壳目录 `仿真环境-参赛包/simulator/`。

排查：

```bash
docker inspect dna-mac-trial-netsim-1 \
  --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'
```

正确挂载应指向顶层 `simulator/conf|data|assets|logs`。用 `compose.local.yml` 重建即可。

### 8.2 页面按钮灰、卡在“执行中”

两个常见来源：

1. 历史残留任务：`simulator/logs/run/ui-job.json` 的 `phase` 不是 done/failed（如 stopping/starting），前端会把开始按钮和选择器锁住。
   - 前端逻辑在 `app.js` 的 `uiApplyLock()` / `renderUi()`：`active` 或 `running` 都会锁。
   - 轻量修复：把 `ui-job.json` 重置为 `{"action":"stop","phase":"done","detail":"","pid":0,"ts":""}`，页面 2 秒内自动解锁。
2. 业务就绪门：结束/开始后重建网络，`run-servicesim.sh` 在 external 模式等 TX/RX 注入，日志反复出现 `0/N ready（external 等待重注入）`。
   - 修复：`docker compose -f mac-docker-trial/compose.local.yml restart tx rx`。
   - external 模式等待窗最长 600 秒；到点会放行并把任务标 done，但业务可能仍未就绪，下一次开始还会等。

### 8.3 TX/RX 总览页很慢/像没起来

`servicesim/bin/frontend.py` 每次渲染会逐个节点串行请求健康接口（每节点 timeout 3s）。23 个节点、Mac 转译下实测 10001 页约 20s、10002 约 22s、`/health` 约 27s。

判断真实状态看：

```bash
docker compose -f mac-docker-trial/compose.local.yml ps -a
tail -n 20 simulator/logs/run/ui-worker.log
```

出现 `46/46 ready` 即注入完成；不要用浏览器几秒超时判断 tx/rx 是否重启成功。

### 8.4 日志噪声

- `sch_htb: quantum of class ... is big`：tc 对超大带宽链路的告警；仿真把超限带宽封顶到 1000Mbps，属正常。
- `上报重试 ... ws://127.0.0.1:8091/topo ... Connection refused`：该构建已停用 WS 态势通道，属无害噪声。

### 8.5 页面/浏览器缓存

前端每 2 秒轮询 `/sdn-ui/meta`，状态修正后一般自动解锁；若仍显示旧界面：

- `Cmd+Shift+R` 硬刷新；
- 无痕窗口访问 `http://localhost:10000`；
- 开发者工具 Network 勾选 Disable cache。

nginx 对 index.html/js/css 已发 `no-store`。

### 8.6 Docker 连接问题

- `permission denied ... docker.sock`：Docker Desktop 未运行，或命令在受限沙箱内；在普通终端确认 `docker info` 可用。
- `docker compose logs` 正常但 `docker compose exec` 报权限：同样检查是否在沙箱内执行。

## 10. 路径机制：flow 级路径与 service-paths.json

### 10.1 路径是 flow 级，不是 service 级（源码核实）

业务路径以"源-宿 UAV 对"为键，不是以业务为键。源码出处 `netsim/openapi.py` 的 `_flow_for()`：

```python
def _flow_for(src_nid, dst_nid):
    ip1 = (im.nodes.get(src_nid) or {}).get('ip')
    ip2 = (im.nodes.get(dst_nid) or {}).get('ip')
    name = CTX['flow_of_ips'](ip1, ip2)          # 由两端 IP 对命名，方向无关
    return (name, CTX['list_flows']()[name])
```

之后设路/查路都以这个 flow 名为键：`CTX['set_path'](flow, labs)`、`CTX['get_path'](flow)`。

结论：

- 同一对 UAV 之间不管有几条业务，**只装一条路径，大家共用**；
- flow 名是无向的（`(A→B)` 与 `(B→A)` 是同一 flow），日志里表现为 `流 h3-h7` 这类主机对；
- 日志证据：`[初始引流] 业务 BGV0001 → 流 h3-h7：s5 → s6 → s1 → s2`。

### 10.2 service-paths.json 结构（离线候选，service 级）

文件是**生成器离线算路**的产物，粒度是 service 级；运行时被压扁成 flow 级（见 10.3）。

顶层字段：

| 字段 | 内容 |
| --- | --- |
| `scenarioId` | 场景标识（如 `sce01`） |
| `desc` | 说明：`services`＝T0 初始路径；`postEvents`＝每脚本事件后末态路径 |
| `services` | 40 条初始业务，每条 `srcNodeId`/`dstNodeId`/`requirement`/`paths[]` |
| `postEvents` | 10 个脚本，每脚本 `desc`/`onlineServices`/`offlineServices`/`linkParams`/`services` |

每条 `services[i].paths[]` 含 3 条候选路径，每条：

| 字段 | 含义 |
| --- | --- |
| `pathNo` | 1 / 2 / 3 |
| `nodes[]` | 源→目的经过的节点 id 序列（如 `UAV0003→GND005→GND006→…`） |
| `links[]` | 对应链路 id 序列（如 `L00021, L00005, …`） |
| `metrics{}` | 端到端合成：`delayMs`/`jitterMs`/`packetLossRate`/`ber`/`bottleneckBps` |

`postEvents[<脚本>]` 是"该脚本全部事件应用后"的末态快照，含 `linkParams`（路径涉及链路的末态参数）与每条业务的末态选定路径。**运行时只用 `services`（T0 初始），`postEvents` 是文档性快照，不参与运行。**

### 10.3 初始引流机制（源码 `_install_service_path`）

启动建网时对每条业务"初始引流"，逻辑：

1. 查 `service-paths.json` 里该业务的 `paths[0].nodes`，把 GND 节点转成交换机 lab（s1..s10），UAV/AIR 主机节点被过滤掉；
2. 有预置路径 → 装上；**无 service-paths.json** 时兜底走 `_bfs_via` **纯 BFS 最短路**（只看 up 链路、不看任何 QoS）；
3. 并发装机，线程池 `ThreadPoolExecutor(SIM_PATH_CONC=32)`（**固定参数，与本地 CPU 线程数无关**）。

两个关键点：

- `service-paths.json` 里每条业务虽有 **3 条候选**，运行时 `_svc_paths_doc()` **只取 `paths[0]`**（第 1 条），`paths[1]`/`paths[2]` 不用；
- 无该文件时，所有业务都会被塞到"跳数最少"的最短路上 → 流量高度集中 → 基线就拥塞。

### 10.4 no-path 的真相：并发竞态，不是没路

40 条业务归并到 **17 个 flow**（同一对 UAV 的算一个），每 flow 只装一条路，因此初始引流结果分三类：

| 结果 | 数量 | 含义 |
| --- | --- | --- |
| `installed` | 17 | 每 flow "抢赢"的那条业务，负责装路 |
| `no-path` | 14 | 与同 flow 兄弟业务竞态失败（`set_path` 撞车 + BFS 兜底也失败） |
| `already` | 9 | 同 flow 兄弟业务晚到，检测到路已存在，静默跳过 |

`no-path` 是**并发竞态的日志噪音，不是"路不可达"**：它的 flow 已被兄弟业务装上路径，业务照常跑。17 + 14 + 9 = 40 正好对上。每条 `no-path` 业务都与某条 `installed` 业务同 flow。（竞态里 `set_path` 为何返回失败的确切原因「待核对」，但"flow 最终都有路"这一结果已核实。）

### 10.5 小结：离线 service 级 vs 运行时 flow 级

```
离线（生成器）：40 业务 × 3 候选路径 = 120 条（service 级）
    ↓ _flow_for + set_path(flow)
运行时（仿真器）：17 flow × 1 条路 = 17 条（flow 级）
```

两者不矛盾：离线按 service 算候选，运行时按 flow 装一条路。

## 11. 两套 QoS 与基线未达标根因

### 11.1 两套 QoS 必须同时看

| 口径 | 数据源 | 用途 |
| --- | --- | --- |
| 静态路径 QoS | 候选路径链路参数合成 | 下发校验（不满足返回 1004）/ 生成器选路 |
| 实测 QoS | 逐秒真实报文统计 | 评分 `actual.qosMeet` |

静态合成公式与容差见 [数学建模方案 §4](../common/modeling/数学建模方案.md)
（**唯一权威源**，公式严格对齐 `openapi.py _compose_qos`）。

**静态通过 ≠ 实测达标**（CLAUDE.md 关键事实）。基线"未达标"几乎全是实测不达标。

### 11.2 基线未达标的根因：拥塞，不是没路

加了 `service-paths.json` 后基线仍大面积未达标，根因是**生成器按"单业务孤立"选路，不做全局负载均衡**：每条业务都拿到"单看可行"的路，但这些路全指向同一批瓶颈链路，一叠加就堵死。

实测（sce20261010-conf02/sce01）真正超容的是接入/mesh 链路：

| 链路 | 类型 | 共用 flow 数 | 需求 / 容量 | 利用率 |
| --- | --- | ---: | ---: | ---: |
| `L00013` GND009–GND007 | 微波 | 6 | 66.9 / 26 Mbps | **257%** |
| `L00017` UAV0001–GND001 | 微波 | 6 | 72.9 / 29 Mbps | **251%** |
| `L00021` UAV0003–GND005 | 微波 | 6 | 55.5 / 23 Mbps | **241%** |
| `L00005` GND005–GND006 | 微波 | 6 | 55.5 / 24 Mbps | **231%** |
| `L00006` GND006–GND001 | 5G | 6 | 55.5 / 31 Mbps | **179%** |
| `L00001` GND001–GND002 | 微波 | 5 | 40.3 / 24 Mbps | **168%** |

注意一个容易误读的点：`GND001–GND007` 之间确实有 10 个 flow 共用 `L00015`，但它是 **7.4Gbps 光纤**，需求 95.9Mbps、利用率 1.3%，不是瓶颈；同一对节点还有 `L00016` 卫通（当前路径未选中）。旧版本把“10 个 flow 都在同一对节点”误写成“超过链路容量”，这里按 `linkId` 更正。

真正被打爆的是 20~30Mbps 的微波/5G 接入与 mesh 链路。**这是 agent 真正要解决的：把挤在瓶颈链路上的 flow 分散到备选路径。**

> **口径更正（2026-11-20 会话）**：上表「需求/容量」是把**两个方向**的业务需求加总后对一个 `bw` 比的**半双工口径**，与仿真器不符——`apply_link` 给链路两端各挂一个 `rate=bw` 的 TBF，两方向是**独立的全双工桶**（见 2.4）。按方向拆开重算，关键接入链路是：
>
> | 链路 | 容量 | 出向 Σ需求 | 入向 Σ需求 | 出向利用率 | 入向利用率 |
> | --- | ---: | ---: | ---: | ---: | ---: |
> | `L00017` UAV0001–GND001 | 29M | 31.5M | 41.5M | **109%** | **143%** |
> | `L00021` UAV0003–GND005 | 23M | 21.9M | 33.6M | 95% | **146%** |
>
> 结论（接入/mesh 超容）不变，但「251%」「241%」是两方向加总；单方向实际是 109%/143%、95%/146%，模型里应按方向记账。

**测试业务单独看能放下，超载几乎全是背景业务叠出来的**（同场景按 `category` 拆分，方向性）：

| UAV | 接入链路 | 容量 | 只算 test（出/入） | test+background（出/入） |
| --- | --- | ---: | --- | --- |
| UAV0001 | L00017 | 29M | 35% / 60% | **109% / 143%** |
| UAV0003 | L00021 | 23M | 18% / 0% | 95% / **146%** |
| UAV0006 | L00027 | 28M | 31% / 5% | 95% / 8% |
| UAV0002/4/5/7 | — | 20–31M | ≤35% / ≤32% | ≤80% |

含义：**test-only 最高只用到 60%**，理论上全放得下；但每个 UAV 只有一条像样接入链路、背景业务终点固定，**背景绕不开接入链路**，所以超载是**物理容量墙**——重路由只能在骨干段缓解，接入段（UAV0001 的 5 条 test）救不回来。

### 11.3 源端速率机制（tx.py `rate_bps()`）

发送侧按 `requirement.bandwidthBps × 1.03`（`SERVICESIM_RATE_HEADROOM=1.03`）发，留 3% 余量抵消抖动，因为带宽判定容差为 0。两类差异：

| 业务类型 | 发送方式 | 余量 |
| --- | --- | --- |
| data / background（light） | `_loop_data` 恒定码率 + 整包向上取整修复 | 3~5%，抗丢包较强 |
| voice/video/image（test） | `_loop_media` 资产循环推流 | 仅 ~0.8%（前缀开销吃掉 2%），对丢包极敏感 |

所以 `effBwBps = min(发送速率, 接收速率)` 掉到需求以下，**几乎都是网络丢包（拥塞）导致**，不是"源端发不够"。voice 等 media 类因为余量薄，是最先带宽不达标的。

### 11.4 链路类型画像：光纤为什么基本不是瓶颈

**核算方法**：把每条业务 `paths[0]` 的需求带宽按路径累加到链路上，再和 `net-topo.json` 的链路容量比较；同时检查 `postEvents` 的事件末态路径。覆盖现有 15 个场景、149 个含光纤路径的事件末态。

代表性结果（光纤利用率按最保守的 **1Gbps 数据面上限**算）：

| 场景 | 业务数 | 全网需求合计 | 最忙光纤链路 | 最忙瓶颈链路 |
| --- | ---: | ---: | --- | --- |
| conf02 / sce01 | 40 | 142 Mbps | 95.9 Mbps → **9.6%** | 微波 66.9/26 Mbps → **257%** |
| conf02 / sce05 | 180 | 617 Mbps | 225.5 Mbps → **22.6%** | 微波 132/29 Mbps → **455%** |
| conf01 / sce10 | 500 | 1016 Mbps | 423.3 Mbps → **42.3%** | 5G 161.1/23 Mbps → **700%** |

> 注：上表「最忙瓶颈链路」的利用率同样是**两方向加总**口径，单方向会低一些（见 11.2 口径更正）；「光纤」列的结论不受影响。

关键结论：

- 按 `net-topo.json` 原始容量（光纤 6.6~9.9Gbps），最忙光纤利用率只有 **0.9%~6.1%**；即使按 1Gbps 上限，也只有 **42.3%**，仍有 2.3 倍余量；
- 149 个含光纤末态里，**0 条光纤超过 1Gbps**，最高 43.3%；
- 真正被打爆的是 **微波、5G、VHF/UHF**，普遍 2~7 倍超容；卫通在现有库里很少超容，但时延太高，通常只做备份。

原因：

1. 光纤只用在**跨簇骨干**（每对相邻簇一条主光纤 + 一条备卫通）和 EXT001 引接；EXT001 不在业务路径上。
2. **大部分业务是簇内流量**，走微波/5G mesh，不经过光纤。
3. **全网总需求才 1Gbps 量级**，光纤单链路是 1~10Gbps；跨簇流量分散到多条光纤后，单条只有几百 Mbps。
4. 光纤带宽下限就是 1Gbps（`linkTypes.json` 的 `fiber` 范围），`link_param_change` 也不能把它压到 1Gbps 以下。

**但这不是结构性保证**，有四个限定：

- 当前结论是**现有场景库的统计事实**；官方全规模场景（≥300 无人平台、450+ 背景业务）或自建集中型拓扑，仍可能把一条光纤推到 1Gbps 附近；
- **光纤不是带宽瓶颈 ≠ 光纤永远满足 QoS**：抖动最高 5ms、丢包最高 1%、误码最高 1e-6，劣化后仍可能违反紧业务需求；
- 数据面有宿主能力上限：标称 6.6~9.9Gbps，veth/OVS/本机实际跑不到；当前业务量远低于 1Gbps，所以不影响，但不要把“光纤标称 5Gbps”当成可兑现的吞吐；
- 重路由可能把大量 flow 推向光纤：跨簇绕行会增加跳数和时延，仍要看 `actual.effBwBps` 与排队时延。

**对 agent 的含义**：优化重点放在微波/5G/VHF/UHF 的 flow 聚合上；光纤仍要纳入 QoS 过滤和实测监控，但不必把它当容量风险点。

### 11.5 本会话补充口径（优先级 / test·background / 上报时序）

**① 优先级取值 1~8（不是 1~9），「8 高」是我们的约定、官方未定义方向。**

- 仿真器校验 `1 <= priority <= 8`（`sim_src/servicesim/servicesim/core.py:61-62`）；`项目背景.md`、`数学建模方案.md` 也都写 `[1,8]`。
- 官方赛题 PDF、接口文档只把 `priority` 当字段列出（如 `priority:6`），**没说 1 高还是 8 高**。
- 本项目口径是 **8 最高、1 最低**（`数学建模方案.md:261` 用 `α = Σ 2^priority`，指数放大高优先级），属工程约定，**待官方核对**。
- 仿真器本身**不拿 priority 做 QoS/调度**（只是报文头+日志字段），真正影响优先级的是测评软件加权。

**② test 与 background 的模拟方式。**

| | test | background（light） |
| --- | --- | --- |
| 发送 | data 走 `_loop_data`；image/voice/video 走 `_loop_media`（循环读 assets 真实文件，首/末块带 FIRST/LAST） | 一律走 `_loop_data`：**不读素材**，按 `bandwidthBps` 恒定码率发零填充 UDP（带 32B 业务头，`flags=0` 无首末语义） |
| 接收 | 全量逐包统计 + 组装媒体文件 + 质量打分（PSNR/SSIM、PESQ、VMAF）+ 逐秒 `qosMeet` | 只做最少到达计数，**不写逐包日志、不组文件、不打分** |
| 速率 | `requirement.bandwidthBps × 1.03`（media 前缀开销再吃掉约 2%） | 同左（data/light 整包向上取整修复） |

一句话：**每条业务都是「单方向、持续推流」的 UDP 模拟**，src 一直发、dst 一直收；test 与 background 的区别只在「发什么内容」和「收端统不统计」。

**③ 公开 API 不返回 category，POST 也不按 category 过滤。**

- 列表 `/api/open/v1/services` 只返回 `serviceId/serviceType/srcNodeId/dstNodeId/priority/status`（`openapi.py:2013`）；详情显式 `it.pop('category')`（`:2035`）。
- category 只在内部 `/api/ctrl/v1/svc-meta`（需 `ctrlToken`，`:2137-2141`、`:2216-2217`）。
- **`POST /services/{id}/path` 对 test 和 background 一视同仁**：`_set_service_path`（`openapi.py:2058-2107`）全程不读 category，只要 serviceId 存在就能调。**但路径是 flow 级**，所以动一条 test 会连带同 flow 的 background，反之亦然。

**④ `qosMeet` 是「最近 1 秒」逐秒快照，读之前要等稳态。**

- 默认 `settle_ms=300`（`config.py:64`）：到达时刻早于「now−300ms」的包才计入丢包；启动/换路瞬间有在途偏差。
- 首秒无序号基线，`rx.py:526-530` 把首秒丢包**强置 0**（避免启动虚高 87%）。
- TBF 队列 + OVS 流表进入稳态需要时间，媒体首文件也有开销。建议启动后 **≥30~60s** 再读，并**连续读多秒看趋势**（95% 边缘的业务会抖）。

**⑤ 一次测试只跑一个脚本；不选脚本 = 只跑业务、无事件。**

- 接口文档：一次测试实例运行一个脚本（`仿真软件接口.md:167`）。
- 实现口径：`start` 不带 `scriptId` 时不加载脚本引擎，只 `svc.ensure_up()` 跑 40 条初始业务（`openapi.py:2264-2298`）→ **零事件**，适合做纯静态/纯容量实验。
- 注意文档说「scriptId 三者缺一返回 1001」，但实现与前端允许不选，**存在文档/实现出入，以实测为准**。
- 本场景 10 个脚本共 **104 个事件**（`sce01-stats.md:16`），但每脚本独立：script-01 只有 7 个、script-08 最多 15 个；**不是一次跑 104 个**。

### 12.1 flow → 业务映射表

import json, collections
