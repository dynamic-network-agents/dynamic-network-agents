# 无人平台组网设计方案

> 面向「资源受限环境下通信网络资源管控」竞赛：无人平台的组网方式、链路建立、资源分配调度、数据传输，以及可参考的协议标准与成熟方案。

> 修订版 v2.0｜2026-11-05。基于原文保留主体结构，补充动态仿真架构/统一对象模型，并修订协议术语、链路承载语义、QoS准入与场景边界。

## 1. 无人平台概述

**无人平台（Unmanned Platform / Unmanned System）**：不搭载机上操作人员、可自主或遥控执行任务的装备/载具。在通信网络语境下，它是网络中的**机动节点（mobile node）**，通过无线链路接入机动通信网络，向指挥/协同节点回传数据和接收指令。

| 类型 | 名称 | 典型任务 |
|------|------|----------|
| 空中 | 无人机（UAV） | 侦察、测绘、中继、打击 |
| 地面 | 无人车（UGV） | 巡逻、运输、排爆 |
| 水面 | 无人艇（USV） | 巡逻、探测、反潜 |
| 水下 | 无人潜航器（UUV/AUV） | 探测、布雷、水下中继 |

**关键背景**：无人平台处于高速机动、高动态拓扑、窄带宽、强干扰环境下，链路随机通断、带宽动态收缩，因此通信网络需要从"人工配置、中心调度"转向"分布式、自感知、自决策、自协同"的智能化自治模式。

**链路质量五要素**（对应赛题链路参数模型）：`delayMs`（时延）、`jitterMs`（抖动）、`bandwidthBps`（带宽）、`ber`（误码率）、`packetLossRate`（丢包率）。

**业务类型与 QoS 门槛**：

| 业务类型 | QoS 敏感点 |
|----------|-----------|
| 话音 | 时延、抖动敏感 |
| 视频 | 带宽敏感 |
| 数据 | 丢包敏感 |
| 图片 | 带宽 + 可靠性 |

## 2. 组网方式：分级混合 + 控制/数据面分离

无人平台组网**不是单一模式**，而是在三种基本形态之上，针对"高机动 + 资源受限 + 抗毁"需求演化出的**分级混合式**。核心结论：

> **数据面分布式自组网 + 管控面分层协调（协调器统一编排、仲裁，支持降级自治）**

### 2.1 三种基本组网形态

| 组网方式 | 结构 | 决策方式 | 典型实例 | 优点 | 缺点 |
|----------|------|----------|----------|------|------|
| 集中式（有中心） | 星型/树型，节点统一连中心基站/AP | 中心统一调度 | 蜂窝网（基站）、IEEE 802.11 基础设施模式 | 资源分配集中高效、接入管理简单、QoS 可控 | 单点故障、抗毁性差、覆盖受限、不适应高速机动节点 |
| 分布式自组网（Ad Hoc / MANET） | 无中心、对等多跳 | 各节点本地决策 | AODV（RFC 3561）、OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）、IEEE 802.11 ad-hoc / 802.11s mesh | 抗毁强、即插即用、拓扑自适应、适合机动 | 路由/控制开销大、容量受限、全局优化困难 |
| 分级/分层混合式（分簇） | 簇头 + 簇成员，骨干 + 接入 | 簇头局部协调 + 骨干全局协调 | 分簇路由（如 LEACH/HEED 思想）、战术数据链分层组网 | 兼顾抗毁与效率、扩展性好 | 簇头选举/维护有开销、簇头成为局部关键节点 |

**形态选择的分析**：

- **纯集中式不可行**：无人平台高速机动、链路随机通断，中心链路一旦中断全网失联；且中心基站覆盖受限，无法跟随平台机动。
- **纯分布式在窄带宽下开销过大**：资源受限（窄带宽）场景下，分布式路由的洪泛/控制报文开销占比高，且缺乏全局视图，难以做带宽、路由的全局优化和冲突仲裁。
- **分级混合是折中**：数据面用分布式自组网保证抗毁与自愈，管控面用分层协调保证全局优化与冲突仲裁，是军用机动通信的成熟思路（参考 Link 16/TTNT 的分层组网理念）。

### 2.2 控制面与数据面分离

借鉴 **SDN（软件定义网络，OpenFlow/ONF）** 的"控制与转发分离"思想，但**不是**照搬集中式 SDN 控制器，而是适配无人平台场景的"**分布式数据面 + 分层/半集中管控面**"：

| 层面 | 模式 | 职责 | 成熟技术 |
|------|------|------|----------|
| 数据面（连通 + 转发） | 分布式为主 | 邻居发现、多跳转发、拓扑自愈 | MANET 路由（OLSR/AODV）、DTN 存储转发 |
| 管控面（决策 + 仲裁） | 分层、可降级 | 态势汇总、资源优化、冲突仲裁、策略校验 | 协调器 Coordinator + 策略中心 |

**协调器 ≠ 数据必经中心**：协调器是管控面的编排者（任务调度、冲突仲裁、策略校验），**业务数据流不经过协调器**，底层数据转发仍由分布式路由完成。协调器只下发"策略"（路由、带宽、优先级），不转发"数据"。

**降级自治机制（抗毁关键）**：协调器是"逻辑协调中心"而非"物理唯一中心"。当协调器或骨干链路被毁，系统应能逐级降级：

1. 协调器失效 → 区域**簇头/汇聚节点**临时接管本区域协调；
2. 簇头也失效 → 退化为**预置规则 + 节点本地自治**（按固化优先级、最短路径规则运行）；
3. 链路恢复 → 重新选举/上报，恢复全局协调。

这一"可降级、可替换"设计是无人平台网络抗毁性的核心，也是赛题"从中心调度转向自协同"的落地体现。

### 2.3 自组织网络（SON）思想

3GPP 定义的**自组织网络（Self-Organizing Network, SON）**三大能力，与赛题理念一一对应：

| SON 能力 | 含义 | 赛题对应 |
|----------|------|----------|
| 自配置（Self-Configuration） | 节点即插即用、自动入网、自动获取参数 | 分布式组网、邻居发现 |
| 自优化（Self-Optimization） | 自动调路由/带宽/功率等参数 | 自决策、资源动态调度 |
| 自愈（Self-Healing） | 故障自动检测与恢复 | 自感知、故障诊断、自愈建议 |

无人平台组网可视为 SON 思想在"高动态、抗毁、资源受限"场景下的强化版本。

## 3. "分布式、自感知、自决策、自协同"的工程化落地

四个理念不是口号，每一项都能落到具体机制与协议上。**关键区分**："分布式/自感知"主要在**数据面**（用成熟网络协议实现），"自决策/自协同"主要在**管控面**（用多智能体 + 确定性算法实现）；LLM 只负责意图理解、故障解释、工具选择，**不直接跑路由协议、不做精确数值计算**。

### 3.1 分布式：去中心化组网与决策

| 机制 | 技术手段 | 说明 |
|------|----------|------|
| 邻居发现 | HELLO 消息周期广播 | 节点周期广播自身 ID、位置、序列号，结合链路对称性/邻居状态判定建立邻接关系 |
| 分布式路由（主动式） | OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）/ OLSRv2（RFC 7181） | 周期洪泛链路状态，全网维护一致拓扑视图，低时延 |
| 分布式路由（反应式） | AODV（RFC 3561） | 有数据才发起路由发现（RREQ/RREP），省开销 |
| 分簇 | LEACH、HEED 等分簇算法 | 节点聚簇、簇头局部协调，降低全局控制开销 |
| 去中心化决策 | 每节点本地计算下一跳 | 用 Dijkstra/K 最短路本地算路，无需全局控制器 |

### 3.2 自感知：网络状态与频谱感知

| 感知维度 | 技术手段 | 赛题映射 |
|----------|----------|----------|
| 邻居/拓扑感知 | HELLO 信标、拓扑控制消息（OLSRv2 的 TC）、全网快照 | 拓扑感知、连通分量分析 |
| 链路质量感知 | **ETX（期望传输次数，De Couto 等 2003）**、SNR、RSSI、误码率、丢包率 | `ber`、`packetLossRate`、`delayMs`、`jitterMs` |
| 频谱/干扰感知 | 认知无线电、频谱扫描、干扰检测、动态频谱接入（IEEE 802.22 WRAN） | 强干扰场景下的自适应换频/跳频 |
| 异常感知 | 阈值规则 + 时序异常检测 | 故障诊断、异常事件检测 |

其中 **ETX** 是自组织网络最常用的链路代价度量：ETX = 1 /（正向成功投递率 × 反向成功投递率），可由误码率、丢包率换算而来，直接作为路由权重，使算法"感知"链路质量。这是把赛题的链路五要素接入路由决策的关键桥梁。

### 3.3 自决策：本地路由 + 智能体策略

决策分**两个层次**，各司其职：

| 层次 | 决策主体 | 决策内容 | 技术 |
|------|----------|----------|------|
| 本地（数据面） | 每个节点 | 下一跳选择、本地转发 | 分布式路由 + Dijkstra/K 最短路 |
| 全局（管控面） | 运维 Agent → 资源 Agent → 协调器 | 故障定位、候选路由、带宽分配、QoS 优先级 | LLM 意图理解 + OR-Tools/NetworkX 确定性算法 + 策略校验 |

**LLM 的定位边界**（赛题评分点 2.3 的关键）：LLM 负责解析业务约束、解释故障、判断调用哪类工具、生成规范的工具调用参数、总结决策依据；**不负责**精确算最短路径/最大流/带宽分配（这些由确定性算法保证可复现、可校验），**不绕过**策略校验直接改网络状态。

### 3.4 自协同：冲突仲裁与协作传输

| 协同机制 | 技术手段 | 说明 |
|----------|----------|------|
| 资源冲突仲裁 | 优先级调度、多维资源加锁、快照版本校验 | 多业务争用链路时按优先级/最低保障带宽分配 |
| 资源协商 | 博弈论、拍卖/竞价机制 | 分布式频谱/带宽竞价，避免互相抢占 |
| 协作传输 | 多路径并行、协作分集、中继协作 | 提高可靠性与吞吐 |
| Agent 协同 | A2A 消息（运维 ↔ 资源 ↔ 协调器） | 交换诊断结果、约束、候选策略 |

### 3.5 四者闭环

"分布式、自感知、自决策、自协同"构成一个闭环，对应赛题要求的"状态采集 → 异常识别 → 故障诊断 → 资源评估 → 策略生成 → 策略校验 → 策略下发 → 效果反馈 → 再评估"：

```
自感知（采集/诊断）
   │ 态势 + 约束
   ▼
自决策（本地路由 + 智能体生成策略）
   │ 候选策略
   ▼
自协同（冲突仲裁 + 校验 + 协作传输）
   │ 已校验策略下发 + 执行反馈
   ▼
分布式数据面执行 → 再自感知（闭环）
```

## 4. 组网分层与节点角色

无人平台网络是典型的**"接入网 — 中继层 — 骨干网"三层结构**，各层职责、带宽、机动性不同。

```
        ┌───────────── 骨干网 (Backbone) ─────────────┐
        地面站/指挥所 ◄──高带宽微波/卫星──► 卫星/预警机
                     │                    │
        ┌────────────▼──── 中继层 (Relay) ────────────┐
        中继机/中继节点（多跳转发、扩展覆盖、绕视距遮挡）
                     │                    │
        ┌────────────▼──── 接入网 (Access) ───────────┐
        末端无人平台（UAV/UGV/UUV，单跳或多跳接入）
```

### 4.1 三层结构详述

| 层次 | 组成 | 链路特点 | 主要功能 |
|------|------|----------|----------|
| 接入网（Access） | 末端无人平台 | 近距离、带宽较小、机动性强、链路断续 | 业务产生/接收、单跳或多跳接入中继/骨干 |
| 中继层（Relay） | 中继机、升空平台 | 中距、承上启下、需覆盖/绕遮挡 | 多跳转发、扩展覆盖、克服视距遮挡、延伸接入范围 |
| 骨干网（Backbone） | 地面站、预警机、卫星终端 | 高带宽、长距、相对稳定 | 跨区域互联、上联卫星/指挥所、承接大容量回传 |

**层次间关系**：接入层末端平台先接入最近的**中继节点**，中继节点逐跳把数据汇聚到**骨干节点**，再由骨干网通过微波/卫星链路送抵**地面指挥所/卫星**。带宽自接入层向骨干层逐级增大，机动性自骨干层向接入层逐级增强。

### 4.2 节点角色与功能

| 角色 | 职责 | 典型载体 |
|------|------|----------|
| 普通节点（member） | 业务源/宿，接入网络 | 末端无人机、无人车 |
| 中继节点（relay） | 多跳转发、扩大覆盖、克服遮挡 | 中继机、升空平台 |
| 簇头/汇聚节点（cluster head / sink） | 区域内局部协调、数据汇聚、临时接管 | 区域中心节点 |
| 骨干节点/网关（backbone / gateway） | 跨区域互联、上联卫星/指挥所、异构网互联 | 地面站、预警机、卫星终端 |
| 指挥控制节点（C2） | 全局态势汇总、任务下达 | 指挥所、地面站 |

### 4.3 层次间的链路建立与入网/退网

链路建立遵循"邻居发现 → 质量测量 → 拓扑建立 → 路由计算"四步（详见第 5 章），层次间连接的核心动作：

1. **接入选择**：末端平台入网时广播接入请求，选择信号最强/路径最优的邻近中继或簇头接入。
2. **中继建立**：中继节点之间以及中继到骨干之间建立转发路径，形成多跳链。
3. **骨干上联**：骨干节点通过微波/卫星链路与地面站、卫星建立高带宽回传。
4. **入网/退网**：节点上线广播 → 拓扑更新（链路状态通告）→ 触发路由重算 → 智能体感知连通度变化 → 生成替代路径/自愈建议。

### 4.4 分簇与簇头机制

分级混合组网中，**分簇**是控制开销、提升扩展性的关键手段：

| 分簇算法 | 来源 | 思想 |
|----------|------|------|
| LEACH | Heinzelman 等，2000（WSN 经典） | 簇头轮换、簇内单跳，均衡能耗 |
| HEED | Younis & Fahmy，2004 | 混合分布式分簇，考虑剩余能量与通信代价 |

无人平台场景可借鉴其"簇头轮换 + 簇头降级"思想：簇头不是固定节点，可轮换选举，簇头失效时成员重新选簇头，避免单点故障。

### 4.5 与赛题节点/链路的对应

赛题样例数据中 `GND`（地面）→ `AIR`（空中）的 `microwave`（微波）链路，正对应"骨干/地面指挥节点 ↔ 空中中继/机动节点"的骨干-接入关系。链路类型字段 `linkType` 可扩展为 `microwave`（微波）、`satellite`（卫星）、`vhf/uhf`（超短波）等，对应本章的骨干、中继、接入各层。

## 5. 链路建立过程

一条链路从"节点开机"到"可承载业务"，遵循"**邻居发现 → 链路质量测量 → 拓扑建立 → 路由计算 → 链路维护/失效处理**"的完整生命周期。本节按此展开，并给出每步对应的协议标准与赛题落地。

### 5.1 总体流程

```
节点开机/入网
   │ ① 邻居发现（HELLO 广播与邻居/链路状态判定）
   ▼
链路质量测量（RSSI/SNR/BER → ETX 代价）
   │ ② 生成链路代价，作为路由权重
   ▼
拓扑建立（主动式洪泛 / 反应式按需探测）
   │ ③ 形成全网或局部拓扑视图
   ▼
路由计算（Dijkstra / K 最短路 / CSPF）
   │ ④ 确定下一跳 / 候选路径
   ▼
链路维护（周期性探测 + 失效检测 + 重路由）
```

### 5.2 邻居发现（Neighbor Discovery）

| 机制 | 说明 | 标准/来源 |
|------|------|-----------|
| HELLO 消息周期广播 | 节点周期广播自身 ID、位置、能力、序列号，收到即确认邻居 | OLSRv2 HELLO（RFC 7181；OLSRv1 RFC 3626 为 Experimental） |
| 双向链路判定 | 通过双向HELLO信息/链路状态判断可用邻接；具体过程依路由协议而定 | OLSRv2 RFC 7181 |
| 失效判定 | 连续若干周期未收到 HELLO，判定邻居失效 | 定时器超时机制 |

**要点**：

- HELLO 报文携带节点唯一标识、位置、移动性信息、当前时间，为后续链路测量和拓扑建立提供原始输入。
- 只有确认**双向可达**的邻居才纳入路由计算，避免单向链路的"隐藏终端"问题。
- 邻居表维护有效期（lifetime），超时未刷新即删除，对应赛题"节点下线"的自动感知。

### 5.3 链路质量测量（Link Quality Measurement）

链路质量是路由决策的核心输入，分**物理层原始指标**和**链路层综合代价**两层：

| 指标 | 含义 | 来源 |
|------|------|------|
| RSSI | 接收信号强度 | 物理层 |
| SNR | 信噪比 | 物理层 |
| BER | 误码率 | 物理层，赛题字段 `ber` |
| 丢包率 | 数据包丢失比例 | 链路层，赛题字段 `packetLossRate` |
| 时延/抖动 | 端到端时延、抖动 | 赛题字段 `delayMs`、`jitterMs` |

**ETX（期望传输次数，Expected Transmission Count）** 是最常用的综合链路代价（De Couto 等，2003）：

> ETX = 1 /（正向投递率 df × 反向投递率 dr）

- df = 1 − 正向丢包率，dr = 1 − 反向丢包率（可由 `packetLossRate`、`ber` 换算）。
- ETX 越小链路越好，作为 Dijkstra 等最短路算法的**边权**，让路由"感知"链路质量。
- 进一步引入 **ETT（期望传输时间，Draves 等，2004）**，把带宽也纳入代价：ETT = ETX ×（平均包长 / 链路带宽），对应赛题 `bandwidthBps`。

**赛题落地**：不要把五要素简单等同于 ETX。ETX主要反映双向投递成功率；时延、抖动、带宽应作为独立指标。建议先按业务硬约束过滤候选路径（带宽下限、时延/抖动/丢包上限），再对可行路径按业务权重评分。BER 与包丢失率也不可直接互换，二者关系受包长、调制编码、重传等影响。

### 5.4 拓扑建立（Topology Establishment）

按信息获取方式分三类路由协议的拓扑建立机制：

| 类型 | 机制 | 代表协议 | 适用 |
|------|------|----------|------|
| 主动式（表驱动） | 周期洪泛链路状态，全网维护一致拓扑 | OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）、OLSRv2（RFC 7181）、OSPF（RFC 2328）类比 | 密集、低时延要求 |
| 反应式（按需） | 有数据才发起路由发现（RREQ/RREP） | AODV（RFC 3561）、DSR（RFC 4728） | 稀疏、流量少 |
| 混合式 | 区域内主动 + 区域间反应 | ZRP | 大规模分层 |

**关键机制**：

- **拓扑控制消息（OLSRv2 的 TC）**：OLSRv2 使用 TC 传播拓扑信息，并通过 MPR 机制减少冗余转发；LSA 是 OSPF 术语，不应称为 OLSR 的消息。
- **MPR（多点中继）**：OLSR 用于**减少洪泛冗余**的机制——每个节点只选少量邻居作为中继转发控制报文，降低控制开销，适合窄带宽场景（RFC 3626）。
- **按需路由发现**：AODV 中源节点广播 RREQ，目标/中间节点回 RREP，沿途建立反向/正向路由，不维护全网拓扑，省开销。

**赛题落地**：仿真层可用"全网快照 + NetworkX 连通分量分析"简化实现主动式拓扑建立；动态场景下用事件驱动触发重算，模拟反应式的按需更新。

### 5.5 路由计算（Route Computation）

拓扑视图建立后，用图算法计算转发路径：

| 算法 | 用途 | 来源 |
|------|------|------|
| Dijkstra | 单源最短路 | Dijkstra 1959，O((V+E) log V) |
| Bellman-Ford | 含负权/分布式距离向量 | 距离向量协议（Babel，RFC 6126） |
| K 最短路（Yen） | 多候选路径，供故障切换 | Yen 1971 |
| CSPF（约束最短路） | 带带宽/时延/丢包约束的路径选择 | MPLS-TE（RFC 3209）思想 |

**关键区分**：

- **分布式**：每节点本地算下一跳（Dijkstra/距离向量），对应数据面。
- **集中式辅助**：由 Python 算法服务算 K 条候选路径 + CSPF 约束过滤，返回给智能体，对应管控面（方案中的算法层）。

### 5.6 链路维护与失效处理（Link Maintenance）

链路是动态的，建立后仍需持续维护：

| 机制 | 说明 | 赛题对应 |
|------|------|----------|
| 失效检测 | 连续若干 HELLO 周期未收到，判定链路中断 | 异常事件检测 |
| 局部修复 | AODV 在断链处就近重路由，避免全局重算 | 替代路径生成 |
| 拓扑更新 | 链路状态变化洪泛全网，触发重算 | 拓扑快速变化场景 |
| 自愈建议 | 智能体基于诊断结果生成恢复策略 | 自愈建议生成 |

**赛题落地**：链路中断（`status` 变 down / 丢包率突增）→ 运维 Agent 感知 → 资源 Agent 计算替代路径 → 策略校验 → 下发 → 反馈，构成一个完整的故障恢复闭环。

### 5.7 与赛题指标/数据的对应

| 环节 | 赛题指标 | 赛题数据字段 |
|------|----------|--------------|
| 邻居发现 + 质量测量 | 状态感知时间 | `linkId`、`srcNodeId`、`dstNodeId`、`params.*` |
| 拓扑建立 + 路由计算 | 策略生成时间 | 拓扑快照、连通分量 |
| 路由计算 + 失效处理 | 策略下发时间、故障恢复时间 | `status`、`ber`、`packetLossRate` |
| 全过程 | 网络连通度、业务 QoS 达标率 | `linkType`、`bandwidthBps` |

| 资源维度 | 分配/调度方式 | 成熟技术 |
|----------|---------------|----------|
| 带宽/时隙 | 按需分配、动态时分、优先级抢占 | 动态 TDMA、DAMA、OFDMA |

## 7. 数据传输

- **多跳转发**：源 → 中继 → 骨干逐跳传递。
- **断续链路容错**：链路随机通断时用**容迟容断（DTN）"存储-转发"**，等链路恢复再传（对应赛题"链路断续多发"）。
- **协同传输**：多路径并行、协作分集，提高可靠性和吞吐。

| AODV | 反应式（按需） | RFC 3561 | 拓扑稀疏、流量少 |

## 9. 落地建议（仿真实现）

> **数据面**采用一种明确的 MANET 路由基线（原型阶段建议 OLSRv2 或 AODV 二选一，后续再评估混合部署），参考 TTNT/Link 16 的设计理念；**管控面**采用多智能体（运维 Agent + 资源控制 Agent + Coordinator 协调仲裁），支持中心降级自治；断续链路可扩展 DTN 存储转发。

仿真环境无需实现完整协议栈，建议：

1. 用 **NetworkX 的连通分量 / 最短路径 / K 最短路** 简化实现"分布式路由"效果；
2. 用**链路代价 ETX**（由误码率、丢包率换算）作为路由权重，让算法"感知"链路质量；
3. 带宽分配用 **OR-Tools 线性/整数规划**，QoS 用 **DiffServ 式优先级队列**建模；
4. 文档中明确"参考 TTNT/Link 16/OLSRv2 标准，仿真层做协议简化"。

## 11. 无人平台动态通信网络仿真架构（新增）

本节给出可落地的仿真系统分层、核心对象、事件闭环和多智能体接口。它是**仿真平台架构**，不代表真实无线设备必然采用同样协议栈；协议行为可按仿真精度分级实现。

### 11.1 架构目标与边界

- **场景可控**：能够注入节点上下线/移动、链路通断/质量变化、业务到达与QoS变化，以及多因素组合事件。
- **网络行为可解释**：把物理链路、逻辑承载、邻居关系、路由、队列和业务流分开建模。
- **策略可执行**：Agent输出的候选策略必须经过约束校验、资源准入和仿真器执行反馈。
- **结果可复现**：固定随机种子、事件时间戳、状态版本、策略版本和指标采样周期。
- **边界明确**：仿真器负责网络状态演化和数据面执行；Agent负责感知、诊断、优化建议和协调，不由LLM直接模拟逐包转发或计算精确最优解。

### 11.2 总体分层架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 场景与实验层  Scenario / Experiment                            │
│ 场景配置、节点轨迹、事件注入、随机种子、测试集、实验编排       │
├──────────────────────────────────────────────────────────────┤
│ 业务层  Service / Flow                                         │
│ 话音/视频/图片/数据/控制业务；流量模型；QoS/SLA；准入与降级      │
├──────────────────────────────────────────────────────────────┤
│ 网络层  Network / Routing                                      │
│ 邻居与拓扑、OLSRv2或AODV路由、路径选择、转发、分区/恢复          │
├──────────────────────────────────────────────────────────────┤
│ 链路层  Link / MAC / Queue                                     │
│ 链路可用性、双向质量、共享介质竞争、队列、调度、重传/丢弃       │
├──────────────────────────────────────────────────────────────┤
│ 物理层抽象  Radio / Channel                                    │
│ 传播损耗、覆盖、干扰、信道占用、RSSI/SNR/BER（按仿真精度选用）  │
├──────────────────────────────────────────────────────────────┤
│ 仿真内核  Discrete-event Engine                                │
│ 时钟、事件队列、状态仓库、规则执行、快照、指标采集、回放        │
└──────────────────────────────────────────────────────────────┘
       ▲状态/观测                         ▼策略/动作
┌──────────────────────────────────────────────────────────────┐
│ 多智能体管控层  Multi-Agent Control                            │
│ 运维Agent → 资源控制Agent → 协调/仲裁器 → 策略校验与执行适配器   │
│ 诊断、路径/资源优化、冲突处理、降级自治、执行结果解释           │
└──────────────────────────────────────────────────────────────┘
```

**说明**：控制面/数据面是网络功能维度；控制链路/数据链路是业务承载维度，二者不可混为一谈。网络控制报文（如HELLO、TC、RREQ/RREP）属于协议控制流量；遥控指令、遥测等C2业务属于业务流。

### 11.3 核心对象模型：Node、Link、Flow

**Node（节点）**建议字段：`nodeId`、`nodeType`、`role`、`position`、`velocity`、`status`、`interfaces[]`、`capabilities[]`、`energy`（可选）、`agentId`（可选）。节点角色（末端/中继/簇头/网关）是逻辑属性，不应决定其必然与哪些节点相连。

**Link（链路/承载）**建议字段：`linkId`、`srcNodeId`、`dstNodeId`、`linkType`、`status`、`direction`、`capacityBps`、`availableBps`、`delayMs`、`jitterMs`、`ber`、`packetLossRate`、`lastUpdatedAt`。需要显式区分：

1. **有向性**：A→B 与 B→A 的质量可不同；如需双向通信，应分别评估两个方向。
2. **承载能力**：`capabilities`可标记`control`、`data`或两者；并非任意节点对都同时存在控制与数据链路。
3. **共享/独立**：控制和数据若共享同一无线承载，建一个共享容量资源并按队列/业务分类竞争；若使用独立接口/信道，则建立不同`linkId`并分别维护参数。
4. **容量语义**：区分物理容量、可用容量、已分配容量和实时吞吐，不能把它们都写成一个`bandwidthBps`。
5. **参数来源**：赛题样例字段作为输入基线；RSSI/SNR、频率、信道占用、接口和队列指标属于可选扩展，不能假定赛题数据一定提供。

**Flow（业务流）**建议字段：`flowId`、`srcNodeId`、`dstNodeId`、`serviceType`、`trafficProfile`、`minBandwidthBps`、`maxBandwidthBps`、`maxDelayMs`、`maxJitterMs`、`maxLossRate`、`priority`、`criticality`、`preemptible`、`state`。`priority`（调度优先级）与`criticality`（任务关键程度）分开配置；不能固定认定话音永远高于视频或数据。

### 11.4 控制链路与数据链路的建模规则

| 场景 | 建模方式 | 资源约束 |
|---|---|---|
| 控制与数据共用同一无线承载 | 一个物理/无线Link，多个业务队列或逻辑承载 | 所有队列共享总容量，调度器实施优先级/权重/限流 |
| 控制与数据使用独立无线接口/信道 | 分别建立Control-Link和Data-Link（不同linkId） | 分别计算容量、时延、丢包和故障状态 |
| 只有控制链路 | 仅声明`control`能力，不生成数据承载 | 仅允许控制类Flow通过 |
| 只有数据链路 | 仅声明`data`能力 | 不应把该链路当作C2保障路径 |
| 单向/非对称链路 | 分方向记录质量和状态 | 路径可行性需逐跳检查对应方向 |

建议数据结构采用“物理链路/接口资源 + 逻辑承载 + Flow”的关系，而不是对每一对节点机械生成两条链路。

### 11.5 事件驱动仿真闭环

1. **事件生成**：场景引擎按时间线/随机过程注入`NODE_UP/DOWN`、`NODE_MOVE`、`LINK_DOWN/UP`、`LINK_PARAM_CHANGE`、`FLOW_ARRIVAL/END`、`QOS_CHANGE`、`INTERFERENCE_ON/OFF`。
2. **状态更新**：仿真内核更新节点、链路、队列和业务流状态，生成带`eventId`与`stateVersion`的事件。
3. **网络机制响应**：链路/邻居超时、拓扑传播、路由更新、队列调度等由规则引擎或协议模块执行。
4. **观测汇聚**：运维Agent获取授权范围内的快照/增量指标，完成异常检测、影响分析和诊断。
5. **资源决策**：资源Agent基于业务约束、可行路径和剩余容量，计算路由、带宽、队列权重、限流/降级等候选动作。
6. **协调与校验**：协调器按状态版本校验策略，执行容量约束、策略冲突、权限和幂等性检查；过期策略拒绝或重算。
7. **执行与反馈**：策略适配器调用仿真器API；仿真器返回成功/失败及原因；继续采样QoS和资源指标，形成闭环。

### 11.6 多智能体职责与接口契约

| 角色 | 输入 | 输出/动作 | 不应越权的事项 |
|---|---|---|---|
| 运维Agent | 拓扑/链路/节点/流量观测、历史事件 | 异常事件、故障定位、受影响Flow、置信度 | 不直接修改底层链路或伪造观测 |
| 资源控制Agent | 诊断结果、Flow QoS、链路容量、候选路径 | 路由/带宽/队列/限流/降级候选策略 | 不绕过准入和容量检查 |
| Coordinator | 多Agent候选策略、快照版本、规则 | 冲突仲裁、策略批准/拒绝、降级自治 | 不成为业务数据转发必经点 |
| Policy Adapter | 已批准策略及版本 | 调用仿真器、返回执行状态 | 不自行改变策略语义 |

建议统一消息信封：`messageId`、`traceId`、`taskId`、`from`、`to`、`messageType`、`stateVersion`、`createdAt`、`payload`。策略应包含`policyId`、`baseStateVersion`、`validUntil`、`actions[]`、`constraints`、`reason`、`rollbackPolicy`。

### 11.7 路由、QoS与资源控制基线

- 路由协议原型先选一种：OLSRv2（主动式，RFC 7181）或AODV（按需式，RFC 3561）。OLSRv2使用HELLO进行链路感知/邻居发现，使用TC传播拓扑；AODV使用RREQ/RREP/RERR，HELLO可选。不要把OLSR的TC称为OSPF LSA，也不要把HELLO写成必然需要独立HELLO-ACK的握手。
- QoS按Flow约束进行准入：`bandwidth >= minBandwidth`、`delay <= maxDelay`、`jitter <= maxJitter`、`loss <= maxLoss`；先判可行，再做优化。资源不足时明确拒绝、排队或降级，不得标记为“已保障”。
- DiffServ（RFC 2475）用于分类/标记和逐跳PHB，不等于端到端资源预留；RSVP（RFC 2205）是资源预留信令，不是路由协议，预留状态需要沿路径维护。仿真器可实现简化准入控制，不必声称完整实现RSVP。
- 路由代价可使用ETX表达双向投递可靠性；时延、抖动、带宽、BER和丢包率应分别保留，按业务进行约束过滤和评分。
- 对源节点故障与中继节点故障分别处理：中继失效可能通过替代路径恢复；源节点失效时，源业务无法仅靠重路由恢复，除非有备份源、缓存或数据副本接管。

### 11.8 仿真精度分级与实现建议

| 级别 | 实现内容 | 适合阶段 |
|---|---|---|
| L0：图与事件抽象 | Node/Link/Flow、事件注入、连通性、路径和资源约束 | 最小可运行版本 |
| L1：网络行为 | 邻居超时、OLSRv2/AODV简化状态机、路由收敛、分区恢复 | 核心赛题验证 |
| L2：业务与队列 | 流量生成、队列、调度、丢弃、拥塞、QoS统计 | QoS与资源管控评估 |
| L3：无线抽象 | 路径损耗、干扰、信道竞争、速率自适应 | 扩展实验 |
| L4：协议/设备级 | 更完整协议栈或与外部网络仿真器联动 | 有明确需求后再做 |

第一阶段建议完成L0+必要L1+简化L2；不要一开始实现完整4G/5G或军用波形协议栈。仿真结果应标明模型假设、抽象层级和未建模因素。

### 11.9 评价指标与测试设计

至少统计：状态感知时延、策略生成时延、策略下发时延、路由恢复时间、网络连通度、QoS达标率、关键业务保障率、资源利用率、控制开销、策略执行成功率、业务中断时长。对每个指标给出起止时间定义、采样周期、统计窗口和分母口径。

测试集应覆盖单因素基线、双因素组合、多因素极端组合、未见拓扑/随机种子；对比“无Agent基线规则”“单Agent”“多Agent协同”，在相同事件序列和资源约束下重复试验并报告均值/分位数。
