1. 无人平台概述

无人平台（Unmanned Platform / Unmanned System）：不搭载机上操作人员、可自主或遥控执行任务的装备/载具。在通信网络语境下，它是网络中的机动节点（mobile node），通过无线链路接入机动通信网络，向指挥/协同节点回传数据和接收指令。

类型 名称 典型任务
空中 无人机（UAV） 侦察、测绘、中继、打击
地面 无人车（UGV） 巡逻、运输、排爆
水面 无人艇（USV） 巡逻、探测、反潜
水下 无人潜航器（UUV/AUV） 探测、布雷、水下中继

关键背景：无人平台处于高速机动、高动态拓扑、窄带宽、强干扰环境下，链路随机通断、带宽动态收缩，因此通信网络需要从”人工配置、中心调度”转向”分布式、自感知、自决策、自协同”的智能化自治模式。

链路质量五要素（对应赛题链路参数模型）：delayMs（时延）、jitterMs（抖动）、bandwidthBps（带宽）、ber（误码率）、packetLossRate（丢包率）。

业务类型与 QoS 门槛：

业务类型 QoS 敏感点
话音 时延、抖动敏感
视频 带宽敏感
数据 丢包敏感
图片 带宽 + 可靠性

2. 组网方式：分级混合 + 控制/数据面分离

无人平台组网不是单一模式，而是在三种基本形态之上，针对”高机动 + 资源受限 + 抗毁”需求演化出的分级混合式。核心结论：

数据面分布式自组网 + 管控面分层协调（协调器统一编排、仲裁，支持降级自治）

2.1 三种基本组网形态

组网方式 结构 决策方式 典型实例 优点 缺点
集中式（有中心） 星型/树型，节点统一连中心基站/AP 中心统一调度 蜂窝网（基站）、IEEE 802.11 基础设施模式 资源分配集中高效、接入管理简单、QoS 可控 单点故障、抗毁性差、覆盖受限、不适应高速机动节点
分布式自组网（Ad Hoc / MANET） 无中心、对等多跳 各节点本地决策 AODV（RFC 3561）、OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）、IEEE 802.11 ad-hoc / 802.11s mesh 抗毁强、即插即用、拓扑自适应、适合机动 路由/控制开销大、容量受限、全局优化困难
分级/分层混合式（分簇） 簇头 + 簇成员，骨干 + 接入 簇头局部协调 + 骨干全局协调 分簇路由（如 LEACH/HEED 思想）、战术数据链分层组网 兼顾抗毁与效率、扩展性好 簇头选举/维护有开销、簇头成为局部关键节点

形态选择的分析：

  • 纯集中式不可行：无人平台高速机动、链路随机通断，中心链路一旦中断全网失联；且中心基站覆盖受限，无法跟随平台机动。
  • 纯分布式在窄带宽下开销过大：资源受限（窄带宽）场景下，分布式路由的洪泛/控制报文开销占比高，且缺乏全局视图，难以做带宽、路由的全局优化和冲突仲裁。
  • 分级混合是折中：数据面用分布式自组网保证抗毁与自愈，管控面用分层协调保证全局优化与冲突仲裁，是军用机动通信的成熟思路（参考 Link 16/TTNT 的分层组网理念）。

2.2 控制面与数据面分离

借鉴 SDN（软件定义网络，OpenFlow/ONF） 的”控制与转发分离”思想，但不是照搬集中式 SDN 控制器，而是适配无人平台场景的”分布式数据面 + 分层/半集中管控面”：

层面 模式 职责 成熟技术
数据面（连通 + 转发） 分布式为主 邻居发现、多跳转发、拓扑自愈 MANET 路由（OLSR/AODV）、DTN 存储转发
管控面（决策 + 仲裁） 分层、可降级 态势汇总、资源优化、冲突仲裁、策略校验 协调器 Coordinator + 策略中心

协调器 ≠ 数据必经中心：协调器是管控面的编排者（任务调度、冲突仲裁、策略校验），业务数据流不经过协调器，底层数据转发仍由分布式路由完成。协调器只下发”策略”（路由、带宽、优先级），不转发”数据”。

降级自治机制（抗毁关键）：协调器是”逻辑协调中心”而非”物理唯一中心”。当协调器或骨干链路被毁，系统应能逐级降级：

  1. 协调器失效 → 区域簇头/汇聚节点临时接管本区域协调；
  2. 簇头也失效 → 退化为预置规则 + 节点本地自治（按固化优先级、最短路径规则运行）；
  3. 链路恢复 → 重新选举/上报，恢复全局协调。

这一”可降级、可替换”设计是无人平台网络抗毁性的核心，也是赛题”从中心调度转向自协同”的落地体现。

2.3 自组织网络（SON）思想

3GPP 定义的自组织网络（Self-Organizing Network, SON）三大能力，与赛题理念一一对应：

SON 能力 含义 赛题对应
自配置（Self-Configuration） 节点即插即用、自动入网、自动获取参数 分布式组网、邻居发现
自优化（Self-Optimization） 自动调路由/带宽/功率等参数 自决策、资源动态调度
自愈（Self-Healing） 故障自动检测与恢复 自感知、故障诊断、自愈建议

无人平台组网可视为 SON 思想在”高动态、抗毁、资源受限”场景下的强化版本。

3. “分布式、自感知、自决策、自协同”的工程化落地

四个理念不是口号，每一项都能落到具体机制与协议上。关键区分：“分布式/自感知”主要在数据面（用成熟网络协议实现），“自决策/自协同”主要在管控面（用多智能体 + 确定性算法实现）；LLM 只负责意图理解、故障解释、工具选择，不直接跑路由协议、不做精确数值计算。

3.1 分布式：去中心化组网与决策

机制 技术手段 说明
邻居发现 HELLO 消息周期广播 节点周期广播自身 ID、位置、序列号，结合链路对称性/邻居状态判定建立邻接关系
分布式路由（主动式） OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）/ OLSRv2（RFC 7181） 周期洪泛链路状态，全网维护一致拓扑视图，低时延
分布式路由（反应式） AODV（RFC 3561） 有数据才发起路由发现（RREQ/RREP），省开销
分簇 LEACH、HEED 等分簇算法 节点聚簇、簇头局部协调，降低全局控制开销
去中心化决策 每节点本地计算下一跳 用 Dijkstra/K 最短路本地算路，无需全局控制器

3.2 自感知：网络状态与频谱感知

感知维度 技术手段 赛题映射
邻居/拓扑感知 HELLO 信标、拓扑控制消息（OLSRv2 的 TC）、全网快照 拓扑感知、连通分量分析
链路质量感知 ETX（期望传输次数，De Couto 等 2003）、SNR、RSSI、误码率、丢包率 ber、packetLossRate、delayMs、jitterMs
频谱/干扰感知 认知无线电、频谱扫描、干扰检测、动态频谱接入（IEEE 802.22 WRAN） 强干扰场景下的自适应换频/跳频
异常感知 阈值规则 + 时序异常检测 故障诊断、异常事件检测

其中 ETX 是自组织网络最常用的链路代价度量：ETX = 1 /（正向成功投递率 × 反向成功投递率），可由误码率、丢包率换算而来，直接作为路由权重，使算法”感知”链路质量。这是把赛题的链路五要素接入路由决策的关键桥梁。

3.3 自决策：本地路由 + 智能体策略

决策分两个层次，各司其职：

层次 决策主体 决策内容 技术
本地（数据面） 每个节点 下一跳选择、本地转发 分布式路由 + Dijkstra/K 最短路
全局（管控面） 运维 Agent → 资源 Agent → 协调器 故障定位、候选路由、带宽分配、QoS 优先级 LLM 意图理解 + OR-Tools/NetworkX 确定性算法 + 策略校验

LLM 的定位边界（赛题评分点 2.3 的关键）：LLM 负责解析业务约束、解释故障、判断调用哪类工具、生成规范的工具调用参数、总结决策依据；不负责精确算最短路径/最大流/带宽分配（这些由确定性算法保证可复现、可校验），不绕过策略校验直接改网络状态。

3.4 自协同：冲突仲裁与协作传输

协同机制 技术手段 说明
资源冲突仲裁 优先级调度、多维资源加锁、快照版本校验 多业务争用链路时按优先级/最低保障带宽分配
资源协商 博弈论、拍卖/竞价机制 分布式频谱/带宽竞价，避免互相抢占
协作传输 多路径并行、协作分集、中继协作 提高可靠性与吞吐
Agent 协同 A2A 消息（运维 ↔︎ 资源 ↔︎ 协调器） 交换诊断结果、约束、候选策略

3.5 四者闭环

“分布式、自感知、自决策、自协同”构成一个闭环，对应赛题要求的”状态采集 → 异常识别 → 故障诊断 → 资源评估 → 策略生成 → 策略校验 → 策略下发 → 效果反馈 → 再评估”：

自感知（采集/诊断）
   │ 态势 + 约束
   ▼
自决策（本地路由 + 智能体生成策略）
   │ 候选策略
   ▼
自协同（冲突仲裁 + 校验 + 协作传输）
   │ 已校验策略下发 + 执行反馈
   ▼
分布式数据面执行 → 再自感知（闭环）

4. 组网分层与节点角色

无人平台网络是典型的“接入网 — 中继层 — 骨干网”三层结构，各层职责、带宽、机动性不同。

        ┌───────────── 骨干网 (Backbone) ─────────────┐
        地面站/指挥所 ◄──高带宽微波/卫星──► 卫星/预警机
                     │                    │
        ┌────────────▼──── 中继层 (Relay) ────────────┐
        中继机/中继节点（多跳转发、扩展覆盖、绕视距遮挡）
                     │                    │
        ┌────────────▼──── 接入网 (Access) ───────────┐
        末端无人平台（UAV/UGV/UUV，单跳或多跳接入）

4.1 三层结构详述

层次 组成 链路特点 主要功能
接入网（Access） 末端无人平台 近距离、带宽较小、机动性强、链路断续 业务产生/接收、单跳或多跳接入中继/骨干
中继层（Relay） 中继机、升空平台 中距、承上启下、需覆盖/绕遮挡 多跳转发、扩展覆盖、克服视距遮挡、延伸接入范围
骨干网（Backbone） 地面站、预警机、卫星终端 高带宽、长距、相对稳定 跨区域互联、上联卫星/指挥所、承接大容量回传

层次间关系：接入层末端平台先接入最近的中继节点，中继节点逐跳把数据汇聚到骨干节点，再由骨干网通过微波/卫星链路送抵地面指挥所/卫星。带宽自接入层向骨干层逐级增大，机动性自骨干层向接入层逐级增强。

4.2 节点角色与功能

角色 职责 典型载体
普通节点（member） 业务源/宿，接入网络 末端无人机、无人车
中继节点（relay） 多跳转发、扩大覆盖、克服遮挡 中继机、升空平台
簇头/汇聚节点（cluster head / sink） 区域内局部协调、数据汇聚、临时接管 区域中心节点
骨干节点/网关（backbone / gateway） 跨区域互联、上联卫星/指挥所、异构网互联 地面站、预警机、卫星终端
指挥控制节点（C2） 全局态势汇总、任务下达 指挥所、地面站

4.3 层次间的链路建立与入网/退网

链路建立遵循”邻居发现 → 质量测量 → 拓扑建立 → 路由计算”四步（详见第 5 章），层次间连接的核心动作：

  1. 接入选择：末端平台入网时广播接入请求，选择信号最强/路径最优的邻近中继或簇头接入。
  2. 中继建立：中继节点之间以及中继到骨干之间建立转发路径，形成多跳链。
  3. 骨干上联：骨干节点通过微波/卫星链路与地面站、卫星建立高带宽回传。
  4. 入网/退网：节点上线广播 → 拓扑更新（链路状态通告）→ 触发路由重算 → 智能体感知连通度变化 → 生成替代路径/自愈建议。

4.4 分簇与簇头机制

分级混合组网中，分簇是控制开销、提升扩展性的关键手段：

分簇算法 来源 思想
LEACH Heinzelman 等，2000（WSN 经典） 簇头轮换、簇内单跳，均衡能耗
HEED Younis & Fahmy，2004 混合分布式分簇，考虑剩余能量与通信代价

无人平台场景可借鉴其”簇头轮换 + 簇头降级”思想：簇头不是固定节点，可轮换选举，簇头失效时成员重新选簇头，避免单点故障。

4.5 与赛题节点/链路的对应

赛题样例数据中 GND（地面）→ AIR（空中）的 microwave（微波）链路，正对应”骨干/地面指挥节点 ↔︎ 空中中继/机动节点”的骨干-接入关系。链路类型字段 linkType 可扩展为 microwave（微波）、satellite（卫星）、vhf/uhf（超短波）等，对应本章的骨干、中继、接入各层。

5. 链路建立过程

一条链路从”节点开机”到”可承载业务”，遵循”邻居发现 → 链路质量测量 → 拓扑建立 → 路由计算 → 链路维护/失效处理”的完整生命周期。本节按此展开，并给出每步对应的协议标准与赛题落地。

5.1 总体流程

节点开机/入网
   │ ① 邻居发现（HELLO 广播与邻居/链路状态判定）
   ▼
链路质量测量（RSSI/SNR/BER → ETX 代价）
   │ ② 生成链路代价，作为路由权重
   ▼
拓扑建立（主动式洪泛 / 反应式按需探测）
   │ ③ 形成全网或局部拓扑视图
   ▼
路由计算（Dijkstra / K 最短路 / CSPF）
   │ ④ 确定下一跳 / 候选路径
   ▼
链路维护（周期性探测 + 失效检测 + 重路由）

5.2 邻居发现（Neighbor Discovery）

机制 说明 标准/来源
HELLO 消息周期广播 节点周期广播自身 ID、位置、能力、序列号，收到即确认邻居 OLSRv2 HELLO（RFC 7181；OLSRv1 RFC 3626 为 Experimental）
双向链路判定 通过双向HELLO信息/链路状态判断可用邻接；具体过程依路由协议而定 OLSRv2 RFC 7181
失效判定 连续若干周期未收到 HELLO，判定邻居失效 定时器超时机制

要点：

  • HELLO 报文携带节点唯一标识、位置、移动性信息、当前时间，为后续链路测量和拓扑建立提供原始输入。
  • 只有确认双向可达的邻居才纳入路由计算，避免单向链路的”隐藏终端”问题。
  • 邻居表维护有效期（lifetime），超时未刷新即删除，对应赛题”节点下线”的自动感知。

5.3 链路质量测量（Link Quality Measurement）

链路质量是路由决策的核心输入，分物理层原始指标和链路层综合代价两层：

指标 含义 来源
RSSI 接收信号强度 物理层
SNR 信噪比 物理层
BER 误码率 物理层，赛题字段 ber
丢包率 数据包丢失比例 链路层，赛题字段 packetLossRate
时延/抖动 端到端时延、抖动 赛题字段 delayMs、jitterMs

ETX（期望传输次数，Expected Transmission Count） 是最常用的综合链路代价（De Couto 等，2003）：

ETX = 1 /（正向投递率 df × 反向投递率 dr）

  • df = 1 − 正向丢包率，dr = 1 − 反向丢包率（可由 packetLossRate、ber 换算）。
  • ETX 越小链路越好，作为 Dijkstra 等最短路算法的边权，让路由”感知”链路质量。
  • 进一步引入 ETT（期望传输时间，Draves 等，2004），把带宽也纳入代价：ETT = ETX ×（平均包长 / 链路带宽），对应赛题 bandwidthBps。

赛题落地：不要把五要素简单等同于 ETX。ETX主要反映双向投递成功率；时延、抖动、带宽应作为独立指标。建议先按业务硬约束过滤候选路径（带宽下限、时延/抖动/丢包上限），再对可行路径按业务权重评分。BER 与包丢失率也不可直接互换，二者关系受包长、调制编码、重传等影响。

5.4 拓扑建立（Topology Establishment）

按信息获取方式分三类路由协议的拓扑建立机制：

类型 机制 代表协议 适用
主动式（表驱动） 周期洪泛链路状态，全网维护一致拓扑 OLSRv2（RFC 7181；OLSRv1 RFC 3626 为 Experimental）、OLSRv2（RFC 7181）、OSPF（RFC 2328）类比 密集、低时延要求
反应式（按需） 有数据才发起路由发现（RREQ/RREP） AODV（RFC 3561）、DSR（RFC 4728） 稀疏、流量少
混合式 区域内主动 + 区域间反应 ZRP 大规模分层

关键机制：

  • 拓扑控制消息（OLSRv2 的 TC）：OLSRv2 使用 TC 传播拓扑信息，并通过 MPR 机制减少冗余转发；LSA 是 OSPF 术语，不应称为 OLSR 的消息。
  • MPR（多点中继）：OLSR 用于减少洪泛冗余的机制——每个节点只选少量邻居作为中继转发控制报文，降低控制开销，适合窄带宽场景（RFC 3626）。
  • 按需路由发现：AODV 中源节点广播 RREQ，目标/中间节点回 RREP，沿途建立反向/正向路由，不维护全网拓扑，省开销。

赛题落地：仿真层可用”全网快照 + NetworkX 连通分量分析”简化实现主动式拓扑建立；动态场景下用事件驱动触发重算，模拟反应式的按需更新。

5.5 路由计算（Route Computation）

拓扑视图建立后，用图算法计算转发路径：

算法 用途 来源
Dijkstra 单源最短路 Dijkstra 1959，O((V+E) log V)
Bellman-Ford 含负权/分布式距离向量 距离向量协议（Babel，RFC 6126）
K 最短路（Yen） 多候选路径，供故障切换 Yen 1971
CSPF（约束最短路） 带带宽/时延/丢包约束的路径选择 MPLS-TE（RFC 3209）思想

关键区分：

  • 分布式：每节点本地算下一跳（Dijkstra/距离向量），对应数据面。
  • 集中式辅助：由 Python 算法服务算 K 条候选路径 + CSPF 约束过滤，返回给智能体，对应管控面（方案中的算法层）。

5.6 链路维护与失效处理（Link Maintenance）

链路是动态的，建立后仍需持续维护：

机制 说明 赛题对应
失效检测 连续若干 HELLO 周期未收到，判定链路中断 异常事件检测
局部修复 AODV 在断链处就近重路由，避免全局重算 替代路径生成
拓扑更新 链路状态变化洪泛全网，触发重算 拓扑快速变化场景
自愈建议 智能体基于诊断结果生成恢复策略 自愈建议生成

赛题落地：链路中断（status 变 down / 丢包率突增）→ 运维 Agent 感知 → 资源 Agent 计算替代路径 → 策略校验 → 下发 → 反馈，构成一个完整的故障恢复闭环。

11. 无人平台动态通信网络仿真架构（新增）

本节给出可落地的仿真系统分层、核心对象、事件闭环和多智能体接口。它是仿真平台架构，不代表真实无线设备必然采用同样协议栈；协议行为可按仿真精度分级实现。

11.1 架构目标与边界

  • 场景可控：能够注入节点上下线/移动、链路通断/质量变化、业务到达与QoS变化，以及多因素组合事件。
  • 网络行为可解释：把物理链路、逻辑承载、邻居关系、路由、队列和业务流分开建模。
  • 策略可执行：Agent输出的候选策略必须经过约束校验、资源准入和仿真器执行反馈。
  • 结果可复现：固定随机种子、事件时间戳、状态版本、策略版本和指标采样周期。
  • 边界明确：仿真器负责网络状态演化和数据面执行；Agent负责感知、诊断、优化建议和协调，不由LLM直接模拟逐包转发或计算精确最优解。

11.3 核心对象模型：Node、Link、Flow

Node（节点）建议字段：nodeId、nodeType、role、position、velocity、status、interfaces[]、capabilities[]、energy（可选）、agentId（可选）。节点角色（末端/中继/簇头/网关）是逻辑属性，不应决定其必然与哪些节点相连。

Link（链路/承载）建议字段：linkId、srcNodeId、dstNodeId、linkType、status、direction、capacityBps、availableBps、delayMs、jitterMs、ber、packetLossRate、lastUpdatedAt。需要显式区分：

  1. 有向性：A→B 与 B→A 的质量可不同；如需双向通信，应分别评估两个方向。
  2. 承载能力：capabilities可标记control、data或两者；并非任意节点对都同时存在控制与数据链路。
  3. 共享/独立：控制和数据若共享同一无线承载，建一个共享容量资源并按队列/业务分类竞争；若使用独立接口/信道，则建立不同linkId并分别维护参数。
  4. 容量语义：区分物理容量、可用容量、已分配容量和实时吞吐，不能把它们都写成一个bandwidthBps。
  5. 参数来源：赛题样例字段作为输入基线；RSSI/SNR、频率、信道占用、接口和队列指标属于可选扩展，不能假定赛题数据一定提供。

Flow（业务流）建议字段：flowId、srcNodeId、dstNodeId、serviceType、trafficProfile、minBandwidthBps、maxBandwidthBps、maxDelayMs、maxJitterMs、maxLossRate、priority、criticality、preemptible、state。priority（调度优先级）与criticality（任务关键程度）分开配置；不能固定认定话音永远高于视频或数据。

11.4 控制链路与数据链路的建模规则

场景 建模方式 资源约束
控制与数据共用同一无线承载 一个物理/无线Link，多个业务队列或逻辑承载 所有队列共享总容量，调度器实施优先级/权重/限流
控制与数据使用独立无线接口/信道 分别建立Control-Link和Data-Link（不同linkId） 分别计算容量、时延、丢包和故障状态
只有控制链路 仅声明control能力，不生成数据承载 仅允许控制类Flow通过

11.5 事件驱动仿真闭环

  1. 事件生成：场景引擎按时间线/随机过程注入NODE_UP/DOWN、NODE_MOVE、LINK_DOWN/UP、LINK_PARAM_CHANGE、FLOW_ARRIVAL/END、QOS_CHANGE、INTERFERENCE_ON/OFF。
  2. 状态更新：仿真内核更新节点、链路、队列和业务流状态，生成带eventId与stateVersion的事件。
  3. 网络机制响应：链路/邻居超时、拓扑传播、路由更新、队列调度等由规则引擎或协议模块执行。
  4. 观测汇聚：运维Agent获取授权范围内的快照/增量指标，完成异常检测、影响分析和诊断。
  5. 资源决策：资源Agent基于业务约束、可行路径和剩余容量，计算路由、带宽、队列权重、限流/降级等候选动作。
  6. 协调与校验：协调器按状态版本校验策略，执行容量约束、策略冲突、权限和幂等性检查；过期策略拒绝或重算。
  7. 执行与反馈：策略适配器调用仿真器API；仿真器返回成功/失败及原因；继续采样QoS和资源指标，形成闭环。

11.7 路由、QoS与资源控制基线

  • 路由协议原型先选一种：OLSRv2（主动式，RFC 7181）或AODV（按需式，RFC 3561）。OLSRv2使用HELLO进行链路感知/邻居发现，使用TC传播拓扑；AODV使用RREQ/RREP/RERR，HELLO可选。不要把OLSR的TC称为OSPF LSA，也不要把HELLO写成必然需要独立HELLO-ACK的握手。
  • QoS按Flow约束进行准入：bandwidth >= minBandwidth、delay <= maxDelay、jitter <= maxJitter、loss <= maxLoss；先判可行，再做优化。资源不足时明确拒绝、排队或降级，不得标记为“已保障”。
  • DiffServ（RFC 2475）用于分类/标记和逐跳PHB，不等于端到端资源预留；RSVP（RFC 2205）是资源预留信令，不是路由协议，预留状态需要沿路径维护。仿真器可实现简化准入控制，不必声称完整实现RSVP。
  • 路由代价可使用ETX表达双向投递可靠性；时延、抖动、带宽、BER和丢包率应分别保留，按业务进行约束过滤和评分。
  • 对源节点故障与中继节点故障分别处理：中继失效可能通过替代路径恢复；源节点失效时，源业务无法仅靠重路由恢复，除非有备份源、缓存或数据副本接管。

级别 实现内容 适合阶段
L0：图与事件抽象 Node/Link/Flow、事件注入、连通性、路径和资源约束 最小可运行版本
L1：网络行为 邻居超时、OLSRv2/AODV简化状态机、路由收敛、分区恢复 核心赛题验证
L2：业务与队列 流量生成、队列、调度、丢弃、拥塞、QoS统计 QoS与资源管控评估
L3：无线抽象 路径损耗、干扰、信道竞争、速率自适应 扩展实验
L4：协议/设备级 更完整协议栈或与外部网络仿真器联动 有明确需求后再做

第一阶段建议完成L0+必要L1+简化L2；不要一开始实现完整4G/5G或军用波形协议栈。仿真结果应标明模型假设、抽象层级和未建模因素。

11.9 评价指标与测试设计

至少统计：状态感知时延、策略生成时延、策略下发时延、路由恢复时间、网络连通度、QoS达标率、关键业务保障率、资源利用率、控制开销、策略执行成功率、业务中断时长。对每个指标给出起止时间定义、采样周期、统计窗口和分母口径。

测试集应覆盖单因素基线、双因素组合、多因素极端组合、未见拓扑/随机种子；对比“无Agent基线规则”“单Agent”“多Agent协同”，在相同事件序列和资源约束下重复试验并报告均值/分位数。

0. 文档约定

0.1 场景模板（6 部分）

每个小场景统一按以下 6 部分描述：

  1. 背景：场景发生的业务背景与触发原因。
  2. 参与方：涉及哪些节点/智能体。
  3. 前置条件（Precondition）：场景发生前网络必须满足的状态。

1. 大场景：初始组网

1.1 小场景：全网冷启动

1. 背景：任务开始，所有节点同时开机，网络从零开始自组织成网，无预配置拓扑；无线接口、信道、地址与必要安全参数已按实验假设完成初始化。

2. 参与方：C、B1、R1、R2、U1、U2、G1、G2（全部节点）。

3. 前置条件：所有节点已上电、无线模块就绪，但尚未建立任何链路；各节点只有自身 ID 和角色配置。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 U1 广播 HELLO{nodeId:"U1",type:"UAV",seq:1} R1 收到，回 双向HELLO状态确认（非独立ACK报文） R1 邻居表新增 U1 → ETX 1.0 U1 与 R1 建立双向邻居
2 R1 广播 HELLO B1 收到并回 ACK；U1 收到并回 ACK B1、U1 各自邻居表新增 R1 R1 同时连 B1 和 U1
3 B1 广播 HELLO C、R1、R2 收到并回 ACK 各节点邻居表更新 B1 与 C、R1、R2 建邻居
4 各节点传播 TC{自己和邻居的链路代价} 全网节点收到并转发 每节点拓扑表拼出全网地图 全网拓扑视图一致
5 各节点本地跑 Dijkstra — 每节点路由表生成到全网目的地的下一跳 全网路由建立
6 C 向仿真器请求全局快照 仿真器返回 nodes[]/links[] C 保存 snapshotVersion=1 协调器获得全局视图

5. 后置状态：全网连通，每节点有完整邻居表、拓扑表、路由表；C 持有初始快照；可承载业务。

6. 智能体 vs 普通无 LLM 差别：普通网络采用HELLO/TC拓扑维护与路由算法 也能自动成网（步骤 1-5 都是协议层，两者相同）。差别在步骤 6 及之后：智能体版本由运维 Agent 对初始拓扑做主动评估（连通度、关键节点、单点风险），并生成初始资源规划；无 LLM 版本只有”能连通”，没有”态势评估和初始优化”。

1.2 小场景：分批/增量入网

1. 背景：R2 因故晚开机，网络已由其他节点组成，R2 现在加入。

2. 参与方：R2、B1、G1、G2、C。

3. 前置条件：除 R2 外全网已连通；R2 开机但未接入。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 R2 广播 HELLO B1、G1、G2 收到并回 ACK 各节点邻居表新增 R2 R2 与 B1、G1、G2 建邻居
2 R2 发布自己的 TC 全网收到，触发增量拓扑更新 各节点拓扑表新增 R2 及其链路 全网拓扑增量刷新
3 各节点重算路由 — 部分节点路由表更新（如 G1 改走 R2） 流量可能切到 R2
4 C 更新全局快照 — C 快照 snapshotVersion+1 协调器感知新拓扑

5. 后置状态：R2 入网，拓扑更新，部分流量切换到经 R2 的更优路径。

6. 智能体 vs 普通无 LLM 差别：普通网络靠增量 TC 也能把 R2 纳入（步骤 1-3）。差别：智能体版本由运维 Agent 识别”有新节点入网”这一事件并评估其影响（是否成为更优中继、是否需要重分配带宽），资源 Agent 决定是否主动迁移业务；无 LLM 版本只做协议级路由收敛，不主动优化业务分布。

2. 大场景：节点动态

2.1 小场景：节点上线

同 1.2 分批入网（单个节点上线可复用同一流程）。

2.2 小场景：节点下线（故障）

1. 背景：U2 因被毁/故障突然失联，不再响应任何报文。这是赛题明确的”节点下线”建模手段。

2. 参与方：U2、R1、C、运维 Agent、资源 Agent。

3. 前置条件：U2 通过 R1 接入，且有一条业务流（如 U2→C 的视频）正在传输。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 U2 停止广播（物理失联） R1 连续 N 个周期收不到 U2 的 HELLO R1 邻居表 U2 条目 lifetime 超时 R1 判定 U2 下线
2 R1 传播 TC{U2 不可达} 全网收到，触发拓扑更新 各节点拓扑表移除 U2 全网知道 U2 下线
3 C 检测到快照变化，创建诊断任务 运维 Agent 收到网络快照 C 分配 traceId/taskId 进入智能体诊断
4 运维 Agent 调用拓扑分析工具 返回连通分量、受影响业务 诊断结果：U2 下线、影响 FLOW(U2→C) 生成 DIAGNOSIS_RESULT
5 运维 Agent 发 DIAGNOSIS_RESULT 资源 Agent 收到 读取 affectedNodes、impactedFlows 资源 Agent 得知故障与约束
6 资源 Agent 调用路由算法 返回替代路径（若有）或”业务无替代路径” 生成 CANDIDATE_POLICY 候选策略
7 资源 Agent 发 CANDIDATE_POLICY C 收到并校验 C 校验拓扑有效性、容量 策略通过/拒绝
8 C 下发 POLICY_APPLY 仿真器执行 仿真器应用策略并反馈 业务恢复或标记不可恢复

5. 后置状态：U2 已从全网拓扑移除；U2 相关业务流或被重路由恢复、或被标记为中断；路由表收敛。

6. 智能体 vs 普通无 LLM 差别：普通网络靠”HELLO 超时 → TC 洪泛 → 重算路由”也能把 U2 移除、恢复连通（步骤 1-2）。差别在步骤 3-8：智能体版本能解释”为什么 U2 下线、影响了哪些业务、业务能否恢复”，并给出可追溯的自愈建议；无 LLM 版本只知道”U2 断了、重路由了”，不区分业务影响、无根因、无解释。

2.3 小场景：节点移动

1. 背景：U1 高速机动，位置变化导致原邻居链路质量下降、新邻居出现。

2. 参与方：U1、R1、R2、运维 Agent、资源 Agent。

3. 前置条件：U1 经 R1 接入，移动到 R1/R2 覆盖交界处。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 U1 持续广播 HELLO（位置更新） R1、R2 都收到 R1 邻居表 U1 代价升高；R2 邻居表新增 U1 链路质量动态变化
2 各节点更新 TC 全网触发拓扑更新 拓扑表链路代价刷新 全网感知 U1 移动
3 运维 Agent 检测链路质量波动 调用质量评估工具 评估 R1-U1 代价 vs R2-U1 代价 识别”U1 应切换接入”
4 资源 Agent 计算切换方案 返回新接入路径 生成 CANDIDATE_POLICY 候选切换策略
5 C 校验并下发 仿真器执行 更新路由表 U1 切换到 R2 接入

5. 后置状态：U1 切换到更优邻居，业务不中断或短暂中断后恢复。

6. 智能体 vs 普通无 LLM 差别：普通网络靠 ETX 代价变化也能让路由自动切换（步骤 1-2，类似 handover）。差别：智能体版本预测性切换（提前评估、主动迁移业务），并解释切换原因；无 LLM 版本是反应式的，代价超过阈值才被动切换，可能已造成丢包。

3. 大场景：链路动态

3.1 小场景：链路中断

1. 背景：R1-B1 链路因遮挡/干扰中断（status→down）。这是赛题”链路随机通断”的核心场景。

2. 参与方：R1、B1、C、运维 Agent、资源 Agent。

3. 前置条件：存在经 R1-B1 的业务流（如 U1→C 的话音）。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 链路 R1-B1 状态变 down R1、B1 双向检测到失联 双方邻居表删除对方 判定链路中断
2 R1、B1 传播 TC{R1-B1 中断} 全网拓扑更新 拓扑表移除该链路 全网知道中断
3 运维 Agent 收到快照变化 调用故障诊断工具 定位”R1-B1 中断，影响 FLOW(U1→C)” 生成 DIAGNOSIS_RESULT
4 运维 Agent 发 DIAGNOSIS_RESULT 资源 Agent 收到 读取 affectedLinks、constraints 得知约束”R1-B1 不可用”
5 资源 Agent 调用 K 最短路算法 返回替代路径（如 U1→R1→R2→B1→C） 生成 CANDIDATE_POLICY 候选替代路由
6 C 校验替代路径 校验拓扑有效、容量足够 通过校验 策略可下发
7 C 下发 POLICY_APPLY 仿真器应用 更新相关节点路由表 业务切换到替代路径

5. 后置状态：业务经替代路径恢复，全网路由收敛；R1-B1 标记为 down。

6. 智能体 vs 普通无 LLM 差别：普通网络靠 TC+Dijkstra 也能收敛到替代路径（步骤 1-2）。差别：智能体版本主动生成多条候选路径并择优（考虑业务 QoS 约束，不只”最短”），且能解释”为什么选这条路”；无 LLM 版本只算最短路径，不区分业务 QoS，可能把话音切到高时延路径导致 QoS 不达标。

3.2 小场景：链路质量退化

1. 背景：R1-B1 链路未断，但误码率/丢包率/时延显著变差（如 ber 从 1e-4 升到 1e-2）。

2. 参与方：R1、B1、运维 Agent、资源 Agent、C。

3. 前置条件：R1-B1 链路 up 但质量恶化，承载的视频业务出现卡顿。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 R1 测量链路参数变化 更新邻居表 R1-B1 的 ETX 代价 ETX 显著升高 链路质量被感知
2 R1 传播 TC{R1-B1 代价升高} 全网拓扑更新 拓扑表代价刷新 全网知道质量退化
3 运维 Agent 检测 ber/packetLossRate 异常 调用阈值+时序检测 判定”质量退化事件” 识别退化
4 运维 Agent 发 DIAGNOSIS_RESULT 资源 Agent 收到 constraints 含”R1-B1 质量不达标” 资源 Agent 知约束
5 资源 Agent 评估业务 QoS 调用 QoS 评估工具 判断视频业务是否仍达标 决定是否切路径/降级
6 资源 Agent 生成策略（切路径或降码率） C 校验并下发 更新路由或业务参数 业务 QoS 恢复

5. 后置状态：业务切换到质量更好的路径，或降级保障；链路质量被持续监控。

6. 智能体 vs 普通无 LLM 差别：这是差别最大的场景。仅依赖连通状态的路由配置可能不会因质量退化而切路；但配置了链路度量、遥测或TE策略的传统网络也可以检测和响应——链路仍 up，OSPF 不重路由，视频继续卡顿丢包。智能体版本通过运维 Agent 主动监测 ber/packetLossRate/delayMs，识别”质量退化但未断”，并主动切路径或降级保障。这是”自感知”能力的核心体现。

3.3 小场景：链路恢复

1. 背景：此前中断的 R1-B1 链路恢复 up。

2. 参与方：R1、B1、C、运维 Agent、资源 Agent。

3. 前置条件：R1-B1 之前为 down，业务正走替代路径。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 R1、B1 重新收到对方 HELLO 双向握手成功 邻居表恢复 R1-B1 链路恢复
2 传播 TC{R1-B1 恢复} 全网拓扑更新 拓扑表恢复该链路 全网知道恢复
3 运维 Agent 检测恢复事件 评估原路径质量 对比原路径 vs 替代路径代价 决定是否切回
4 资源 Agent 决定切回或保持 C 校验下发 更新路由 业务回到最优路径

5. 后置状态：链路恢复，业务按代价择优走原路径或继续走替代路径。

6. 智能体 vs 普通无 LLM 差别：普通网络也会自动收敛回原路径（最短路径）。差别：智能体版本有策略地判断”是否值得切回”（避免频繁振荡），并记录决策；无 LLM 版本只要原路径更短就切回，可能在高动态下引起路由振荡。

3.4 小场景：链路随机通断（间歇性断续）

1. 背景：链路 up↔︎down 频繁切换（间歇性），稳定路径不存在。

2. 参与方：R1、B1、运维 Agent、资源 Agent、C。

3. 前置条件：R1-B1 链路间歇性断续，业务时通时断。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 链路频繁 up↔︎down 各节点反复更新邻居表/TC 拓扑频繁变更 路由频繁重算
2 运维 Agent 检测”高频断续”模式 判定为间歇性故障 记录断续频率 识别不稳定链路
3 资源 Agent 采取防抖策略 提高切换阈值、加迟滞 避免路由振荡 策略稳定
4 数据面启用 DTN 存储转发 断续期间缓存数据，链路恢复再传 缓存队列 数据不丢失

5. 后置状态：业务通过 DTN 存储转发在断续链路下仍能送达；策略防抖避免振荡。

6. 智能体 vs 普通无 LLM 差别：仅使用常规路由收敛机制时，间歇链路可能引发频繁更新和业务丢包；是否振荡取决于协议定时器、度量和防抖配置（协议只做”尽力转发”）。智能体版本通过运维 Agent 识别”断续模式”并加迟滞防抖，同时启用 DTN 存储转发兜底。这是应对”链路随机通断”的关键增益。

4. 大场景：拓扑结构

4.1 小场景：网络分区/割裂

1. 背景：多条关键链路同时断，网络裂成两个不连通子网。

2. 参与方：全网节点、C、运维 Agent、资源 Agent。

3. 前置条件：存在把网络分成两半的关键链路集。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 关键链路集同时中断 各节点检测失联 拓扑表更新 网络分裂
2 运维 Agent 调用连通分量分析 返回两个不连通分量 判定”拓扑分区” 识别分区
3 运维 Agent 发 DIAGNOSIS_RESULT{topologyPartition:true} 资源 Agent 收到 得知分区 进入分区处理
4 各分区内自治运行 分区内重算路由 分区内路由表 分区内仍连通
5 资源 Agent 尝试跨分区恢复 若有可修复链路则下发 恢复策略 分区可能重新合并

5. 后置状态：网络分为两个自治分区，分区内业务正常，跨分区业务中断/降级。

6. 智能体 vs 普通无 LLM 差别：普通网络分区后只是”各自连通、跨区不通”，无全局感知。智能体版本通过运维 Agent 主动识别”这是分区而非普通故障”，并触发分区自治 + 降级运行 + 恢复尝试，是抗毁性的体现。

4.2 小场景：分区合并

1. 背景：隔离的两个分区之间的链路恢复，重新连通。

2. 参与方：两个分区的边界节点、C、运维 Agent。

3. 前置条件：网络处于分区状态，恢复链路出现。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 边界节点互相发现 HELLO邻居/双向链路判定 邻居表恢复 跨区链路恢复
2 洪泛 TC 两分区拓扑融合 拓扑表合并 全网重连
3 运维 Agent 检测合并事件 重算连通度 判定”分区已合并” 恢复全局视图

5. 后置状态：网络重新连通，全局路由收敛，跨区业务恢复。

6. 智能体 vs 普通无 LLM 差别：普通网络靠 TC 洪泛自动合并。差别：智能体版本能识别合并事件并协调跨区资源重新分配，避免合并瞬间的资源冲突。

4.3 小场景：关键节点失效（割点/中继）

1. 背景：R1 是多个末端节点的唯一上游（割点），R1 被毁导致其下所有末端失联。

2. 参与方：R1、其下末端节点、C、运维 Agent、资源 Agent。

3. 前置条件：R1 是割点，U1、U2 只经 R1 上联。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 R1 失效 U1、U2 检测到 R1 失联 邻居表删除 R1 末端失联
2 运维 Agent 识别”关键节点失效” 分析影响范围 判定 R1 是割点 识别单点风险
3 资源 Agent 寻找备用中继 若有备用中继则切换 生成 CANDIDATE_POLICY 恢复或确认不可恢复
4 簇头机制触发重选 区域内重选簇头 新簇头产生 局部自治接管

5. 后置状态：若存在备用中继则业务恢复；否则该区域业务中断，触发簇头重选降级运行。

6. 智能体 vs 普通无 LLM 差别：普通网络只知”R1 断了、末端失联”。智能体版本能提前识别割点/单点风险（运维 Agent 的关键节点分析），并在设计时通过冗余中继规避，故障时主动切换。这是”抗毁性设计”的体现。

5. 大场景：资源与带宽

5.1 小场景：带宽下降

1. 背景：R1-B1 链路可用带宽从 8Mbps 收缩到 1Mbps（bandwidthBps 下降）。

2. 参与方：R1、B1、运维 Agent、资源 Agent、C。

3. 前置条件：R1-B1 承载多条业务流，总需求 6Mbps。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 带宽动态收缩 各节点测量到 bandwidthBps 下降 更新链路参数 带宽受限被感知
2 运维 Agent 检测带宽下降事件 评估总需求 vs 新容量 判定”带宽不足” 识别瓶颈
3 运维 Agent 发 DIAGNOSIS_RESULT 资源 Agent 收到 constraints 含”带宽 1Mbps” 资源 Agent 知约束
4 资源 Agent 调用带宽分配算法（OR-Tools） 返回重分配方案 按优先级分配 1Mbps 生成 CANDIDATE_POLICY
5 C 校验（容量、优先级） 下发 POLICY_APPLY 更新带宽分配 关键业务保障、低优先级降级

5. 后置状态：带宽按业务优先级重新分配，话音等高优先级业务保障，低优先级业务降级/排队。

6. 智能体 vs 普通无 LLM 差别：差别巨大的场景。若未配置带宽遥测/资源管理策略，传统网络可能不会主动进行跨业务的联合重分配；但具备遥测、队列管理和流量工程的网络也能检测并响应带宽下降（链路仍 up，协议不重路由），所有业务继续竞争 1Mbps，导致拥塞丢包、无差别劣化。智能体版本通过运维 Agent 感知 bandwidthBps 变化，资源 Agent 用优化算法按优先级重分配，实现”关键业务保障、普通业务降级”。这是”资源动态调度”的核心价值。

5.2 小场景：拥塞

1. 背景：业务量突增超过链路容量，产生拥塞。

2. 参与方：R1、B1、资源 Agent、C。

3. 前置条件：某链路流量逼近或超过容量。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 流量突增 链路队列增长、时延上升 监测到拥塞指标 拥塞发生
2 运维 Agent 检测拥塞 定位拥塞链路 判定拥塞点 识别瓶颈
3 资源 Agent 执行限流/调度 优先级队列（DiffServ） 高优先级先发 拥塞缓解
4 资源 Agent 可选切流到其他路径 C 校验下发 更新路由 负载均衡

5. 后置状态：拥塞缓解，高优先级业务不受影响，低优先级业务可能被限流。

6. 智能体 vs 普通无 LLM 差别：普通网络拥塞后只能被动丢包（TCP 降速）。智能体版本主动限流 + 优先级调度 + 负载均衡，把拥塞影响限定在低优先级业务。

5.3 小场景：多业务争抢同一链路

1. 背景：话音、视频两条流同时竞争同一条有限带宽链路。

2. 参与方：两条业务流、资源 Agent、C。

3. 前置条件：两业务总需求超过链路容量。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 两业务同时请求带宽 资源 Agent 收到竞争 检测到冲突 资源冲突
2 资源 Agent 按优先级仲裁 话音优先于视频 分配带宽 话音保障
3 C 做冲突仲裁审批 下发分配结果 更新各流带宽 冲突解决

5. 后置状态：高优先级业务得到保障，低优先级业务被降级或拒绝，冲突消解。

6. 智能体 vs 普通无 LLM 差别：若未配置差异化QoS策略，两条流可能按默认队列规则竞争；传统网络可通过DiffServ/队列调度实施差异化保障，无业务语义，话音可能被视频挤掉导致时延超标。智能体版本理解”话音时延敏感、视频带宽敏感”的差异，按优先级差异化保障。这是”冲突仲裁”能力的体现。

8. 大场景：复合与极端

8.1 小场景：多重故障

1. 背景：多个节点 + 多条链路同时异常（如 R1 下线同时 R2-B1 链路中断）。

2. 参与方：全网节点、C、运维 Agent、资源 Agent。

3. 前置条件：网络正常，多个故障同时注入。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 多故障同时注入 各节点检测各自失联 多处邻居表/拓扑更新 多重故障
2 运维 Agent 综合分析 识别多个故障及其交互影响 关联分析 完整故障视图
3 资源 Agent 联合优化 多约束下重算路由+带宽 联合调度 全局最优恢复
4 C 仲裁多个候选策略 冲突消解 统一策略集 协调下发

5. 后置状态：系统在多重约束下尽可能恢复关键业务，可能部分业务降级。

6. 智能体 vs 普通无 LLM 差别：分布式路由协议仍可在各节点按统一协议规则收敛；多Agent的额外价值在于把业务QoS、跨链路资源和任务关键度纳入联合诊断与策略编排，而不是假定传统路由必然冲突。智能体版本通过协调器全局联合优化 + 冲突仲裁，得到全局一致的恢复方案。这是”多 Agent 协作 + 复杂约束处理”的核心场景。

8.2 小场景：协调器失效 / 降级自治

1. 背景：管控面协调器 C 被毁，系统需降级为区域自治继续运行。

2. 参与方：C、各簇头、区域节点。

3. 前置条件：C 正常运行，突然失效。

4. 步骤：

# 主体行为 目标行为 数据操作 结果
1 C 失效 各节点检测到 C 失联 管控面失去中心 协调器失效
2 各区域簇头检测并接管 簇头广播接管声明 新协调角色产生 局部接管
3 各区域自治运行 区域内本地调度 退化为预置规则 降级自治
4 （可选）重新选举协调器 新协调器上任 恢复全局协调 重新集中

5. 后置状态：系统降级为区域自治，关键业务仍维持，全局优化暂停。

6. 智能体 vs 普通无 LLM 差别：这是智能体架构的抗毁性优势。若系统存在单一且不可替代的控制中心，中心失效会影响集中管控；数据面是否中断取决于转发架构和已有自治能力；智能体系统设计为”协调器可降级、簇头可接管”，失效后仍能降级自治运行。这是”中心可降级、可替换”设计的直接体现。

9. 建模修订与执行约束（新增）

本节统一本需求文档中的协议假设、链路语义和场景判定规则，避免场景步骤把“仿真器内部动作”误写成协议标准规定的报文流程。

9.1 协议基线与消息命名

建议原型阶段明确选定一种路由协议作为基线：

  • OLSRv2（RFC 7181）：主动式MANET路由。HELLO用于链路感知、邻居发现和MPR相关信息；TC用于拓扑信息传播。HELLO本身不是“收到后必须回复独立HELLO-ACK”的通用握手流程。
  • AODV（RFC 3561）：按需路由，典型消息为RREQ、RREP、RERR；HELLO是可选的邻居可达性机制，RREP-ACK只用于特定确认场景。
  • LSA是OSPF常用术语，不应作为OLSR的正式消息名。若场景采用OLSRv2，本文统一使用HELLO/TC；若采用AODV，则使用其RREQ/RREP/RERR流程。
  • 若使用“简化拓扑通告”作为仿真器内部事件，应明确标注为SIM_TOPOLOGY_UPDATE，不要冒充协议报文。

9.2 链路、承载与业务流不是同一个对象

链路必须允许非对称和能力差异。A→B与B→A的时延、带宽、丢包和可达状态可能不同；双向会话需分别验证两个方向。每条链路/承载应声明capabilities（如control、data），不要默认任意节点对都同时具备控制链路和数据链路。

模型情况 推荐表达 场景执行规则
控制与数据共用无线资源 一个物理Link + 不同Flow/队列 总容量由所有队列共享，调度器决定资源份额
控制与数据独立承载 不同linkId/接口/信道 两条承载的状态、带宽、时延分别变化
仅有控制或仅有数据 capabilities只声明实际能力 不支持的Flow类型必须判定不可达
单向/不对称链路 分方向的Link状态/指标 路径逐跳检查对应方向，不以单向可达代替双向可用

赛题样例中的链路字段是基础输入；接口、频率、RSSI、SNR、队列等字段属于仿真扩展，需在数据字典中标注来源和默认值。

9.3 统一业务QoS与资源准入

每条Flow至少应配置：flowId、源/宿、serviceType、需求速率或流量模型、minBandwidthBps、maxDelayMs、maxJitterMs、maxLossRate、priority、criticality、preemptible。媒体类型只说明典型性能敏感点，不能直接推出固定优先级；任务关键度与调度优先级分开。

推荐统一决策顺序：

  1. 按链路状态、方向和承载能力过滤不可用链路；
  2. 计算候选路径并检查逐跳带宽、时延、抖动和丢包约束；
  3. 对可行路径进行业务加权评分；
  4. 执行准入控制和容量分配；
  5. 配置队列、整形/限流、必要时抢占或降级；
  6. 执行后测量实际QoS，未达标则回滚、重算或明确标记降级。

DiffServ用于流量分类/标记和逐跳PHB，不自动提供端到端带宽预留；RSVP是资源预留信令，不是路由协议。仿真器可以采用简化的集中式准入模型，但应称为“RSVP/IntServ思想的抽象”，不能声称完整实现标准协议。

9.4 对已有场景步骤的必要修正

  • 全网冷启动：无线接口、信道、地址、安全/认证等基础配置应作为前置条件或明确抽象掉；“没有预配置拓扑”不等于“没有任何网络配置”。HELLO只能发现实际可达邻居，不保证全网必然连通。
  • 节点下线：区分业务源/宿节点失效与中继节点失效。中继失效可能改道；源节点失效时，源业务不能仅靠重路由恢复，除非配置备份源、缓存或副本。
  • 节点移动/链路恢复：增加切换迟滞和稳定观察窗口，避免链路质量波动时乒乓切换。先建后拆可作为仿真策略，但不是所有路由协议的自动保证。
  • 网络分区/关键节点失效：只有在拓扑确实形成多个连通分量，或节点确实为割点时，才能得出分区/割点结论；若存在备用路径，不能直接宣称末端失联。
  • 质量退化/干扰：BER升高不能单独证明存在干扰；可结合SNR、RSSI、信道占用或干扰事件标签。换频/跳频必须以设备/波形支持为前提。IEEE 802.22是WRAN动态频谱接入标准，不应直接当作无人平台战术跳频机制的标准依据。
  • 带宽下降/拥塞：区分物理容量、可用容量、已分配容量、实际吞吐和队列积压；避免同一个bandwidthBps字段承载多个含义。
  • 多重故障/协调器失效：若有多协调器接管，需定义选举、租约/任期、状态版本、脑裂避免和冲突策略；仅写“簇头接管”不足以保证一致性。

9.5 多智能体与普通网络的对照口径

对比实验应把普通网络基线定义清楚，例如“固定路由+默认队列”“OLSRv2+AQM/队列策略”“带遥测的规则式资源控制”。不能笼统声称传统网络无法感知链路退化、不能做带宽调度或必然路由冲突。多智能体的合理增益应聚焦于：

  • 将链路/拓扑变化与业务影响关联起来；
  • 联合考虑多条业务流、不同QoS约束和多链路资源；
  • 形成可追踪的诊断、候选策略、冲突仲裁和执行反馈闭环；
  • 在复杂组合场景中减少人工规则编排成本，并用量化指标验证是否优于基线。

9.6 场景实验统一记录字段

建议每次注入事件记录：scenarioId、eventId、eventTime、randomSeed、affectedNodes[]、affectedLinks[]、affectedFlows[]、beforeStateVersion、afterStateVersion、expectedEffect。每条策略记录policyId、baseStateVersion、actions[]、decisionLatencyMs、applyLatencyMs、applyStatus、rollbackReason。

评价指标至少统一定义：状态感知时延、策略生成时延、策略下发时延、路由恢复时间、网络连通度、业务QoS达标率、关键业务保障率、资源利用率、控制开销、策略执行成功率和业务中断时长。复赛测试集应采用相同事件序列和随机种子对不同方法做公平对比，并保留未见拓扑/参数组合用于泛化测试。
