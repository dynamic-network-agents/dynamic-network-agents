# 动态通信网络多智能体项目目录拆分方案

## 1. 文档目的

本文档明确动态通信网络多智能体项目的代码组织方式。项目在保持现有
`frontend/` 目录及其内部结构不变的前提下，将仿真器、LLM
多智能体平台和确定性算法拆分为三个相对独立的模块，为后续将其迁移到独立 Git
仓库、独立部署和独立迭代做好准备。

本方案采用**模块先拆分、仓库后拆分**的策略：开发初期仍可放在同一个父目录中，但每个模块具有清晰的职责边界、独立依赖、测试和启动方式。

## 2. 总体设计原则

1.  **前端保持不动**：现有 `frontend/`
    目录结构、技术栈和职责不因本次拆分而调整。
2.  **仿真器独立**：仿真环境、网络拓扑、链路行为、业务流量、资源模型和仿真事件由
    `simulator/` 负责。
3.  **智能体平台独立**：LLM
    接入、多智能体角色、任务编排、RAG、技能库、工具调用和决策流程由
    `agent-platform/` 负责。
4.  **算法独立**：拓扑分析、路由计算、带宽分配、故障诊断等确定性算法由
    `algorithms/` 以进程内 Python 库承载，被仿真器、后端和智能体平台 import
    调用（无独立进程、无 HTTP 面）。
5.  **后端作为业务入口和集成层**：`backend/` 负责对前端提供统一
    API，并协调仿真器、智能体平台和算法库。
6.  **通过契约通信**：模块间优先通过 HTTP API、WebSocket 和 JSON
    数据契约通信，不直接依赖其他模块的内部 Python 类。
7.  **模块可独立运行和测试**：仿真器、智能体平台分别拥有自己的依赖清单、配置、测试、Dockerfile
    和 README；算法库拥有独立依赖、测试与 README。
8.  **先保证确定性闭环**：核心仿真、策略校验、资源计算和执行流程优先使用可测试的确定性逻辑；LLM
    用于意图理解、诊断辅助、工具选择和参数建议，不绕过策略校验。

### 3.1 顶层 vs 模块内目录归属判定

| 目录 | 顶层 | 模块内 | 判定标准 |
|------|------|--------|----------|
| `scenarios/` | 共享场景**数据**（JSON/YAML） | `simulator/scenarios/` 为场景加载与内置模板**代码** | 数据放顶层、代码放模块 |
| `configs/` | 跨模块、部署级默认配置 | 各模块私有默认配置 | 影响多模块/编排 → 顶层；只服务本模块 → 模块内 |
| `knowledge_base/` | 不设 | 唯一归 `agent-platform/knowledge_base/` | 知识库只被智能体平台消费 |
| `experiments/` `scripts/` | 唯一归顶层 | 不设模块内同名目录 | 实验记录、编排/初始化脚本天然跨模块 |
| `tests/` | 不设 | 每模块各自 `tests/` | 测试随模块走，CI 按模块跑 |
| `algorithms/` | 不设 | 唯一归 `algorithms/` | 进程内库：无顶层数据、无独立进程，随调用方运行 |

> 仓库拆分后（§7.2），共享场景数据留主平台仓库；`simulator/tests/` 与 `examples/` 使用自带的本地
> fixture，不依赖顶层 `scenarios/`。

## 4. 模块职责边界

### 4.1 frontend：交互展示层

负责： - 网络拓扑、节点和链路状态可视化； -
仿真场景配置、启动、暂停和停止； - 节点、链路、业务流和资源状态展示； -
智能体任务、诊断过程、决策结果展示； - 实验指标和结果报告展示。

前端只面向 `backend/` 提供的统一
API，不直接调用仿真器或智能体平台的内部接口。

### 4.2 backend：主业务后端与集成层

负责： - 对前端提供统一 REST API 和 WebSocket； -
用户请求校验、会话与仿真任务管理； -
调用仿真器创建场景、启动仿真、注入事件和获取快照； - 将网络状态、业务
QoS 和资源状态组织成智能体任务输入； -
调用智能体平台执行诊断、策略生成和任务编排； -
将候选策略提交给仿真器进行合法性校验和执行； -
汇总指标、保存实验结果并向前端推送状态。

不负责： - 实现 SimPy 仿真内核； - 实现完整的网络协议和路由仿真； - 承载
Ollama / Qwen 的底层模型适配； - 将智能体平台内部的 Agent
类直接暴露给前端。

### 4.3 simulator：动态通信网络仿真器

负责： - 仿真时钟、事件调度和仿真生命周期； -
节点、链路、拓扑及其动态变化； -
链路带宽、时延、丢包率、连通状态等参数变化； -
节点上线、下线、移动或失联等事件； -
数据、图片、话音、视频等业务流量建模； - 业务
QoS、队列、带宽和资源约束建模； -
网络发现、路由、转发及链路可达性的仿真执行； -
候选策略的约束校验、策略执行和效果反馈； - 仿真指标采集与输出。

建议仿真器内部以 SimPy 作为离散事件仿真基础。路由计算、带宽分配、故障诊断等确定性优化算法不在 simulator 内重复实现，而是调用 `algorithms/`（NetworkX / OR-Tools）；simulator 只负责把算法结果落地到仿真状态并推进（**计算归 algorithms、执行归 simulator**）。

### 4.4 algorithms：确定性算法库

负责（全部为无状态纯计算，输入输出确定性、可复现）： - 拓扑分析、连通性与最短路径等图算法； -
动态路由计算（最短路、多路径、故障重路由）； - 带宽与多维资源分配优化（OR-Tools 等）； -
网络异常诊断与根因推理； - 为智能体平台的诊断与决策提供确定性计算支撑。

边界要求： - 以进程内 Python 库被 `simulator/`、`backend/`、`agent-platform/`
import 调用，无独立进程、无 HTTP 面； - 不持有仿真状态、不推进仿真时钟、不直接读写数据库或消息队列； -
计算归 algorithms、执行归 simulator：路由/带宽等「怎么算」在 algorithms，「怎么落地到仿真状态」在
simulator； - 对外数据结构遵循 `contracts/` 契约，经 `interfaces/` 适配为内部类型。

### 4.5 agent-platform：LLM 多智能体平台

负责： - 运维智能体、资源控制智能体和协调器等角色； -
智能体任务接收、拆解、调度和状态管理； -
多智能体协作、冲突检测和仲裁； - Ollama / Qwen 等模型接入与模型配置； -
RAG 检索、知识库管理和提示词模板； -
技能库、工具注册、工具调用与结果解析； -
网络异常诊断、候选策略生成和决策说明； -
对智能体执行过程进行日志记录和可追溯管理。

边界要求： - LLM 不直接替代精确的数值优化算法； - LLM
生成的候选策略必须经过规则、约束和仿真器校验； -
资源分配等需要确定性和可复现性的计算，由 `algorithms/` 库完成； -
智能体平台通过标准输入输出契约与仿真器、后端交互，不依赖仿真器内部类。

### 4.6 contracts：公共通信契约

负责定义跨模块稳定的数据结构和 API 规范，例如： -
节点、链路和业务流描述； - 网络状态快照； - 业务 QoS 状态； -
故障诊断结果； - 候选资源控制策略； - 策略执行结果； -
仿真任务状态和实验指标。

`contracts/`
是接口规范的单一事实来源。模块内部可以有自己的领域模型，但跨模块传输时应转换为契约定义的数据结构。

`schema` 文件名与 §3 的 `contracts/schemas/` 清单一一对应；各字段定义以
`docs/frontend/前后端数据模型与接口规范_v1.0.md` 为唯一事实源，禁止在模块内另写一套 schema。

### 4.7 关键归属判定（防双归属）

| 能力 | 唯一归属 | 说明 |
|------|----------|------|
| 控制回路编排（状态感知→诊断→策略→校验执行） | `agent-platform/orchestration/` | `backend/services/` 只做跨模块**调用**编排（顺序、超时、重试、事务），不做智能体决策逻辑 |
| 向量存储（FAISS）与业务持久化 | `backend/persistence/` | `agent-platform/rag/`、`knowledge/` 通过 backend 提供的检索接口访问，不直连向量库 |
| 数据库迁移（Alembic） | `backend/alembic/` | 唯一迁移入口，其他模块不持有迁移脚本 |
| 路由计算 / 带宽分配 / 故障诊断等确定性算法 | `algorithms/` | 无状态纯函数，被 simulator/backend/agent-platform 进程内调用；不持有仿真状态 |
| 仿真执行与状态推进 | `simulator/` | 时钟、事件、拓扑/链路/流量状态落地；路由/带宽结果来自 algorithms |

### 4.8 契约生成与防漂移（机制）

单一事实源是流程，不是口号，按单向链执行：

``` text
docs/frontend/前后端数据模型与接口规范_v1.0.md   （人读事实源，改这里）
        │  脚本导出
        ▼
contracts/schemas/*.schema.json                  （机器读契约）
        │  各模块用 datamodel-code-generator 生成
        ▼
各模块 interfaces/ 的 Pydantic DTO（只做适配，不回写、不重定义）
```

约定：

1. 导出方向单向、不回写；发现契约缺口先改接口规范，再重新导出，禁止模块内私自定义 schema。
2. **OpenAPI 二选一**（写死避免两份来源）：
   - 方案 A：以 `contracts/openapi/*.yaml` 为唯一源，三个 FastAPI 服务从它派生/校验路由；
   - 方案 B：以 FastAPI 代码自动生成 OpenAPI，`contracts/openapi/` 只做导出快照，CI 对比差异。
   - 建议先取 **方案 B**（开发快），阶段五固化 API 时切到方案 A。
3. CI 增加契约一致性检查：接口规范 ↔ schemas ↔ openapi 三方对比，不一致即 fail。

## 5. 模块之间如何通信

### 5.1 推荐通信方式

第一阶段建议采用： - **HTTP
REST**：创建任务、启动仿真、注入事件、提交策略、查询状态； -
**WebSocket**：推送仿真状态、智能体执行进度和实时指标； -
**JSON**：作为跨服务数据交换格式； - **OpenAPI / JSON
Schema**：定义接口和数据结构。

暂时不必为了模块拆分引入 Kafka、RabbitMQ
等消息队列。等到出现高并发事件流、异步任务积压、服务解耦或可靠消息投递等明确需求时，再评估消息中间件。

起步阶段通过 `integrations/` 的客户端接口做**进程内适配**：`simulator_client` 与
`agent_platform_client` 先提供 in-process 实现（直接调用本仓库内的 Python 包），接口稳定后再替换为
HTTP 实现。调用方只依赖接口、不感知实现，既降低早期三套服务的联调成本，也不破坏 §6 的解耦约束。

`algorithms/` 作为进程内库，直接被各模块 import、不经过 HTTP，其公共函数签名即其「接口」，输入输出数据结构遵循 `contracts/`。

### 5.2 典型业务闭环

### 5.3 建议的初始 API

**仿真器 API**

  方法   路径                                  用途
  ------ ------------------------------------- --------------------------
  POST   `/api/v1/simulations`                 创建仿真任务
  POST   `/api/v1/simulations/{id}/start`      启动仿真
  POST   `/api/v1/simulations/{id}/pause`      暂停仿真
  POST   `/api/v1/simulations/{id}/stop`       停止仿真
  GET    `/api/v1/simulations/{id}/snapshot`   获取网络状态快照
  POST   `/api/v1/simulations/{id}/events`     注入节点、链路或业务事件
  POST   `/api/v1/simulations/{id}/policies`   校验并执行候选策略
  GET    `/api/v1/simulations/{id}/metrics`    获取仿真指标

**智能体平台 API**

  方法   路径                          用途
  ------ ----------------------------- --------------------
  POST   `/api/v1/tasks`               创建智能体任务
  GET    `/api/v1/tasks/{id}`          查询任务状态
  POST   `/api/v1/diagnosis`           请求网络状态诊断
  POST   `/api/v1/decisions`           请求候选策略或决策
  POST   `/api/v1/tasks/{id}/cancel`   取消智能体任务
  WS     `/api/v1/stream`              推送智能体执行过程

**后端 API（前端唯一入口，草案）**

  方法   路径                                  用途
  ------ ------------------------------------- --------------------------
  POST   `/api/v1/experiments`                 创建实验（关联场景与智能体任务）
  GET    `/api/v1/experiments/{id}`            查询实验状态
  POST   `/api/v1/experiments/{id}/start`      启动闭环（仿真→决策→校验执行）
  POST   `/api/v1/experiments/{id}/stop`       停止实验
  GET    `/api/v1/experiments/{id}/results`    获取指标与结果
  WS     `/api/v1/experiments/{id}/stream`     推送状态、指标与决策过程

以上路径是建议的初始接口草案，正式实现时应以 `contracts/openapi/` 中的
OpenAPI 定义为准。

**算法库**：`algorithms/` 为进程内库，无 HTTP API；对外提供 `compute_route` /
`allocate_bandwidth` / `diagnose` / `analyze_topology` 等 Python 函数，输入输出遵循
`contracts/` 数据结构，故不在此列 HTTP 端点。

**术语约定**：`experiment`（实验，backend 顶层资源）、`simulation`（仿真运行，simulator 资源）、
`task`（智能体任务，agent-platform 资源）三者语义不同，全文档与 API 不得混用。

**前端同步**：统一 `/api/v1` 后，前端 `.env.example` 的 `VITE_API_BASE_URL`、MSW `handlers.ts`
的 `MOCK_API_BASE` 以及测试中硬编码的 `http://localhost:8000/api` 需同步改为 `/api/v1`，并回归
`pnpm test` / `pnpm build`。

## 6. 跨模块数据与调用约束

为避免模块独立后产生强耦合，建议遵守以下约束：

1.  不直接跨项目导入内部实现类，例如不要在后端中直接写
    `from simulator.domain import NetworkSnapshot`。
2.  对外接口使用 JSON Schema 定义的数据结构；各模块通过 DTO / Adapter
    转换为自己的内部领域对象。
3.  所有请求携带 `request_id` 或 `task_id`，便于日志关联和故障排查。
4.  对创建任务、注入事件和提交策略等写操作设计幂等机制，避免重试造成重复执行。
5.  接口包含 `schema_version` 或 API 版本，支持契约演进。
6.  设置请求超时、任务取消和明确的错误码。
7.  对策略执行保留校验结果、执行记录和状态变更记录。
8.  对仿真快照、策略输入和实验输出保留必要的时间戳，便于复现实验。
9.  命名约定：包名统一 `snake_case` 且与目录一致；资源术语按 §5.3 的 experiment/simulation/task
    约定执行；`knowledge/`（加载与管理代码）与 `knowledge_base/`（数据）语义易混，建议后者改为
    `knowledge_data/`。
10. 拆分独立仓库或对外发布前，将 `simulator/` 包重命名为带项目前缀的名字（如 `dynsim`）、
    `algorithms/` 重命名为 `dynalg`，避免 `import simulator` / `import algorithms` 与第三方同名包冲突。

## 7. 独立部署与独立仓库规划

### 7.1 开发初期：单仓库、多模块

初期仍使用一个父目录：

``` text
dynamic-network-agent/
├── frontend/
├── backend/
├── simulator/
├── agent-platform/
├── contracts/
└── ...
```

每个 Python 模块分别维护 `pyproject.toml`、依赖、测试和
README。通过根目录 `docker-compose.yml` 启动联调环境。

### 7.2 后期：拆分为多个 Git 仓库

当接口和模块职责稳定后，可以拆成：

**主平台仓库：`dynamic-network-platform/`**

``` text
dynamic-network-platform/
├── frontend/
├── backend/
├── contracts/              # 也可后续进一步独立
├── scenarios/
├── experiments/
├── scripts/
├── docs/
├── docker-compose.yml
└── README.md
```

**仿真器仓库：`dynamic-network-simulator/`**

``` text
dynamic-network-simulator/
├── simulator/
├── tests/
├── configs/
├── examples/
├── pyproject.toml
├── Dockerfile
└── README.md
```

> 拆分前将 `simulator/` 包重命名为带项目前缀的名字（如 `dynsim`），避免 `import simulator` 与第三方
> 同名包冲突。

**智能体平台仓库：`dynamic-network-agent/`**

``` text
dynamic-network-agent/
├── agent_platform/
├── knowledge_base/
├── configs/
├── tests/
├── pyproject.toml
├── Dockerfile
└── README.md
```

`contracts/`
可以先保留在主平台仓库；如果多个项目或外部团队都需要复用，再单独建立契约仓库或发布版本化
SDK。

`algorithms/` 作为被三处共用的库，初期随主平台仓库分发；接口稳定后可单独建仓库或发布为内部版本化
Python 包（如 `dynalg`）。

## 8. 推荐实施顺序

### 阶段一：明确边界，不急于搬代码

-   盘点当前 `backend/` 中的仿真代码、LLM 代码和平台业务代码；
-   标记每个模块的输入、输出和依赖；
-   确定跨模块的数据结构；
-   建立 `contracts/` 初始目录和第一版 Schema；
-   搭好共享工程化基线：根目录 `ruff` / `mypy` / `pytest` 配置 + `pre-commit`，以及 `Makefile`
    （或 `justfile`）统一 `lint` / `test` / `typecheck` 入口；确定依赖管理策略（uv workspace 或各
    模块独立 venv）；
-   落地 §4.8 的契约生成脚本与 CI 一致性检查。

### 阶段二：抽离仿真器

-   先建立 `algorithms/` 进程内库（graph / routing / allocation / diagnosis），simulator 的路由、带宽、诊断改为调用该库，不在 simulator 内重复实现优化算法；
-   将 SimPy 仿真环境、事件和流量模型迁入
    `simulator/`；
-   为仿真器建立独立启动入口；
-   提供创建仿真、启动仿真、注入事件和查询快照的 API；
-   为仿真器建立独立测试，确保基础仿真行为可复现。

### 阶段三：抽离智能体平台

-   将 Agent、LLM、RAG、Skills、Tools 和 Orchestration 迁入
    `agent-platform/`；
-   为智能体平台建立独立启动入口；
-   提供任务创建、诊断、决策和任务状态查询 API；
-   保证候选策略输出满足契约格式，并能被后端和仿真器识别。

### 阶段四：后端改为服务调用

-   后端通过 `simulator_client` 调用仿真器；
-   后端通过 `agent_platform_client` 调用智能体平台；
-   后端统一处理用户请求、业务流程、持久化和前端推送；
-   移除后端对仿真器和智能体平台内部实现的直接依赖。

### 阶段五：联调、容器化与仓库拆分

-   使用 Docker Compose 启动前端、后端、仿真器和智能体平台；
-   验证完整业务闭环；
-   检查服务异常、超时、重试和任务取消行为；
-   固化 API / Schema 版本；
-   在模块职责和接口稳定后，再迁移到独立 Git 仓库。

## 9. 第一阶段验收标准

目录拆分完成后，至少应满足：

-   [ ] `frontend/` 的原有结构和职责保持不变；
-   [ ] `backend/` 不再承载仿真内核和 LLM 平台核心实现；
-   [ ] `simulator/` 能独立安装、启动和运行测试；
-   [ ] `agent-platform/` 能独立安装、启动和运行测试；
-   [ ] `contracts/` 已定义核心跨模块数据结构；
-   [ ] 后端通过 API Client 调用仿真器和智能体平台；
-   [ ] 仿真器可以独立创建场景、运行仿真、注入事件和返回快照；
-   [ ] 智能体平台可以独立接收任务并返回诊断结果或候选策略；
-   [ ] 候选策略必须经过仿真器校验后才能执行；
-   [ ] `algorithms/` 能独立安装、导入并运行测试，同输入同输出可复现；
-   [ ] simulator 的路由/带宽/诊断通过调用 algorithms 完成，不在 simulator 内重复实现；
-   [ ] Docker Compose 可以启动完整联调环境；
-   [ ]
    端到端流程能够完成"场景运行---状态感知---智能体决策---策略校验执行---指标反馈"。

## 10. 最终建议

推荐采用以下六个核心顶层模块：

``` text
frontend + backend + simulator + agent-platform + algorithms + contracts
```

其中： - `frontend`：保持现状，负责交互和可视化； -
`backend`：统一业务入口和模块集成； -
`simulator`：独立负责动态通信网络仿真； - `agent-platform`：独立负责 LLM
多智能体运行时和决策协同； - `algorithms`：独立确定性算法库（进程内库），承载拓扑分析、路由计算、带宽分配与故障诊断； -
`contracts`：定义跨模块通信规范。

**关键决策：先在一个代码仓库中完成模块化和接口解耦，再在接口稳定后拆分
Git 仓库。**
这样既能尽早建立清晰的工程边界，也能避免过早进行多仓库开发带来的版本同步、联调和依赖管理成本。
