# 文档说明

本方案基于项目当前确定的技术栈重新设计，作为后续需求拆解、系统开发、算法实现、仿真实验和竞赛交付的统一依据。原有“Vue 3 + Spring Boot + Python + Qwen3 + RAG”总体架构不再作为本方案的技术基线；本方案采用 React + TypeScript 前端、Python + FastAPI 单一后端，并由 Python 统一承载智能体编排、算法服务和仿真服务。

本方案以赛题任务说明书为需求边界：构建至少包含通信网络运维智能体、通信网络资源控制智能体的多智能体协同体系；在仿真环境中实现网络状态感知、故障识别、链路优选、多维资源动态调度；通过动态场景和量化指标验证效果。官方仿真器接口、最终测试集字段、现场运行资源限制及评测细则如有更新，应以竞赛组织方正式材料为准。

# 1. 项目概述与建设目标

## 1.1 项目定位

建设一套面向高动态、窄带宽、强干扰无人平台通信网络的资源管控多智能体仿真系统。系统以可控、可复现的动态网络仿真环境为基础，以运维智能体和资源控制智能体为核心，通过协调器完成任务编排、策略校验、冲突仲裁与执行反馈，形成“感知—诊断—决策—校验—执行—评估”的闭环。

## 1.2 总体目标

- 构建动态网络仿真环境：支持节点上线/下线/移动、链路通断和参数时变、业务流新增/变更/结束，以及多扰动组合场景。
- 实现网络态势感知与故障诊断：能够识别拓扑变化、链路质量退化、网络分区、容量瓶颈和业务受影响范围。
- 实现资源控制与 QoS 保障：能够生成可执行的候选路径、带宽分配、业务优先级和降级策略。
- 实现多智能体协作：至少包含运维智能体和资源控制智能体，并由协调器统一编排、校验、仲裁和追踪。
- 实现可解释、可复现的实验评估：支持基线算法对照、相同随机种子复现实验、指标统计和结果导出。
- 形成可交付工程：提供源代码、部署说明、配置模板、测试用例、实验报告和演示流程。

## 1.3 核心设计原则

| 原则 | 设计要求 |
| --- | --- |
| 算法确定性优先 | 路径计算、容量约束、带宽优化、策略合法性校验由确定性算法完成；LLM 不直接编造数值或写入网络状态。 |
| 仿真与管控解耦 | 仿真器负责环境状态演进和策略效果反馈；Agent 通过 API/工具接口读取快照、提交候选策略。 |
| 控制面与数据面分离 | 业务数据由网络图中的链路转发；协调器只负责策略和管控消息，不作为业务数据转发节点。 |
| 分布式数据面、分层管控面 | 数据面模拟 MANET 多跳自组网；管控面采用运维 Agent、资源 Agent 与协调器协同，支持降级自治。 |
| 先规则后模型 | 先以规则、技能和算法实现稳定闭环，再将 Qwen3 接入意图理解、复杂诊断、工具选择和解释。 |
| 模块化单体优先 | 初期以单一 FastAPI 服务和清晰模块边界实现，只有性能或部署需求明确时才拆分微服务。 |
| 全链路可追溯 | 每轮任务保存输入快照、事件、Agent 消息、算法参数、策略版本、校验结果和执行反馈。 |

| --- | --- | --- | --- |

| 多智能体协同体系设计 | Agent 分工、A2A 消息、任务调度、冲突仲裁 | Coordinator、O&M Agent、Resource Agent | 协作时序、消息记录、策略决策链 |

## 2.2 网络与业务建模范围

网络采用分级混合式抽象：接入层末端无人平台、中继层机动中继节点、骨干层地面站/指挥节点。数据面以分布式自组网方式建模，管控面以多智能体分层协调方式建模。初期不实现完整无线协议栈，而是在仿真层抽象邻居发现、链路状态更新、路由计算和多跳转发过程。

| 对象 | 关键属性/状态 | 说明 |
| --- | --- | --- |
| 节点 Node | nodeId、nodeType、position、status、mobility、compute/resource attributes | 可区分 UAV、UGV、USV、UUV、relay、backbone、gateway 等角色 |
| 链路 Link | linkId、srcNodeId、dstNodeId、status、delayMs、jitterMs、bandwidthBps、ber、packetLossRate、timestamp | 保留赛题样例字段语义；注意统一 bandwitdhBps/bandwidthBps 拼写映射 |
| 业务流 Flow | flowId、src、dst、serviceType、requiredBandwidth、maxDelay、maxJitter、maxLoss、priority、status | 覆盖数据、图片、话音、视频，参数应可配置而非写死 |
| 路由 Route | flowId、path、nextHop、cost、reservedBandwidth、validUntil | 区分节点本地路由表与协调器全局策略 |
| 资源状态 | 链路剩余带宽、队列占用、节点能量/算力（可选） | 第一阶段优先实现带宽；其他维度按赛题数据与开发时间逐步扩展 |
| 事件 Event | eventId、eventType、targetId、eventTime、payload、seed | 仿真事件可排程、回放和复现 |

## 2.3 QoS 业务模型

| 业务类型 | 主要敏感指标 | 初始策略倾向（可配置） |
| --- | --- | --- |
| 话音 | 时延、抖动、丢包 | 较高优先级；控制排队时延；必要时保护最低带宽 |
| 视频 | 带宽、时延、丢包 | 按带宽需求分配；拥塞时允许自适应降码率/降级 |
| 图片 | 带宽、可靠性 | 允许缓存/重传；可容忍一定传输时延 |
| 数据 | 可靠性、丢包、时延上限 | 按业务等级保障可靠传输，非紧急数据可延后发送 |

以上是仿真策略的初始建模假设，不代表赛题给出了固定 QoS 数值。具体门限、业务优先级和降级规则应在配置文件中定义，并在实验报告中说明来源与假设。

## 3.1 确定技术栈

| 层次 | 选型 | 主要职责 | 阶段策略 |
| --- | --- | --- | --- |
| 前端 | TypeScript + React | 网络态势、拓扑、Agent 协作、仿真控制、实验分析 | 从单页工作台起步，组件化扩展 |
| 后端/API | Python + FastAPI | 统一 API、业务服务、任务管理、权限/校验入口 | 单体应用、模块化分层 |

| 网络算法 | NetworkX + SciPy + OR-Tools | 拓扑分析、路径计算、优化分配、约束求解 | 算法服务独立模块，输入输出结构化 |
| 仿真 | SimPy + NetworkX | 离散事件推进、拓扑变化、链路状态、业务流与队列 | 仿真时钟与 API 调度解耦 |
| 模型 | Ollama + Qwen3 | 意图理解、诊断辅助、策略解释、工具选择 | 小参数量、低比特量化，按机器资源选模型 |

| 数据库 | SQLite，后续 PostgreSQL | 场景、任务、快照、策略、实验结果、审计记录 | 先 SQLite，数据并发或规模上升再迁移 |
| 缓存 | 进程内状态管理 | 当前仿真状态、短期上下文、运行时对象 | 仅单进程原型；多 worker/多实例时再评估 Redis |

## 3.3 核心运行闭环

```text
场景事件发生
  → 仿真器更新节点/链路/业务状态
  → 生成事件与网络快照（snapshotVersion）
  → Coordinator 创建 taskId / traceId
  → O&M Agent：态势评估、异常检测、故障诊断、影响分析
  → Resource Agent：路由候选、带宽分配、QoS 策略
  → Coordinator：拓扑/容量/QoS/安全约束校验与冲突仲裁
  → Simulation Adapter：应用策略（幂等）
  → 仿真器推进并反馈实际效果
  → Metrics：计算 QoS、连通度、恢复时间等
  → 归档决策链、更新前端态势
```

## 3.4 架构边界

- FastAPI 负责接口、业务流程和任务治理，不承担耗时算法的具体实现细节。
- NetworkX/SciPy/OR-Tools 负责确定性计算，必须返回可检查的结构化结果。
- Qwen3 不直接操作 NetworkX 图对象或数据库，不允许直接写入链路、路由和资源配置。
- 仿真器是网络状态与执行效果的事实来源；Agent 的诊断和策略不能反向伪造仿真事实。
- RAG 存储相对稳定的知识材料，不用于查询实时链路状态；实时状态必须来自仿真快照/API。
- 单进程内存状态仅适用于开发阶段；部署多 worker 前必须解决仿真状态一致性与任务锁问题。

## 4.2 典型业务流程：链路中断

1. SimPy 在仿真时间 t 触发链路 Lx 状态变为 down，NetworkX 图中移除该边或标记为不可用。
2. 仿真事件总线生成 LINK_DOWN 事件，携带链路 ID、事件时间、前后状态和快照版本。
3. Coordinator 创建诊断任务，将网络快照和事件上下文发送给 O&M Agent。
4. O&M Agent 计算连通分量、受影响节点/业务流、候选故障原因及约束，输出 DIAGNOSIS_RESULT。
5. Resource Agent 根据业务 QoS 和可用链路调用 K 最短路、容量约束与 OR-Tools 分配算法，输出 CANDIDATE_POLICY。
6. Coordinator 对策略进行路径合法性、链路容量、业务 QoS、优先级与策略版本校验；冲突时执行仲裁。
7. Simulation Adapter 应用策略，仿真器继续推进并返回业务恢复、丢包、时延和资源占用反馈。
8. 系统归档诊断、候选策略、校验、执行和评估结果，更新前端时间线。

## 4.3 其他必须覆盖的流程

- 节点上线/晚加入：邻居发现、拓扑更新、可选路径变化评估、业务迁移判断。
- 节点下线：邻居老化/节点失效、拓扑分区识别、受影响业务统计、重路由或中断标记。
- 节点移动：位置变化映射为链路质量变化、新邻居出现、旧邻居退化和接入切换。
- 带宽骤降：识别链路容量收缩、判断业务总需求超载、重新分配带宽和降级低优先级业务。
- 链路质量退化/干扰：基于 BER、丢包、时延、抖动变化评估链路代价，触发路径重选。
- 业务突发/优先级冲突：业务流新增或需求上调，进行容量竞争、优先级仲裁和准入控制。
- 控制器/骨干链路失联：协调器或上联不可达时，区域节点退化到本地预置规则，恢复后重新同步。

# 5. 多智能体体系与协作机制

## 5.1 Agent 角色

| 角色 | 核心职责 | 输入 | 输出 | 禁止事项 |
| --- | --- | --- | --- | --- |
| Coordinator | 统一编排、任务调度、冲突仲裁、策略校验、执行和审计 | 用户任务、仿真事件、快照、Agent 结果 | task、A2A 消息、校验结果、策略执行命令 | 不替代网络算法；不把自身当数据转发中心 |
| O&M Agent | 全网态势采集、拓扑感知、链路评估、异常检测、故障诊断、自愈建议 | 网络快照、事件、业务流状态 | DIAGNOSIS_RESULT、约束、影响范围、置信度 | 不直接下发资源策略、不修改仿真状态 |
| Resource Control Agent | 业务需求分析、路由调整、带宽分配、QoS 保障 | 诊断结果、业务 QoS、拓扑/容量快照 | CANDIDATE_POLICY、优化目标与代价 | 不绕过 Coordinator 校验；不虚构容量和路径 |
| 可选 Scenario Agent | 自然语言转场景配置、组合场景生成 | 用户场景描述、模板、参数边界 | ScenarioSpec 草案 | 不得绕过参数校验直接启动高风险实验 |

## 5.2 Agent 编排：先自研状态机

建议第一阶段采用自研状态机，而不是一开始引入 LangGraph。当前主流程清晰、角色数量有限、执行节点可枚举，自研状态机更容易控制时序、调试和复现。将每个 Agent 封装为统一接口，状态机只管理任务状态与依赖；未来出现复杂循环推理、动态子图、人工审批分支或多轮规划时，再评估迁移 LangGraph。

| 状态 | 进入条件 | 执行动作 | 成功转移 | 异常转移 |
| --- | --- | --- | --- | --- |
| RECEIVED | 用户/仿真事件进入 | 创建 taskId、traceId、输入快照 | SNAPSHOTTED | FAILED |
| SNAPSHOTTED | 快照完成 | 校验版本和字段完整性 | DIAGNOSING | RETRY/FAILED |
| DIAGNOSING | 运维诊断开始 | 调用 O&M Agent/技能 | PLANNING | RETRY/DEGRADED |
| PLANNING | 诊断结果可用 | 调用 Resource Agent 和算法工具 | VALIDATING | RETRY/NO_POLICY |
| VALIDATING | 候选策略生成 | 约束校验、冲突仲裁 | APPLYING | REJECTED/REPLAN |
| APPLYING | 策略通过校验 | 幂等下发仿真器 | EVALUATING | RETRY/FAILED |
| EVALUATING | 执行反馈到达 | 计算 QoS 和恢复指标 | COMPLETED | DEGRADED |
| COMPLETED | 任务闭环结束 | 持久化结果与审计链 | 终态 | — |

## 5.3 A2A 消息协议

A2A 先采用进程内异步消息/事件对象实现，保留未来跨进程传输能力。消息应有统一 envelope，payload 按 messageType 使用不同 Pydantic Schema 校验。

```json
{
  "messageId": "msg-uuid",
  "traceId": "trace-uuid",
  "taskId": "task-uuid",
  "fromAgent": "om_agent",
  "toAgent": "resource_agent",
  "messageType": "DIAGNOSIS_RESULT",
  "snapshotVersion": 42,
  "createdAt": "2026-11-06T10:00:00+08:00",
  "deadlineMs": 3000,
  "payload": {
    "affectedLinks": ["L12"],
    "failedNodes": [],
    "impactedFlows": ["FLOW-01"],
    "constraints": [{"type":"LINK_UNAVAILABLE","targetId":"L12"}]
  }
}
```

建议定义的消息类型：TASK_REQUEST、SNAPSHOT_READY、DIAGNOSIS_RESULT、CANDIDATE_POLICY、POLICY_VALIDATION_RESULT、POLICY_APPLY、POLICY_APPLIED、EXECUTION_FEEDBACK、TASK_FAILED。

## 5.4 冲突仲裁与降级

- 先满足硬约束：路径必须连通、链路必须可用、总分配带宽不得超过可用容量、策略版本必须匹配。
- 再满足业务保障：按业务优先级、QoS 违约程度、业务重要性和最低保障带宽进行排序。
- 最后优化整体效益：在硬约束和关键业务保障满足后，优化总吞吐、资源利用率和业务公平性。
- 无法满足所有业务时，明确输出被降级/拒绝的业务、原因和预期影响，禁止静默超配。
- 协调器失联时，允许区域节点使用预置规则和本地路由自治；恢复后合并快照并消解策略版本冲突。

# 6. 动态通信网络仿真设计

## 6.1 仿真内核职责

SimPy 负责离散事件时间推进，NetworkX 负责当前网络拓扑及图算法输入。两者不应混淆：SimPy 是事件调度器，NetworkX 是网络结构与算法计算载体。仿真器维护权威状态，Agent 获取只读快照并通过策略接口改变状态。

## 6.2 仿真时间与运行模式

| 模式 | 说明 | 用途 |
| --- | --- | --- |
| 实时近似模式 | 仿真时间按固定倍率推进，前端持续接收事件 | 演示态势变化和实时协作 |
| 加速批量模式 | 不等待真实时间，快速推进 SimPy 环境 | 批量实验、参数扫描、随机种子对照 |
| 单步调试模式 | 每推进一个事件/时间片暂停，等待用户继续 | 排查状态机、算法和策略错误 |
| 回放模式 | 按已归档事件序列和随机种子重放 | 复现问题和演示决策过程 |

## 6.3 场景扰动维度

| 扰动类别 | 可配置事件 | 关键参数 |
| --- | --- | --- |
| 节点变化 | NODE_UP、NODE_DOWN、NODE_MOVE | 目标节点、发生时间、位置、恢复时间 |
| 链路通断 | LINK_DOWN、LINK_UP、LINK_FLAP | 链路 ID、持续时间、抖动频率 |
| 链路质量 | LINK_PARAM_CHANGE、INTERFERENCE_START/END | 时延、抖动、带宽、BER、丢包率 |
| 业务变化 | FLOW_START、FLOW_STOP、FLOW_DEMAND_CHANGE | 源宿、业务类型、带宽需求、QoS 门限、优先级 |
| 资源约束 | CAPACITY_REDUCTION、QUEUE_CONGESTION | 链路容量、队列容量、调度权重 |
| 组合事件 | 多事件在同一窗口发生 | 事件间隔、随机分布、场景随机种子 |

## 6.4 场景库规划

| 场景编号 | 场景名称 | 主要测试能力 |
| --- | --- | --- |
| S01 | 全网冷启动与初始组网 | 邻居发现抽象、拓扑建立、初始路由 |
| S02 | 节点晚加入/上线 | 增量拓扑更新、业务迁移评估 |
| S03 | 关键节点下线 | 故障检测、连通分量、业务影响分析 |
| S04 | 节点移动与接入切换 | 链路质量变化、新邻居发现、路径切换 |
| S05 | 链路随机通断 | 快速故障识别、路由恢复、稳定性 |
| S06 | 带宽骤降 | 容量瓶颈检测、带宽重分配、业务降级 |
| S07 | 强干扰导致链路质量恶化 | ETX/质量评分、链路优选 |
| S08 | 业务突发与资源争抢 | QoS 优先级、准入控制、冲突仲裁 |
| S09 | 多故障组合 | 多事件并发、跨 Agent 协同 |
| S10 | 协调器/骨干失联 | 降级自治、局部策略和恢复同步 |

## 6.5 数据面路由抽象

仿真层可借鉴 MANET 的邻居发现、链路状态通告、主动式/反应式路由思想，但不宣称实现了完整 OLSR/AODV 协议栈。每个节点可维护邻居表、拓扑表和路由表；协调器维护全局快照。业务包按路径逐跳转发，链路时延、丢包、容量和队列影响端到端指标。

- 邻居表：只保存一跳邻居及链路质量、最近更新时间和有效期。
- 拓扑表：保存已知节点和链路状态，支持增量更新。
- 路由表：保存到目的节点的下一跳、路径代价、有效期；目的地不等于邻居。
- 全局快照：协调器用于跨业务资源优化和策略仲裁，不代表所有数据流都经过协调器。

# 7. 网络算法与资源调度设计

## 7.1 算法工具箱

| 算法/工具 | 输入 | 输出 | 用途 |
| --- | --- | --- | --- |
| NetworkX 连通分量 | 可用拓扑图 | 连通分量、孤立节点 | 拓扑分区与业务可达性 |
| Dijkstra | 源/宿、边权 | 单条最低代价路径 | 基线路由与快速重算 |
| K 最短路径 | 源/宿、边权、K | 候选路径集合 | 资源 Agent 候选路径 |
| ETX 估计 | 正反向投递率或丢包估计 | 链路传输代价 | 链路可靠性权重 |
| SciPy 优化/统计 | 链路/流量数据、目标函数 | 数值优化结果、统计结果 | 指标分析、辅助优化 |
| OR-Tools CP-SAT/LP | 业务需求、链路容量、路径候选、优先级 | 带宽分配/准入/降级方案 | 资源受限下的多业务调度 |
| 策略校验器 | 候选策略、快照、约束 | 通过/拒绝及原因 | 执行前安全边界 |

## 7.2 链路代价设计

可将链路质量映射为综合代价，作为路径算法的边权。建议先实现可解释的归一化加权模型，再通过实验校准权重。

```text
cost(link) =
  w_delay   * normalize(delayMs)
+ w_jitter  * normalize(jitterMs)
+ w_loss    * normalize(packetLossRate)
+ w_ber     * normalize(ber)
+ w_load    * normalize(usedBandwidth / capacity)
+ w_hop     * hopPenalty

若链路 status != up 或 capacity <= 0，则视为不可用。
权重、归一化区间和阈值均由配置文件管理，并记录到实验元数据。
```

ETX 可作为可靠性代价的一种候选指标：ETX = 1 / (df × dr)，其中 df、dr 分别为正向和反向成功投递率。若当前数据仅提供单向 packetLossRate，则应明确采用近似估计，不应把近似值描述为真实测量 ETX。

## 7.3 带宽分配模型

建议将带宽调度建模为带容量约束的业务资源分配问题。对每条链路 e，分配给业务 f 的带宽 x(f,e) 不得超过链路可用容量；业务路径上的瓶颈链路必须满足端到端带宽要求或允许降级后的需求。

```text
目标函数（示意）：
最大化 Σ_f priority_f * deliveredBandwidth_f
       - λ1 * QoSViolationPenalty
       - λ2 * RouteChangePenalty
       - λ3 * ResourceFragmentationPenalty

约束：
Σ_f x(f,e) <= availableCapacity(e),  对每条链路 e
0 <= x(f,e) <= demand(f)
若 flow f 被接纳，则其路径必须连通且链路均为 up
关键业务满足最低保障带宽/时延约束（可配置）
```

第一版不必同时求解所有复杂维度。建议先实现：候选路径生成 → 业务按优先级排序 → OR-Tools 分配带宽 → 校验链路容量 → 输出无法满足的业务与降级原因。后续再加入多路径分流、切换代价和公平性目标。

## 7.4 QoS 评估

- 端到端时延：链路传播/处理时延与排队时延之和。
- 端到端抖动：按业务包到达时延序列计算变化量或统计方差。
- 丢包率：发送包数与成功接收包数计算，区分链路丢包和拥塞丢包。
- 带宽满足率：实际交付吞吐与需求带宽的比值。
- QoS 达标：业务的所有硬门限满足，或按业务定义的加权达标规则判定。

# 8. 大模型、技能库与 RAG 设计

## 8.1 Qwen3 的职责边界

| 适合交给 Qwen3 | 不交给 Qwen3 |
| --- | --- |
| 自然语言任务解析与场景参数草案 | 直接计算最短路径、最优带宽数值 |
| 复杂异常的辅助解释与根因假设 | 凭语言模型推测不存在的链路/节点状态 |
| 根据任务选择可用技能/工具 | 绕过策略校验直接写网络配置 |
| 将诊断和算法结果转成可读报告 | 代替 OR-Tools 求解容量约束 |
| 解释不同策略的权衡与风险 | 把模型输出当成仿真执行事实 |

## 8.2 Ollama 本地模型服务

通过 Ollama 在本地加载适配硬件的小参数量、低比特量化 Qwen3 模型。模型名称、量化级别、上下文长度、温度、超时和并发限制统一配置。启动时进行模型健康检查；模型不可用时，核心网络管控流程必须能退化到规则与确定性算法。

## 8.3 技能库设计

| Skill | 功能 | 主要工具 |
| --- | --- | --- |
| topology_assessment | 连通分量、关键节点、桥接边、孤立节点 | NetworkX |
| link_quality_evaluation | 链路质量评分、ETX 近似、退化检测 | Python/SciPy |
| fault_impact_analysis | 故障影响节点、业务流和可达性分析 | NetworkX |
| route_candidate_generation | Dijkstra/K 最短路径、约束过滤 | NetworkX |
| bandwidth_optimization | 带宽分配、业务准入和降级 | OR-Tools |
| qos_evaluation | 端到端 QoS 指标和违约判定 | 仿真统计模块 |
| policy_validation | 容量、路径、版本、优先级和安全校验 | 规则引擎 |
| experiment_analysis | 多轮实验统计、基线对比和报告摘要 | SciPy/Pandas（可选） |

## 8.4 RAG 的范围与阶段

RAG 仅检索相对稳定的知识：赛题说明、项目设计规范、MANET 路由知识、QoS 规则、算法说明、技能使用文档和历史实验案例。第一阶段可选 FAISS（轻量本地向量索引）或 Chroma（便于管理文档与元数据）；二者择一即可，不建议初期同时引入。后续如需要与 PostgreSQL 统一存储和多用户检索，再评估 pgvector。

- 切分时保留标题层级、文档来源、页码/段落、版本和适用范围。
- 检索结果必须携带来源，模型回答应区分知识库事实、当前快照事实和推断。
- 实时网络状态不写入 RAG；RAG 不作为拓扑数据库、路由表或资源状态缓存。
- 先完成无 RAG 的确定性闭环，再以可量化任务测试 RAG 是否提升诊断正确率和解释质量。

# 11. 实验验证与评价体系

## 11.1 对照实验组

| 实验组 | 说明 | 目的 |
| --- | --- | --- |
| A：静态/规则基线 | 固定路由或简单最短路，固定优先级策略 | 衡量基本网络能力 |
| B：传统算法组 | 动态拓扑 + Dijkstra/K 最短路 + 规则带宽分配 | 衡量确定性算法本身的收益 |
| C：多智能体协作组 | O&M + Resource + Coordinator，结合技能/LLM/RAG | 衡量诊断、业务级调度和协作收益 |

三组实验必须使用相同拓扑初始条件、业务流、事件序列、仿真时长和随机种子。应避免仅比较不同随机场景下的单次结果。

## 11.2 关键评价指标

| 指标 | 定义/统计方式 | 对应能力 |
| --- | --- | --- |
| 状态感知时间 | 事件发生至系统识别并形成有效状态/告警的时间 | 感知效率 |
| 策略生成时间 | 诊断结果可用至候选策略生成完成的时间 | 算法与 Agent 决策效率 |
| 策略下发时间 | 策略通过校验至仿真器确认应用的时间 | 控制链路效率 |
| 故障恢复时间 | 故障发生至关键业务恢复 QoS 或恢复连通的时间 | 自愈能力 |
| 网络连通度 | 当前可达节点对/理论可达节点对，或按场景定义的连通比例 | 网络韧性 |
| 业务 QoS 达标率 | 满足各业务配置 QoS 门限的业务流比例/时间占比 | 业务保障能力 |
| 带宽利用率 | 实际承载吞吐/可用容量 | 资源利用效率 |
| 业务中断率 | 发生中断或不可达的业务流比例/持续时间占比 | 业务连续性 |
| 策略成功率 | 成功通过校验并正确应用的策略数/提交策略数 | 策略可靠性 |
| 资源超配次数 | 出现链路分配总量超过容量的次数 | 约束安全性 |
| Agent 协作开销 | 消息数量、模型调用耗时、工具调用耗时 | 协作效率 |

## 11.3 实验矩阵

至少覆盖单因素和组合因素两类实验。单因素用于定位各模块能力，组合场景用于验证复杂动态环境下的整体闭环。每个关键场景建议多随机种子重复运行，报告均值、标准差和最差分位数；具体重复次数根据运行资源确定并记录。

## 11.4 实验可复现要求

- 记录场景配置版本、随机种子、算法版本、权重参数、模型版本/量化方式、提示词版本和 RAG 索引版本。
- 记录每次事件的仿真时间、实际墙钟时间和执行顺序。
- 记录原始输入、网络快照、Agent 消息、工具输入输出、策略校验和反馈。
- 实验结果支持 JSON/CSV 导出，并能由相同配置重新运行。

## 12.2 部署形态

初期建议单机部署：React 静态资源 + FastAPI 单实例 + Ollama 本地模型服务 + SQLite + 本地向量索引。开发阶段可直接本地启动；稳定后再使用 Docker Compose 管理前端、后端和 Ollama。

仿真服务与 FastAPI 同进程时，必须限制为单一仿真执行器，避免多 worker 导致内存中的 SimPy 环境分裂。若后续需要多 worker，可将仿真执行器独立为单实例进程，通过任务队列/API 与 FastAPI 通信；此时再评估 Redis。

## 12.3 工程质量要求

- 领域模型和 API Schema 分离，使用 Pydantic 对输入输出做严格校验。
- 算法模块提供单元测试和小规模固定拓扑的黄金用例。
- 仿真事件、策略应用和状态机转移均有结构化日志。
- 模型调用设置超时、重试上限和降级路径；禁止无限重试阻塞仿真。
- 关键算法和状态机不依赖 LLM 在线可用性。
- 固定依赖版本和运行环境，提供一键启动与健康检查脚本。

# 13. 分阶段实施计划与里程碑

| 阶段 | 目标 | 主要任务 | 验收标准 |
| --- | --- | --- | --- |
| 阶段 0：需求冻结 | 建立统一需求与数据规范 | 确认节点/链路/业务模型、QoS 配置、事件格式、场景清单、官方数据适配 | 数据字典、接口草案、场景规格冻结 |
| 阶段 1：仿真 MVP | 跑通动态网络仿真 | SimPy 时钟、NetworkX 拓扑、节点/链路/业务事件、快照 API | 能运行冷启动、节点下线、链路中断和带宽变化 |
| 阶段 2：算法闭环 | 实现可用的确定性管控 | 拓扑诊断、链路代价、Dijkstra/K 路径、OR-Tools 带宽分配、策略校验 | 链路中断后能生成并应用合法替代策略 |
| 阶段 3：多智能体协作 | 实现两个必需 Agent 和协调器 | 状态机、A2A、超时/重试、仲裁、审计追踪 | 完整展示感知—诊断—决策—执行—反馈链 |
| 阶段 4：模型增强 | 接入 Qwen3 与知识库 | Ollama 适配、技能选择、诊断解释、RAG 检索、模型降级 | 模型增强不破坏确定性结果；模型离线仍能闭环 |
| 阶段 5：前端与实验 | 形成可演示可评估产品 | React 工作台、拓扑可视化、实验 Runner、指标、报告导出 | 可现场演示、多组对照实验可复现 |
| 阶段 6：交付加固 | 满足复赛部署要求 | 性能测试、异常恢复、文档、部署包、测试集回归 | 干净环境可部署、接口稳定、交付物齐全 |

## 13.1 开发顺序建议

严格建议先完成仿真内核与算法闭环，再开发 Agent 的语言模型能力。若先做大模型对话和复杂前端，容易出现界面完整但网络行为不可信、策略不可执行、实验无法复现的问题。

## 13.2 最小可行版本（MVP）边界

- 至少 6–8 个节点、若干条链路，支持节点下线、链路中断、带宽变化和业务流变化。
- 至少两类业务优先级差异，逐步扩展到数据、图片、话音、视频四类。
- 实现 O&M Agent、Resource Agent、Coordinator 的闭环；LLM 可先关闭。
- 实现路径重算、带宽分配、策略校验和仿真执行反馈。
- 至少提供静态/传统算法/多智能体三组对照实验中的前两组，逐步补齐第三组。

## 14.2 主要风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 仿真复杂度失控 | 开发周期拉长，难以稳定复现 | 不实现完整无线协议栈；优先抽象节点/链路/业务和关键机制 |
| LLM 响应慢或不稳定 | 影响实时闭环 | LLM 不在硬实时路径；超时降级到规则/算法 |
| 多 Agent 设计过度复杂 | 协作难调试、消息链不透明 | 初期固定三角色、固定状态机、结构化消息 |
| 内存状态与多 worker 冲突 | 仿真状态不一致 | 初期单 worker；仿真执行器串行化；扩展时独立进程 |
| 资源优化模型过大 | 求解时间过长或无解 | 先做候选路径剪枝、优先级分配和小规模 CP-SAT |
| QoS 参数缺少官方依据 | 实验结论可信度不足 | 配置参数显式标注来源/假设，做敏感性分析 |
| 官方接口或测试集变化 | 数据适配返工 | 建立 Adapter 层，内部领域模型与外部格式隔离 |
| RAG 检索噪声 | 模型误用知识 | 保留来源元数据、检索阈值、拒答/无依据提示，核心逻辑不依赖 RAG |

# 附录 B：关键设计决策与待确认事项

| 事项 | 当前建议 | 需确认内容 |
| --- | --- | --- |
| Agent 编排框架 | 自研状态机作为 MVP；保留 LangGraph 接口适配 | 是否出现复杂循环、多分支人工审批等需求 |
| RAG 引擎 | FAISS 与 Chroma 二选一，后期再考虑 pgvector | 知识库规模、元数据过滤和多用户需求 |
| 仿真粒度 | 离散事件 + 抽象链路转发，不做完整 PHY/MAC 协议栈 | 赛题官方仿真器是否要求特定时间步长/字段 |
| 网络协议参考 | 参考 MANET/OLSR/AODV/DTN 思想，明确是仿真抽象 | 是否需要实现协议报文级流程 |
| QoS 数值 | 配置化，不将示例值视为官方门限 | 官方测试集/评测是否提供业务门限 |
| 资源维度 | 第一版重点做带宽、路由、优先级；扩展时增加时隙/能量/算力 | 赛题是否要求多维资源均落地 |
| 模型规模与量化 | 以目标机器实测吞吐和内存占用选型 | 最终 CPU/GPU、内存和模型加载限制 |
| 数据库迁移 | SQLite 起步，PostgreSQL 后续 | 是否需要多人并发或远程部署 |
| 缓存 | 初期进程内状态；多进程后评估 Redis | 是否需要多实例运行和任务跨进程共享 |

最终建议：将“可运行的仿真闭环”作为项目第一优先级，将“可解释的确定性算法”作为第二优先级，将“Qwen3 驱动的智能化增强”作为第三优先级。通过清晰的数据契约、策略校验和实验复现机制，确保系统既体现多智能体智能化能力，也具备通信网络资源管控问题所要求的工程可信度。
