## 0. 一句话

感知 → 建图 → 按 flow 聚合业务 → K 短路径 + 静态 QoS 过滤 → **优先级加权贪心分配（方向容量记账、F1/F2/F3 分类、背景让路、局部搜索）** → 限流下发 → 实测反馈增量重排。

不追求"全部达标"，只最大化「**测试业务优先级加权达标数**」。

---

## 1. 定位与边界

**做**：确定性、可复现、可离线单测的流级选路；对动态事件做增量重排；输出每 flow 一条路径。

**不做**：
- 不生成/解释链路（LLM 不参与热路径）；
- 不追求全达标（物理不可能，见 §6）；
- 不做带宽分配、准入控制、队列调度（公开接口没有这些动作）；
- 不在接入段硬瓶颈上浪费动作（F1 直接认输）。

---

## 2. 关键事实（来自实测，先定死）

1. **flow 是无序端点对**：仿真器 `_flow_for` 匹配 `(ip1,ip2)` 或 `(ip2,ip1)`，所以 A→B 与 B→A 是**同一个 flow**。现有 `models.py` 的 `flow_key=(src,dst)` 是**有序**的，需改为无序。
2. **flow = 业务集合**：同一对 UAV 的 test + background 共用一条路径，**决策单位是 flow**，不是 service。
3. **链路全双工**：`apply_link` 对链路两端各挂一个 `rate=bw` 的 TBF，A→B 与 B→A 是两个独立令牌桶，**容量按方向记账**。
4. **接入链路是单点硬瓶颈**：每个 UAV 基本只有一条像样接入链路；背景业务目的 UAV 固定，绕不开。部分 UAV 纯 test 就超容 → 物理不可行（F1）。
5. **双 QoS**：静态必须过（否则 1004）；实测 `actual.qosMeet` 才是评分口径。
6. **唯一杠杆是重路由**：`POST /services/{serviceId}/path`。

## 3. 目标函数与约束

### 3.1 目标

$$
\max \sum_{f\in F} w_f \cdot \mathbb{1}\big[\text{flow } f \text{ 的全部 test 业务 } \text{qosMeet}\big],
\qquad
w_f=\sum_{s\in S_f,\ \text{test}} 2^{\text{priority}(s)}
$$

- `priority` 按 **8 最高、1 最低**（**已定按现状，等后续官方确认**；官方未定义方向，见数学建模 §6.4）。
- **保护对象限定为 test**：`background` 不计权重，只作负载/让路对象；test/background 分类走内部 `/api/ctrl/v1/svc-meta`（`ctrlToken`），无 token 时用 `TSV*` 前缀或统一保护兜底。

### 3.2 约束

- **硬约束 1（静态 QoS）**：`path_f` 对 $S_f$ 中**每条**业务静态可行（`compose_qos` + `check_qos`）。
- **硬约束 2（flow 单路径）**：每个 flow 只能选一条路径，不可拆分。
- **硬约束 3（接入段容量）**：接入链路方向负载 ≤ 容量；超容即 F1，不强行分配。
- **软约束（骨干段容量）**：$\sum_{f:e\in P_f,\text{dir}}\mathrm{dem}_f(\text{dir}) \le b_e(1-\rho)$，允许轻微超载；$\rho$ 建议 0.2。

## 5. 核心算法

### 5.1 数据准备

对每个 flow $f$：
- `S_f`：组内业务（含 test/background）；
- $R_f$：静态需求 `flow_requirement`（时延/抖动/丢包/误码取 min，带宽取 max）；
- `dem_f(dir)`：按每条业务 `src→dst` 方向，把 `bandwidthBps` 累加到路径各链路的方向上。

### 5.2 三类 flow（F1/F2/F3）

| 类 | 判据 | 处理 |
| --- | --- | --- |
| **F1 硬不可行** | 端点接入链路**纯 test** 方向需求 > 容量 | 标 `sacrifice`，不投入动作，报告单列 |
| **F2 背景诱因** | test-only 放得下，但 test+bg 超容 | 尽力保 test，不保证 |
| **F3 可行** | 全放得下 | 正常分配 |

判据的"接入链路"= UAV–GND 最后一跳。F1 是物理容量墙，不是路由问题。

### 5.3 候选路径

每 flow 用 `k_shortest_paths`（Yen，权重 `delay`，$K=30\sim100$）生成候选，`compose_qos` + `check_qos` 硬过滤。并行链路（如 GND001–GND007 的 fiber + satcom）由 `nx.MultiGraph` 自动区分。

### 5.4 两阶段贪心

1. **Test 优先**：非 F1 的 flow 按 $w_f$ 降序，逐条选"静态可行 + 方向容量装得下"的最便宜路径；装不下则退化为"最便宜静态可行路径"并标 `partial`。
2. **背景填位**：纯背景 flow 在剩余容量里选"最大链路利用率最小"的路径（least-contention），不改混合 flow（混合 flow 已随 test 一起定）。

### 5.5 局部搜索

对已分配的 test flow，尝试与**低权重 flow 或纯背景 flow**交换路径；若优先级加权达标数提升且静态可行则接受；每轮上限 N 次，防震荡。

### 5.6 防抖与切换（已实现）

只在下述任一情况下改路：

1. **修复**：当前路径失效（链路不在图中/不连续）或静态 QoS 已违约 —— 无条件下发；
2. **改进**：全量重排后的**优先级加权达标数增益** $\Delta\text{score}\ge \Delta_{\min}$；
3. 同一 flow 两次改路间隔 $\ge \Delta T$（`min_switch_interval_sec`）。

没有第 2 条就没有终点：只要重排结果"看起来更好一点点"就改路，会形成永不停歇的路径 churn。
背景流单独挪动（达标数不变）默认**不算增益**，不为此改路；它随修复/改进批次一起被处理。

硬失败（F1/F2）flow 在现状可用时**钉住**：物理上救不回来，重排只会白花动作预算。

### 5.7 规划是纯函数，下发才是增量

规划器输出只取决于 `(flows, graph, config)`，**不看当前已装路径**：同一份快照重算两次必然完全一致（离线已验证）。
调用方拿「已装路径」与「计划路径」做差集，只下发差集；差集非空也未必下发 —— 还要过
「修复失效路径 or $\Delta\text{score}\ge\Delta_{\min}$」这道闸。

由此闭环的不动点是可证的：

```text
一次批下发完成 → installed == plan → 再规划（同快照）差集为空 → 静默
```

> 为什么不用"把 incumbent 喂进贪心、现状优先"的做法：实测在规模场景上既更差也不稳定
> —— sce05 上分数从 592 掉到 384，且重规划仍有 43 个 flow 抖动。根因是贪心按顺序累加负载，
> "现状优先"让重规划看到与首次摆放不同的中间负载，反而破坏确定性。稳定性交给
> 「确定性纯函数 + Δscore 闸门 + 事件触发」三件套，比让规划器猜稳定性可靠。

### 5.8 epoch 状态机与收敛判据（已实现）

**一个 epoch = 一次冻结快照 + 一次规划 + 一个下发批 + 一次校验。**

```text
QUIESCENT ──可行动事件/心跳命中──> EPOCH ──批量下发──> SETTLING ──> VERIFYING ──┐
    ↑                                                                          │
    └──────────────── 收敛 / 纠正预算耗尽 ←───────────────────────────────────┘
```

**触发源只有四类**（其余一律不动）：

| 触发 | 事件 | 说明 |
| --- | --- | --- |
| 可行动事件 | `link_state_changed`（含 `param_change`）、`node_state_changed`、`service_state_changed` 且 `status∉running` | **必须过滤**自己下发产生的 `pathChanged=true & running` |
| 校验失败 | 见下方 L2 | 有界纠正 |
| 实测心跳 | 每 `heartbeat_sec` 采样一次 | **只查上一轮预测达标的 flow** |
| 强制 | 启动首轮 | 一次 |

事件成簇到达时先合窗 `trigger_settle_sec`（等最后一个可行动事件静默后再规划），避免一个事件簇触发多次全量规划。

**收敛判据（三层，只有第一层可证明）：**

- **L1 执行收敛**：`plan - installed = ∅`。冻结快照 + 增量计划保证有限步达成，这是"不再下发"的硬判据。
- **L2 观测收敛**：可达集 $A$ 上「预测达标集合 = 实测达标集合」连续 $H$ 个 1s 窗（`verify_windows`/`verify_votes`）。
  $$A(t)=\{f:\ f\ \text{非 F1/F2 且存在静态可行路径}\}$$
  **F1/F2 不进判据**——否则那几个物理上不可能达标的 flow 会让循环永远不收敛。
- **L3 优化收敛**（可选）：同一快照上无候选重排能把 $\Delta$ 提过 $\Delta_{\min}$ → 记 `best_effort`。
  只是**局部最优**，报告里写"当前模型与观测分辨率下的不动点"，不要写"最优"。

**下发批的规则：**

1. 批内**不重算**（重算 = 换计划 = 把瞬态无限延长）；
2. 批内收到新的可行动事件 → 中止剩余下发，用新快照重开 epoch；
3. 修复类优先（先恢复连通），其余按 `flow_key` 字典序保证可复现；
4. 批后 `settle_s` 静置，再按多窗投票比较预测与实测；失配路径进惩罚集（下一轮候选剔除），
   纠正轮数上限 `corrective_rounds`；
5. 全场批次数上限 `max_batches_per_run`（防"没有尽头"）。

**为什么不是「逐条 POST → 等反馈 → 重算」**：一次断链在 conf01/sce10 上会让 205/491 个 flow 需要改路，
而单次全量规划就要 23~60s（见 §6 的规模数据）——逐条重算在整场 30 分钟内不可行；
更根本的是，逐条下发时重算看到的是**自己刚造出来的中间态**，对它求最优没有意义。

**顺序只影响瞬态**：sce01 断一条承重链路后 6 个待切换 flow 的 720 种排列实测中间态峰值完全相同
（都被不可避的接入瓶颈压住）。所以顺序只保留一条正确性规则（先释放、后占用），不为此做优化。

### 5.10 主循环伪代码

```text
loop(every 1s):
    events = poll_events(since)              # GET /events, <=10s
    act    = [e for e in events if actionable(e)]    # 丢弃自己的 pathChanged
    if act: pending = True; last_act = now
    if phase == SETTLING:
        if act: abort(); force_epoch = True; continue
        if now < settle_until: continue
        phase = VERIFYING
    if phase == VERIFYING:
        sample(); if enough_windows: compare_and_maybe_correct()
        continue
    if force or (pending and now - last_act >= trigger_settle):
        G = build_graph(links, nodes)         # 只收 up/online, 剔除 EXT001
        flows = group_services_by_flow(services)
        plans = plan(flows, G, cfg)                   # 纯函数：同快照同结果
        delta = {f: plan[f] for f in plans if plan[f] != installed[f]}
        if delta and (repair(delta) or Δscore >= Δmin):
            for f in order(delta): POST(f)    # 批内不重算、不 sleep 等反馈
            phase = SETTLING
    elif heartbeat_due() and predicted_flow_violating():
        force_epoch = True
```

## 6. 本场景预期（sce20261010-conf02/sce01）

- 40 条业务 → **17 个 flow**，其中 **8 个含 test**（6 混合 + 2 纯 test）。
- **F1 为 0 个**：所有 UAV 的 test-only 需求最高只到 60%（UAV0001 出/入 35%/60%）。
- **F2 硬失败 3 个 flow / 5 条 test 业务**：TSV0002/0005/0006/0007/0008，全部
  端点在 UAV0001，接入链路 L00017（29M）单价/双向合计 109%（出 31M）/ 143%（入 41M）由背景业务叠满。
  > 注意单位：决策与下发单位是 flow，这 5 条 test 只落在 3 个 flow 上
  > （UAV0001–UAV0002 / –UAV0004 / –UAV0006）。
  > 初版把这一组写成"F1"，按 §5.2 的定义应为 **F2**（test-only 放得下、test+bg 超容）。
- **可达上限 ≈ 5/10**：TSV0004/0009 稳，TSV0010/0003/0001 边缘（所在 UAV 出向 95%）。
- 算法要点：**不把动作浪费在 3 个 F2 flow 上**（钉住）；优先保 F3。F2 在报告里单列 `sacrificed`。
- **规模数据**（离线实测，用于判断闭环是否可行）：

  | 场景 | 业务 / flow | 单次全量规划 | 断一条承重链路后需改路 |
  | --- | --- | ---: | ---: |
  | conf02/sce01 | 40 / 17 | ~0.1s | 6 / 17 |
  | conf02/sce05 | 180 / 172 | 2.2s（含局部搜索 16.6s） | — |
  | conf01/sce10 | 500 / 491 | 23.3s（含局部搜索 60.0s） | 205 / 491（13 个失去可行路径） |

  这组数字是 §5.8「批内不重算」的直接依据：逐条"POST→等反馈→重算"在 sce10 上要 3.4 小时量级。

## 7. 验收标准

1. **单测（离线）**：给定 `net-topo.json` + `bg-service.json`，输出每 flow 一条静态可行路径 + 方向利用率表。
2. **分类一致**：F1 为空集、F2 = UAV0001 的 3 个 flow（5 条 test 业务），与本场景人工分析一致。
3. **不退化**：优先级加权 test 达标数不低于现状 `optimize_flow` 单 flow 结果。
4. **不违规下发**：不下发静态违规路径；同一 flow 改路间隔 ≥ $\Delta T$。
5. **可复现**：同一输入两次运行输出一致（无随机性，或固定随机种子）。
6. **幂等收敛**：把 `plan()` 的输出当"已装路径"喂回去，同一快照重算**一条都不改**；
   闭环连跑 5 轮 `step()`，POST 次数为 0。
7. **批内不重算**：一次 epoch 内 `plan()` 只调 1 次，POST 次数 = 本批 delta 条数。
8. **有界**：注入 20 个连续事件，全场 POST 次数 ≤ Σ|delta|、批次 ≤ `max_batches_per_run`。
9. **实测反馈有效**：构造"规划路径实测违约"的场景，下一轮必须换到不同路径（且受纠正轮数上限约束）。

> 6~9 已落地为单测（`tests/test_reroute_loop.py`、`tests/test_planner_offline.py`）；
> 3 仍待与 `optimize_flow` 对比（T3.2）。
