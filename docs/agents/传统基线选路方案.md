# 传统基线选路方案（FPCB：Flow-Priority-Capacity Baseline）

> 版本：v1.0　整理日期：2026-11-22
> 定位：确定性、**非 LLM** 的热路径方案。它既是 `src/baseline/` 的升级规格，也是后续多智能体的**确定性内核**；LLM 只做态势解释、优先级增强与复盘，不生成链路。
> 相关文档：`docs/math_modeling/数学建模方案.md` §6.2/§6.5（容量与硬不可行）、`docs/simulator/仿真器相关.md` §11.2（方向性口径）、任务清单 `docs/task_split/flow_planner_task.md`。

---

## 0. 一句话

感知 → 建图 → 按 flow 聚合业务 → K 短路径 + 静态 QoS 过滤 → **优先级加权贪心分配（方向容量记账、F1/F2/F3 分类、背景让路、局部搜索）** → 限流下发 → 实测反馈增量重排。

不追求"全部达标"，只最大化「**测试业务优先级加权达标数**」。

---

## 1. 定位与边界

**做**：确定性、可复现、可离线单测的流级选路；对动态事件做增量重排；输出每 flow 一条路径。

**不做**：
- 不生成/解释链路（LLM 不参与热路径）；
- 不追求全达标（物理不可能，见 §6）；
- 不做带宽分配、准入控制、队列调度（公开接口没有这些动作）；
- 不在接入段硬瓶颈上浪费动作（F1 直接认输）。

---

## 2. 关键事实（来自实测，先定死）

1. **flow 是无序端点对**：仿真器 `_flow_for` 匹配 `(ip1,ip2)` 或 `(ip2,ip1)`，所以 A→B 与 B→A 是**同一个 flow**。现有 `models.py` 的 `flow_key=(src,dst)` 是**有序**的，需改为无序。
2. **flow = 业务集合**：同一对 UAV 的 test + background 共用一条路径，**决策单位是 flow**，不是 service。
3. **链路全双工**：`apply_link` 对链路两端各挂一个 `rate=bw` 的 TBF，A→B 与 B→A 是两个独立令牌桶，**容量按方向记账**。
4. **接入链路是单点硬瓶颈**：每个 UAV 基本只有一条像样接入链路；背景业务目的 UAV 固定，绕不开。部分 UAV 纯 test 就超容 → 物理不可行（F1）。
5. **双 QoS**：静态必须过（否则 1004）；实测 `actual.qosMeet` 才是评分口径。
6. **唯一杠杆是重路由**：`POST /services/{serviceId}/path`。

## 3. 目标函数与约束

### 3.1 目标

$$
\max \sum_{f\in F} w_f \cdot \mathbb{1}\big[\text{flow } f \text{ 的全部 test 业务 } \text{qosMeet}\big],
\qquad
w_f=\sum_{s\in S_f,\ \text{test}} 2^{\text{priority}(s)}
$$

- `priority` 按 **8 最高、1 最低**（**已定按现状，等后续官方确认**；官方未定义方向，见数学建模 §6.4）。
- **保护对象限定为 test**：`background` 不计权重，只作负载/让路对象；test/background 分类走内部 `/api/ctrl/v1/svc-meta`（`ctrlToken`），无 token 时用 `TSV*` 前缀或统一保护兜底。

### 3.2 约束

- **硬约束 1（静态 QoS）**：`path_f` 对 $S_f$ 中**每条**业务静态可行（`compose_qos` + `check_qos`）。
- **硬约束 2（flow 单路径）**：每个 flow 只能选一条路径，不可拆分。
- **硬约束 3（接入段容量）**：接入链路方向负载 ≤ 容量；超容即 F1，不强行分配。
- **软约束（骨干段容量）**：$\sum_{f:e\in P_f,\text{dir}}\mathrm{dem}_f(\text{dir}) \le b_e(1-\rho)$，允许轻微超载；$\rho$ 建议 0.2。

## 5. 核心算法

### 5.1 数据准备

对每个 flow $f$：
- `S_f`：组内业务（含 test/background）；
- $R_f$：静态需求 `flow_requirement`（时延/抖动/丢包/误码取 min，带宽取 max）；
- `dem_f(dir)`：按每条业务 `src→dst` 方向，把 `bandwidthBps` 累加到路径各链路的方向上。

### 5.2 三类 flow（F1/F2/F3）

| 类 | 判据 | 处理 |
| --- | --- | --- |
| **F1 硬不可行** | 端点接入链路**纯 test** 方向需求 > 容量 | 标 `sacrifice`，不投入动作，报告单列 |
| **F2 背景诱因** | test-only 放得下，但 test+bg 超容 | 尽力保 test，不保证 |
| **F3 可行** | 全放得下 | 正常分配 |

判据的"接入链路"= UAV–GND 最后一跳。F1 是物理容量墙，不是路由问题。

### 5.3 候选路径

每 flow 用 `k_shortest_paths`（Yen，权重 `delay`，$K=30\sim100$）生成候选，`compose_qos` + `check_qos` 硬过滤。并行链路（如 GND001–GND007 的 fiber + satcom）由 `nx.MultiGraph` 自动区分。

### 5.4 两阶段贪心

1. **Test 优先**：非 F1 的 flow 按 $w_f$ 降序，逐条选"静态可行 + 方向容量装得下"的最便宜路径；装不下则退化为"最便宜静态可行路径"并标 `partial`。
2. **背景填位**：纯背景 flow 在剩余容量里选"最大链路利用率最小"的路径（least-contention），不改混合 flow（混合 flow 已随 test 一起定）。

### 5.5 局部搜索

对已分配的 test flow，尝试与**低权重 flow 或纯背景 flow**交换路径；若优先级加权达标数提升且静态可行则接受；每轮上限 N 次，防震荡。

### 5.6 防抖与切换

仅当满足以下之一才改路：
1. 当前路径失效（断链/节点下线）；
2. 当前路径静态违约，或实测连续 $N$ 窗 `qosMeet=false`；
3. 替代路径使优先级加权收益提升超过 $\Delta_{\min}$。

同一 flow 两次改路间隔 ≥ $\Delta T$（如 10s）。

### 5.7 主循环伪代码

```text
loop:
    ev = poll_events(since)                  # GET /events, <=10s
    G  = build_graph(links, nodes)           # 只收 up/online, 剔除 EXT001
    flows = group_services_by_flow(services) # 无序端点对
    for f in flows:
        f.cands = [p for p in k_shortest_paths(G, f.src, f.dst, K)
                   if static_ok(f, p)]
        f.dem   = directional_demand(f)
        f.cls   = classify(f, capacity)      # F1/F2/F3
    assign = plan(flows, G, capacity)        # 两阶段贪心 + 局部搜索
    for f in assign:
        if switch_worth_it(f, assign[f], delta_min) and not debounced(f):
            submit_path(f, assign[f])        # PathExecutor, requestId 幂等
    for f in assign:
        if measured_violation(f, N=3): mark_dirty(f)
    sleep(1s)
```

## 6. 本场景预期（sce20261010-conf02/sce01）

- 40 条业务 → **17 个 flow**，其中 **8 个含 test**（6 混合 + 2 纯 test）。
- **F1 硬失败 5 条**：TSV0002/0005/0006/0007/0008（全卡 UAV0001 接入链路 L00017，入向 143% / 出向 109%）。
- **可达上限 ≈ 5/10**：TSV0004/0009 稳，TSV0010/0003/0001 边缘（所在 UAV 出向 95%）。
- 算法要点：**不把动作浪费在 5 条 F1 上**；优先保 F3，其次 F2；F1 在报告里单列。

---

## 7. 验收标准

1. **单测（离线）**：给定 `net-topo.json` + `bg-service.json`，输出每 flow 一条静态可行路径 + 方向利用率表。
2. **分类一致**：F1 集合与本场景人工分析一致（UAV0001 的 5 条）。
3. **不退化**：优先级加权 test 达标数不低于现状 `optimize_flow` 单 flow 结果。
4. **不违规下发**：不下发静态违规路径；同一 flow 改路间隔 ≥ $\Delta T$。
5. **可复现**：同一输入两次运行输出一致（无随机性，或固定随机种子）。

---

## 8. 与后续 Agent 的关系

- **传统基线 = 热路径**：确定性、可复现、可单测，承担"算出链路"。
- **Agent/LLM = 冷路径**：态势解释、优先级编排建议、实验复盘、报告生成；不生成链路。
- 后续可把 `flow_planner` 作为"资源控制智能体"的确定性工具，由运维智能体提供事件/态势输入。
