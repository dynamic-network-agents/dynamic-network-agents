> 权威接口定义：`doc/仿真软件接口.md`；本文件补充本次会话中核实的实现细节、两套 QoS 的区别与代码位置。

## 0. 文档定位与维护

- 本文件说明智能体**看什么、怎么调、怎么决策、怎么验证**。
- 规则和代码位置以当前发布镜像为准；镜像升级后需重新核对。
- 新增内容按章节追加，保留编号稳定；实测结论注明环境。

## 1. 智能体任务与闭环

目标任务：在动态扰动下保障无人集群通信网络的业务 QoS，核心动作是**重路由**和**业务保障**。

推荐闭环：

```
轮询事件 → 感知拓扑/链路/业务 → 判断受影响业务
        → 计算满足 QoS 的候选路径 → 下发路径
        → 复查实际 QoS（actual.qosMeet） → 继续轮询
```

智能体不需要解析脚本，也不需要直接操作 OVS/tc；脚本事件由仿真控制面执行，智能体只通过 API 观测和下发路径。

## 2. 接入与通用约定

### 2.1 基础信息

- Base URL：`http://{服务器IP}:10100/api/open/v1`
- 本机：`http://localhost:10100/api/open/v1`
- 令牌：`simulator/conf/gateway.json` 的 `openTokens`
- 请求头：`X-Open-Token: <公开令牌>`
- 可选：`X-Agent-Id: <agentId>`（≤64 字符，仅用于同队多实例区分与日志）
- 重试标识：`X-Retry-Of: <原始 requestId>`（超时重传/故障重试，不计冗余调用）

读取令牌：

```bash
TOKEN=$(python3 -c "import json;print(json.load(open('simulator/conf/gateway.json'))['openTokens'][0])")
```

### 2.2 响应包络

```json
{"code":0,"msg":"ok","data":{},"time":"10:03:02.125480","tsUs":1800237782125480}
```

- `code`：0 成功；非 0 见错误码；
- `time`/`tsUs`：服务器本地时间与 Unix 微秒，同源；
- 提交类请求带 `requestId`（≤64 字符）实现幂等；
- 建议调用超时 6 秒；触发频控（1005）应退避重试。

### 2.3 错误码

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 1001 | 参数非法 |
| 1002 | 令牌缺失或无效 |
| 1003 | 资源不存在 |
| 1004 | 状态冲突（含链路断开/不连通/QoS 不满足） |
| 1005 | 触发频控 |
| 1006 | 令牌权限不足 |
| 2000 | 服务器内部错误 |

## 3. 数据模型

### 3.1 节点

- `nodeType`：`uav`（无人平台）、`ground`（地面节点）、`air`（空中节点）；
- `status`：`online` / `offline`；
- 业务节点：`uav` + `air`；地面节点通常只做转发，不在 `sim-nodes.json` 的业务注入表中；
- 典型 IP：UAV `10.1.1.x`，AIR `10.3.0.x`，GND `10.2.x.x`。

### 3.2 链路

- `linkType`：`fiber`、`satcom`、`vhf`、`uhf`、`microwave`、`5g`；
- `status`：`up` / `down`；
- `params`：
  - `delayMs`（毫秒，float）
  - `jitterMs`（毫秒，float）
  - `bandwidthBps`（bit/s，int）
  - `ber`（误码率，小数）
  - `packetLossRate`（丢包率，0~1 小数）
- 参数范围由 `simulator/conf/linkTypes.json` 约束。

### 3.3 业务

- `serviceType`：`data`、`image`、`voice`、`video`；
- `status`：`pending`、`running`、`stopped`、`finished`、`failed`；
- `priority`：优先级；
- `requirement`：QoS 需求上限/带宽下限；
- `path`：`pathId` + `segments`；
- `actual`：最近约 1 秒实测值：
  - `avgDelayMs`
  - `jitterMs`
  - `effBwBps`
  - `errPct`（百分比 0~100）
  - `packetLossRate`（0~1）
  - `qosMeet`（true/false，实测是否达标）

  -d '{
    "requestId":"agt01-20261113150500-001",
    "srcNodeId":"UAV0012",
    "dstNodeId":"UAV0088",

      {"type":"link","id":"L00201"},
      {"type":"link","id":"L00112"}

```bash
curl -X POST -H "X-Open-Token: $TOKEN" -H "Content-Type: application/json" \
  http://localhost:10100/api/open/v1/simulation/start \

```

`requestId` 幂等；同 requestId 重复调用不重复启动。

## 5. 事件机制与注入

### 5.1 事件类型

- `node_state_changed`：节点上下线/位置变化；payload 含 `instanceId`、`nodeId`、`state`、`position`；
- `link_state_changed`：链路参数/状态变化；payload 含 `instanceId`、`linkId`、`event`、`params`；
- `service_state_changed`：业务状态/路径变化；payload 含 `instanceId`、`serviceId`、`status`、`pathChanged`。

### 5.2 事件号

- 脚本事件：`EVT001`~`EVT999`，按计划时刻升序，同刻按脚本数组序；
- 运行期人工/API 事件：从 `EVT1000` 起自增；
- `srcEventId`：仅脚本事件派生的事件携带，指向触发它的脚本事件号。

### 5.3 注入过程（实现）

脚本引擎在 `netsim` 容器 `/opt/simulator/netsim/script_engine.py`：

1. `load()` 读取 `scripts/<script>.json`，要求非空数组，每项含 `time`、`eventType`，按 `(time, idx)` 排序并编号 `EVT001...`；
2. `start()` 记录 `self._t0 = time.time()`，启动调度线程；
3. 调度线程对每个事件等待到 `T0 + time`，调用 `api.apply(eventType, attrs, eid)`；
4. `_fire()` 记录 `planned_us`、`eff_us`，计算 `deviationMs = eff_us - planned_us`；
5. 事件类型由 `apply` 落到网络：链路参数（tc）、链路状态（up/down）、节点上下线、节点移动、业务新增；
6. 遇到 `stop` 事件结束；脚本文件热修改会触发热重载（保留已发事件）。

因此 T0 是**脚本真正开始执行时**设定的；慢启动只会推迟 T0，不会让相对 T0 的事件提前丢失。

### 5.4 事件时间窗口

| 套件 | 事件窗口 | stop |
| --- | --- | --- |
| conf01 | T0+3~26 分钟 | 1800s |
| conf02 | T0+3~26 分钟 | 1800s |
| conf04 | T0+2~27 分钟 | 1800s |

前 2~3 分钟是基线窗口；最后几分钟是收尾窗口。提前结束（自动结束分钟数小于事件时间）会漏掉后续事件。

## 6. 路径下发与校验

### 6.1 segments

- `type=link`：邻接段，严格逐跳，路径必须使用该链路；并行链路由此区分；
- `type=node`：必经节点约束；节点段前后由系统按最小时延自动补齐链路，补齐链路计入路径与计分；
- 纯链路段序列是标准用法，评测计分以此口径为准。

### 6.2 受理规则

- `accepted`：受理并执行；
- `rejected`：
  - 1001：段不存在/段类型非法/段列表不连续；
  - 1004：链路断开或不连通/参数不满足业务 QoS 需求。

### 6.3 路径决策策略

1. 从事件/拓扑找出受影响业务（源宿、当前路径、需求）；
2. 在可用 up 链路中搜索候选路径；
3. 用静态 QoS 合成（见第 7 节）筛选满足需求的路径；
4. 优先时延低、跳数少、稳定的路径；
5. 下发后查询实际 QoS，必要时二次调整。

## 7. 两套 QoS 校验规则

### 7.1 实测 QoS（页面“未达标”）

位置：

- `servicesim-rx` 容器 `/opt/simulator/servicesim/servicesim/core.py` 的 `Service.qos_meet()`（约第 106 行）；
- `/opt/simulator/servicesim/servicesim/rx.py` 逐秒统计与 `out['qosMeet'] = svc.qos_meet(...)`（约第 552 行）；
- 抖动 RFC3550 计算在 `rx.py` 约第 262~268 行；
- 页面显示在 `netsim` 容器 `/opt/simulator/netsim/nginx/web/app.js` 约第 463、477 行。

五项全部满足才 `qosMeet=true`：

```text
avgDelayMs <= requirement.delayMs + 1.0
jitterMs <= requirement.jitterMs + 1e-9
effBwBps >= requirement.bandwidthBps
errPct <= requirement.ber * 100 + 1e-9
packetLossRate <= requirement.packetLossRate + 1e-9
```

实测值来源：

- `avgDelayMs`：收包单向时延平均；
- `jitterMs`：`jitter += (|本次时延 - 上次时延| - jitter) / 16`；
- `effBwBps`：`min(发送速率, 接收速率)`，无收包时为 0；
- `errPct`：无效包/收包数×100；
- `packetLossRate`：`(期望包数 - 结算包数)/期望包数`。

页面列显示：

- `true` → 达标
- `false` → 未达标
- 空 → 实测填充中

### 7.2 静态路径 QoS（下发/自动选路）

位置：`netsim` 容器 `/opt/simulator/netsim/openapi.py`

- `_compose_qos(param_list)`（约第 1880~1892 行）
- `_qos_violations(comp, req)`（约第 689~703 行）
- 路径下发校验约第 2083~2092 行；自动选路约第 760~795 行

合成公式（`b_i, d_i, j_i, p_i, ε_i` 为第 i 跳链路的带宽/时延/抖动/丢包率/误码率，`R` 为业务发送速率）：

```text
端到端时延   D = Σ d_i
端到端抖动   J = sqrt(Σ j_i²)
端到端带宽   B = min_i b_i
端到端丢包   L = 1 - Π(1 - p_i)
端到端误码   ε ≈ Σ ε_i
```

校验条件：

```text
D <= req.delayMs + 1.0
J <= req.jitterMs + 1e-9
B >= req.bandwidthBps
L <= req.packetLossRate + 1e-9
ε <= req.ber + 1e-12
```

任一违规 → 路径设置返回 1004；自动选路优先选无违规路径，实在没有才降级 best-effort。

查看源码（`openapi.py` 是 base85+zlib 包装件）：

```bash
docker compose -f mac-docker-trial/compose.local.yml exec -T netsim \
  cat /opt/simulator/netsim/openapi.py | python3 -c "
import sys,re,base64,zlib
s=sys.stdin.read(); m=re.search(r\"b85decode\\('([^']+)'\\)\", s)
print(zlib.decompress(base64.b85decode(m.group(1))).decode())
" | sed -n '689,703p;1880,1892p'
```

### 7.3 两者区别

| 项目 | 实测 QoS | 静态路径 QoS |
| --- | --- | --- |
| 数据来源 | 最近 1 秒真实报文 | 候选路径链路参数 |
| 触发 | 业务运行时每秒 | 下发路径/自动重算 |
| 用途 | 页面达标/未达标 | 受理校验、选路 |
| 时延 | 实测平均 | 逐跳求和 |
| 抖动 | RFC3550 平滑估计 | 均方根合成 |
| 带宽 | min(发送,接收) | 瓶颈链路最小值 |
| 丢包 | 实测比例 | `1-Π(1-p_i)` |
| 误码 | errPct 与 ber×100 比 | 逐跳近似求和 |

同需求阈值，不同数据源：静态校验通过不代表实测一定达标；实测未达标也可能是瞬时波动。

## 8. 决策流程与时间管理

1. 启动后先等待 T0（页面/API 返回 `t0Time`/`t0TsUs`）；
2. T0 后前 2~3 分钟是基线窗口，先建立初始业务/路径快照；
3. 持续轮询 `/events`（≤10s），同时定期拉 `/topology`、`/links`、`/services`；
4. 对受影响业务计算候选路径并下发；
5. 用 `/services/{id}` 的 `actual.qosMeet` 复查；
6. 事件持续到约 T0+26/27 分钟，脚本在 1800s 发 stop；自动结束看门狗到点也会终止；
7. 结束后仿真写日志，测评软件自动读取；智能体不需要再提交结果。

慢环境与 T0：

- T0 由脚本引擎 `start()` 设置，发生在 TX/RX 就绪门通过之后；
- 环境慢只会推迟 T0，不会让 T0 相对事件提前触发；
- 真正会漏事件的是把自动结束设得比事件窗口短，或中途手动结束。

## 9. 自查与排查

```bash
# 元数据：当前任务/运行状态/场景列表
curl -sS http://localhost:10000/sdn-ui/meta | python3 -m json.tool

# 运行状态（ctrl token）
CTRL=$(python3 -c "import json;print(json.load(open('simulator/conf/gateway.json'))['ctrlToken'])")
curl -sS -H "X-Ctrl-Token: $CTRL" http://localhost:10100/api/ctrl/v1/run-info | python3 -m json.tool

# 业务实例就绪门
tail -n 20 simulator/logs/run/ui-worker.log
```

常见问题：

- 调接口 1002：检查 `X-Open-Token` 是否来自 `gateway.json` 的 `openTokens`；
- 调接口 1001：检查 `requestId`、`segments` 连续性、段类型；
- 调接口 1004：路径断开/不连通或静态 QoS 不满足，换路径；
- 事件轮询没数据：检查 `sinceTsUs` 游标，首次用 0；
- 页面卡“执行中”：看 `ui-job.json` 是否残留非 done/failed 任务，或 `ui-worker.log` 是否 `0/N ready`（需要重启 tx/rx）。
