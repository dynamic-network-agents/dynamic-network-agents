# 模块边界与依赖方向

> 定位：**每一层的职责、允许依赖、硬约束**。与 `src/CLAUDE.md` 的模块地图对应，
> 但本文额外说明**为什么这么切**、**哪些依赖被禁止**。
> 关联：[总体框架](总体框架.md)。

---

## 1. 为什么要分 `common/`

原结构是 6 个平铺的顶层包（`api` / `math_modeling` / `algorithms` / `baseline` /
`agents` / `util`）。问题：

1. **入口与底座混在一起**——`baseline/` 里既有入口（`main.py`）又有感知层
   （`snapshot.py`），还混着闭环控制。将来 `agents/` 要复用感知与控制时，边界无处安放。
2. **算法层内部按前缀区分而非按领域**——`flow_models.py`/`flow_candidates.py` 与
   `graph.py`/`capacity.py` 平铺在一个目录，两类算法混放。
3. **包名与内容错位**——`api/` 实际是"仿真器 HTTP 适配层"，`util/` 里只有配置文件。

重组后：`baseline/` 与 `agents/` 是**两个入口**，其余全在 `common/`。

---

## 2. 各层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| `common/modeling/` | 数据模型、QoS 合成与判定、链路代价归一化 | 不做 IO、不依赖图 |
| `common/algorithms/` | 拓扑 / 路径 / flow 三类算法 | 不读仿真器、不看已装路径 |
| `common/perception/` | 冻结快照、事件流 | 不做决策 |
| `common/simulator/` | HTTP 协议适配（client / executor） | 不含决策逻辑 |
| `common/control/` | epoch 状态机、下发闸门、实测校验 | 不做网络算法 |
| `common/observability/` | 决策留痕、指标产出 | **不参与决策**（只记录） |
| `common/config/` | 配置与令牌读取 | 无业务逻辑 |
| `baseline/` | 传统路径入口 | — |
| `agents/` | 智能体入口（ops / resource / a2a / llm） | — |

---

## 3. 硬约束（违反即架构异味）

### 3.1 分层约束

```
modeling ← topology / path / flow ← perception ← simulator ← control ← baseline / agents
```

- `common/modeling` 不得 import `algorithms` / `perception` / `simulator` / `control` / 入口层；
- `common/algorithms` 不得 import `perception` / `simulator` / `control` / 入口层；
- `common/perception` 与 `common/simulator` 不得 import `control` / 入口层；
- 入口层只允许依赖 `common/*`，**不得被 `common/*` 反向 import**。

### 3.2 职责约束

- **LLM 不生成链路**：只做解释、优先级增强、故障诊断建议。路径一律由
  `common/algorithms/` 产出。
- **所有写动作过闸门**：必须经 `common/control/dispatch_gate.py`
  （修复失效路径 or Δscore ≥ Δmin）。绕过闸门会导致路径 churn。
- **运维智能体无写权限**：只产出 A2A 建议消息。
- **仲裁必须确定性**：同样输入必得同样输出，不得引入时间/随机依赖。
- **令牌不入代码**：`common/config` 是唯一读 `gateway.json` 与 `configs/*.yaml` 的地方。
- **规划器是纯函数**：输出只取决于 `(flows, graph, config)`。

### 3.3 为什么 `observability` 独立

它**不参与决策**，只记录。但赛题四项指标里三项（状态感知时间、策略生成时间、
策略下发时间）靠它产出，且 baseline 与 agent 必须用**同一套计时口径**——
若各写各的，对比实验的数据不可比。独立成层也让"记录"与"决策"职责清晰。

### 3.4 为什么 LLM 通道在 `agents/` 而非 `common/`

baseline 是确定性闭环，全程**不走 LLM**。放进共享层会给 baseline 引入一条它不走的
依赖（还得为它准备无用的配置与降级路径）。放在 `agents/llm/` 后：
`common/` 保持零 LLM 依赖，两个智能体共享同一份 LLM 通道。

---

## 4. 三条关键接缝（扩展时的接入点）

### 4.1 规划器接缝

`common/algorithms/flow/planner.py::plan(flows, graph, config)` 是**稳定门面**。
换规划器只需换门面实现，`common/control/` 与 `common/perception/` 零改动。

### 4.2 决策核心接缝

`common/control/` 的状态机不关心"谁给出路径建议"——baseline 直接用规划器输出，
agent 侧可换成两个智能体的协同产物。**这是 baseline/agent 公平对比的结构保证**。

### 4.3 指标接缝

`common/observability/timeline.py::DecisionTimeline` 是统一的留痕入口。
任何决策流程只要 `mark(EventKind.PERCEPTION/DECISION/DISPATCH, ...)`，
指标就能自动聚合出来——不需要各方案各写一套统计。

## 6. 维护约定

- 新增模块前先问：**它属于入口还是底座？属于底座的哪一层？**
- 依赖方向只能**向下**，不能横向绕过（例：`common/control` 不能直接 import
  `common/algorithms` 以外的私有模块）。
- 模块职责变化时，**同步更新** `src/CLAUDE.md` 的模块地图与本文的对应表。
