# 算法边界与停止条件

> 定位：**算法能解什么、不能解什么、什么时候必须停**。
> 这是「实验验证」与「结果分析」两节的理论基础——只有知道边界，才知道结果该怎么解读。
> 关联：[闭环状态机与收敛判据](../common/control/闭环状态机与收敛判据.md)；
> [flow 级联合选路](../common/algorithms/flow级联合选路.md)。

---

## 1. 算法能解什么

| 能解 | 说明 |
|---|---|
| 静态 QoS 不满足的路径替换 | 换一条满足五项指标的路径 |
| 断链/节点下线导致的连通性恢复 | 在剩余 up 链路中搜候选 |
| 多 flow 共享容量竞争 | 方向容量记账 + 优先级加权贪心 |
| 容量分配不均导致的拥塞 | 局部搜索换路径提升加权达标数 |
| 实测违约的路径规避 | 惩罚集机制（下一轮剔除违约路径） |

## 2. 算法**不能**解什么

| 不能解 | 原因 | 正确处理 |
|---|---|---|
| **物理容量墙**（接入段 test-only 超容） | F1：不是路由问题 | 分类为 F1，**钉住**（现状可用就不动） |
| **背景业务挤占接入段**（F2） | test 放得下但 test+bg 放不下 | 尽力保 test，不保证 |
| **无静态可行路径** | 需求超出所有候选的能力 | 报无路径，不降级（降级会被 1004 拒绝） |
| **带宽分配 / 准入 / 队列调度** | 公开接口**没有**这些动作 | 唯一杠杆是重路由 |
| **干扰与射频层问题** | 仿真器不建模 | 不在范围内 |
| **脚本解析与场景生成** | 智能体不需要解析脚本 | 脚本事件由仿真控制面执行 |
| **瞬时抖动的根因** | 实测 QoS 是逐秒统计，可能只是波动 | 多窗投票降低误判 |

> **一句话**：算法只能在**路径空间**里做文章。容量墙、接口缺失、仿真器不建模的
> 现象，一律不在算法职责内——遇到时正确地"认输"比硬撑更重要。

## 3. 停止条件（三重，任一触发即止）

### 3.1 场景自然结束（外部）

- 脚本在 1800s 发 `stop` 事件；
- 自动结束看门狗到点；
- 事件窗口结束（conf01/conf02：T0+26 分钟；conf04：T0+27 分钟）。

**这不是算法的停止条件，而是赛题的**。算法要保证的是：在窗口内**尽可能多地**把
QoS 保住，而不是在最后一刻还在改路。

### 3.2 收敛（算法的正常停止）

三重判据，全部满足即进入静默：

| 判据 | 形式 | 依据 |
|---|---|---|
| **① 差集为空**（可证） | `plan − installed = ∅` | 规划是纯函数，同快照重算必同结果 |
| **② 预测=实测连续 H 窗** | 多窗投票达标 | `verifier.py` 的采样投票 |
| **③ 无待处理事件** | 事件队列空且合窗完成 | 感知层 |

> **① 是可证的**：一次批下发完成 → `installed == plan` → 再规划（同快照）差集为空 → 静默。
> **② 排除 F1/F2**：物理上救不回来的 flow 不参与判据，否则永远不收敛。

### 3.3 预算耗尽（兜底停止）

| 预算 | 常量 | 作用 |
|---|---|---|
| 全场批次数 | `max_batches_per_run`（60） | 防"没有尽头" |
| 单轮 LLM 工作项 | `agents/a2a` 的 `max_items_per_round` | 防 LLM 调用打满预算 |
| 全场调度轮数 | `agents/a2a` 的 `max_rounds` | 防调度循环 |

## 4. 三条"必须停"的工程判据

### 4.1 没有 Δmin 就没有终点

只要重排结果"看起来更好一点点"就改路，会形成**永不停歇的路径 churn**：
动作数爆炸、评测指标被"无效动作"淹没、仿真器频控触发。

闸门：**修复失效路径** or **加权达标数增益 ≥ Δmin**（默认 2.0，单位 $\sum 2^{priority}$）。

背景流单独挪动（达标数不变）默认**不算增益**——不为此改路。

### 4.2 F1/F2 要钉住

硬失败 flow 在现状可用时**钉住**：物理上救不回来，重排只会白花动作预算。

### 4.3 无候选时不降级

若排除惩罚路径后一条候选都不剩，**回退到不排除**——flow 彻底失去路径比走一条
实测违约的路更糟。

## 5. 怎么判断"结果好"

| 指标 | 定义 | 出处 |
|---|---|---|
| test 业务保障率 | $\frac{\#\{s:\text{test} \wedge \text{actual.qosMeet}\}}{\#\{s:\text{test}\}}$ | 实测 |
| 状态感知时间 | 事件出现 → 感知完成 | `common/observability/` |
| 策略生成时间 | 感知完成 → 决策完成 | 同上 |
| 策略下发时间 | 决策完成 → 下发完成 | 同上 |
| 动作数 | 下发次数 / 涉及 flow 数 | 同上 |
| 收敛时间 | 从首次触发到差集为空 | `common/control/` |
| 收敛性 | 差集为空后是否又触发下发 | 闭环不动点 |

**解读结果的纪律**：

1. **达标率低不等于算法差**——先看是否撞上 F1/F2（物理墙），撞上了就该认输；
2. **动作数多不等于算法差**——可能场景本身扰动多，要看"动作数/事件数"比值；
3. **收敛后仍有下发 = bug**——不动点被破坏，不是参数问题。

## 6. 边界内的可调参数

| 参数 | 调大 | 调小 | 副作用 |
|---|---|---|---|
| `reroute_min_gain`（Δmin） | 更保守、动作更少 | 更激进、达标可能更高 | 调大 → 可能错过增益；调小 → churn 风险 |
| `settle_sec` | 校验更准（数据面更稳） | 收敛更快 | 调大 → 每个 epoch 更慢 |
| `verify_windows` / `verify_votes` | 判定更稳（少误判） | 更快出结论 | 调大 → 更慢，可能错过瞬态改善 |
| `corrective_rounds` | 更强的自愈 | 更快收敛 | 调大 → 动作预算消耗大 |
| `k_shortest_paths`（K） | 候选更多样 | 更快 | 调大 → 计算量与候选排序成本上升 |
| `bandwidth_headroom`（ρ） | 更保守（留更多余量） | 更激进（塞更多流） | 调小 → 更容易超载违约 |
| `heartbeat_sec` | 更省调用 | 更快发现违约 | 调小 → agent 调用量上升（评测扣分项） |

> 标定方法见 [扩展指引](../common/algorithms/扩展指引.md) §4；实验记录见 `experiments/`。

## 7. 与 agent 的关系

本篇的停止条件**两边通用**（`common/control/` 共用）。agent 侧只多两条：

- LLM 调用预算（单轮工作项数、全场轮数）；
- 仲裁否决次数（同一动作被反复否决 → 应停止重试）。

详见 [baseline 与 agents 的共享与对比](baseline与agents的共享与对比.md)。
